Managed Kubernetes and Alternatives

Running the Kubernetes control plane yourself (etcd backups, certificate rotation, upgrades) is a job. Almost everyone should let a cloud provider do it. This lesson compares EKS, GKE and AKS, covers lightweight distributions, explains where the money goes, and lists genuine alternatives.

Why managed

With self-managed Kubernetes (kubeadm, kops, Talos, etc.) you own the control plane: HA etcd, API server certificates, version upgrades every few months (Kubernetes ships roughly three minor versions a year and supports each for about 14 months), security patches. Managed services run and patch the control plane for you, integrate with cloud IAM, load balancers and disks, and offer one-click upgrades. You still own your nodes' configuration, workloads, networking policy, add-ons and cost.

Example: create a cluster

# EKS with eksctl
eksctl create cluster --name demo --region eu-west-1 \
  --nodegroup-name std --node-type t3.medium --nodes 3

# GKE
gcloud container clusters create-auto demo --region europe-west1

# AKS
az aks create -g rg-demo -n demo --node-count 3 --enable-managed-identity

# Fetch credentials into kubeconfig
aws eks update-kubeconfig --name demo
gcloud container clusters get-credentials demo --region europe-west1
az aks get-credentials -g rg-demo -n demo

In real projects create clusters with Terraform (see the IaC section) so they are reviewable and reproducible.

Where the money goes

 Monthly bill
 ├── Worker nodes (compute)        usually 60-80 percent. Over-provisioned requests = waste
 ├── Control plane fee             small, fixed per cluster
 ├── Load balancers                one per Service type=LoadBalancer; consolidate with Ingress/Gateway
 ├── NAT gateways and egress       cross-AZ and internet traffic can be a nasty surprise
 ├── Persistent disks and snapshots
 └── Observability                 logs and metrics volume (often large)

Cost levers:

  • Right-size requests (VPA recommendations, tools like Kubecost or OpenCost): nodes are billed for what is reserved, not what is used.
  • Spot / preemptible instances for stateless and batch workloads; 60-90 percent cheaper, can be reclaimed with short notice. Use PDBs and multiple instance types.
  • Autoscaling (HPA + Karpenter or Cluster Autoscaler) so you do not pay for idle nodes at night.
  • Fewer clusters: each carries a fixed fee and overhead (monitoring, ingress). But too few risks blast radius. Many teams use one per environment or per region, not per app.
  • Reserved capacity / savings plans for the stable baseline.
  • Keep traffic within an availability zone where sensible (topology-aware routing).
Managed does not mean hands-off

You must still upgrade clusters (providers force it eventually, and unsupported versions cost extra), patch node images, manage add-ons (CNI, CoreDNS, CSI drivers), restrict API server access, and secure workloads. Plan an upgrade routine, for example quarterly, tested on staging first.

Lightweight and edge distributions

  • k3s (Rancher/SUSE): a single binary under 100 MB, SQLite or embedded etcd, includes Traefik, a service load balancer and local storage. Runs on a Raspberry Pi or a 1 GB VPS. Excellent for edge, homelabs, CI and small production setups.
  • k0s, MicroK8s, Talos Linux: other minimal options; Talos is an immutable, API-managed OS built only for Kubernetes.
  • OpenShift: Red Hat's enterprise distribution with a built-in developer platform and stricter defaults.
  • Rancher / Cluster API: manage many clusters uniformly.
# k3s in one line on a fresh Linux VPS
curl -sfL https://get.k3s.io | sh -
sudo k3s kubectl get nodes

Decision guide

  • Fewer than about five services, small team: Cloud Run / ECS Fargate / PaaS.
  • Many services, multiple teams, need for portability, operators and a vast ecosystem: managed Kubernetes.
  • Edge, on-prem or tight budget: k3s.
  • Strong need to avoid vendor lock-in: Kubernetes (but data gravity and managed databases lock you in anyway).
Pick the least complexity that meets the requirement

You can always move to Kubernetes later because containers are portable; going the other way is rarer. The skills in this section remain valuable either way: declarative config, health checks, requests and limits, and rolling updates apply to every platform.

Try it

  1. Install k3s (or k3d) and run the Deployment, Service and Ingress from earlier lessons. Traefik is already there.
  2. Deploy the same container to Cloud Run (gcloud run deploy --image ... --allow-unauthenticated) or ECS Fargate and compare the effort and what you gave up.
  3. Estimate the monthly cost of a 3-node cluster plus one load balancer on your cloud's pricing calculator.
