Why Container Orchestration?

Running one container on one server is easy. Running two hundred containers across thirty servers, keeping them healthy, updating them without downtime and scaling them with traffic is a different problem entirely. Orchestration is the software that solves it, and Kubernetes is the one that won.

Start with the problem

Imagine you have containerised your app (see the Docker lessons). On a single VPS you run docker compose up -d and you are done. Now the business grows. Here is what breaks, in the order it usually hurts.

1. Scheduling: where should this container run?

With ten servers and fifty containers, someone has to decide which container goes on which machine. A container needs 2 GB of RAM and half a CPU; server 3 has 1.5 GB free; server 7 has 6 GB free but is in a different availability zone from the database. Doing this in a spreadsheet works for a week. This is a bin-packing problem with constraints, and the component that solves it is called a scheduler.

2. Self-healing: things die, constantly

Processes crash, nodes lose power, disks fill, kernels panic. At small scale you get paged and restart things. At large scale, something is always broken somewhere. Without automation, every failure is a 3 a.m. phone call. With orchestration, the system notices that three replicas were requested but two exist, and starts a third on a healthy machine, with no human involved.

3. Scaling: capacity should follow demand

Traffic doubles at lunchtime. You can over-provision permanently (expensive) or add and remove instances automatically (needs a system that knows how to start new copies, register them with the load balancer and remove them again).

4. Rollouts: updating without an outage

Replacing version 1 with version 2 across twenty instances without dropping requests needs ordering: start a new one, wait until it is healthy, route traffic to it, stop an old one, repeat. If version 2 is broken, stop and go back. Hand-written deploy scripts get this wrong in new and creative ways.

5. Service discovery and load balancing

When containers move around and IP addresses change every restart, how does the checkout service find the payments service? You need stable names and a load balancer that automatically tracks which instances are alive.

6. Configuration, secrets and storage

The same image should run in dev, staging and production with different settings, and databases need disks that follow them when they move.

The key idea: declare desired state

Older tools were imperative: "start container X on server 3". Kubernetes is declarative: you write down what you want ("five copies of this image, each with 256 MB of memory, reachable at this name") and controllers continuously work to make reality match. You stop issuing commands and start describing outcomes.

  You write:                    Kubernetes continuously does:
  ┌──────────────────┐          ┌──────────────────────────────────┐
  │ replicas: 5      │ ───────▶ │ observe: 4 running                │
  │ image: shop:2.3  │          │ diff:    need 1 more              │
  └──────────────────┘          │ act:     schedule a new Pod       │
        desired state           │ repeat forever                    │
                                └──────────────────────────────────┘
Why this matters

Declarative state turns operations into data. Your whole system is described by files you can review in a pull request, diff, roll back with git and re-apply to a brand new cluster. This is the foundation that makes GitOps (see the IaC section) possible.

A brief history

Google ran an internal system called Borg for over a decade. In 2014 they open-sourced a redesign as Kubernetes (Greek for "helmsman", abbreviated k8s: k, 8 letters, s) and donated it to the Cloud Native Computing Foundation. Competitors such as Docker Swarm and Mesos existed, but Kubernetes' extensible API and vendor-neutral governance won. Every major cloud now offers a managed version, so it is the de facto common API for running containers.

When you do NOT need Kubernetes

This is the most valuable section for a new engineer. Kubernetes is powerful but carries real cost: a steep learning curve, many moving parts, YAML sprawl, and an operational surface (upgrades, networking, security) that someone must own.

  • One app, a few containers. A single VM with Docker Compose and a systemd unit, behind a reverse proxy, is simpler and often more reliable.
  • A small team with no platform experience. A managed PaaS (Render, Fly.io, Railway, Heroku, Cloud Run, App Runner) gives you 90 percent of the benefits with 5 percent of the complexity.
  • Mostly serverless workloads. If your logic is functions and queues, Lambda or Cloud Run may fit better.
  • Low traffic, no HA requirement. Downtime of a minute during a deploy may be perfectly acceptable.

You start to genuinely benefit from Kubernetes when you have many services, multiple teams deploying independently, a need for consistent scaling and rollout behaviour, multi-cloud or on-prem portability requirements, or an ecosystem need (operators, service mesh, GPU scheduling).

The resume-driven-development trap

Many startups adopt Kubernetes at ten users and spend more engineering time on the cluster than on the product. Choose it because you have the problems above, not because it is fashionable. Learning it is still worth it: the concepts (declarative config, reconciliation, service discovery) show up everywhere.

Try it

  1. List the services your team runs. For each, write down how it is scheduled, restarted on failure, scaled and updated today.
  2. Count how many of those answers are "a person does it by hand". Those are the places orchestration would help.
  3. Decide honestly: would a managed PaaS solve your actual pain with less effort?
