Configuration and Secrets

Build one image, run it everywhere. Anything that differs between environments (URLs, feature flags, passwords) is injected at runtime through ConfigMaps and Secrets. Handling this well, especially secrets, is where many clusters quietly go wrong.

Why separate config from images

If a database URL is baked into the image you need a different build per environment, so what you tested is not what you ship. The twelve-factor principle: store config in the environment. Kubernetes provides two objects to do that.

ConfigMap

Key-value pairs of non-sensitive data, either simple values or whole files.

apiVersion: v1
kind: ConfigMap
metadata:
  name: shop-config
data:
  LOG_LEVEL: "info"                 # all values are strings
  FEATURE_NEW_CART: "true"
  app.properties: |                 # a whole file
    cache.ttl=60
    retries=3

Create from the CLI: kubectl create configmap shop-config --from-literal=LOG_LEVEL=info --from-file=app.properties.

Secret

Same shape, intended for passwords, tokens and keys. Values are base64-encoded in data, or given as plain text in stringData (converted on write).

apiVersion: v1
kind: Secret
metadata:
  name: shop-db
type: Opaque
stringData:
  DB_PASSWORD: "s3cr3t-value"
  DB_URL: "postgres://shop:s3cr3t-value@db:5432/shop"

Other types include kubernetes.io/tls (cert + key), kubernetes.io/dockerconfigjson (registry login, used as imagePullSecrets) and kubernetes.io/basic-auth.

Base64 is not encryption

Anyone who can read the Secret object can decode it with base64 -d. By default Secrets sit unencrypted in etcd. Enable encryption at rest (EncryptionConfiguration, or KMS provider on managed clusters), restrict get secrets with RBAC, and never commit Secret YAML to git in plain form.

Consuming config: env vars vs volumes

spec:
  containers:
    - name: shop
      image: ghcr.io/example/shop:2.3.1
      envFrom:                          # every key becomes an env var
        - configMapRef: { name: shop-config }
      env:
        - name: DB_PASSWORD             # a single key from a Secret
          valueFrom:
            secretKeyRef: { name: shop-db, key: DB_PASSWORD }
      volumeMounts:
        - name: cfg
          mountPath: /etc/shop          # app.properties appears as a file
          readOnly: true
        - name: creds
          mountPath: /var/run/secrets/db
          readOnly: true
  volumes:
    - name: cfg
      configMap: { name: shop-config }
    - name: creds
      secret: { secretName: shop-db, defaultMode: 0400 }
Environment variablesVolume mounts
Update behaviourFixed at container start; need a restartFiles update in place after a short delay (not with subPath)
FitSimple scalar settingsConfig files, certificates, large values
Leak riskShow up in env, crash dumps, child processesLower; file permissions apply

For secrets, volumes (backed by tmpfs, never written to node disk) are the safer choice, though env vars are widely used and acceptable in many setups.

Rolling out config changes

Changing a ConfigMap does not restart Pods that use it as env vars. Common fixes: put a hash of the config in a Pod template annotation (Helm: checksum/config: {{ include ... | sha256sum }}), use Kustomize's configMapGenerator (appends a content hash to the name so a change triggers a rollout), or run kubectl rollout restart deploy/shop. For immutability, set immutable: true on the ConfigMap.

Managing secrets properly

The problem: GitOps wants everything in git, but secrets must not be in git. Three mainstream solutions:

Sealed Secrets

A controller in the cluster holds a private key. You encrypt a Secret locally with the public key using kubeseal, producing a SealedSecret that is safe to commit. Only that cluster can decrypt it.

kubectl create secret generic shop-db --from-literal=DB_PASSWORD=x --dry-run=client -o yaml \
  | kubeseal --format yaml > shop-db-sealed.yaml
git add shop-db-sealed.yaml   # safe

Simple, no external dependency. Downsides: bound to one cluster's key (back it up!), rotation is manual.

External Secrets Operator (ESO)

The source of truth lives in a real secret manager (AWS Secrets Manager, GCP Secret Manager, Azure Key Vault, HashiCorp Vault, 1Password). ESO syncs values into native Kubernetes Secrets.

apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: shop-db
spec:
  refreshInterval: 1h
  secretStoreRef:
    kind: ClusterSecretStore
    name: aws-secrets
  target:
    name: shop-db            # the Kubernetes Secret created
  data:
    - secretKey: DB_PASSWORD
      remoteRef:
        key: prod/shop/db
        property: password

You get central rotation, audit logs and access control, and git only contains references. This is the common choice in production.

Others

  • Secrets Store CSI Driver: mounts secrets from a vault straight into Pods as files.
  • SOPS (with age or KMS): encrypts values inside YAML files in git; Flux and Argo CD plugins decrypt on apply.
  • Vault Agent / Vault Secrets Operator: dynamic, short-lived credentials.

Best practices

  • Never put secrets in images, ConfigMaps, command-line args or logs.
  • Give each workload its own narrowly scoped Secret and RBAC; prefer workload identity (IAM roles for service accounts) over static cloud keys when possible.
  • Plan for rotation: apps should re-read files or be restarted on change.
  • Enable etcd encryption and audit logging of secret access.
  • ConfigMaps and Secrets are limited to 1 MiB.

Try it

  1. Create a ConfigMap and mount it as a file in an nginx Pod; kubectl exec and cat it.
  2. Edit the ConfigMap and watch the mounted file update (about a minute) while an env var from the same map does not.
  3. Create a Secret, read it back with kubectl get secret -o jsonpath='{.data.DB_PASSWORD}' | base64 -d, and note how little protection base64 gives.
