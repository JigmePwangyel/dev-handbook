Namespaces, RBAC and Pod Security

A cluster is shared by many teams, apps and automation. Without boundaries, one team's mistake deletes another's database. Namespaces partition the cluster, RBAC decides who can do what, quotas stop noisy neighbours, and Pod security keeps containers from escaping.

Namespaces

A namespace is a named scope for most resources. Names must be unique within a namespace, not across the cluster, so web can exist in both staging and prod. Default ones: default, kube-system (control plane add-ons), kube-public, kube-node-lease.

kubectl create namespace shop-prod
kubectl get pods -n shop-prod
kubectl config set-context --current --namespace=shop-prod
kubectl api-resources --namespaced=false      # cluster-scoped kinds: Node, PV, StorageClass, Namespace...

Common layouts: one namespace per team, per app, or per environment-per-app. For hard isolation between environments (prod vs dev) use separate clusters; namespaces are a soft boundary (shared nodes, shared kernel, shared control plane).

What namespaces do NOT do

They do not isolate the network (use NetworkPolicy), do not limit resources (use ResourceQuota), and do not restrict permissions (use RBAC). They are just the scope to which those controls attach.

ServiceAccounts: identity for Pods

Humans authenticate with certificates or an OIDC identity provider; Pods authenticate as a ServiceAccount. Every namespace has a default one. The token is projected into the Pod at /var/run/secrets/kubernetes.io/serviceaccount/ and is short-lived and audience-bound in modern clusters.

apiVersion: v1
kind: ServiceAccount
metadata:
  name: shop
  namespace: shop-prod
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/shop   # cloud identity binding
automountServiceAccountToken: false   # do not mount a token unless the app calls the API

Give each workload its own ServiceAccount; never share default. Most apps never talk to the Kubernetes API, so disable the token mount.

RBAC

Role-Based Access Control answers "may subject S perform verb V on resource R?" It is purely additive: there are no deny rules; absence of a grant means denied.

ObjectScopeMeaning
RoleOne namespaceA set of permissions
ClusterRoleCluster-wide (or reusable template)Permissions, including non-namespaced resources
RoleBindingOne namespaceGrants a Role or ClusterRole to subjects within that namespace
ClusterRoleBindingCluster-wideGrants across all namespaces
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: shop-prod
rules:
  - apiGroups: [""]                 # "" = core group
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-team-read-pods
  namespace: shop-prod
subjects:
  - kind: Group
    name: shop-developers           # from your identity provider
    apiGroup: rbac.authorization.k8s.io
  - kind: ServiceAccount
    name: shop
    namespace: shop-prod
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io

Test it without guessing:

kubectl auth can-i delete pods -n shop-prod --as=jane
kubectl auth can-i list secrets -n shop-prod --as=system:serviceaccount:shop-prod:shop
kubectl auth can-i --list -n shop-prod --as=jane

Built-in ClusterRoles to reuse: view, edit, admin (namespace-level) and cluster-admin (everything). A typical pattern: bind edit to developers in their own namespaces via RoleBinding, view in prod.

RBAC pitfalls
  • Never bind cluster-admin to CI tokens or apps casually; it is root for the cluster.
  • get secrets, create pods, exec and the escalate/bind verbs are powerful: reading secrets reveals credentials, creating a Pod can mount them.
  • Wildcards (resources: ["*"]) grow with new CRDs. Be explicit.
  • Audit with tools like kubectl-who-can, rbac-lookup or Kubescape.

ResourceQuota and LimitRange

Without limits, one namespace can consume the entire cluster.

apiVersion: v1
kind: ResourceQuota
metadata: { name: team-quota, namespace: shop-dev }
spec:
  hard:
    requests.cpu: "10"
    requests.memory: 20Gi
    limits.memory: 40Gi
    pods: "50"
    persistentvolumeclaims: "10"
    services.loadbalancers: "1"      # avoid surprise cloud bills
---
apiVersion: v1
kind: LimitRange
metadata: { name: defaults, namespace: shop-dev }
spec:
  limits:
    - type: Container
      default:        { memory: 256Mi }
      defaultRequest: { cpu: 100m, memory: 128Mi }
      max:            { memory: 2Gi }

When a compute quota is set, Pods must declare requests/limits or be rejected; a LimitRange supplies defaults so developers do not hit that wall.

Pod security

By default a container may run as root, add Linux capabilities or even be privileged, which is nearly host root. The built-in Pod Security Admission enforces three standard profiles per namespace via labels:

ProfileAllows
privilegedAnything (system components only)
baselineBlocks known escalations: hostNetwork, privileged, hostPath etc.
restrictedHardened best practice: non-root, no privilege escalation, seccomp, drop all capabilities
kubectl label namespace shop-prod \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/warn=restricted

A Pod that passes restricted:

spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    seccompProfile: { type: RuntimeDefault }
  containers:
    - name: shop
      image: ghcr.io/example/shop:2.3.1
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities: { drop: ["ALL"] }

For richer rules (only allow images from your registry, require labels) use a policy engine: Kyverno, OPA Gatekeeper, or the built-in ValidatingAdmissionPolicy (CEL).

Checklist

  • Separate namespaces per team or app; default-deny NetworkPolicy in each.
  • A ServiceAccount per workload, least-privilege Roles, token mounting off by default.
  • Quotas and LimitRanges on shared namespaces.
  • restricted Pod Security on app namespaces.
  • Humans via SSO groups, not shared kubeconfig certificates.

Try it

  1. Create a namespace, a ServiceAccount, a Role that can only list Pods, and a RoleBinding. Verify with kubectl auth can-i using --as=system:serviceaccount:....
  2. Add a ResourceQuota of 2 Pods and try to scale a Deployment to 5. Read the error events.
  3. Label a namespace enforce=restricted and try to run nginx as root; then fix the Pod's securityContext.
