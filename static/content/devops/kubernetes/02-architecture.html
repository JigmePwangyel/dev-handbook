Kubernetes Architecture

A Kubernetes cluster is a set of machines split into a control plane that makes decisions and worker nodes that run your containers. Underneath, everything is one idea repeated many times: a controller compares desired state with actual state and closes the gap.

Control plane components

kube-apiserver

The front door and the only component that talks to etcd. Every client (kubectl, the scheduler, kubelets, controllers, your CI) uses its REST API. It authenticates the caller, authorises the request (RBAC), runs admission controllers (which can validate or mutate objects, e.g. inject defaults or reject privileged Pods) and persists the result. It is stateless and can be run in multiple replicas behind a load balancer.

etcd

A distributed, strongly consistent key-value store (Raft consensus) holding the entire cluster state: every Deployment, Secret, Node and Pod. If etcd is lost and you have no backup, the cluster forgets everything it was supposed to run. Run 3 or 5 members for quorum, use fast SSDs, and back it up (etcdctl snapshot save). Managed offerings do this for you.

kube-scheduler

Watches for Pods that have no node assigned and picks one. It runs two phases: filtering (remove nodes that cannot host the Pod: not enough CPU or memory, taints the Pod does not tolerate, wrong node selector) and scoring (rank the survivors: spread across zones, prefer nodes with the image cached, balance load). It then writes the chosen node name into the Pod; it never starts anything itself.

kube-controller-manager

A single binary that runs many controllers: the Deployment controller, ReplicaSet controller, Node controller (marks nodes NotReady, evicts Pods), Job controller, EndpointSlice controller, ServiceAccount controller and more. Each is a loop of the form described below.

cloud-controller-manager

On cloud providers, this integrates with the cloud API: creating a load balancer when you make a Service of type LoadBalancer, attaching disks, reporting node lifecycle.

Node components

kubelet

The agent on each node. It watches the API server for Pods assigned to its node, tells the container runtime to start the containers, runs probes, reports status back and mounts volumes. It is the one that actually makes a Pod real.

Container runtime

Anything implementing the Container Runtime Interface (CRI): containerd (most common) or CRI-O. Docker Engine itself has not been supported directly since 1.24, but images built with Docker run fine, since the image format is a standard (OCI).

kube-proxy

Programs the node's network rules (iptables or IPVS; nftables in newer versions) so that traffic sent to a Service's virtual IP gets load-balanced to the Pods behind it. Some CNI plugins like Cilium replace it with eBPF. Covered in the networking lesson.

CNI plugin

Not part of core, but required: a Container Network Interface plugin (Calico, Cilium, Flannel, the cloud provider's VPC CNI) gives each Pod an IP and makes Pod-to-Pod traffic work across nodes.

The reconciliation loop

This is the single most important concept in Kubernetes.

        ┌─────────────────────────────────────────┐
        ▼                                         │
  observe actual state ──▶ compare to desired ──▶ act to reduce difference
  (watch API server)        (spec in etcd)        (create/delete/update)

Every object has a spec (what you want) and a status (what is). Controllers use watches, not polling, to be notified of changes. They are level-triggered: they react to "current state differs from desired" rather than to individual events, so if a controller crashes and restarts it simply re-reads the world and carries on. That makes the system robust.

Walkthrough: kubectl apply -f deployment.yaml with 3 replicas

  1. kubectl sends the Deployment to the API server, which authenticates, authorises, validates, and stores it in etcd.
  2. The Deployment controller sees a new Deployment and creates a ReplicaSet.
  3. The ReplicaSet controller sees "want 3, have 0" and creates 3 Pod objects (no node assigned yet).
  4. The scheduler sees 3 unscheduled Pods, filters and scores nodes, and binds each Pod to a node.
  5. The kubelet on each chosen node sees a Pod bound to it, pulls the image, asks containerd to start the containers, then reports status Running.
  6. The EndpointSlice controller notices ready Pods and updates Service endpoints; kube-proxy updates rules.

No component calls another directly. They coordinate only by reading and writing objects through the API server. That loose coupling is why you can swap in a custom scheduler or add your own controller.

Declarative and extensible

Because everything is "objects plus controllers", you can add new object types with CustomResourceDefinitions and write your own controller (an operator) to manage, say, a PostgreSQL cluster. Tools like cert-manager, Argo CD and Crossplane work exactly this way.

Pitfalls and best practices

  • The API server is the bottleneck and the security perimeter. Restrict who can reach it and use RBAC.
  • Do not run workloads on control plane nodes in production; they are tainted by default for this reason.
  • Back up etcd, or use a managed control plane.
  • Keep versions skewed within supported limits (kubelet may lag the API server by a few minor versions); upgrade control plane first.
  • Do not edit objects the controllers manage (e.g. Pods owned by a ReplicaSet): your change will be reverted.

Try it

On a local cluster (next lesson), run kubectl get pods -n kube-system and identify the control plane components as Pods. Then run kubectl get events -w in one terminal and kubectl create deployment demo --image=nginx --replicas=3 in another; match each event to a step in the walkthrough above.
