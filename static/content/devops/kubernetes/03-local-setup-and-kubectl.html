Local Setup and kubectl Essentials

You do not need a cloud account to learn Kubernetes. A full cluster runs on your laptop in under a minute. This lesson sets one up, teaches the kubectl commands you will use daily, and dissects the shape of every Kubernetes YAML file.

Choosing a local cluster

ToolHow it worksBest for
kindRuns each "node" as a Docker container; multi-node supportedCI pipelines, testing, learning multi-node behaviour
minikubeVM or container with a single node, many addons (minikube addons enable ingress)Beginners, trying addons
k3dRuns k3s (lightweight Kubernetes) in DockerFast, low-memory clusters
Docker Desktop / Rancher DesktopBuilt-in single-node cluster toggleZero extra install

All need a container runtime (Docker, Podman or similar) running first.

Install and create a cluster with kind

# macOS (Linux: download the binary from the kind releases page)
brew install kind kubectl

# single-node cluster
kind create cluster --name dev

# or multi-node, with a port mapped for later ingress experiments
cat <<'EOF' > kind-config.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
    extraPortMappings:
      - containerPort: 80
        hostPort: 8080
  - role: worker
  - role: worker
EOF
kind create cluster --name dev --config kind-config.yaml

kubectl cluster-info --context kind-dev
kubectl get nodes

Alternatives: minikube start or k3d cluster create dev --agents 2. Delete with kind delete cluster --name dev.

Loading local images

A local cluster cannot see images in your Docker daemon automatically. Load them in: kind load docker-image myapp:dev --name dev (minikube: minikube image load myapp:dev). Use a non-latest tag, since :latest defaults to imagePullPolicy: Always and the cluster will try to pull from a registry.

kubectl and contexts

kubectl reads ~/.kube/config, which lists clusters, users (credentials) and contexts (a cluster + user + default namespace). The current context determines which cluster every command hits.

kubectl config get-contexts            # list
kubectl config current-context
kubectl config use-context kind-dev    # switch cluster
kubectl config set-context --current --namespace=staging   # default namespace
Production foot-gun

Running kubectl delete against the wrong context is a classic outage. Show the current context in your shell prompt (kube-ps1) and consider tools like kubectx/kubens. Prefer separate kubeconfig files per environment and CI-driven changes to production.

Daily commands

# Read
kubectl get pods                       # in current namespace
kubectl get pods -A                    # all namespaces
kubectl get pods -o wide               # node and IP
kubectl get deploy,svc,pods -l app=web # multiple kinds, label selector
kubectl get pod web-1 -o yaml          # full object
kubectl describe pod web-1             # human-readable detail + Events
kubectl logs web-1                     # stdout/stderr
kubectl logs -f web-1 -c sidecar --previous   # follow, specific container, last crash
kubectl api-resources                  # every kind the cluster knows
kubectl explain deployment.spec.strategy      # built-in schema docs

# Write
kubectl apply -f manifest.yaml         # create or update declaratively
kubectl apply -f dir/ -R               # a whole folder
kubectl delete -f manifest.yaml
kubectl create deployment web --image=nginx:1.27 --dry-run=client -o yaml > web.yaml
kubectl diff -f manifest.yaml          # preview what apply would change

# Interact
kubectl exec -it web-1 -- sh
kubectl port-forward svc/web 8080:80   # localhost:8080 -> Service port 80
kubectl scale deploy/web --replicas=5
kubectl top pods                       # needs metrics-server

Set up an alias (alias k=kubectl) and shell completion (source <(kubectl completion zsh)).

Imperative vs declarative

kubectl create/run/scale are imperative shortcuts, handy for experiments. kubectl apply -f is declarative and the right way to manage anything real: the YAML file in git is the source of truth. A good trick is generating YAML with --dry-run=client -o yaml and then editing it.

Anatomy of a manifest

Every Kubernetes object has the same four top-level fields:

apiVersion: apps/v1          # API group and version of this kind
kind: Deployment             # the type of object
metadata:                    # identity
  name: web                  # unique within kind + namespace
  namespace: default
  labels:                    # key/values you query and select by
    app: web
  annotations:               # non-identifying metadata (tools, notes)
    owner: team-shop
spec:                        # DESIRED state; shape depends on kind
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:1.27
          ports:
            - containerPort: 80
# status:                    # ACTUAL state, written by Kubernetes, never by you
  • apiVersion: find it with kubectl api-resources or kubectl explain. Core objects (Pod, Service) use v1; Deployments use apps/v1; Ingress networking.k8s.io/v1.
  • Labels and selectors are how objects find each other. A Service picks Pods by label; a Deployment owns Pods that match its selector. A mismatch is the most common beginner bug.
  • Multiple objects can live in one file separated by ---.
Learn from the cluster itself

kubectl explain pod.spec.containers --recursive prints every legal field with types, offline. Much faster than searching docs.

Pitfalls

  • YAML indentation is semantic. Use an editor with a Kubernetes schema plugin and run kubectl apply --dry-run=server to validate against the real API.
  • Unquoted values like yes, on or 1.20 may be parsed as booleans or floats. Quote strings in env values.
  • kubectl edit changes live objects and leaves your files out of date. Edit the file and apply.

Try it

  1. Create a kind cluster with two workers; run kubectl get nodes -o wide.
  2. Run kubectl create deployment hello --image=nginx:1.27 --replicas=2 --dry-run=client -o yaml > hello.yaml, apply it, then kubectl port-forward deploy/hello 8080:80 and curl it.
  3. Delete one Pod with kubectl delete pod and watch it come back with kubectl get pods -w.
