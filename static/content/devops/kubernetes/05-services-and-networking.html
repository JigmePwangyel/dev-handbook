Services and Networking

Pods come and go and their IPs change constantly. A Service gives a set of Pods one stable name and virtual IP, and load-balances across the healthy ones. This lesson covers the Service types, cluster DNS, what kube-proxy really does, and how NetworkPolicy locks traffic down.

The networking model

Kubernetes imposes three rules, implemented by the CNI plugin:

  1. Every Pod gets its own IP.
  2. Any Pod can reach any other Pod by IP without NAT, across nodes.
  3. Agents on a node can reach all Pods on that node.

This flat network is simple for apps, but Pod IPs are ephemeral. If frontend hard-coded 10.244.1.17 for the API, it would break at the next restart. Hence Services.

Service basics

A Service selects Pods by label and exposes them on a stable virtual IP (the ClusterIP) and DNS name. Only Pods that pass their readiness probe receive traffic.

apiVersion: v1
kind: Service
metadata:
  name: shop
spec:
  type: ClusterIP            # default
  selector:
    app: shop                # matches Pod labels
  ports:
    - name: http
      port: 80               # port on the Service
      targetPort: 8080       # port on the Pod (number or named port)

Behind the scenes the EndpointSlice controller keeps a list of ready Pod IPs for the Service: kubectl get endpointslices -l kubernetes.io/service-name=shop. If this list is empty, your selector is wrong or no Pods are ready. This is the number one cause of "my Service doesn't work".

apiVersion: v1
kind: Service
metadata:
  name: shop-public
  annotations:
    service.beta.kubernetes.io/aws-load-balancer-type: "external"   # provider specific
spec:
  type: LoadBalancer
  selector: { app: shop }
  ports:
    - port: 443
      targetPort: 8080
  externalTrafficPolicy: Local   # preserve client IP, avoid extra hop
Cost trap

Each LoadBalancer Service provisions a separate cloud load balancer (typically $15-25/month plus traffic). For many HTTP services, use one Ingress or Gateway in front instead (next lesson).

Cluster DNS

CoreDNS runs in the cluster and every Pod is configured to use it. Each Service gets:

shop.default.svc.cluster.local
<service>.<namespace>.svc.cluster.local

Within the same namespace just use shop; across namespaces use shop.other-ns. Pods in a StatefulSet behind a headless Service get db-0.db.default.svc.cluster.local. Environment variables like SHOP_SERVICE_HOST also exist but DNS is the recommended approach.

kubectl run tmp --rm -it --image=busybox:1.36 -- nslookup shop
kubectl run tmp --rm -it --image=curlimages/curl -- curl -s http://shop/healthz

How kube-proxy works

The ClusterIP is virtual: no interface owns it and nothing listens on it. kube-proxy on each node watches Services and EndpointSlices and programs kernel rules so that packets addressed to the ClusterIP are rewritten (DNAT) to a randomly chosen ready Pod IP.

  • iptables mode (long-time default): chains of rules with probability-based selection. Fine up to a few thousand Services, rule updates get slow beyond that.
  • IPVS mode: kernel load balancer with hash tables and more algorithms; scales better.
  • nftables mode: the modern replacement for iptables, GA in recent releases.
  • eBPF (Cilium): can replace kube-proxy entirely, with better performance and observability.

Load balancing happens at connection level (L4), so a long-lived gRPC or HTTP/2 connection sticks to one Pod. For per-request balancing you need an L7 proxy, a service mesh, or client-side balancing with a headless Service.

NetworkPolicy

By default all Pods can talk to all Pods. A compromised frontend can reach your database. NetworkPolicy is a firewall at the Pod level. Once any policy selects a Pod, traffic of that direction is denied except what policies allow. It requires a CNI that enforces it (Calico, Cilium; plain Flannel does not).

# 1. Default deny all ingress in the namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: shop
spec:
  podSelector: {}          # all Pods
  policyTypes: [Ingress]
---
# 2. Allow only the API to reach the database on 5432
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: db-allow-api
  namespace: shop
spec:
  podSelector:
    matchLabels: { app: db }
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels: { app: api }
      ports:
        - protocol: TCP
          port: 5432

If you also deny egress, remember to allow DNS (UDP/TCP 53 to kube-dns) or everything breaks mysteriously.

Pitfalls and best practices

  • Match targetPort to the port your app actually listens on, and make the app listen on 0.0.0.0, not 127.0.0.1.
  • Use named ports so changing a number does not require editing every Service.
  • Start with a default-deny policy per namespace, then add allows.
  • Do not use NodePort in production for public traffic; node IPs change.
  • Expose databases only as ClusterIP.

Try it

  1. Deploy nginx with 3 replicas and a ClusterIP Service. Run kubectl get endpointslices and note the three Pod IPs.
  2. From a temporary busybox Pod, wget -qO- shop. Break the selector label and watch the endpoints go empty.
  3. On a kind cluster with Calico or Cilium, apply a default-deny policy and confirm the busybox Pod can no longer reach nginx.
