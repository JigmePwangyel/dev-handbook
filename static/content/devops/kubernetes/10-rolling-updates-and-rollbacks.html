Rolling Updates and Rollbacks

Shipping a new version should not mean downtime. Kubernetes Deployments replace Pods gradually, only advancing when the new ones are healthy, and keep history so you can undo a bad release with one command.

What happens without it

The naive deploy is "stop v1, start v2". Between those two steps users see errors. If v2 crashes on boot, you are down until you manually fix or revert. A rolling update trades speed for safety: at every moment enough healthy Pods exist to serve traffic.

How a rolling update works

A Deployment owns ReplicaSets, one per Pod template version. On a change to spec.template, the Deployment controller creates a new ReplicaSet and shifts replicas from old to new in steps.

 replicas: 4, maxSurge: 1, maxUnavailable: 0

 start      RS-v1 [■ ■ ■ ■]            RS-v2 [ ]
 step 1     RS-v1 [■ ■ ■ ■]            RS-v2 [□]     surge: 5 Pods total, new not ready yet
 step 2     RS-v1 [■ ■ ■ ■]            RS-v2 [■]     new is Ready
 step 3     RS-v1 [■ ■ ■  ]            RS-v2 [■ □]   old terminated, next new started
 ...
 end        RS-v1 [        ]  (kept, 0 replicas, for rollback)   RS-v2 [■ ■ ■ ■]

Strategy settings

spec:
  replicas: 4
  revisionHistoryLimit: 10        # old ReplicaSets kept for rollback
  progressDeadlineSeconds: 600    # mark rollout "failed" if no progress
  minReadySeconds: 10             # new Pod must stay Ready this long to count
  strategy:
    type: RollingUpdate           # the default (alternative: Recreate)
    rollingUpdate:
      maxSurge: 25%               # extra Pods above desired during update
      maxUnavailable: 0           # how many may be below desired
SettingEffect
maxSurgeHigher means a faster rollout but needs spare capacity. Number or percentage.
maxUnavailable0 keeps full capacity throughout (needs surge > 0). Default is 25% for both.
minReadySecondsCatches Pods that pass readiness then crash a few seconds later.
progressDeadlineSecondsController sets condition Progressing=False; CI can fail on it.

Recreate kills all old Pods first, then starts new ones. Accept the downtime when two versions can not coexist (for example a schema-incompatible singleton or RWO volume that cannot attach twice).

Rolling updates depend on readiness probes

Without a readiness probe Kubernetes considers a Pod ready as soon as the process starts, so it may send traffic and tear down old Pods before the new app can answer. A correct readiness probe is what makes a rollout zero-downtime. Also remember that during a rollout v1 and v2 run simultaneously: your APIs and database schemas must be backward compatible (expand and contract migrations).

kubectl rollout in practice

kubectl set image deploy/shop shop=ghcr.io/example/shop:2.4.0   # or edit YAML and apply
kubectl rollout status deploy/shop            # blocks until done; exit code != 0 on failure
kubectl rollout history deploy/shop           # list revisions
kubectl rollout history deploy/shop --revision=3
kubectl rollout undo deploy/shop              # back to previous revision
kubectl rollout undo deploy/shop --to-revision=2
kubectl rollout pause deploy/shop             # batch several edits, then...
kubectl rollout resume deploy/shop
kubectl rollout restart deploy/shop           # fresh Pods, same template (pick up new config)

Record why a change happened with an annotation (kubernetes.io/change-cause) so history is readable. In a CI pipeline, the deploy step usually runs kubectl rollout status --timeout=5m and runs rollout undo if it fails.

GitOps rollback

If git is the source of truth, rollback means git revert and letting Argo CD or Flux apply it, rather than kubectl rollout undo, which creates drift from git.

Graceful shutdown

When a Pod is terminated, two things happen concurrently: it is removed from Service endpoints, and SIGTERM is sent. Endpoint removal takes a moment to propagate through kube-proxy and ingress controllers, so requests can still arrive after SIGTERM. Mitigate:

spec:
  terminationGracePeriodSeconds: 45
  containers:
    - name: shop
      lifecycle:
        preStop:
          exec: { command: ["sleep", "10"] }   # let endpoints drain first

And make the app, on SIGTERM, stop accepting new connections, finish in-flight requests and exit. Many frameworks need explicit shutdown hooks.

PodDisruptionBudgets

Rolling updates are voluntary disruptions you control. But cluster operations also evict Pods: node drains for upgrades, autoscaler scale-down. A PodDisruptionBudget limits how many Pods of an app may be down at once during such voluntary evictions.

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: shop }
spec:
  minAvailable: 2          # or: maxUnavailable: 1
  selector:
    matchLabels: { app: shop }

kubectl drain node-1 then evicts Pods one by one while respecting the budget, waiting if necessary. PDBs do not protect against crashes or node failure. Beware minAvailable equal to replicas: nothing can ever be evicted and upgrades hang forever.

Beyond built-in rolling updates

StrategyHowTool
Blue-greenRun both versions fully, flip Service selector or routePlain Services; Argo Rollouts
CanarySend 5 percent, 25 percent, ... of traffic to v2 while watching metrics, auto-abort on errorsArgo Rollouts, Flagger, Gateway API weights
Feature flagsDeploy dark, enable per userApp level

Native Deployments shift Pod counts, not traffic percentages; for fine-grained canaries use a progressive delivery controller.

Pitfalls

  • A rollout stuck at "Waiting for rollout to finish": new Pods fail readiness, are Pending (no capacity for surge), or image is wrong. Old Pods keep serving, which is the point. Inspect with kubectl describe.
  • :latest image tags: re-applying identical YAML changes nothing, and rollback cannot restore a specific version.
  • revisionHistoryLimit: 0 disables rollback.
  • Database migrations that break the old version during the rollout window.

Try it

  1. Deploy 4 replicas of nginx:1.26 with a readiness probe. Update to nginx:1.27 while running kubectl get pods -w in another terminal.
  2. Update to a nonexistent tag nginx:nope, watch the rollout stall with ImagePullBackOff while old Pods keep serving, then kubectl rollout undo.
  3. Add a PDB with minAvailable 3 and run kubectl drain on a worker to see it respected.
