Probes, Resources and Autoscaling

Kubernetes can only keep your app healthy and right-sized if you tell it what healthy means and how much it needs. Probes, resource requests and limits, and autoscalers are the three levers that turn a pile of Pods into a resilient, efficient system.

Health probes

By default Kubernetes only knows if a container's main process is alive. A deadlocked web server is "alive" but useless. Probes let the kubelet ask the app directly.

ProbeQuestionOn failure
startupProbeHas the app finished booting?Container is killed and restarted; other probes are disabled until it passes
readinessProbeCan it serve traffic right now?Removed from Service endpoints; not restarted
livenessProbeIs it stuck beyond recovery?Container is restarted
containers:
  - name: shop
    image: ghcr.io/example/shop:2.3.1
    startupProbe:                  # allows up to 30 x 5 = 150 s to boot
      httpGet: { path: /healthz, port: 8080 }
      periodSeconds: 5
      failureThreshold: 30
    readinessProbe:
      httpGet: { path: /ready, port: 8080 }
      periodSeconds: 5
      timeoutSeconds: 2
      failureThreshold: 3
    livenessProbe:
      httpGet: { path: /healthz, port: 8080 }
      periodSeconds: 10
      timeoutSeconds: 2
      failureThreshold: 3
      # other mechanisms: tcpSocket, exec (command), grpc
Liveness probes cause outages

A common disaster: the liveness probe checks the database. The database blips, every Pod fails liveness, Kubernetes restarts the entire fleet at once and turns a blip into an outage. Keep liveness checks local and cheap (is this process responsive?). Put dependency checks in readiness at most, and be careful there too. If unsure, use no liveness probe rather than a bad one.

Readiness is what makes rolling updates safe: a new Pod only receives traffic, and an old one is only removed, once readiness passes.

Requests and limits

Each container declares resources:

resources:
  requests:        # what the scheduler RESERVES; used to place the Pod
    cpu: 250m      # 250 millicores = 0.25 of a core
    memory: 256Mi
  limits:          # the ceiling enforced at runtime
    memory: 512Mi
    # cpu limit often omitted, see below
  • Requests drive scheduling. A Pod requesting 4 Gi only lands on a node with 4 Gi unreserved. Also the guaranteed share under contention.
  • CPU limit: compressible. Exceeding it means throttling (slowness), not death. Many teams set CPU requests but no CPU limits to avoid needless throttling; others keep them for fairness. Both are defensible; know the trade-off.
  • Memory limit: incompressible. Exceeding it means the kernel kills the container: OOMKilled, exit code 137.

Without requests, the scheduler thinks Pods are free, overcommits nodes, and everything slows or gets evicted. Without memory limits, one leaky Pod can take down a node's neighbours.

QoS classes

Derived automatically; determines eviction order when a node runs out of memory.

ClassConditionEvicted
GuaranteedEvery container has requests = limits for CPU and memoryLast
BurstableAt least one request or limit set, not GuaranteedMiddle
BestEffortNothing setFirst

Right-sizing: watch real usage (kubectl top pods, Prometheus) and set memory request close to typical peak with a limit with headroom, and CPU request near typical usage. JVM and Node apps need runtime flags aware of the container limit (modern JVMs are; for Node set --max-old-space-size below the limit).

Horizontal Pod Autoscaler (HPA)

Adds or removes replicas based on metrics. It needs metrics-server installed and CPU/memory requests on the Pods (utilisation is computed relative to the request).

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: shop }
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: shop
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 70 }
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300   # avoid flapping
    scaleUp:
      policies:
        - { type: Percent, value: 100, periodSeconds: 60 }

The formula: desired = ceil(current * currentMetric / targetMetric). Custom and external metrics (requests per second, queue length) work through a metrics adapter, or use KEDA, which scales on Kafka lag, SQS depth, cron schedules and more, and can scale to zero.

HPA works only if your app scales horizontally (stateless or shared-nothing) and starts fast.

Vertical Pod Autoscaler (VPA)

Adjusts the requests of a workload based on observed usage. Modes: Off (recommendations only, safest start), Initial, and Auto/Recreate (evicts Pods to apply new values; newer versions support in-place resize on recent Kubernetes). Do not let HPA and VPA both react to CPU on the same workload. A common pattern: VPA in recommendation mode to guide manual right-sizing.

Cluster Autoscaler and Karpenter

HPA creates Pods, but if no node has room they sit Pending. The Cluster Autoscaler watches for unschedulable Pods and adds nodes to a node group; it removes nodes that stay underused and whose Pods can move elsewhere. Karpenter (AWS, spreading to others) provisions right-sized individual instances directly without pre-defined node groups, often faster and cheaper, mixing spot and on-demand.

 traffic ↑ ─▶ HPA adds Pods ─▶ no room? Pods Pending ─▶ Cluster Autoscaler adds a node ─▶ Pods scheduled
 traffic ↓ ─▶ HPA removes Pods ─▶ nodes underused ─▶ autoscaler drains and removes node

Node scale-up takes minutes. For spiky traffic, keep headroom with low-priority "pause" Pods that get preempted, or a higher minReplicas.

Pitfalls

  • HPA shows <unknown> targets: metrics-server missing or requests not set.
  • Readiness probe too aggressive, so new Pods never become ready and HPA keeps adding more.
  • Memory limit lower than the real working set: endless OOMKilled restarts. Check kubectl describe pod for "Last State: Terminated, Reason: OOMKilled".
  • Slow startup with a short liveness: restart loop. Use a startupProbe.
  • Scale-down kills in-flight requests: handle SIGTERM and use a preStop sleep of a few seconds so endpoints propagate first.

Try it

  1. Install metrics-server on kind (it needs --kubelet-insecure-tls locally). Run kubectl top nodes.
  2. Deploy a CPU-burning app, attach an HPA at 50 percent, and generate load with kubectl run -it load --image=busybox -- sh -c "while true; do wget -q -O- http://shop; done". Watch kubectl get hpa -w.
  3. Set a memory limit of 20Mi on a Pod that allocates more and observe OOMKilled.
