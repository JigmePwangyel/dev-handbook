Ingress and the Gateway API

Services expose ports; Ingress and Gateway expose HTTP(S) applications. They give you host and path routing, TLS termination and one shared entry point for dozens of services instead of one costly load balancer each.

Why Ingress exists

Suppose you have shop, blog and api. With LoadBalancer Services you pay for three cloud LBs, get three IPs, and handle TLS three times. What you want is one public entry point that looks at the HTTP Host header and path and routes: shop.example.com to the shop Service, example.com/blog to the blog, and so on. That is a layer 7 reverse proxy (see the Networking section), managed declaratively.

 Internet ──▶ Cloud LB ──▶ Ingress controller Pods (nginx/Traefik/Envoy)
                                  │ routes by host + path
              ┌───────────────────┼───────────────────┐
              ▼                   ▼                   ▼
        Service shop        Service blog         Service api

Two parts: resource and controller

An Ingress object is just a set of routing rules. Nothing happens until an Ingress controller is installed to watch those objects and configure a real proxy. Kubernetes does not ship one. Common choices:

ControllerNotes
ingress-nginxVery widespread; the community project is being retired (best-effort maintenance only after March 2026), so check migration plans for new builds
TraefikDynamic config, built-in Let's Encrypt, default in k3s
HAProxy, Kong, Contour/EnvoyPerformance or API-gateway features
Cloud-native (AWS Load Balancer Controller, GKE Ingress)Provisions the cloud's own L7 LB per Ingress

Pick one with ingressClassName; a cluster can have several.

An Ingress example

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod   # request a certificate
spec:
  ingressClassName: nginx
  tls:
    - hosts: [shop.example.com, api.example.com]
      secretName: web-tls            # cert-manager creates and renews this
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service: { name: shop, port: { number: 80 } }
    - host: api.example.com
      http:
        paths:
          - path: /v1
            pathType: Prefix
            backend:
              service: { name: api, port: { number: 80 } }

Install ingress-nginx on kind or minikube with their documented manifests/addons, then point DNS (or /etc/hosts or a *.localtest.me wildcard) at the controller's address.

TLS automation with cert-manager

Manually buying and rotating certificates does not scale and expired certs are a classic outage. cert-manager is an operator that obtains certificates from Let's Encrypt (or an internal CA) and renews them automatically about 30 days before expiry.

helm repo add jetstack https://charts.jetstack.io
helm install cert-manager jetstack/cert-manager \
  -n cert-manager --create-namespace --set crds.enabled=true
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: ops@example.com
    privateKeySecretRef:
      name: letsencrypt-account-key
    solvers:
      - http01:
          ingress:
            ingressClassName: nginx

The flow: the Ingress annotation causes cert-manager to create a Certificate, which creates an ACME Order; Let's Encrypt validates domain ownership by requesting a token over HTTP (HTTP-01) or via a DNS TXT record (DNS-01, required for wildcard certs); the signed certificate is stored in the Secret named in tls.secretName and the controller picks it up.

Use staging first

Let's Encrypt production has strict rate limits. Create a second ClusterIssuer pointing at the staging server and test with it before switching.

Limitations of Ingress

  • It only models HTTP(S). TCP/UDP, gRPC routing, header matching and traffic splitting need vendor-specific annotations that are not portable.
  • One resource mixes the concerns of infrastructure admins (which load balancer, which certs) and app developers (which paths).

Gateway API: the successor

The Gateway API (gateway.networking.k8s.io) is the official, more expressive replacement, GA for core HTTP features and supported by Envoy Gateway, Istio, Cilium, Traefik, NGINX Gateway Fabric, Contour and cloud providers. It splits roles into separate objects:

ObjectOwned byPurpose
GatewayClassInfrastructure providerWhich implementation (like StorageClass)
GatewayCluster operatorListeners: ports, protocols, hostnames, TLS
HTTPRoute, GRPCRoute, TCPRouteApp developersRouting rules attached to a Gateway
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: public
  namespace: infra
spec:
  gatewayClassName: envoy
  listeners:
    - name: https
      protocol: HTTPS
      port: 443
      hostname: "*.example.com"
      tls:
        mode: Terminate
        certificateRefs: [{ name: wildcard-tls }]
      allowedRoutes:
        namespaces: { from: All }
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: shop
  namespace: shop
spec:
  parentRefs: [{ name: public, namespace: infra }]
  hostnames: ["shop.example.com"]
  rules:
    - matches:
        - path: { type: PathPrefix, value: / }
      backendRefs:
        - { name: shop-v1, port: 80, weight: 90 }   # canary: 90/10 split
        - { name: shop-v2, port: 80, weight: 10 }

Native support for weighted traffic splitting, header matching, redirects, rewrites and cross-namespace delegation replaces the pile of annotations. For new clusters, prefer Gateway API; keep Ingress where it already works.

Pitfalls

  • Forgetting ingressClassName: no controller claims the Ingress and nothing happens.
  • The backend Service has no ready endpoints: you get 503 from the proxy. Check kubectl get endpointslices.
  • Path rewriting surprises: /api forwarded as-is to an app expecting /. Configure rewrite or make the app base-path aware.
  • HTTP-01 challenges fail if DNS does not point at the controller or a redirect rule blocks /.well-known/acme-challenge.
  • Large uploads hit default proxy body size limits (nginx: 1 MB).

Try it

  1. On kind (with the extraPortMappings config from lesson 3) install an ingress controller and create an Ingress routing /a and /b to two different echo Services.
  2. Read kubectl describe ingress and find the backends and any events.
  3. Stretch: install cert-manager with a self-signed ClusterIssuer and get a TLS Secret issued for a local hostname.
