Pods and Workload Controllers

The Pod is Kubernetes' smallest deployable unit, but you almost never create one directly. You create a controller (Deployment, StatefulSet, DaemonSet, Job) that manages Pods for you. Choosing the right controller is the core design decision for every workload.

Pods

A Pod is one or more containers that share a network namespace (one IP, they talk over localhost), can share volumes, and are always scheduled together on the same node. Why not just containers? Because some processes are tightly coupled: a web app plus a log shipper, or a proxy sidecar. The Pod is the unit of co-location.

apiVersion: v1
kind: Pod
metadata:
  name: web
  labels:
    app: web
spec:
  containers:
    - name: app
      image: ghcr.io/example/shop:2.3.1
      ports:
        - containerPort: 8080
      env:
        - name: LOG_LEVEL
          value: "info"
    - name: log-shipper            # sidecar sharing the Pod
      image: fluent/fluent-bit:3.1
  initContainers:                  # run to completion BEFORE app containers
    - name: wait-for-db
      image: busybox:1.36
      command: ["sh","-c","until nc -z db 5432; do sleep 2; done"]
  restartPolicy: Always

Pods are ephemeral: when one dies it is not repaired, it is replaced by a new Pod with a new name and IP. Never rely on a Pod's IP or local filesystem surviving.

Do not run naked Pods

A bare Pod is not rescheduled if its node dies. Always wrap Pods in a controller.

The controller family

  Deployment ──owns──▶ ReplicaSet ──owns──▶ Pod, Pod, Pod     (stateless apps)
  StatefulSet ────────────────────────────▶ Pod-0, Pod-1      (stable identity + disks)
  DaemonSet ──────────────────────────────▶ one Pod per node  (agents)
  Job ────────────────────────────────────▶ Pods that finish  (batch)
  CronJob ──creates──▶ Job ───────────────▶ on a schedule

ReplicaSet

Ensures N identical Pods exist, using a label selector. If one dies it makes another. You rarely use it directly because a Deployment manages ReplicaSets for you, which enables rolling updates (a new ReplicaSet per version).

Deployment

The default choice for stateless apps (web servers, APIs, workers). It gives you replicas, rolling updates, rollbacks and scaling.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: shop
spec:
  replicas: 3
  selector:
    matchLabels:             # must match template labels; immutable after creation
      app: shop
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:                  # the Pod template
    metadata:
      labels:
        app: shop
    spec:
      containers:
        - name: shop
          image: ghcr.io/example/shop:2.3.1   # pin a tag or digest, never :latest
          ports:
            - containerPort: 8080
          resources:
            requests: { cpu: 100m, memory: 128Mi }
            limits:   { memory: 256Mi }
          readinessProbe:
            httpGet: { path: /healthz, port: 8080 }

Changing anything in spec.template (for example the image) triggers a rollout: a new ReplicaSet scales up while the old one scales down. Changing replicas does not.

StatefulSet

For workloads that need a stable identity: databases, Kafka, ZooKeeper, Elasticsearch. Differences from a Deployment:

  • Pods are named name-0, name-1, ... and keep their name across restarts.
  • Each Pod gets its own PersistentVolumeClaim via volumeClaimTemplates, which survives Pod deletion.
  • Created and updated in order (0, then 1, ...) and deleted in reverse.
  • Requires a headless Service (clusterIP: None) giving each Pod a DNS name like db-0.db.default.svc.
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
spec:
  serviceName: db            # headless Service name
  replicas: 3
  selector:
    matchLabels: { app: db }
  template:
    metadata:
      labels: { app: db }
    spec:
      containers:
        - name: postgres
          image: postgres:17
          volumeMounts:
            - { name: data, mountPath: /var/lib/postgresql/data }
  volumeClaimTemplates:
    - metadata: { name: data }
      spec:
        accessModes: ["ReadWriteOnce"]
        resources: { requests: { storage: 20Gi } }
Honest advice

A StatefulSet gives you identity and storage, not replication, backups or failover. For production databases, use a managed service (RDS, Cloud SQL) or a mature operator (CloudNativePG, Strimzi) rather than hand-rolling it.

DaemonSet

Runs exactly one Pod on every node (or a selected subset), including nodes added later. Typical uses: log collectors (Fluent Bit), node metrics exporters, CNI plugins, security agents.

apiVersion: apps/v1
kind: DaemonSet
metadata: { name: node-exporter }
spec:
  selector:
    matchLabels: { app: node-exporter }
  template:
    metadata:
      labels: { app: node-exporter }
    spec:
      tolerations:
        - operator: Exists     # also run on tainted nodes
      containers:
        - name: exporter
          image: quay.io/prometheus/node-exporter:v1.8.2
          ports: [{ containerPort: 9100, hostPort: 9100 }]

Job and CronJob

A Job runs Pods until a number of them complete successfully: database migrations, report generation. A CronJob creates Jobs on a cron schedule.

apiVersion: batch/v1
kind: CronJob
metadata: { name: nightly-report }
spec:
  schedule: "0 2 * * *"           # 02:00 daily (cluster time, UTC by default)
  concurrencyPolicy: Forbid       # skip if previous still running
  successfulJobsHistoryLimit: 3
  jobTemplate:
    spec:
      backoffLimit: 3             # retries before marking failed
      activeDeadlineSeconds: 3600
      ttlSecondsAfterFinished: 86400
      template:
        spec:
          restartPolicy: OnFailure   # Jobs must be OnFailure or Never
          containers:
            - name: report
              image: ghcr.io/example/report:1.4
              args: ["--since=24h"]

Make jobs idempotent: Kubernetes may run one twice on rare occasions.

Choosing

NeedUse
Stateless service, scale and roll outDeployment
Stable network identity, per-Pod diskStatefulSet
One per nodeDaemonSet
Run once to completionJob
On a scheduleCronJob

Pitfalls

  • Selectors are immutable on Deployments; changing them means recreating.
  • Without resources.requests the scheduler is blind and nodes get overcommitted.
  • Pods are killed with SIGTERM and a 30 s grace period (terminationGracePeriodSeconds). Handle SIGTERM and finish in-flight requests.
  • Using :latest makes rollbacks meaningless since you cannot tell what version is running.

Try it

  1. Apply the Deployment above (use nginx:1.27 if you lack the image). Delete a Pod and watch the ReplicaSet replace it.
  2. Run kubectl get rs, change the image tag, apply again, and compare ReplicaSets before and after.
  3. Create a Job that runs echo hello and read its logs.
