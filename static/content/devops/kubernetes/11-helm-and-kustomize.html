Helm and Kustomize

A real application is a dozen YAML files, and you need several copies of them: dev, staging, production, each slightly different. Copy-pasting YAML does not scale. Helm and Kustomize are the two standard answers: one templates, the other patches.

The problem

Staging runs 1 replica with a small database; production runs 6 with a big one; the image tag and hostname differ. If you copy the manifests, a fix in one place must be repeated everywhere and the copies drift. We need a single source plus a small, explicit set of differences.

HelmKustomize
ApproachGo templates + values; packages as versioned chartsPlain YAML + declarative patches; no templating
Built into kubectlNo (separate CLI)Yes: kubectl apply -k
Best forInstalling third-party software; distributing your app; parametrisingYour own app's per-environment variations
Extra featuresRelease tracking, hooks, rollback, dependenciesSimplicity, valid YAML at every step

Many teams use both: Helm for third-party charts (ingress, cert-manager, Prometheus), Kustomize (or Helm) for their own apps.

Helm

Concepts

  • Chart: a package: templates + default values + metadata.
  • Values: the parameters you override.
  • Release: one installed instance of a chart in a cluster. Helm tracks revisions in a Secret, so you can upgrade and roll back.
helm repo add bitnami https://charts.bitnami.com/bitnami
helm search repo redis
helm show values bitnami/redis > redis-values.yaml     # see all knobs

helm install cache bitnami/redis -n data --create-namespace -f redis-values.yaml
helm upgrade cache bitnami/redis -n data -f redis-values.yaml --set replica.replicaCount=3
helm list -A
helm history cache -n data
helm rollback cache 1 -n data
helm uninstall cache -n data

helm template cache bitnami/redis -f redis-values.yaml   # render YAML locally, no cluster
helm lint ./mychart

Chart layout

 shop/
 ├── Chart.yaml          name, version (chart), appVersion
 ├── values.yaml         defaults
 ├── values-prod.yaml    environment override (optional)
 ├── templates/
 │   ├── _helpers.tpl    reusable named templates
 │   ├── deployment.yaml
 │   ├── service.yaml
 │   ├── ingress.yaml
 │   └── NOTES.txt
 └── charts/             dependencies

Templating

# values.yaml
replicaCount: 2
image:
  repository: ghcr.io/example/shop
  tag: "2.3.1"
resources:
  requests: { cpu: 100m, memory: 128Mi }
ingress:
  enabled: false
  host: ""

# templates/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "shop.fullname" . }}
  labels:
    app.kubernetes.io/name: shop
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app.kubernetes.io/name: shop
  template:
    metadata:
      labels:
        app.kubernetes.io/name: shop
      annotations:
        checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
    spec:
      containers:
        - name: shop
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          resources:
            {{- toYaml .Values.resources | nindent 12 }}

# templates/ingress.yaml
{{- if .Values.ingress.enabled }}
apiVersion: networking.k8s.io/v1
kind: Ingress
...
{{- end }}

Override per environment: helm upgrade --install shop ./shop -f values-prod.yaml --set image.tag=$GIT_SHA. Precedence: chart defaults, then -f files in order, then --set.

Template complexity is Helm's cost

Indentation-sensitive text templating generating YAML is error-prone and hard to read. Keep templates simple, always check output with helm template, pin chart versions, and review the rendered diff (helm diff plugin) before upgrading production. Treat third-party charts as code you depend on: read what they create.

Kustomize

Kustomize keeps a base of plain, valid YAML and layers overlays that patch it. No placeholders, no template language.

 shop/
 ├── base/
 │   ├── kustomization.yaml
 │   ├── deployment.yaml
 │   └── service.yaml
 └── overlays/
     ├── staging/
     │   └── kustomization.yaml
     └── production/
         ├── kustomization.yaml
         └── replicas-patch.yaml

# base/kustomization.yaml
resources:
  - deployment.yaml
  - service.yaml
labels:
  - pairs: { app.kubernetes.io/name: shop }
    includeSelectors: true

# overlays/production/kustomization.yaml
resources:
  - ../../base
namespace: shop-prod
namePrefix: prod-
images:
  - name: ghcr.io/example/shop
    newTag: 2.3.1                 # CI updates this line
patches:
  - path: replicas-patch.yaml
configMapGenerator:
  - name: shop-config
    literals:
      - LOG_LEVEL=warn            # name gets a content hash; changes roll Pods

# overlays/production/replicas-patch.yaml  (strategic merge patch)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: shop
spec:
  replicas: 6
kubectl kustomize overlays/production      # render and inspect
kubectl diff -k overlays/production
kubectl apply -k overlays/production

Kustomize can also inline Helm charts (helmCharts:) for post-rendering patches, a handy combination.

Choosing

  • Installing someone else's software: Helm.
  • Your own app, a handful of environments, want readable diffs: Kustomize.
  • Shipping an app for external users to configure: Helm chart.
  • GitOps: both are first-class in Argo CD and Flux.

Pitfalls

  • Helm values with no schema: add values.schema.json to catch typos.
  • Secrets in values.yaml committed to git. Use external secrets instead.
  • Helm CRD handling: CRDs in crds/ are installed once and never upgraded or deleted by Helm. Plan CRD upgrades separately.
  • Kustomize patches silently do nothing if the target name or kind does not match; check the rendered output.
  • Unpinned chart versions: helm upgrade may pull breaking changes.

Try it

  1. Create a chart with helm create shop, run helm template shop ./shop, then install it on kind and change replicaCount with --set.
  2. Build the Kustomize layout above with staging (1 replica) and production (3 replicas) overlays and compare kubectl kustomize output of each.
  3. Break a Helm upgrade intentionally (bad image tag) and use helm rollback.
