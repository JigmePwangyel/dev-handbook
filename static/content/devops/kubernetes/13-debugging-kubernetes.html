Debugging Kubernetes

Things will go wrong: Pods that will not start, Services that return nothing, rollouts that hang. Debugging Kubernetes is a learnable skill built on a small toolkit and a consistent flow: read the status, read the events, read the logs, and narrow down.

The toolkit

kubectl get pods -o wide                      # status, restarts, node, IP
kubectl describe pod NAME                     # config + EVENTS at the bottom (read this first)
kubectl logs NAME [-c container] [--previous] # --previous = logs of the last crashed instance
kubectl logs -l app=shop --tail=50 --all-containers
kubectl get events --sort-by=.lastTimestamp -n NS     # what the cluster has been doing
kubectl exec -it NAME -- sh                   # shell inside
kubectl port-forward pod/NAME 8080:8080       # reach it from your laptop
kubectl debug -it NAME --image=busybox:1.36 --target=app   # ephemeral debug container
kubectl debug node/NODE -it --image=ubuntu    # host-level debugging
kubectl get pod NAME -o yaml                  # status section: conditions, lastState, exit codes
kubectl top pod / kubectl top node            # resource usage
Events are the cluster talking to you

The Events section of kubectl describe says why the scheduler could not place a Pod, why an image failed to pull, why a probe failed. Events expire after about an hour, so check early.

Pod lifecycle statuses

The STATUS column tells you which stage failed:

 Pending ─▶ ContainerCreating ─▶ Running ─▶ Succeeded / Failed
    │              │                │
    │              │                └─ CrashLoopBackOff, OOMKilled, Error
    │              └─ ImagePullBackOff, volume/secret mount errors
    └─ unschedulable (no node fits)

Pending: it was never scheduled

Run kubectl describe pod and read the FailedScheduling event:

MessageMeaning and fix
Insufficient cpu / memoryNo node has enough unreserved resources. Lower requests, add nodes, or check the autoscaler.
node(s) had untolerated taintAdd a toleration or use different nodes.
didn't match Pod's node affinity/selectorLabel mismatch; check nodeSelector and kubectl get nodes --show-labels.
unbound immediate PersistentVolumeClaimsPVC is Pending: no StorageClass, no capacity, wrong zone.
exceeded quota (on ReplicaSet events)Namespace ResourceQuota full.

ImagePullBackOff / ErrImagePull

The kubelet cannot download the image. In describe events find the real reason:

  • manifest unknown / not found: typo in the image name or tag does not exist. Try docker pull with the exact string.
  • unauthorized / pull access denied: private registry needs imagePullSecrets: 
    kubectl create secret docker-registry regcred \
  --docker-server=ghcr.io --docker-username=USER --docker-password=TOKEN
# then in the Pod spec:  imagePullSecrets: [{ name: regcred }]
  • Network or DNS issues from the node, registry rate limits (Docker Hub), architecture mismatch (arm64 image on amd64 nodes shows as exec format error instead).
  • Local clusters: image built locally but not loaded (kind load docker-image) and imagePullPolicy forcing a pull.

CrashLoopBackOff

The container starts, exits, and Kubernetes restarts it with growing delay (10 s, 20 s, up to 5 minutes). The cause is almost always in the app, not Kubernetes.

  1. kubectl logs POD --previous: the final output before the crash. Missing env var, cannot reach DB, bad config file, stack trace.
  2. kubectl describe pod: look at Last State: Terminated and its Reason and Exit Code.
Exit code / reasonLikely cause
1Application error: read logs
0 in a DeploymentProcess finished immediately (wrong command, daemonizes itself); a long-running container must stay in the foreground
126 / 127Command not executable / not found (wrong command or entrypoint)
137, OOMKilledExceeded memory limit (or SIGKILL after grace period). Raise limit or fix the leak.
139Segmentation fault
143SIGTERM: terminated normally, often by a failing liveness probe or a rollout

Liveness probe failures also look like crash loops: events show Liveness probe failed. Loosen thresholds or add a startupProbe. If the container dies too fast to inspect, override its command to sleep: kubectl debug POD -it --copy-to=debug --container=app -- sh gives you a copy to poke at.

Other common states

  • ContainerCreating forever: volume attach/mount failure, missing ConfigMap/Secret (MountVolume.SetUp failed), CNI problems (failed to create pod sandbox).
  • CreateContainerConfigError: references a ConfigMap/Secret key that does not exist.
  • Terminating forever: stuck finalizer or an unreachable node. Last resort: kubectl delete pod X --force --grace-period=0 (understand the risk for StatefulSets).
  • Evicted: node pressure (disk or memory). kubectl describe node shows conditions.
  • Running but 0/1 READY: readiness probe failing; check the probe path and port.

Service and network problems

"The Pod is Running but I cannot reach it." Work along the path:

 client ─▶ Ingress/Gateway ─▶ Service ─▶ EndpointSlice ─▶ Pod:targetPort ─▶ app
   1            2               3             4                5              6
  1. Does the app work? kubectl port-forward pod/NAME 8080:8080 and curl localhost:8080. If not, it is an app problem; also confirm it listens on 0.0.0.0.
  2. Does the Service select the Pods? kubectl get endpointslices -l kubernetes.io/service-name=NAME or kubectl get endpoints NAME. Empty means a label selector mismatch or Pods not ready.
  3. Do ports match? Service targetPort must equal the container's listening port.
  4. Does DNS work? kubectl run t --rm -it --image=busybox:1.36 -- nslookup NAME. Check CoreDNS Pods in kube-system.
  5. Can a Pod reach the Service? From a debug Pod: curl -v http://NAME.NS:PORT. If it fails but Pod IP works, suspect kube-proxy; if the Pod IP also fails, suspect NetworkPolicy or CNI.
  6. Ingress: kubectl describe ingress, check class, host, backend; look at ingress controller logs. A 503 means no endpoints; a 404 means no rule matched; a 502/504 means the backend misbehaved.

Rollouts and the control plane

  • Deployment not progressing: kubectl rollout status, then inspect the new ReplicaSet's Pods (kubectl get rs), then Pods as above.
  • Pods not being created at all: kubectl describe rs events show quota or admission webhook rejections or PodSecurity violations.
  • Node NotReady: kubectl describe node, then kubelet logs (journalctl -u kubelet) via node access or kubectl debug node.
  • kubectl get componentstatuses is deprecated; use kubectl get --raw='/readyz?verbose'.

A troubleshooting flow

 kubectl get pods
   │
   ├─ Pending ───────────▶ describe pod ▶ FailedScheduling? resources / taints / PVC / quota
   ├─ ImagePullBackOff ──▶ describe pod ▶ name/tag typo? registry auth? network?
   ├─ ContainerCreating ─▶ describe pod ▶ missing Secret/ConfigMap? volume? CNI?
   ├─ CrashLoopBackOff ──▶ logs --previous + exit code ▶ app error / OOMKilled / probe
   ├─ Running 0/1 ───────▶ readiness probe failing ▶ describe, logs, check port/path
   └─ Running 1/1 but unreachable ▶ port-forward ▶ endpoints ▶ ports ▶ DNS ▶ NetworkPolicy ▶ ingress
Habits that save hours
  • Always read the Events before guessing.
  • Change one thing at a time; reproduce with a minimal debug Pod.
  • Ship a debug image or use kubectl debug: distroless images have no shell.
  • Centralised logs and metrics (see the Observability section) make this far faster than live kubectl.
  • Tools: k9s (terminal UI), stern (multi-Pod logs), Lens, kubectl-neat.

Try it

Break things on purpose, then fix each using only kubectl:

  1. Deploy nginx:does-not-exist (ImagePullBackOff).
  2. Request cpu: 100 (Pending, Insufficient cpu).
  3. Run busybox with command: ["sh","-c","exit 1"] (CrashLoopBackOff).
  4. Create a Service whose selector has a typo and diagnose with endpoints.
  5. Reference a nonexistent Secret in envFrom (CreateContainerConfigError).
