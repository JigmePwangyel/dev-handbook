Storage: Volumes, PVs and PVCs

Container filesystems vanish when a container restarts. Anything that must survive, such as a database, uploaded files or a queue, needs a volume whose lifecycle is independent of the Pod. Kubernetes abstracts storage so your YAML does not care whether the disk is an EBS volume, a Google Persistent Disk or an NFS share.

The problem

A container's writable layer is deleted with the container. Even within a Pod, a restarted container starts clean. And since Pods can be rescheduled to another node, data on a node's local disk may not follow. We need storage that is (a) outside the container, (b) optionally outside the node, and (c) requested by developers without knowing infrastructure details.

Persistent storage: three objects

  Developer              Cluster admin / provisioner         Cloud / storage
 ┌────────────┐ binds  ┌───────────────┐ backed by  ┌───────────────┐
 │    PVC     │───────▶│      PV       │───────────▶│ EBS / PD / NFS │
 │ "20Gi, RWO"│        │ real volume   │            └───────────────┘
 └─────┬──────┘        └───────────────┘
       │ created on demand by
 ┌─────▼──────────┐
 │ StorageClass   │  "gp3", "premium-ssd": provisioner + parameters
 └────────────────┘
  • PersistentVolume (PV): a piece of storage in the cluster. A cluster-scoped resource, backed by a real disk.
  • PersistentVolumeClaim (PVC): a developer's request: "I need 20 Gi, single-writer". Namespaced. Kubernetes binds it to a matching PV.
  • StorageClass: describes a tier of storage and the provisioner that creates it. With dynamic provisioning, creating a PVC causes the provisioner (a CSI driver) to create the disk and PV automatically. Nobody pre-creates PVs by hand any more.

StorageClass

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast
  annotations:
    storageclass.kubernetes.io/is-default-class: "false"
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
  encrypted: "true"
reclaimPolicy: Delete             # or Retain
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer   # create the disk in the zone where the Pod lands

Check what exists: kubectl get storageclass. kind and minikube include a default one using local disk.

PVC and using it in a Pod

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: uploads
spec:
  accessModes: ["ReadWriteOnce"]
  storageClassName: fast
  resources:
    requests:
      storage: 20Gi
---
apiVersion: v1
kind: Pod
metadata: { name: uploader }
spec:
  containers:
    - name: app
      image: nginx:1.27
      volumeMounts:
        - { name: data, mountPath: /usr/share/nginx/uploads }
  volumes:
    - name: data
      persistentVolumeClaim: { claimName: uploads }

Access modes

ModeMeaningTypical backing
ReadWriteOnce (RWO)One node mounts read-writeBlock disks (EBS, PD)
ReadWriteOncePod (RWOP)Exactly one PodCSI drivers supporting it
ReadOnlyMany (ROX)Many nodes read-onlyNFS, some file stores
ReadWriteMany (RWX)Many nodes read-writeEFS, Filestore, CephFS, NFS

Block disks are RWO and zone-bound: a Pod using an EBS volume in us-east-1a cannot start in 1b. This is why WaitForFirstConsumer matters, and why Deployments with RWO volumes and several replicas on different nodes fail.

Reclaim policy and data safety

  • Delete: deleting the PVC deletes the PV and the cloud disk. Convenient, dangerous for important data.
  • Retain: the PV and disk remain after the PVC is deleted for manual recovery. Use for precious data.
PVCs are not backups

A volume is one copy of data on one disk. Use VolumeSnapshots (CSI) and tools like Velero for backups, and database-level backups for databases. Test restores.

StatefulSet volumes

With a Deployment all replicas share one PVC (only works for RWX). A StatefulSet's volumeClaimTemplates instead creates a PVC per replica (data-db-0, data-db-1), and when Pod db-1 is rescheduled it reattaches to data-db-1. Scaling the StatefulSet down does not delete PVCs by default (configurable via persistentVolumeClaimRetentionPolicy), protecting data but leaving orphaned disks to clean up.

Expanding and snapshotting

# expand (StorageClass needs allowVolumeExpansion: true); you can only grow
kubectl patch pvc uploads -p '{"spec":{"resources":{"requests":{"storage":"50Gi"}}}}'

apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata: { name: uploads-snap }
spec:
  volumeSnapshotClassName: csi-snap
  source: { persistentVolumeClaimName: uploads }

Pitfalls

  • PVC stuck Pending: no default StorageClass, wrong class name, no capacity, or a CSI driver not installed. kubectl describe pvc tells you.
  • Pod stuck ContainerCreating with a "Multi-Attach error": an RWO volume is still attached to another node (old Pod terminating).
  • Running databases on network disks has latency; for high performance consider local SSDs with replication handled by the database.
  • Do not use hostPath for app data: it ties the Pod to one node and is a container-escape risk.

Try it

  1. On your kind cluster create a PVC and a Pod writing a file into it. Delete the Pod, recreate it, and confirm the file persists.
  2. Run kubectl get pv,pvc,storageclass and trace the binding.
  3. Create a 2-replica StatefulSet with volumeClaimTemplates and observe the per-Pod PVCs.
