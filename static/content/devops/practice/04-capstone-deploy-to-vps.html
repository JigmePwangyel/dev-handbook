Capstone: Deploy to a VPS

Stage 3: put Notely on a real server behind nginx with a Let's Encrypt certificate, and make the pipeline update it automatically with minimal downtime. This is the same flow as a "real" deployment, just without the orchestrator.

Target layout on the server

 /opt/notely/
 ├── compose.yaml        # production compose (pulls images, no build)
 ├── .env                # secrets + IMAGE_TAG   (chmod 600, not in git)
 └── nginx/notely.conf   # (or nginx runs on the host; see below)

 Internet :443 ─▶ nginx (host) ─▶ 127.0.0.1:3000 ─▶ api container ─▶ db container (internal network only)

Design choice: nginx on the host (installed by apt) handles TLS with certbot, while the app and database run in Compose. It keeps certificates simple and lets nginx survive app redeploys. The alternative is to run nginx or Caddy as another container; Caddy gives automatic HTTPS with almost zero config.

1. Prepare the server

# as root on a fresh Ubuntu 24.04 VPS
adduser --disabled-password --gecos "" deploy
mkdir -p /home/deploy/.ssh
# paste YOUR public key and a separate CI deploy key's public key:
cat >> /home/deploy/.ssh/authorized_keys
chown -R deploy:deploy /home/deploy/.ssh && chmod 700 /home/deploy/.ssh && chmod 600 /home/deploy/.ssh/authorized_keys

# harden SSH: no root, no passwords (see hardening lesson), then:
systemctl reload ssh

# firewall
ufw default deny incoming; ufw allow OpenSSH; ufw allow 80,443/tcp; ufw enable

# install docker (official convenience script or apt repo) and give deploy access
curl -fsSL https://get.docker.com | sh
usermod -aG docker deploy      # note: docker group is root-equivalent
apt install -y nginx certbot python3-certbot-nginx
mkdir -p /opt/notely && chown deploy:deploy /opt/notely
Docker group = root

Anyone who can run docker can mount the host filesystem. That is acceptable for a dedicated deploy user whose key lives only in CI, but restrict that key (command= and restrict options in authorized_keys) if you want to go further.

2. Production compose file

# /opt/notely/compose.yaml
services:
  db:
    image: postgres:17-alpine
    restart: unless-stopped
    env_file: .env                      # POSTGRES_USER / POSTGRES_PASSWORD / POSTGRES_DB
    volumes:
      - pgdata:/var/lib/postgresql/data
    networks: [internal]                # no published ports at all
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
      interval: 10s
      retries: 6

  api:
    image: ghcr.io/OWNER/notely:${IMAGE_TAG}
    restart: unless-stopped
    env_file: .env
    environment:
      DATABASE_URL: postgres://${POSTGRES_USER}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB}
    ports:
      - "127.0.0.1:3000:3000"           # only nginx on the host can reach it
    depends_on:
      db: { condition: service_healthy }
    networks: [internal]

networks:
  internal:
volumes:
  pgdata:
# /opt/notely/.env   (chmod 600)
POSTGRES_USER=notely
POSTGRES_PASSWORD=<long random value from: openssl rand -base64 32>
POSTGRES_DB=notely
IMAGE_TAG=sha-1a2b3c4

If the GHCR package is private, log in once on the server with a read-only classic token (read:packages): echo $TOKEN | docker login ghcr.io -u USERNAME --password-stdin. Making the package public avoids this for a demo.

3. nginx and TLS

Point DNS first: an A record for notely.example.com to the VPS IP (check with dig +short notely.example.com). Then:

# /etc/nginx/sites-available/notely
server {
    listen 80;
    server_name notely.example.com;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 30s;
    }
}
ln -s /etc/nginx/sites-available/notely /etc/nginx/sites-enabled/
nginx -t && systemctl reload nginx
certbot --nginx -d notely.example.com --agree-tos -m you@example.com --redirect
systemctl list-timers | grep certbot     # auto-renewal is installed as a timer
certbot renew --dry-run
curl -I https://notely.example.com/healthz

Certbot edits the config to add the 443 listener and the HTTP-to-HTTPS redirect. Block /metrics from the public internet (location = /metrics { deny all; }) and let Prometheus scrape it internally.

4. First deploy by hand

cd /opt/notely
docker compose pull
docker compose up -d
docker compose run --rm api node src/migrate.js   # or apply migrations/001_init.sql via psql
docker compose ps
curl -s localhost:3000/healthz

Doing it manually once teaches you what the pipeline must automate.

5. Automate: a deploy job in GitHub Actions

Create a dedicated key pair (ssh-keygen -t ed25519 -f deploy_key -N ""), put the public half in the server's authorized_keys, and store the private half as a repo secret DEPLOY_SSH_KEY, plus DEPLOY_HOST. Capture the host key fingerprint (ssh-keyscan -t ed25519 host) as DEPLOY_KNOWN_HOSTS so you verify the server rather than trust blindly.

  deploy:
    needs: image
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-24.04
    environment: production          # add required reviewers for manual approval
    steps:
      - name: Configure SSH
        run: |
          install -m 700 -d ~/.ssh
          echo "${{ secrets.DEPLOY_SSH_KEY }}" > ~/.ssh/id_ed25519
          chmod 600 ~/.ssh/id_ed25519
          echo "${{ secrets.DEPLOY_KNOWN_HOSTS }}" > ~/.ssh/known_hosts
      - name: Deploy
        env:
          TAG: sha-${{ github.sha }}
        run: |
          SHORT=$(echo "${GITHUB_SHA}" | cut -c1-7)
          ssh deploy@${{ secrets.DEPLOY_HOST }} "SHORT=sha-${SHORT} bash -s" << 'EOF'
            set -euo pipefail
            cd /opt/notely
            sed -i "s/^IMAGE_TAG=.*/IMAGE_TAG=${SHORT}/" .env
            docker compose pull api
            docker compose run --rm api node src/migrate.js
            docker compose up -d --no-deps api
            for i in $(seq 1 30); do
              curl -fsS localhost:3000/healthz && exit 0
              sleep 2
            done
            echo "health check failed" >&2; exit 1
          EOF
      - name: Smoke test
        run: curl -fsS https://notely.example.com/healthz

The docker/metadata type=sha,format=short tag is the first 7 characters of the commit SHA prefixed with sha-, which is what the script reconstructs.

Zero-downtime-ish updates

docker compose up -d --no-deps api stops the old container and starts the new one, which causes a few seconds of 502 errors. Options, from simple to robust:

ApproachHowDowntime
Plain recreatecompose up -dA few seconds
nginx retryproxy_next_upstream error timeout http_502; plus a short retry window masks the blipNear zero for GETs
Blue-green with two compose projectsRun api-blue on :3001 and api-green on :3002; start the new one, health check, switch the nginx upstream port, nginx -s reload, stop the old oneZero; instant rollback
Rolling via Swarm / Kubernetesdocker service update with --update-order start-firstZero
Tools like KamalHealthcheck-gated container swap behind kamal-proxyZero
# blue-green sketch (run on the server)
CURRENT=$(cat /opt/notely/active_port)          # 3001 or 3002
NEXT=$([ "$CURRENT" = 3001 ] && echo 3002 || echo 3001)
APP_PORT=$NEXT docker compose -p notely-$NEXT up -d api
until curl -fs localhost:$NEXT/healthz; do sleep 1; done
sed -i "s/127.0.0.1:$CURRENT/127.0.0.1:$NEXT/" /etc/nginx/sites-enabled/notely
nginx -t && nginx -s reload                      # reload is graceful: no dropped connections
docker compose -p notely-$CURRENT stop api
echo $NEXT > /opt/notely/active_port

Remember migrations must be backward compatible so both versions can run against one database during the switch.

Rollback

ssh deploy@host
cd /opt/notely
sed -i 's/^IMAGE_TAG=.*/IMAGE_TAG=sha-PREVIOUS/' .env
docker compose up -d --no-deps api

Because every image is immutable and tagged by SHA, rollback is a one-line change. Keep the last N tags (docker image prune carefully) and record each deployed tag in a log file or a GitHub deployment record.

Verify like an operator

  • docker compose logs --tail 50 api and journalctl -u nginx for errors.
  • ss -tlnp: only 22, 80, 443 should listen on public interfaces. Verify 5432 is not exposed: nmap -p 5432 your.ip from your laptop.
  • docker stats --no-stream for resource use; add swap or a bigger plan if memory is tight.
  • Reboot the VPS and confirm everything comes back (restart: unless-stopped plus docker enabled at boot).
Back up from day one

Add a cron job: docker compose exec -T db pg_dump -U notely -Fc notely | age -r YOUR_PUBKEY | rclone rcat remote:notely-backups/$(date +%F).dump.age, then restore it into a scratch container once to prove it works.

Try it

  1. Provision the VPS, perform the hardening steps, point DNS and get a valid certificate. Check it with curl -vI.
  2. Deploy manually once, then add the deploy job and push a trivial change; watch it roll out and verify the SHA in the running container: docker compose images api.
  3. Push a commit that fails the health check (for example, a bad DATABASE_URL). Does the pipeline fail and leave the old version serving? If not, improve the script.
  4. Practise a rollback and time it.
