Capstone: Containerize the App

Stage 1: package Notely and its database so that docker compose up gives any teammate (or any server) an identical environment in one command. This is the "build once, run anywhere" step everything else depends on.

Goals

  • A small, secure, fast-building production image.
  • A Compose file for local development with Postgres, migrations and live reload.
  • Configuration through environment variables only.

The Dockerfile (multi-stage)

A multi-stage build separates build-time tooling from the runtime image, shrinking size and attack surface. Order instructions from least to most frequently changing so layer caching works.

# syntax=docker/dockerfile:1
ARG NODE_VERSION=22

# ---- deps: install production dependencies only ----
FROM node:${NODE_VERSION}-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci --omit=dev

# ---- runtime ----
FROM node:${NODE_VERSION}-alpine AS runtime
ENV NODE_ENV=production
WORKDIR /app
# non-root user (the node image ships with one called "node")
COPY --from=deps --chown=node:node /app/node_modules ./node_modules
COPY --chown=node:node package.json ./
COPY --chown=node:node src ./src
COPY --chown=node:node migrations ./migrations
USER node
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s \
  CMD wget -qO- http://127.0.0.1:3000/healthz || exit 1
CMD ["node", "src/server.js"]

Key decisions explained:

  • Copy package*.json before the source: dependency installation is cached until the lockfile changes, so a code edit rebuilds in seconds.
  • npm ci gives reproducible installs from the lockfile.
  • Exec-form CMD ["node", ...] makes node PID 1 so it receives SIGTERM and shuts down gracefully (shell form would wrap it in sh -c and swallow the signal). Add --init or tini if your app spawns children.
  • Non-root user: a compromised app does not own the container.
  • Pin by digest in real production (node:22-alpine@sha256:...) and let Renovate bump it.

Compose for local development

# compose.yaml
services:
  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_USER: notely
      POSTGRES_PASSWORD: devpassword      # dev only!
      POSTGRES_DB: notely
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./migrations:/docker-entrypoint-initdb.d:ro   # runs *.sql on FIRST init only
    ports:
      - "127.0.0.1:5432:5432"             # bound to localhost only
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U notely -d notely"]
      interval: 5s
      timeout: 3s
      retries: 10

  api:
    build: .
    environment:
      DATABASE_URL: postgres://notely:devpassword@db:5432/notely
      PORT: 3000
    ports:
      - "3000:3000"
    depends_on:
      db:
        condition: service_healthy        # wait until Postgres accepts connections
    restart: unless-stopped

volumes:
  pgdata:
docker compose up --build -d
docker compose ps
docker compose logs -f api
curl -s localhost:3000/healthz
docker compose down            # keeps the volume (data survives)
docker compose down -v         # also deletes the volume (fresh start)
Pitfalls you will probably hit

1) depends_on without condition: service_healthy only waits for the container to start, not for Postgres to be ready. 2) Inside Compose, the hostname is the service name (db), not localhost. 3) Scripts in docker-entrypoint-initdb.d run only when the data directory is empty; later schema changes need a real migration tool. 4) Without a named volume the database vanishes with the container.

Development override with live reload

Compose automatically merges compose.override.yaml on top of compose.yaml, so developers get a hot-reload workflow while production uses the plain file.

# compose.override.yaml
services:
  api:
    build:
      target: deps          # dev stage with all deps; add a "dev" stage if you need devDependencies
    command: node --watch src/server.js
    volumes:
      - ./src:/app/src      # bind mount: edit on host, see changes in container
    environment:
      LOG_LEVEL: debug

Compose 2.22+ also offers docker compose watch with a develop.watch section that syncs files or rebuilds on change without bind-mount quirks.

Proper migrations

The initdb trick is fine on day one; replace it soon with a migration runner executed as a one-off container so schema changes are versioned and repeatable (twelve-factor XII):

  migrate:
    build: .
    command: ["node", "src/migrate.js"]     # or use flyway/dbmate/golang-migrate images
    environment:
      DATABASE_URL: postgres://notely:devpassword@db:5432/notely
    depends_on:
      db: { condition: service_healthy }
    profiles: ["tools"]

# run on demand
docker compose run --rm migrate

Trade-offs

Alpine uses musl libc, which occasionally breaks native Node modules or changes DNS behaviour; -slim (Debian) is the safer default if you hit odd issues. Distroless images are tiny and have no shell, which is excellent for security and slightly annoying for debugging (use kubectl debug or an ephemeral debug container).

Try it

  1. Write the Dockerfile, .dockerignore and compose.yaml, then run docker compose up --build and create a note with curl.
  2. Run docker compose down then up again and confirm the note persists. Then use down -v and confirm it is gone.
  3. Change one line of source and rebuild: observe cached layers in the output. Then change package.json and watch the install layer re-run.
  4. Scan with trivy image notely:dev and reduce the highest-severity finding by updating the base image.
