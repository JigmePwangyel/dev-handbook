Pipeline Best Practices and Anti-Patterns

Building a first pipeline is easy. Keeping it fast, trusted and maintainable for years, with dozens of engineers and hundreds of repos, is the real craft. This lesson collects the practices that separate pipelines people love from pipelines people route around.

Why pipelines decay

A pipeline is a product with users: your developers. Like any product it accumulates debt. Tests get slower one at a time. A flaky test is "retried" until it is normal. Someone copies a workflow into 40 repos and the copies drift. Nobody owns it. Eventually engineers merge without waiting, or bypass the system, and you have lost the safety you built it for. The principles below are how you prevent that.

Best practices

1. Treat the pipeline as code

  • Definitions in Git, reviewed via PR, tested on branches. No click-configured jobs.
  • Keep logic in scripts you can run locally (make ci, ./scripts/test.sh, npm run); keep the CI file a thin orchestrator. Developers should reproduce a failure on their laptop without pushing 12 "fix ci" commits.
  • Lint your pipeline code (actionlint, GitLab CI Lint, hadolint, shellcheck).
  • Share via reusable workflows, templates, components or shared libraries; version and pin them.

2. Keep it fast

TechniqueTypical win
Run cheap checks first, fail fastSeconds to failure instead of minutes
Parallelise independent jobs; shard long suitesTime = longest branch, not the sum
Cache dependencies and Docker layers (order Dockerfile: dependency manifests before source)Minutes saved per run
Run only affected tests/builds (path filters, Nx/Turborepo/Bazel)Large in monorepos

Bigger or faster runners for the hot pathCheap compared to waiting engineers
Move slow tests off the PR path (post-merge, nightly)Fast PR feedback, still covered

Set an explicit budget, for example "PR feedback under 10 minutes, p90", measure against it, and treat regressions like bugs.

3. Build once, promote the artifact

One immutable, uniquely identified artifact (image digest) flows through every environment. Environment differences are injected configuration. Deploy by SHA or digest, never latest.

4. Make runs reproducible

  • Pin tool versions (.nvmrc, .tool-versions, base image digests), use lockfiles and npm ci.
  • Run in containers or clean ephemeral runners; no state carried over between runs.
  • Avoid depending on external services you do not control (flaky mirrors); use proxies/caches for registries.

5. Fail loudly and clearly

  • set -euo pipefail in shell steps so errors stop the job.
  • Set timeout-minutes everywhere.
  • Upload logs, test reports and screenshots/videos as artifacts; surface results in the PR (annotations, JUnit summaries).
  • Notify the owner, not a firehose channel. Alert fatigue kills attention.

6. Own it

Assign owners (a platform or developer-experience team), define SLOs for the pipeline itself (availability, queue time, p90 duration), and review them regularly. Keep a changelog of pipeline changes.

Anti-pattern: flaky tests

A flaky test passes and fails on the same code. It is the most corrosive pipeline problem because it destroys trust: when red may mean nothing, people stop reading red.

Common causes: timing and race conditions (sleep(2)), shared state or order dependence, reliance on wall-clock time or timezone, unseeded randomness, un-awaited async work, port collisions, network calls to real third parties, resource contention on shared runners, test data left by previous tests.

What to do:

  1. Measure it. Track per-test failure-then-pass-on-retry rates (most CI vendors and tools like BuildPulse or Datadog CI Visibility report this).
  2. Quarantine fast. Move a flaky test to a non-blocking job and file a ticket with an owner and a deadline. A quarantined test with no owner is a deleted test.
  3. Fix the cause, not the symptom: wait on conditions (poll for readiness) rather than fixed sleeps; inject a fake clock; isolate data per test; mock third parties at the network edge.
  4. Retries are a bandage. A limited retry (once) for E2E tests can be pragmatic, but report retried-then-passed tests as flaky, and never blanket-retry whole pipelines.
  5. Reproduce with repetition: run the test 100 times in a loop or with --repeat-each; run it under CPU constraints.
The cost of "just re-run it"

If 5% of runs fail spuriously and a PR needs 6 checks to pass, a large fraction of PRs fail at least once for no reason. Multiply by developers and wait times: flakiness silently taxes lead time, and teaches people that red is normal.

Anti-pattern: slow pipelines

  • Symptoms: PRs sit for 40 minutes; developers batch commits; "I'll merge while it's running".
  • Diagnose: find the critical path; use the platform's timing view; identify the top three slow steps (usually dependency install, test suites, Docker builds).
  • Fix: see the table above. Also remove duplicate work (building the same thing in three jobs), trim image sizes, use multi-stage Docker builds with layer caching, and split the monolith pipeline into per-package pipelines.

Rollbacks: design them before you need them

Every deploy must have a tested way back. Options, from fastest to slowest:

  1. Feature flag off (seconds): for risky features, the quickest remedy and needs no deploy.
  2. Traffic shift back (blue-green swap, canary abort): seconds to a minute.
  3. Redeploy the previous artifact (kubectl rollout undo deployment/shop, or run the deploy workflow with the previous digest): minutes. This is why you keep immutable, versioned artifacts and expose a manual workflow_dispatch with a "version" input.
  4. Revert the commit and let the pipeline redeploy (git revert): minutes to tens of minutes; leaves a clear history; the default for GitOps.
  5. Roll forward with a hotfix: sometimes the only option after a data migration.

Databases are the hard part. Code rolls back easily; schema and data do not. Use the expand/contract pattern: first deploy a backward-compatible schema (add nullable column), then deploy code that uses it, and only later remove the old column. Never ship a destructive migration in the same release as the code that stops needing it.

# manual rollback workflow (GitHub Actions)
on:
  workflow_dispatch:
    inputs:
      image_digest:
        description: "Previously released image digest to redeploy"
        required: true

# Kubernetes quick rollback
kubectl rollout undo deployment/shop
kubectl rollout status deployment/shop --timeout=120s

Rehearse rollbacks. A rollback procedure that has never been run is a hope, not a procedure.

Monorepos

A monorepo keeps many projects in one repository. It makes atomic cross-project changes and shared tooling easy, but naive CI (run everything on every change) does not scale.

  • Affected-only builds: compute which packages changed and which depend on them (Nx affected, Turborepo --filter=...[origin/main], Bazel, Pants, Gradle composite builds).
  • Remote build cache: share task outputs across developers and CI so unchanged work is never redone.
  • Path filters per workflow: on.push.paths in GitHub, rules:changes in GitLab. Beware: required checks that are skipped by path filters can block merges; use the "gate job" pattern.
  • Per-service pipelines generated dynamically (GitLab child pipelines, GitHub reusable workflows with a matrix computed by a first job).
  • Code owners and permissions per directory.
  • Merge queues to keep a busy main green.

Polyrepo trades the opposite way: simple, independent pipelines, but cross-repo changes and version coordination are painful. Pick based on team coupling, not fashion.

Measure the pipeline and the delivery

You cannot improve what you do not measure. Track two families of metrics:

Pipeline healthDelivery performance (DORA)
Duration p50 / p90 (PR and main)Deployment frequency
Queue/wait time for runnersLead time for changes
Success rate on mainChange failure rate
Flaky-test rate; retries per runTime to restore service
Cost per run / per monthRework rate
Time red main stays red (MTTR of the build)Reliability vs SLOs

Dashboards: your CI vendor's analytics, Four Keys, Grafana fed by CI webhooks, DX/Swarmia/LinearB-style tools. Review monthly, pick one metric to improve, and avoid using these as individual performance scores (Goodhart again).

Cost management

  • Cancel redundant runs; set timeouts; limit matrix size to what is meaningful.
  • Avoid expensive runners (macOS, large) unless needed; prefer Linux and ARM where possible.
  • Autoscale self-hosted runners to zero; use spot/preemptible instances for stateless build agents.
  • Set retention on artifacts, caches and logs.
  • Compare against the cost of developer waiting time: 50 engineers losing 10 minutes per PR per day dwarfs most CI bills.

Evolving the pipeline

  1. Start simple: lint + test + build on PRs.
  2. Add the artifact and deploy to staging on main.
  3. Add security scanning and branch protection gates.
  4. Add post-deploy verification and approval-gated production.
  5. Add progressive delivery and automated rollback; consider continuous deployment.
  6. Productise: templates, golden paths, metrics, ownership.
Principle recap

Small batches. Fast feedback. Build once. Same pipeline for everyone. Trust the red. Make rollback boring. Measure and improve continuously.

A review checklist

  • Is PR feedback under ~10 minutes at p90?
  • Does main stay green, and is a red main fixed within the hour?
  • Is there exactly one build per commit, promoted unchanged to prod?
  • Can any engineer reproduce CI locally with one command?
  • Are secrets short-lived, scoped, and absent from fork PRs?
  • Are actions/images/templates pinned and updated by automation?
  • Do we know our flaky tests, and does each have an owner?
  • Have we rolled back in the last quarter, on purpose, to practice?
  • Do we track DORA metrics and act on them?

Try it

  1. Score your project against the review checklist. Pick the two weakest items and write a concrete fix for each.
  2. Export the last 50 pipeline runs (via gh run list --json or the GitLab API) and compute success rate and p90 duration.
  3. Find a test that failed and then passed on re-run in the last month. Reproduce it by running it 100 times and identify the cause.
  4. Practice a rollback in staging: deploy a deliberately bad version, then restore the previous digest using only your pipeline. Time it.
