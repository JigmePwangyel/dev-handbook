Continuous Delivery vs Continuous Deployment

"CD" means two different things, and mixing them up causes real confusion. Both extend CI by automating the path to production. They differ in one decision: does a human press the final button?

Why CD exists

CI leaves you with a tested artifact on main. Without CD, getting that artifact to users is a separate, manual, error-prone project: a ticket to ops, a deployment window, a wiki checklist. That final step is where a lot of lead time and risk hide. CD closes the gap so the path from "merged" to "running in production" is automated, repeatable and boring.

The only difference

In delivery, the pipeline is capable of deploying at any time and a person decides when. In deployment, the pipeline always deploys. Delivery is a capability; deployment is a policy. Most organisations should first achieve delivery, then decide whether deployment fits their risk profile.

Deploy is not release

A powerful mental split: deployment is putting code on production servers. Release is exposing a feature to users. With feature flags, you deploy dark code continuously, then release by flipping a flag, for 1% of users, then 10%, then everyone. Deploys become technical, frequent and low-drama; releases become a business decision, reversible in seconds without a redeploy.

// the code ships to production but is invisible until the flag is on
if (flags.isEnabled('new-checkout', { userId })) {
  return renderNewCheckout();
}
return renderOldCheckout();

Remember to delete flags after rollout; stale flags are tech debt and a source of untested combinations.

Changes move through a series of environments, each more production-like and more costly to break.

Rules of promotion

  • Promote the artifact, not the code. The image shop:3f9a1c2 that passed staging is the one deployed to prod. No rebuild.
  • Configuration differs, binaries don't. Environment-specific values come from environment config and a secrets manager.
  • Keep staging as close to prod as is affordable (same Kubernetes version, same DB engine and version, same topology in miniature). Drift is how "it passed staging" lies.
  • Gate each hop with automated checks (tests, health checks, security scans) and, where needed, approvals.

Approvals and gates

Approvals are controls, and they have a cost. Use them intentionally.

  • Manual approval (GitHub environment "required reviewers", GitLab when: manual, Jenkins input): good for regulated industries, high-blast-radius changes, or until trust in tests is earned.
  • Automated gates: tests, vulnerability scan thresholds, SLO checks ("error budget remaining?"), time windows (no deploys Friday afternoon), change-freeze calendars.
  • Separation of duties: the author of a change cannot be the sole approver of its deployment; the platform enforces this, not a policy document.
Approval theater

A manager clicking "Approve" without looking at anything adds delay but no safety. Real safety comes from tests, progressive rollout and fast rollback. If you must keep approvals for compliance, make the information they need visible (diff, test results, risk) and keep the approval fast, ideally minutes.

Progressive delivery: making deployment safe

Continuous deployment is only responsible if blast radius is small and rollback is automatic. Combine CD with:

  • Rolling update: replace instances gradually, health-checking each batch.
  • Blue-green: run the new version beside the old, switch traffic at once, switch back instantly if bad.
  • Canary: send 1-5% of traffic to the new version, compare error rate and latency against the baseline, then expand (tools: Argo Rollouts, Flagger, service mesh, load balancer weights).
  • Automated rollback triggered by SLO/metric regression.
  • Database migrations that are backward compatible (expand then contract), so old and new code can both run during rollout and rollback is possible.

These strategies are covered in depth in the Deploying section; the key point here is that they are what lets "every merge goes to prod" be a safe sentence.

Release trains

A release train ships on a fixed schedule (say, every two weeks or every Tuesday) with whatever is ready; if your feature misses the train, it takes the next one. It is common for mobile apps (app store review), on-prem software and big organisations.

  • Pros: predictable cadence for marketing, support and customers; amortises release overhead; works when the deploy channel is slow (app stores).
  • Cons: batching increases risk and lead time; features wait for the train; pressure to rush onto it.
  • Tip: even on a train, keep main always releasable and use feature flags; the train just selects a commit to cut, it should not require stabilisation heroics.

Pitfalls

  • "We do CD" but production deploys still need three tickets. That is automation of one stage, not delivery.
  • Rebuilding per environment. Breaks traceability.
  • Shared mutable staging that ten teams fight over. Prefer ephemeral environments.
  • Skipping observability. You cannot deploy continuously if you cannot tell within minutes whether the deploy hurt.
  • Irreversible changes (destructive migrations) bundled into a routine deploy.
  • Deploy windows by fear. If "never on Fridays" is a rule, your rollback or monitoring is not trusted. Fix that, don't schedule around it.

Try it

  1. Draw your project's path from merge to production. Mark every manual step and every wait. These are your CD backlog.
  2. Decide: delivery or deployment? List what would need to be true (tests, flags, monitoring, rollback) to move one step toward deployment.
  3. In GitHub, create an environment named production with a required reviewer and reference it from a job; observe the pause for approval (you will build this in the GitHub Actions lesson).
