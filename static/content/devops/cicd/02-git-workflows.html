Git Workflows: Branching, Reviews and Releases

CI/CD is only as good as the workflow that feeds it. How your team branches, reviews, merges and tags code determines how often you integrate, how risky releases are, and how easily you can trace what is running in production.

Why a workflow at all?

Git gives you cheap branches and no rules. Without an agreed workflow, teams drift into the worst of all worlds: long-lived personal branches, unreviewed pushes to main, "which branch is production?" confusion, and releases nobody can reproduce. A workflow is a small set of conventions that answers: where does new work happen, how does it get reviewed, how does it reach production, and how do we fix production quickly?

The three models you will meet

1. Trunk-based development

Everybody integrates into a single branch (main, the "trunk") at least once a day. Branches, if used at all, live hours to a couple of days. Incomplete work is hidden behind feature flags so unfinished code can be merged and even deployed safely.

 main  ──●──●──●──●──●──●──●──●──●──▶   (always releasable)
          \/  \/    \/
          short-lived branches (< 1-2 days) / small PRs
 releases: tag a commit on main (v1.8.0), or cut a release branch only when needed

Pros: minimal integration pain, fastest feedback, simplest model, best DORA outcomes. Cons: needs strong automated tests, feature flags, and team discipline. It is the model CI was designed around, and the one the DORA research most strongly associates with high performance.

2. GitHub Flow

A lightweight variant: main is always deployable; every change is a short feature branch plus a pull request; merge after review and green checks; deploy from main (often immediately).

 main     ──●────────────●────────────●──▶
            \           /\           /
 feature     ●──●──●───●  ●──●──●───●     (PR, review, CI, merge)

This is trunk-based development with a pull request gate. For most web teams it is the right default.

3. GitFlow

Introduced by Vincent Driessen in 2010. It uses several long-lived branches: main (production), develop (integration), plus feature/*, release/* and hotfix/*.

 main     ──●───────────────────●────────●──▶  (tags v1.0, v1.1)
             \                  / \      /
 release      \        ●──●──●/   \    /
               \      /           \  /
 develop  ──●───●──●──●──●──●──●───●──●──▶
              \  /  \  /
 feature       ●●    ●●
 hotfix                       ●──●  (from main, merged to main AND develop)

Pros: explicit release stabilization; fits software that ships in numbered versions and supports several versions at once (desktop apps, firmware, libraries with LTS lines). Cons: long-lived branches recreate integration hell; double merges (to main and develop); slow flow; poor fit for continuous deployment. Even its author later added a note recommending simpler flows for web apps that deploy continuously.

Recommendation

If you deploy a service you control, use GitHub Flow or trunk-based development. Reach for GitFlow-style release branches only when you truly must maintain several released versions in parallel.

Pull requests and code review

A pull request (GitHub, Bitbucket) or merge request (GitLab) is where CI and humans meet. It bundles the diff, the discussion and the automated checks in one place.

What a good PR looks like

  • Small. Aim for under ~400 lines changed. Review quality collapses on big diffs ("10 lines = 10 comments; 500 lines = LGTM").
  • One purpose. A bug fix and a refactor are two PRs.
  • Described. Why the change, how it was tested, screenshots, links to the issue, rollout/rollback notes.
  • Green before review. Reviewers should not spend time on something a linter or test already rejects.

What reviewers should do

  • Check design, correctness, edge cases, security, and tests. Leave style to the formatter and linter.
  • Review within hours, not days; slow review is a hidden lead-time killer. Many teams set a norm like "first response within one working day".
  • Distinguish blocking comments from suggestions ("nit:").

Branch protection: enforcing the rules

A convention nobody enforces will be broken at 6 p.m. on a Friday. Branch protection (GitHub "rulesets" / protected branches, GitLab protected branches) makes the rules mechanical. For main, a sensible baseline:

  • Require a pull request; no direct pushes, including for admins.
  • Require at least 1 approving review (2 for sensitive repos); dismiss stale approvals when new commits land.
  • Require status checks to pass (your CI jobs by name) and require the branch to be up to date before merging.
  • Require signed commits or linear history if your policy demands it.
  • Use a CODEOWNERS file so changes to certain paths auto-request the owning team.
  • Block force-pushes and branch deletion.
# .github/CODEOWNERS
*                    @acme/backend
/infra/              @acme/platform
/.github/workflows/  @acme/platform   # pipeline changes need platform review
/docs/               @acme/docs
Pipeline changes are code changes

Anyone who can change the workflow file can change what runs with your secrets. Put workflow files under CODEOWNERS and require review for them.

Commits: conventional commits

The Conventional Commits specification gives commit messages a machine-readable shape:

<type>(<optional scope>): <description>

[optional body]

[optional footer(s)]
TypeMeaningVersion bump
featNew featureMINOR
fixBug fixPATCH
feat! or footer BREAKING CHANGE:Incompatible API changeMAJOR
docs, chore, refactor, test, ci, perf, buildNon-user-facingnone (usually)
feat(cart): allow applying multiple discount codes
fix(auth): refresh token before expiry to avoid 401 loop
feat(api)!: remove deprecated /v1/orders endpoint

BREAKING CHANGE: clients must migrate to /v2/orders.

Why bother? Tools such as semantic-release, release-please and git-cliff read these messages to compute the next version and generate a changelog automatically, so releasing becomes a merge instead of a ceremony. A commit-lint check in CI (commitlint) enforces the format. With squash merging, you only need to enforce the PR title.

Semantic versioning

SemVer (MAJOR.MINOR.PATCH, e.g. 2.14.3) is a contract with consumers:

  • MAJOR: incompatible API changes.
  • MINOR: backward-compatible new functionality.
  • PATCH: backward-compatible bug fixes.
  • Pre-release and build metadata: 2.0.0-rc.1, 1.4.2+build.567.

SemVer is essential for libraries. For continuously deployed services, users do not care about version numbers, so many teams identify releases by commit SHA or date-based tags (2026.10.05-3, CalVer). Pick one scheme and apply it consistently to artifacts.

Tags and releases

A tag is a permanent name for a commit. Use annotated tags for releases; they store author, date and message.

# create and push an annotated tag
git tag -a v1.8.0 -m "Release 1.8.0"
git push origin v1.8.0

# list, inspect, check out a release
git tag --list 'v1.*'
git show v1.8.0
git switch --detach v1.8.0

# what changed between releases?
git log --oneline v1.7.0..v1.8.0

A release on GitHub/GitLab is a tag plus release notes and attached assets (binaries, checksums). The common automation pattern: pushing a tag v* triggers a pipeline that builds, tests, publishes the artifacts (npm package, Docker image tagged 1.8.0) and creates the release page.

Release from a tag, deploy from a SHA

Tag the image with both the commit SHA (immutable, always unique) and the semantic version. Never deploy latest; you cannot tell what it contains or roll back to it.

Hotfixes and rollbacks

  • Trunk/GitHub Flow: a hotfix is just a normal small PR through the fast pipeline. Often, git revert <sha> of the bad PR is the fastest fix and goes through the same pipeline.
  • Release branches: branch from the release tag, fix, tag v1.8.1, then merge or cherry-pick the fix back to main so it is not lost.
  • Prefer git revert over rewriting history on shared branches. Never force-push main.

Pitfalls

  • Long-lived feature branches. The number one cause of integration hell. Use feature flags and merge daily.
  • Giant PRs. Split them; stack PRs if needed.
  • Rubber-stamp reviews. Approvals without reading give a false sense of safety.
  • Admins bypassing protection. Rules apply to everyone, or to no one.
  • Secrets committed to Git. Rotating is mandatory; rewriting history is not enough. Enable secret scanning/push protection.
  • Merging when CI is red "just this once". That is how red builds become normal.

Try it

  1. Create a throwaway GitHub repo. In Settings, add a ruleset for main requiring a PR and one approval. Try to push directly and observe the rejection.
  2. Make a branch, commit with feat: add greeting, open a PR, and squash merge it.
  3. Tag v0.1.0 with git tag -a, push it, and create a GitHub release from it.
  4. Install commitlint or try npx release-please to see how commit types drive versions.
