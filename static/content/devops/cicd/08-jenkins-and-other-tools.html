Jenkins and Other CI/CD Tools

GitHub Actions and GitLab CI are not the only options. Jenkins is the veteran you will meet in many companies; CircleCI, Argo and Tekton cover other niches. This lesson shows what each is, how its pipeline looks, and how to choose.

Why there are so many tools

All of them do the same core job (run your build, test and deploy steps on a trigger), but they differ along four axes: where they run (SaaS vs self-hosted), how tied they are to a Git host, how they model pipelines (YAML, Groovy, Kubernetes resources), and what they optimise for (flexibility, convenience, Kubernetes-native delivery, GitOps). Knowing the axes lets you pick without chasing hype.

Jenkins

Jenkins (originally Hudson, 2004-2011) is an open-source automation server written in Java. It is self-hosted, extremely flexible, and has around 2,000 plugins. Its age is both strength and weakness: it can integrate with nearly anything, but it needs care and feeding.

Declarative Jenkinsfile

Pipelines live in a Jenkinsfile in the repo, written in Groovy-based DSL. The declarative syntax is structured and preferred over the older free-form scripted syntax.

pipeline {
  agent none                                  // each stage picks its own agent

  options {
    timeout(time: 30, unit: 'MINUTES')
    disableConcurrentBuilds()
    buildDiscarder(logRotator(numToKeepStr: '30'))
  }

  environment {
    IMAGE = "registry.example.com/shop:${env.GIT_COMMIT}"
  }

  stages {
    stage('Lint & Test') {
      agent { docker { image 'node:22-alpine' } }
      steps {
        sh 'npm ci'
        sh 'npm run lint'
        sh 'npm test'
      }
      post {
        always { junit 'junit.xml' }          // publish test results
      }
    }

    stage('Build image') {
      when { branch 'main' }                  // only on main
      agent { label 'docker' }
      steps {
        withCredentials([usernamePassword(
            credentialsId: 'registry-creds',
            usernameVariable: 'REG_USER', passwordVariable: 'REG_PASS')]) {
          sh '''
            echo "$REG_PASS" | docker login registry.example.com -u "$REG_USER" --password-stdin
            docker build -t "$IMAGE" .
            docker push "$IMAGE"
          '''
        }
      }
    }

    stage('Approve production') {
      when { branch 'main' }
      steps {
        timeout(time: 1, unit: 'HOURS') {
          input message: 'Deploy to production?', ok: 'Deploy'
        }
      }
    }

    stage('Deploy') {
      when { branch 'main' }
      agent { label 'deployer' }
      steps {
        sshagent(credentials: ['deploy-ssh-key']) {
          sh 'ssh deploy@prod.example.com "IMAGE=$IMAGE /opt/shop/deploy.sh"'
        }
      }
    }
  }

  post {
    failure { slackSend channel: '#ci', message: "FAILED: ${env.JOB_NAME} #${env.BUILD_NUMBER}" }
  }
}

Key ideas: agent says where to run (a label, or a Docker image); when conditions stages; post runs cleanup/notifications; withCredentials injects secrets from Jenkins' credential store and masks them in logs; input implements a manual approval; Multibranch Pipeline jobs auto-discover branches and PRs that contain a Jenkinsfile. Shared libraries (Groovy code in a separate repo) hold common steps for many pipelines.

Jenkins in practice

  • Pros: total control; runs anywhere (air-gapped, on-prem); works with any SCM; massive plugin ecosystem; free.
  • Cons: you operate it (upgrades, backups, scaling agents, security patches); plugin sprawl and compatibility; Groovy sandbox quirks; UI shows its age; the controller is a high-value target.
  • Best practice: keep config as code (Jenkins Configuration as Code plugin), run builds only on ephemeral agents (never on the controller), use Kubernetes plugin pods, keep plugins few and updated, back up JENKINS_HOME, put it behind SSO and HTTPS.

CircleCI

A hosted CI/CD SaaS (self-hosted runners available) known for speed, good caching/parallelism and Docker-first design. Config is .circleci/config.yml and uses orbs (shareable config packages).

version: 2.1
orbs:
  node: circleci/node@6

jobs:
  test:
    docker:
      - image: cimg/node:22.9
    steps:
      - checkout
      - node/install-packages            # includes caching
      - run: npm test
workflows:
  main:
    jobs:
      - test
      - deploy:
          requires: [test]
          filters: {branches: {only: main}}

Choose it for: very fast hosted CI independent of your Git host, strong test splitting and insights. Watch for: credit-based pricing, and the 2023 security incident that reminded everyone to rotate secrets held in any CI vendor.

Other hosted and platform-native options

  • Bitbucket Pipelines: built into Bitbucket; simple YAML; natural for Atlassian shops.
  • Azure Pipelines (Azure DevOps): YAML multi-stage pipelines, strong Windows/.NET and enterprise governance.
  • AWS CodePipeline/CodeBuild, Google Cloud Build: cloud-native, great IAM integration, less portable.
  • Buildkite: hosted control plane, you run the agents; popular for large, performance-sensitive monorepos.
  • Drone / Woodpecker CI, Concourse: container-native, lightweight, self-hosted; Concourse is resource-and-pipeline oriented.
  • Dagger: pipelines written in real code (Go, Python, TypeScript) that run identically locally and in any CI, with built-in caching. Reduces CI lock-in.

Kubernetes-native: Tekton

Tekton defines CI/CD as Kubernetes custom resources: Task (a series of container steps), Pipeline (tasks wired together), PipelineRun (one execution). Everything runs as pods.

apiVersion: tekton.dev/v1
kind: Pipeline
metadata: {name: build-and-test}
spec:
  tasks:
    - name: test
      taskRef: {name: npm-test}
    - name: build-image
      runAfter: [test]
      taskRef: {name: buildah}

Pros: cloud-native, scalable, vendor-neutral, a foundation for platforms (it underlies several products). Cons: verbose YAML, steep learning curve, you must build the UX and triggers (Tekton Triggers) yourself.

Argo: Workflows, Events and (most importantly) Argo CD

The Argo project is several tools, and naming confuses people:

ToolRole
Argo CDContinuous delivery via GitOps: watches a Git repo of Kubernetes manifests (or Helm/Kustomize) and continuously reconciles the cluster to match. It does not build or test code.
Argo WorkflowsContainer-native workflow engine for Kubernetes (CI-like jobs, data/ML pipelines as DAGs).
Argo RolloutsProgressive delivery: canary, blue-green, automated analysis and rollback.
Argo EventsEvent-driven triggering of workflows.

The common modern pattern splits CI from CD:

 CI (GitHub Actions / GitLab / Jenkins)           CD (GitOps: Argo CD or Flux)
 ┌──────────────────────────────┐                ┌───────────────────────────────┐
 │ test, build, scan, push image │──▶ update ───▶│ config repo: image: shop:3f9a1 │
 │ registry/shop:3f9a1c2         │   image tag    │        ▲ watches (pull)        │
 └──────────────────────────────┘   in config    │  Argo CD ─▶ applies to cluster │
                                    repo         └───────────────────────────────┘

Benefits: the cluster pulls its desired state, so CI needs no cluster credentials; Git is the audit log and rollback is git revert; drift is detected and corrected. The Infrastructure as Code section covers GitOps in depth. Flux is the main alternative to Argo CD.

How to choose

  1. Start where your code lives. GitHub repo: Actions. GitLab: GitLab CI. Bitbucket: Pipelines. Integration beats feature checklists.
  2. Do you need self-hosting or air-gapped? Jenkins, GitLab self-managed, Buildkite agents, Tekton.
  3. Do you deploy to Kubernetes? Consider a CI tool for build/test plus Argo CD/Flux for delivery.
  4. Scale and speed? Large monorepos or heavy test suites may justify Buildkite, CircleCI, or remote build caches (Bazel, Nx).
  5. Team capacity. Self-hosting means someone owns uptime and security. Small teams should prefer SaaS.
  6. Minimise lock-in by keeping logic in scripts, Makefiles or Dagger modules, with the CI file only orchestrating. Then migrating tools is a rewrite of a thin YAML file.
The tool matters less than you think

The practices (small changes, fast tests, build once, safe rollout) are tool-independent. A well-designed pipeline on Jenkins beats a sloppy one on the shiniest platform. Do not migrate tools to fix a process problem.

Pitfalls

  • Running two CI systems "temporarily" for years.
  • Click-configured Jenkins jobs with no Jenkinsfile: undocumented, unreviewable.
  • Running builds on the Jenkins controller itself (security and stability risk).
  • Treating Argo CD as a CI tool, or expecting GitOps tools to build images.
  • Putting complex logic in plugin-specific syntax that cannot be run locally.

Try it

  1. Run Jenkins locally: docker run -p 8080:8080 -v jenkins_home:/var/jenkins_home jenkins/jenkins:lts-jdk17, finish the setup wizard, and create a Pipeline job from a Jenkinsfile in a repo.
  2. Port your GitHub Actions workflow (or the example above) to GitLab CI or CircleCI. Note what concepts map one-to-one and what does not.
  3. Move the commands out of the YAML into a Makefile (make test, make build), and have the CI file call only those targets.
