Testing and Quality Gates

A pipeline is only as trustworthy as the checks in it. A quality gate is an automated decision: "this change may proceed, or it may not". This lesson covers which checks to run, what each is good for, and how to turn them into gates that protect production without strangling developers.

Why gates?

Without automatic gates, quality depends on individual diligence: reviewers noticing a missing test, someone remembering to run the security scan, a manager eyeballing coverage. Humans are inconsistent, especially at 6 p.m. on release day. Gates move the minimum bar from "people usually remember" to "the merge button is disabled until it is met". That is what lets you deploy often without gambling.

Keep the pyramid shape: many unit, some integration, a handful of E2E for critical journeys (sign-up, checkout). Use Testcontainers or CI service containers so integration tests run against real databases rather than mocks that lie about SQL behavior.

Test quality beats test quantity

  • Deterministic: no sleeping for arbitrary times, no dependence on test order, the current date, or random data without a seed.
  • Isolated: each test creates and cleans its own data.
  • Meaningful: assert on behavior, not implementation details.
  • Fast: slow tests are tests nobody runs.

Code quality: lint, format, types

  • Formatters (Prettier, Black, gofmt): remove style debates; run in "check" mode in CI (prettier --check .).
  • Linters (ESLint, ruff, golangci-lint, Checkstyle): catch bug patterns, unused code, bad practices.
  • Type checkers (TypeScript tsc --noEmit, mypy, pyright): eliminate whole bug classes before runtime.
  • Other linters: hadolint (Dockerfile), actionlint (workflows), shellcheck (bash), yamllint, tflint (Terraform), commitlint.

These are the cheapest gate: run them first, fail in seconds.

Coverage

Code coverage measures which lines/branches the tests execute. It is useful as a negative signal (untested code is definitely unprotected) and weak as a positive one (executing a line is not the same as asserting it works).

  • Set a floor (e.g. fail if overall coverage drops below 70%) and, more usefully, a patch/diff coverage requirement (new code must be at least 80% covered) via Codecov, Coveralls or SonarQube. This prevents decline without demanding the legacy code be fixed at once.
  • Do not chase 100%. Past a point it incentivises meaningless tests (Goodhart's law: when a measure becomes a target it ceases to be a good measure).
  • Mutation testing (Stryker, PIT, mutmut) tells you whether tests would actually notice injected bugs; run it periodically on critical modules.
# Jest: fail the build below thresholds (package.json)
"jest": {
  "coverageThreshold": {
    "global": {"branches": 70, "functions": 75, "lines": 80, "statements": 80}
  }
}

SAST vs DAST

SAST reads source without running it: early, precise about location, but prone to false positives and blind to runtime/config issues. DAST probes the running app from outside like an attacker: finds real exploitable behavior, but slower, needs a deployed environment, and gives less precise code locations. They are complementary.

# Trivy: fail the pipeline on HIGH/CRITICAL fixable vulnerabilities in the image
trivy image --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 ghcr.io/acme/shop:${SHA}

# GitHub: CodeQL (SAST) workflow step
- uses: github/codeql-action/init@v3
  with: {languages: javascript-typescript}
- uses: github/codeql-action/analyze@v3
Make security findings actionable

A gate that blocks on 400 legacy findings gets disabled within a week. Start by blocking only on new findings and Critical/High severity with a fix available, keep a baseline for the rest, and burn it down on a schedule. Allow time-boxed, documented exceptions (a .trivyignore entry with an expiry and owner).

SBOM and provenance

A Software Bill of Materials is a machine-readable inventory of every component in your artifact (formats: SPDX, CycloneDX). Why: when the next Log4Shell lands, you can answer "which of our 300 services contain this library?" in seconds rather than days. Regulations and customers (US executive order 14028, EU Cyber Resilience Act) increasingly require them.

# generate an SBOM for an image and attach it as an attestation
syft ghcr.io/acme/shop:${SHA} -o spdx-json=sbom.spdx.json
cosign attest --yes --predicate sbom.spdx.json --type spdxjson ghcr.io/acme/shop@${DIGEST}

# keyless signing in CI (uses OIDC identity)
cosign sign --yes ghcr.io/acme/shop@${DIGEST}

Pair the SBOM with signatures and provenance (SLSA, GitHub artifact attestations). Then a Kubernetes admission policy (Kyverno, Sigstore policy-controller) can refuse to run images that were not built and signed by your pipeline.

Gates in practice

1. Required status checks (branch protection)

The enforcement point. In GitHub rulesets or branch protection, mark the jobs lint, test, build, codeql as required. The merge button stays disabled until they pass. Remember that a skipped job can count as passing; use a single final "gate" job that needs all others and is the only required check:

  ci-gate:
    if: always()
    needs: [lint, test, build, codeql]
    runs-on: ubuntu-latest
    steps:
      - name: Fail if any required job failed or was cancelled
        run: |
          echo '${{ toJSON(needs) }}' | jq -e 'all(.[]; .result == "success")'

2. Review gates

Required approvals, CODEOWNERS, "dismiss stale approvals", and resolving all conversations.

3. Deployment gates

  • Environment protection rules (reviewers, wait timers, allowed branches).
  • Smoke tests that must pass before traffic shifts; canary analysis comparing error rate and latency with the baseline (Argo Rollouts, Flagger).
  • SLO/error-budget checks: block risky deploys if the budget is exhausted.
  • Change-freeze calendars for holidays or peak events.

4. Quality platforms

SonarQube/SonarCloud, Codacy or CodeClimate combine coverage, duplication, complexity, code smells and security hotspots into a single "quality gate" with pass/fail conditions on new code ("clean as you code").

Designing a good gate

  • Fast. A gate that takes 40 minutes is skipped or worked around.
  • Reliable. False failures train people to hit "re-run". Gate on stable checks; quarantine flaky ones.
  • Clear. Error messages say what to fix and how.
  • Proportionate. Block on what is truly dangerous; warn on the rest.
  • Incremental. Apply thresholds to new code, ratchet them up over time.
  • Owned. Someone maintains rules and exceptions.

Pitfalls

  • Coverage worship: tests without assertions that exist to satisfy the percentage.
  • Scanner noise: unfiltered findings lead to alert fatigue and ignored results.
  • Gates on the wrong branch: checks that only run after merge cannot protect main.
  • Admin bypass of required checks becoming routine.
  • Only scanning at merge: new CVEs are published daily; schedule rescans of what you already shipped.
  • Mocked-everything tests that pass while the real integration is broken.
  • E2E suites on every PR that take 40 minutes and flake. Keep a small smoke subset on PRs; full suites after merge.

Try it

  1. Add npm audit --audit-level=high (or pip-audit) and gitleaks as parallel jobs in your CI.
  2. Run trivy image on a public image such as node:22 and compare with node:22-alpine. What do you learn about base image choice?
  3. Generate an SBOM with syft for one of your images and search it for a package name (jq).
  4. Configure branch protection to require your CI gate job, then open a PR that breaks lint and confirm you cannot merge.
