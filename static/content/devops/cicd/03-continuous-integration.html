Continuous Integration

Continuous Integration (CI) is the practice of merging every developer's work into a shared mainline frequently, and verifying each merge with an automated build and test run. It is a behavior first and a tool second.

The problem CI solves

Software is built by many people changing the same codebase. Two changes that each work alone can fail together. The longer they stay apart, the more expensive and mysterious the failure. Before CI, teams scheduled a painful "integration phase" near the end of a project. CI (coined by Grady Booch, made a core practice of Extreme Programming, and popularised by Martin Fowler's 2000 article) inverts this: integrate so often that integration is boring.

Without CI, you learn that the build is broken from a teammate, from QA, or from a customer. With CI, you learn within minutes, from a bot, on your own pull request.

What CI actually is: the practices

Fowler's list, still the best definition, with modern commentary:

  1. Maintain a single source repository. Everything needed to build lives in version control: code, tests, build scripts, DB migrations, pipeline definitions.
  2. Automate the build. One command (make build, npm ci && npm run build) produces the artifact from a clean checkout. If it takes tribal knowledge, CI cannot run it.
  3. Make the build self-testing. Tests run as part of the build, and a failing test fails the build.
  4. Everyone commits to the mainline every day. This is the "continuous" in CI. Branches that live for weeks mean you are not doing CI, even if a server builds them.
  5. Every commit builds on an integration machine. A clean environment, not a developer laptop.
  6. Keep the build fast. The classic target is under 10 minutes. Beyond that, developers stop waiting, batch their changes, and the feedback loop breaks.
  7. Fix broken builds immediately. A red main is a stop-the-line event. Revert first, investigate second.
  8. Test in a clone of production. Same OS, same runtime version, ideally the same container image.
  9. Make it easy to get the latest artifact. Anyone, including QA and product, can fetch what the latest build produced.
  10. Everyone can see what is happening. Status on the PR, in chat, on a dashboard.

The CI loop

 developer           Git host                CI runner (clean, ephemeral)
 ┌───────┐  push/PR  ┌──────────┐  webhook  ┌───────────────────────────────┐
 │ commit│──────────▶│ branch/PR│──────────▶│ 1 checkout   2 install deps    │
 └───▲───┘           └────┬─────┘           │ 3 lint       4 unit tests      │
     │                    │ status check    │ 5 build      6 integration test│
     │  fix, push again   ▼                 └───────────────┬───────────────┘
     └──────── red ◀── PR shows pass/fail ◀─────────────────┘
                            │ green + review
                            ▼
                      merge to main ──▶ pipeline again ──▶ artifact (CD takes over)

The pipeline runs in two modes: on the PR (verifying the proposed change, often merged with the target branch) and on main after merge (producing the release artifact). Some teams use a merge queue (GitHub merge queue, GitLab merge trains) that tests each PR on top of the other queued changes, preventing "green PR, red main" races.

Fast feedback is the whole point

Think of CI as a latency problem. What matters is the time from git push to a trustworthy answer.

Feedback timeDeveloper behavior
< 5 minWaits, stays in flow, fixes immediately
5-15 minStarts something small, returns
15-45 minContext switches; PRs batch up; fixes cost more
Hours"Run CI" becomes a chore; people merge without waiting; trust erodes

Techniques to stay fast: run cheap checks first (fail fast), parallelise independent jobs, cache dependencies, run only affected tests in large repos, split slow suites into shards, and move slow end-to-end tests to after-merge or nightly runs.

The test pyramid in a pipeline

              /\
             /e2e\            few, slow, brittle   (minutes)  - critical user journeys
            /──────\
           /integr. \         some, medium         (seconds-min) - DB, queues, HTTP APIs
          /──────────\
         /   unit      \      many, fast, isolated (ms)  - pure logic
        /────────────────\

Mike Cohn's pyramid says: write many fast unit tests, fewer integration tests, and very few end-to-end tests. In pipeline terms this maps onto ordering and cost:

LayerRunsSpeedCatchesFlakiness risk
Static analysis (lint, type check)Every push, firstSecondsStyle, type errors, obvious bugsVery low
UnitEvery pushSeconds-1 minLogic errorsLow
IntegrationEvery PR1-5 minWiring, SQL, serialization, contractsMedium
End-to-end / UIAfter merge, on staging; a small smoke subset on PR5-30 minWhole-system regressionsHigh

The anti-pattern is the ice cream cone: few unit tests, a mountain of slow UI tests, and a manual QA layer on top. It is slow, flaky and expensive. Invert it.

Build once, run everywhere

A pillar of both CI and CD: build the artifact once, then test and deploy that exact artifact in every environment. Do not rebuild for staging and again for production. A rebuild can pick up different dependency versions or a different base image, so "what we tested" is no longer "what we shipped".

  • Make the artifact immutable and uniquely identified (Docker image tagged with the commit SHA, or a package with a version and checksum).
  • Keep environment differences in configuration injected at deploy time (env vars, config maps, secrets), never in the build.
  • Pin dependencies with lockfiles (package-lock.json, poetry.lock, go.sum) and use the strict install command (npm ci, not npm install).

A minimal CI job, explained

name: ci
on:
  pull_request:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest          # fresh VM for each run
    timeout-minutes: 15             # never let a stuck job burn money
    steps:
      - uses: actions/checkout@v4   # get the code
      - uses: actions/setup-node@v4
        with:
          node-version-file: .nvmrc # same Node as everyone else
          cache: npm                # restore ~/.npm keyed on the lockfile
      - run: npm ci                 # exact, reproducible install
      - run: npm run lint
      - run: npm test -- --coverage

Notice what this guarantees: a clean machine, pinned runtime, locked dependencies, and a result attached to the PR. The next lessons build this up properly.

Practices around the pipeline

  • Run the same commands locally. Put steps in npm scripts or a Makefile/justfile; the pipeline calls them. Debugging a pipeline you can only run by pushing is miserable.
  • Pre-commit hooks (husky, lefthook, pre-commit) catch trivial failures before pushing. They complement CI; they never replace it because they can be skipped.
  • Treat the build as a team alarm. Whoever broke it fixes or reverts it; notify via chat.
  • Keep branches short and rebase/merge main frequently.
  • Test the database migrations in CI against a real database (service containers) so schema changes are validated every time.
  • Use ephemeral environments. Spin up a disposable preview deployment per PR for reviewers.

Pitfalls

  • Nightly builds mistaken for CI. Feedback must be per-change.
  • Ignoring red builds or retrying until green. That hides flakiness and teaches the team that failures mean nothing.
  • Tests that depend on order, shared state, wall-clock time or the network. They pass locally and fail randomly in CI.
  • CI that differs from local and prod (different Node/Java version, missing system library).
  • Everything in one giant job. You cannot parallelise or tell what failed.
  • Too little coverage of what matters. A green build is only as meaningful as the tests behind it.
Definition of done

A good rule: a change is not "done" when it works on your machine, or even when it is merged, but when it has passed CI on main and is available as a deployable artifact. CI turns "done" from an opinion into a fact.

Try it

  1. Take any small project and write down the exact commands to go from a clean clone to "tests pass". If you need more than three, script them.
  2. Add the minimal workflow above (adjusted to your language) and open a PR that deliberately breaks a test. Watch the check fail on the PR.
  3. Time your pipeline. List the three slowest steps and one way to speed up each.
