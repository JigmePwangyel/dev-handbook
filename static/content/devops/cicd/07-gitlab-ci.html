GitLab CI/CD

GitLab bundles source hosting, CI/CD, a container registry, security scanning and environments into one product. Its pipeline model, stages containing jobs, defined in a single .gitlab-ci.yml, is concise and has influenced many other tools.

The model

 .gitlab-ci.yml in repo root
        │ push / merge request / schedule / API / tag
        ▼
 Pipeline
   stage: build ──▶ stage: test ──────────▶ stage: package ──▶ stage: deploy
     build_app       unit_tests  ┐             docker_image       staging
                     lint        ├ parallel                       production (manual)
                     sast        ┘
 (jobs in a stage run in parallel; next stage starts when all succeed)
        │ each job
        ▼
 GitLab Runner (shell / docker / kubernetes executor) pulls the job and runs it
ConceptMeaning
PipelineThe whole run for a commit or MR.
StageOrdered phase; default order: .pre, build, test, deploy, .post. You can define your own with stages:.
JobA named block with a script:; assigned to a stage.
RunnerThe agent that executes jobs. Shared (GitLab.com), group, or project runners; executor types: docker, kubernetes, shell, etc.
Artifacts / cacheSame distinction as everywhere: artifacts pass outputs; cache speeds dependencies.
EnvironmentA named deploy target with history, URL, rollback button and protected access.
VariablesPredefined (CI_COMMIT_SHA, CI_REGISTRY_IMAGE) and custom, set in UI/API, can be masked, protected, or file-type.

A complete example

Node app: lint and test in parallel, build, package a Docker image to the built-in GitLab registry, deploy to staging automatically, to production after a manual click.

stages: [lint, test, build, package, deploy]

default:
  image: node:22-alpine
  interruptible: true            # newer pipelines on same branch may cancel this job
  timeout: 15 minutes

variables:
  npm_config_cache: "$CI_PROJECT_DIR/.npm"   # keep npm cache inside the project for caching
  IMAGE: "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"

# --- reusable hidden template: names starting with "." are not run ---
.node_setup:
  cache:
    key:
      files: [package-lock.json]               # invalidate when lockfile changes
    paths: [.npm/]
  before_script:
    - npm ci --prefer-offline

lint:
  extends: .node_setup
  stage: lint
  script:
    - npm run lint
    - npm run typecheck

unit_tests:
  extends: .node_setup
  stage: test
  script:
    - npm test -- --coverage
  coverage: '/All files[^|]*\|[^|]*\s+([\d\.]+)/'   # parse % from output
  artifacts:
    when: always
    reports:
      junit: junit.xml                         # shows test results in the MR
    paths: [coverage/]
    expire_in: 1 week

integration_tests:
  extends: .node_setup
  stage: test
  services:
    - name: postgres:16
      alias: db
  variables:
    POSTGRES_PASSWORD: test
    DATABASE_URL: "postgres://postgres:test@db:5432/postgres"
  script:
    - npm run test:integration

build_app:
  extends: .node_setup
  stage: build
  script:
    - npm run build
  artifacts:
    paths: [dist/]
    expire_in: 1 day

docker_image:
  stage: package
  image: docker:27
  services: [docker:27-dind]                  # Docker-in-Docker for building images
  variables:
    DOCKER_TLS_CERTDIR: "/certs"
  before_script:
    - echo "$CI_REGISTRY_PASSWORD" | docker login -u "$CI_REGISTRY_USER" --password-stdin "$CI_REGISTRY"
  script:
    - docker build --pull -t "$IMAGE" .
    - docker push "$IMAGE"
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH   # only on main

deploy_staging:
  stage: deploy
  image: alpine:3.20
  environment:
    name: staging
    url: https://staging.shop.example.com
  before_script:
    - apk add --no-cache openssh-client
    - install -m 700 -d ~/.ssh
    - echo "$SSH_PRIVATE_KEY" > ~/.ssh/id_ed25519 && chmod 600 ~/.ssh/id_ed25519
    - echo "$SSH_KNOWN_HOSTS" > ~/.ssh/known_hosts
  script:
    - ssh deploy@"$STAGING_HOST" "IMAGE=$IMAGE /opt/shop/deploy.sh"
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH

deploy_production:
  extends: deploy_staging
  environment:
    name: production
    url: https://shop.example.com
  script:
    - ssh deploy@"$PROD_HOST" "IMAGE=$IMAGE /opt/shop/deploy.sh"
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
      when: manual                              # human clicks "play"
  resource_group: production                    # serialise prod deploys

Highlights: extends and hidden .templates remove duplication; cache:key:files keys on the lockfile; artifacts:reports:junit surfaces failures in the merge request; resource_group prevents two deploys to the same environment at once; environment gives a deployments page and one-click rollback to a previous deployment.

Rules: controlling when jobs run

rules: replaces the older only/except. Rules are evaluated top to bottom; the first match decides.

job:
  script: ./run.sh
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"       # MR pipelines
    - if: $CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/               # release tags
      variables: {DEPLOY_TARGET: "prod"}
    - changes: ["docs/**/*"]                                 # only when docs changed
      when: never
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
      when: manual
      allow_failure: false
    - when: never                                            # default: don't run

A common trap: a pipeline can be triggered both by a branch push and by an MR event, producing duplicate pipelines. Use workflow:rules at the top level to choose one:

workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS
      when: never                       # avoid duplicate branch pipeline
    - if: $CI_COMMIT_BRANCH || $CI_COMMIT_TAG

DAG pipelines and parallelism

  • needs: [job] lets a job start as soon as its dependencies finish rather than waiting for the whole previous stage, forming a DAG and shortening pipelines.
  • parallel: 4 runs N copies (with CI_NODE_INDEX/CI_NODE_TOTAL) for test sharding; parallel: matrix: runs combinations of variables.
  • interruptible: true + auto-cancel redundant pipelines saves runner time.

Includes, templates and components

Share pipeline logic across projects with include::

include:
  - local: ci/node.yml                                     # file in this repo
  - project: acme/ci-templates                             # another project
    ref: v3.2.0                                            # pin a version
    file: /templates/docker-build.yml
  - template: Security/SAST.gitlab-ci.yml                  # GitLab-provided template
  - component: gitlab.com/acme/components/deploy@1.4.0     # CI/CD component (catalog)
    inputs:
      environment: production

CI/CD components (the catalog) are versioned, parameterised building blocks, the modern way to share pipelines. Pin versions to avoid surprise breakage.

Runners

  • Shared runners on GitLab.com need no setup and run jobs in a fresh VM/container (consumption of compute minutes applies).
  • Self-managed runners: install gitlab-runner, register with a token, pick an executor. The Docker executor runs each job in the image named by image:; the Kubernetes executor spawns a pod per job (good for autoscaling).
  • Tags: label runners (gpu, arm64, prod-deploy) and select with tags: in the job.
  • Docker-in-Docker needs privileged mode, which is a security risk on shared runners. Alternatives: Kaniko, BuildKit rootless, Buildah, or a dedicated build runner.
# register a runner (interactive flags shown non-interactively)
gitlab-runner register \
  --url https://gitlab.example.com \
  --token "$RUNNER_AUTH_TOKEN" \
  --executor docker \
  --docker-image alpine:3.20

Variables, secrets and security

  • Set variables in Settings > CI/CD > Variables. Tick Masked (hidden in logs), Protected (only available on protected branches/tags) and scope by environment.
  • Prefer ID tokens (OIDC) (id_tokens: keyword) to authenticate to cloud and Vault without stored keys.
  • Built-in security templates: SAST, secret detection, dependency scanning, container scanning, DAST, with findings shown in merge requests (some features in paid tiers).
  • Merge request pipelines from forks do not receive protected variables.

Auto DevOps and Review Apps

Review apps deploy every merge request to a temporary URL (environment: name: review/$CI_COMMIT_REF_SLUG with an on_stop job to tear it down) so reviewers and product people can click the real change. Auto DevOps provides an opinionated, zero-config pipeline (build, test, scan, deploy to Kubernetes); good for learning, usually replaced by a custom pipeline later.

Pitfalls

  • Duplicate pipelines from mixing branch and MR triggers (fix with workflow:rules).
  • Forgetting that each job starts clean: pass dist/ with artifacts, use dependencies/needs to control which artifacts are downloaded.
  • Cache not shared across runners (local cache); configure a distributed cache (S3/GCS) for fleets.
  • Privileged DinD on shared runners.
  • Unmasked secrets: masking requires the value to meet format rules (e.g. min length, no spaces).
  • Unpinned include refs (ref: main) mean someone else's change can break your pipeline.
  • YAML anchors vs extends vs !reference: prefer extends; use !reference [.job, script] to reuse fragments.

Try it

  1. Create a free GitLab project, add a .gitlab-ci.yml with two stages (test, deploy) and echo jobs; open the pipeline graph.
  2. Add rules so the deploy job is manual on main and never runs on MRs.
  3. Add the Security/SAST.gitlab-ci.yml template and review the report in the pipeline's Security tab.
  4. Run CI Lint (Pipeline editor) to validate your file before committing.
