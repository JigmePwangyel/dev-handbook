GitHub Actions

GitHub Actions is the CI/CD system built into GitHub. Workflows are YAML files in your repo, triggered by repository events, executed on hosted or self-hosted runners. It is the most widely used CI system today; this lesson goes from concepts to a complete Node app pipeline that tests, builds and pushes a Docker image, and deploys over SSH.

Core concepts

 Event (push, pull_request, schedule, workflow_dispatch, release ...)
        │ triggers
        ▼
 Workflow  (.github/workflows/ci.yml)
   ├─ Job A  ── runs-on: ubuntu-latest ──▶ Runner VM #1
   │    ├─ Step 1: uses: actions/checkout@v4        (reusable Action)
   │    ├─ Step 2: run: npm ci                       (shell command)
   │    └─ Step 3: run: npm test
   └─ Job B  (needs: A) ── Runner VM #2 ...
ConceptMeaning
WorkflowA YAML file under .github/workflows/. A repo can have many.
EventWhat triggers it: push, pull_request, schedule, workflow_dispatch (manual), release, workflow_call (reusable), etc.
JobA set of steps on one runner. Jobs run in parallel unless needs orders them.
StepEither run: (a shell command) or uses: (an action). Steps share the runner's filesystem.
ActionA reusable unit (JavaScript, Docker or composite) from the Marketplace or your own repo.
RunnerThe machine executing a job: GitHub-hosted (ubuntu-latest, windows-latest, macos-latest, ARM variants) or self-hosted.
Context / expressions${{ github.sha }}, ${{ secrets.X }}, ${{ matrix.node }}, ${{ needs.build.outputs.tag }}

Part 1: Continuous integration for a Node app

Save as .github/workflows/ci.yml.

name: CI

on:
  pull_request:
  push:
    branches: [main]

# least privilege: the default token can only read the repo
permissions:
  contents: read

# cancel older runs of the same PR/branch when a new commit arrives
concurrency:
  group: ci-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  lint:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version-file: .nvmrc
          cache: npm                       # caches ~/.npm keyed by package-lock.json
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck

  test:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    strategy:
      fail-fast: false                     # let all matrix legs finish
      matrix:
        node: [20, 22]                     # run on two Node versions
    services:
      postgres:                            # real DB for integration tests
        image: postgres:16
        env:
          POSTGRES_PASSWORD: test
          POSTGRES_DB: app_test
        ports: ["5432:5432"]
        options: >-
          --health-cmd "pg_isready -U postgres"
          --health-interval 5s --health-timeout 5s --health-retries 10
    env:
      DATABASE_URL: postgres://postgres:test@localhost:5432/app_test
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
          cache: npm
      - run: npm ci
      - run: npm test -- --coverage
      - uses: actions/upload-artifact@v4   # keep the report for download/inspection
        if: always()                       # even when tests fail
        with:
          name: coverage-node${{ matrix.node }}
          path: coverage/
          retention-days: 7

Key points: permissions narrows the automatic GITHUB_TOKEN; concurrency saves minutes; services starts sidecar containers on the runner; if: always() runs the step regardless of earlier failures; the matrix creates two independent jobs.

Part 2: Build and push a Docker image

Save as .github/workflows/release.yml. It runs only on main after CI passes (via a shared trigger) and publishes to GitHub Container Registry (GHCR).

name: Build and Deploy

on:
  push:
    branches: [main]
  workflow_dispatch:                       # manual re-run / redeploy

permissions:
  contents: read

concurrency:
  group: deploy-production
  cancel-in-progress: false                # never cancel a deploy mid-flight; queue instead

env:
  IMAGE: ghcr.io/${{ github.repository }}  # e.g. ghcr.io/acme/shop

jobs:
  test:
    uses: ./.github/workflows/ci.yml       # reuse CI (needs "on: workflow_call" in ci.yml)

  build:
    needs: test
    runs-on: ubuntu-latest
    timeout-minutes: 20
    permissions:
      contents: read
      packages: write                      # needed to push to GHCR
    outputs:
      tag: ${{ steps.meta.outputs.version }}
      digest: ${{ steps.push.outputs.digest }}
    steps:
      - uses: actions/checkout@v4

      - uses: docker/setup-buildx-action@v3

      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - id: meta                           # computes tags and labels
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.IMAGE }}
          tags: |
            type=sha,format=long
            type=raw,value=latest,enable={{is_default_branch}}

      - id: push
        uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha             # reuse layers between runs
          cache-to: type=gha,mode=max
          provenance: true                 # attach build provenance attestation

To use uses: ./.github/workflows/ci.yml as a reusable workflow, add workflow_call: under on: in ci.yml. The image gets an immutable sha-<40-char> tag; latest is a convenience pointer only, never what you deploy.

Part 3: Deploy over SSH with an approval gate

Append this job to release.yml. It targets a GitHub environment named production.

  deploy:
    needs: build
    runs-on: ubuntu-latest
    timeout-minutes: 10
    environment:
      name: production                     # applies protection rules + environment secrets
      url: https://shop.example.com
    steps:
      - name: Set up SSH
        env:
          SSH_KEY: ${{ secrets.DEPLOY_SSH_KEY }}
          KNOWN_HOSTS: ${{ secrets.DEPLOY_KNOWN_HOSTS }}   # output of: ssh-keyscan host
        run: |
          install -m 700 -d ~/.ssh
          printf '%s\n' "$SSH_KEY" > ~/.ssh/id_ed25519
          chmod 600 ~/.ssh/id_ed25519
          printf '%s\n' "$KNOWN_HOSTS" > ~/.ssh/known_hosts

      - name: Deploy image by digest
        env:
          HOST: ${{ vars.DEPLOY_HOST }}
          IMAGE_REF: ${{ env.IMAGE }}@${{ needs.build.outputs.digest }}
        run: |
          ssh -i ~/.ssh/id_ed25519 deploy@"$HOST" bash -s -- "$IMAGE_REF" <<'EOF'
            set -euo pipefail
            IMAGE_REF="$1"
            cd /opt/shop
            echo "IMAGE=$IMAGE_REF" > .env.deploy
            docker pull "$IMAGE_REF"
            docker compose --env-file .env.deploy up -d --remove-orphans
          EOF

      - name: Smoke test
        run: |
          for i in 1 2 3 4 5 6; do
            if curl -fsS https://shop.example.com/healthz; then exit 0; fi
            sleep 10
          done
          echo "Health check failed" >&2
          exit 1

Notes: the server's docker-compose.yml would reference image: ${IMAGE}; the private key lives in an environment secret, not repository-wide; the server user deploy should have only the rights it needs; deploying by digest guarantees you run exactly what was built. Using known_hosts instead of disabling host key checking prevents man-in-the-middle attacks.

Environments and approvals

In Settings > Environments create staging and production. For production configure:

  • Required reviewers: the job pauses until one of them approves in the UI.
  • Wait timer: optional delay before deploy.
  • Deployment branches: only main (and tags) may deploy here.
  • Environment secrets and variables: scoped to jobs that reference the environment; only released after approval.

The Deployments tab then gives a history of what version went where and who approved.

Concurrency, caching and artifacts

  • concurrency.group ensures only one run per group; cancel-in-progress: true for CI, false for deploys.
  • actions/cache (or the cache: input of setup actions) restores directories by key. Entries unused for 7 days are evicted and each repo has a size cap (10 GB by default); never rely on it for correctness.
  • upload-artifact / download-artifact pass files between jobs and attach them to the run. Set retention-days.
  • Job outputs pass small strings (needs.build.outputs.digest); use artifacts for files.

Reusable workflows and composite actions

Stop copy-pasting pipelines across repos. A reusable workflow is a full workflow with on: workflow_call, called by other workflows:

# in acme/platform-workflows/.github/workflows/node-ci.yml
on:
  workflow_call:
    inputs:
      node-version: {type: string, default: "22"}
    secrets:
      NPM_TOKEN: {required: false}
jobs:
  ci:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: {node-version: "${{ inputs.node-version }}", cache: npm}
      - run: npm ci && npm test

# in a service repo
jobs:
  ci:
    uses: acme/platform-workflows/.github/workflows/node-ci.yml@v2
    with: {node-version: "20"}
    secrets: inherit

A composite action (action.yml with runs: using: composite) bundles several steps into one reusable step. Use reusable workflows for whole jobs, composite actions for step sequences.

OIDC to the cloud: no long-lived keys

Instead of storing AWS keys as secrets, let the workflow prove its identity with a short-lived OpenID Connect token that the cloud exchanges for temporary credentials.

permissions:
  id-token: write        # allow requesting the OIDC token
  contents: read

steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123456789012:role/gha-deploy
      aws-region: eu-west-1
  - run: aws sts get-caller-identity

On the AWS side the role's trust policy restricts the token's sub claim, for example to repo:acme/shop:environment:production, so only that repo and environment can assume it. The same pattern works with GCP Workload Identity Federation and Azure federated credentials. See the secrets lesson for details.

Other useful features

  • Path filters: on.push.paths: ['src/**', 'package*.json'] skips irrelevant runs.
  • Conditionals: if: github.ref == 'refs/heads/main', if: failure().
  • Schedules: on.schedule: [{cron: '0 3 * * *'}] (UTC).
  • Dependabot keeps actions and dependencies updated via PRs.
  • Job summaries: write Markdown to $GITHUB_STEP_SUMMARY.
  • Self-hosted runners / ARC: run on your own machines or Kubernetes (Actions Runner Controller) for private networking and cost control.
  • Debugging: re-run with debug logging; use act to run workflows locally (approximate).

Pitfalls

  • Using pull_request_target with untrusted code checkout: it runs with secrets and write token on code from forks. A classic supply-chain hole. Use pull_request for untrusted code.
  • Script injection: never interpolate untrusted values (${{ github.event.pull_request.title }}) directly into run:. Pass them via env: and quote.
  • Unpinned third-party actions: @main or even @v3 tags can be moved. Pin to a full commit SHA for anything non-trivial.
  • Over-broad GITHUB_TOKEN permissions. Declare permissions explicitly.
  • Cache poisoning / stale caches and cache used as artifact store.
  • Secrets in logs: secrets are masked, but transformed values (base64, substrings) may not be.
  • YAML gotchas: on and numeric versions: write node-version: "22" quoted so 20.10 is not parsed as 20.1.
  • Hosted-runner minutes are billed (free tier for public repos); long matrices on macOS cost multiples of Linux.
Validate before you push

Use actionlint (a linter for workflow files) locally or in CI. It catches expression typos, bad needs references and shell issues in run: blocks.
