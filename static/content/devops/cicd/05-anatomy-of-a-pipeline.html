Anatomy of a Pipeline

Every CI/CD tool has its own syntax, but they all model the same thing: a graph of stages made of jobs made of steps, passing artifacts along, running on machines called runners. Learn the shape once and you can read any pipeline.

Why think in stages?

A pipeline is an assembly line for software. Each station does one job and either passes the work on or stops the line. Ordering matters for two reasons: fail fast (cheap checks first so you do not waste 20 minutes building something that fails lint in 10 seconds) and confidence gradient (each stage raises confidence before you risk the next, more expensive, more dangerous stage).

Vocabulary

  • Pipeline / workflow: the whole automated process, triggered by an event.
  • Trigger / event: push, pull request, tag, schedule (cron), manual, webhook, another pipeline finishing.
  • Stage: a phase grouping jobs (GitLab, Jenkins). Stages run in order.
  • Job: a unit of work that runs on one runner. Jobs may run in parallel; each starts with a clean environment.
  • Step: one command or action inside a job. Steps in a job share a filesystem and run sequentially.
  • Runner / agent: the machine or container that executes jobs.
  • Artifact: files a job produces for later jobs or for download (build output, test reports).
  • Cache: files reused between runs to save time (dependencies). Not a source of truth.
  • Environment: a deployment target (staging, production) with its own secrets, protection rules and history.

Jobs are isolated: artifacts vs cache

Each job typically starts on a fresh runner. Anything you want to survive must be passed explicitly. Two mechanisms, constantly confused:

Cache key design

Key on the lockfile hash so the cache invalidates exactly when dependencies change, with a fallback prefix key so a near-match still helps. Never cache build outputs you then ship; that breaks reproducibility.

Speed: parallelism, fan-out, matrix, sharding

              ┌─────▶ lint ────────┐
 checkout ───▶├─────▶ unit tests ──┤
              ├─────▶ type-check ──┼──▶ build ──▶ scan ─┬─▶ deploy staging ─▶ e2e ─▶ deploy prod
              └─────▶ integration ─┘                    └─▶ (parallel) SBOM/sign
        (fan-out: independent jobs in parallel)   (fan-in: wait for all via needs)
  • Fan-out / fan-in: independent jobs run concurrently; a downstream job declares dependencies (needs: in GitHub/GitLab) and waits.
  • Matrix: run the same job across combinations (Node 20/22 x ubuntu/windows). One definition, N jobs.
  • Sharding: split a long test suite into N slices run in parallel (jest --shard=1/4, Playwright --shard), then merge reports. A 20-minute suite on 4 shards finishes in about 5.
  • Caching and incremental builds: dependency cache, Docker layer cache, build caches (Turborepo, Gradle, Bazel remote cache).
  • Path filters: skip jobs when only docs changed.
  • Cancel superseded runs: a new push to a PR cancels the older run (concurrency groups).

Parallelism trades money (more concurrent runners) for time. Developer time is almost always more expensive than runner time.

Pipeline as code

Pipelines are defined in a file in the repo (.github/workflows/*.yml, .gitlab-ci.yml, Jenkinsfile). Benefits: versioned, reviewed, branch-specific (a PR can change the pipeline and test the change), reproducible, and visible. The old way, clicking jobs together in a web UI, produced undocumented, unreproducible "snowflake" CI servers.

What a stage must provide

  • Determinism: same inputs, same outputs. Pin tool versions, lock dependencies.
  • Idempotence: re-running a deploy for the same version is safe.
  • Clear failure signal: non-zero exit code means stop; logs say why.
  • Timeouts so hung jobs do not run forever.
  • Isolation: no dependence on state left by earlier runs.

A pipeline in pseudo-YAML

# tool-agnostic sketch
on: [pull_request, push to main]

jobs:
  lint:        {runs: "npm run lint"}
  test:        {runs: "npm test",         needs: []}
  build:       {runs: "npm run build",    needs: [lint, test],  outputs: [dist/]}
  scan:        {runs: "trivy fs .",       needs: [build]}
  package:     {runs: "docker build -t app:$SHA .", needs: [scan]}
  publish:     {runs: "docker push app:$SHA",       needs: [package], only: main}
  deploy-stg:  {runs: "deploy app:$SHA staging",    needs: [publish], env: staging}
  smoke:       {runs: "curl -f https://stg/health", needs: [deploy-stg]}
  deploy-prod: {runs: "deploy app:$SHA production", needs: [smoke],  env: production, approval: true}

Pitfalls

  • One enormous job. No parallelism, hard to read failures.
  • Order that wastes time: running a 10-minute build before a 5-second lint.
  • Relying on cache for correctness. It can be evicted; builds must work cold.
  • Rebuilding per stage. Pass the artifact (or image digest) instead.
  • Mutable tags (latest) between publish and deploy. Deploy by immutable SHA or digest.
  • No verification after deploy. A deploy job that exits 0 only means the command ran, not that the app is healthy.
  • Environment logic hard-coded in scripts with if branch == main sprinkled everywhere; use the platform's rules/conditions.

Try it

  1. Draw your project's pipeline using the stage table. Which stages are missing? Which run in the wrong order?
  2. For each stage, note its duration from a recent run. Find the critical path (the longest chain of dependent jobs); that, not the sum, is your pipeline time.
  3. Decide for each of these whether it belongs in a cache or an artifact: node_modules, dist/, JUnit XML, a Docker image layer, a downloaded Go module.
