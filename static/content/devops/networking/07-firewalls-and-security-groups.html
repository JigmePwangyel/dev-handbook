Firewalls and Security Groups

The moment a server gets a public IP, automated scanners find it, usually within minutes. A firewall decides which network traffic is allowed in and out. The guiding principle is simple: expose only what must be exposed.

The problem

A default server may run SSH, a database, a metrics endpoint, and a debug port, all listening on every interface. Each open port is attack surface. Real incidents: Redis or MongoDB listening publicly with no password (instantly ransomed), Elasticsearch dumps leaking millions of records, SSH brute force. Many are not software bugs, only things that should never have been reachable.

Firewalls enforce least exposure: deny everything by default, then allow specific ports from specific sources.

How packet filtering works

A firewall matches each packet (or connection) against an ordered rule list using source/destination IP, port and protocol, then ACCEPTs, DROPs (silently discard; scanner sees a timeout) or REJECTs (reply with an error; sees "refused").

  • Stateful firewalls track connections. If you allowed an outbound request, the reply is automatically allowed back in. Almost everything today (iptables conntrack, nftables, security groups) is stateful.
  • Stateless filters (AWS Network ACLs) evaluate each packet in isolation, so you must allow both directions including ephemeral return ports.

Default policy matters most: default deny inbound, allow outbound.

Layers of defence

 Internet
    │
    ▼

Defence in depth: any single layer may be misconfigured; several rarely fail together.

ufw: the simple host firewall (Ubuntu)

ufw ("uncomplicated firewall") is a friendly front-end for the kernel's netfilter. Critical: allow SSH before enabling, or you lock yourself out of a remote machine.

sudo ufw status verbose
sudo ufw default deny incoming
sudo ufw default allow outgoing

sudo ufw allow OpenSSH              # or: sudo ufw allow 22/tcp
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw allow 443/udp              # HTTP/3

# Restrict SSH to your office/home IP (better) and rate-limit brute force
sudo ufw allow from 203.0.113.7 to any port 22 proto tcp
sudo ufw limit 22/tcp               # alternative: throttle repeated connection attempts

# Allow DB only from the app server's private IP
sudo ufw allow from 10.0.1.11 to any port 5432 proto tcp

sudo ufw enable
sudo ufw status numbered
sudo ufw delete 3                   # delete rule number 3
Docker bypasses ufw

Docker inserts its own iptables rules for published ports (-p 8080:80), and they are evaluated before ufw's. A container published like that is reachable from the internet even though ufw status shows it denied. Bind to loopback instead (-p 127.0.0.1:8080:80), put a cloud security group in front, or manage rules in the DOCKER-USER chain.

iptables and nftables: the concept

Underneath ufw is the kernel's netfilter. iptables (older) and nftables (current default on modern distros; iptables is often a compatibility shim) organise rules into tables and chains. The main chains for a host: INPUT (to this machine), OUTPUT (from it), FORWARD (routed through it, e.g. container traffic). Rules are checked top to bottom; first match wins; then the chain's default policy applies.

# Show rules
sudo iptables -L -n -v --line-numbers

# A minimal stateful ruleset (conceptual)
sudo iptables -A INPUT -i lo -j ACCEPT
sudo iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
sudo iptables -A INPUT -p tcp --dport 22  -j ACCEPT
sudo iptables -A INPUT -p tcp --dport 443 -j ACCEPT
sudo iptables -P INPUT DROP          # default policy: drop everything else
# nftables equivalent
table inet filter {
  chain input {
    type filter hook input priority 0; policy drop;
    iif lo accept
    ct state established,related accept
    tcp dport { 22, 80, 443 } accept
  }
}

Rules set with these commands vanish on reboot unless persisted (netfilter-persistent, or /etc/nftables.conf). Most people should use ufw/firewalld or cloud security groups and learn raw iptables only for debugging.

Cloud security groups

A security group (AWS; GCP calls them firewall rules, Azure NSGs) is a stateful firewall enforced by the hypervisor around each instance's network interface. You only write allow rules; anything not allowed is denied. Rules specify protocol, port range and a source: a CIDR or another security group.

The security-group-as-source feature is the key to clean architecture:

  0.0.0.0/0 ──443──▶ [ sg-alb ]
                          │ 3000 (source: sg-alb)
                          ▼
                     [ sg-app ]
                          │ 5432 (source: sg-app)
                          ▼
                     [ sg-db ]       no public IP at all, private subnet
  Your IP/32 ──22──▶ bastion/SSM    (or use SSM Session Manager and open no SSH at all)
GroupInbound rules
sg-albTCP 80, 443 from 0.0.0.0/0 and ::/0
sg-appTCP 3000 from sg-alb; TCP 22 from your admin IP only
sg-dbTCP 5432 from sg-app. Nothing else.

Even if someone learns the database IP, the network will not let them connect. AWS CLI example:

aws ec2 authorize-security-group-ingress --group-id sg-0app \
    --protocol tcp --port 3000 --source-group sg-0alb
aws ec2 authorize-security-group-ingress --group-id sg-0app \
    --protocol tcp --port 22 --cidr 203.0.113.7/32

Compare with Network ACLs: stateless, subnet-level, allow and deny rules, evaluated in numeric order. Use as a coarse second layer (for example to block a hostile CIDR); do most work in security groups.

Least exposure checklist

  1. Inventory: sudo ss -tlnp on every server. For each listener ask "does it need to exist, and for whom?"
  2. Bind to localhost or a private IP when the only client is local or internal. Databases: listen_addresses = 'localhost' in Postgres unless remote access is required; Redis bind 127.0.0.1 and requirepass.
  3. Public ports: 80 and 443 only. Not 3000, not 5432, not 6379, not 9090 (Prometheus), not 2375 (Docker API, equivalent to root).
  4. SSH: keys only, PasswordAuthentication no, PermitRootLogin no, restrict by source IP or use a VPN/bastion/SSM; optionally fail2ban.
  5. Egress: allow outbound by default, but sensitive environments restrict it to limit data exfiltration and malware calling home.
  6. Use private subnets for databases and internal services; use a NAT gateway for their outbound needs.
  7. Audit regularly: security groups with 0.0.0.0/0 on anything but 80/443 deserve a ticket. Tools: AWS Config rules, Security Hub, Trivy/Prowler, nmap.

Verifying from the outside

# From a machine OUTSIDE your network: what does the world see?
nmap -Pn -p 1-1000 your.server.ip           # scan only systems you own or are authorised to test
nmap -Pn -p 22,80,443,3000,5432,6379 your.server.ip
nc -zv -w 3 your.server.ip 5432             # expect timeout (dropped), not open

# On the server: what is actually listening, and which rules are active?
sudo ss -tlnp
sudo ufw status verbose

Interpreting nmap states: open (something answered), closed (reachable host, nothing listening: RST), filtered (packets dropped by a firewall). A DROP policy yields filtered, which also slows scanners down.

Pitfalls

  • Locking yourself out by enabling a firewall without an SSH rule. Cloud consoles can fix it; bare VPSs often need a recovery console. Keep a second session open while testing.
  • "Temporary" 0.0.0.0/0 rules that become permanent. Add a description and an owner to every rule.
  • Dynamic home IPs in SSH allow-lists: you get locked out when it changes. Use a VPN with a fixed address or SSM.
  • Forgetting IPv6: a rule for 0.0.0.0/0 but none for ::/0 (or vice versa), or ufw IPv6 disabled while the service listens on ::.
  • Firewall as the only protection: services should still authenticate. Internal networks get breached too.
  • Debugging blind: dropped packets produce timeouts and no log. Enable VPC Flow Logs or ufw logging on to see rejects.

Try it

  1. On a throwaway Ubuntu VM or VPS, keep one SSH session open, then apply: ufw default deny incoming, ufw allow OpenSSH, ufw allow 80,443/tcp, ufw enable. Open a second SSH session to confirm you can still get in.
  2. Run python3 -m http.server 8000 on the box. From your laptop, curl it: it should time out. Then sudo ufw allow 8000/tcp and retry. Remove the rule afterwards.
  3. From your laptop, run nmap -Pn -p 22,80,443,8000,5432 SERVER_IP before and after. Note the open/filtered states.
  4. In a cloud account, sketch the three security groups from this lesson and write the exact inbound rules. Which instances need a public IP? (Answer: only the load balancer, and possibly none other.)
  5. Run sudo ss -tlnp on a server you own and justify each listening port or close it.
