DNS: The Internet's Phone Book

Humans use names like app.example.com; networks use IP addresses. DNS translates between them. It is also the root cause of a startling share of outages, and the lever you pull for most deployment cutovers.

Why DNS exists

Without DNS you would give users 203.0.113.10. When you moved servers, every user and every config file would need updating. DNS adds a level of indirection: users hold a stable name, and you change what it points to. Almost every migration, failover and traffic-shifting trick relies on this indirection.

How resolution works

When your laptop looks up www.example.com, several parties cooperate:

 Browser ──▶ OS stub resolver ──▶ Recursive resolver (ISP, 1.1.1.1, 8.8.8.8)
                                        │ (cache miss)
              1. ask a ROOT server ─────┤  "who handles .com?"       → TLD servers
              2. ask a .com TLD server ─┤  "who handles example.com?" → authoritative NS
              3. ask example.com's      │
                 AUTHORITATIVE server ──┘  "www.example.com?"        → 203.0.113.10
                                        │
                      answer cached for TTL seconds, returned to you
  • Stub resolver: the tiny client in your OS. It forwards the question and caches briefly.
  • Recursive resolver: does the legwork and caches answers for many users.
  • Root servers: know only who runs each top-level domain.
  • TLD servers: know which name servers are authoritative for each domain under them.
  • Authoritative servers: hold the real records. Your DNS provider (Cloudflare, Route 53, your registrar) runs these.

Caching at every level is why DNS is fast, and also why changes are not instant.

The apex CNAME problem

A CNAME cannot coexist with other records at the same name, and the zone apex (example.com itself) must have SOA and NS records. So you cannot put a standard CNAME at the apex. Solutions: use an A record at the apex; or use your provider's proprietary "ALIAS"/"ANAME"/"CNAME flattening" (Route 53 Alias, Cloudflare flattening) which resolves the target server-side and returns A records.

TTL and "propagation"

Every record has a TTL (time to live, in seconds): how long resolvers may cache it. TTL 300 means "reuse this answer for up to 5 minutes."

"DNS propagation" is a misleading term. Nothing is pushed anywhere. Your authoritative server changes instantly; the delay is the world's recursive resolvers still holding the old answer until their cached copy expires. A change from IP X to IP Y takes up to the old TTL to be seen everywhere. Some resolvers and ISPs ignore low TTLs, and browsers and JVMs add their own caches.

The migration playbook

24 to 48 hours before a planned cutover, lower the TTL to 60 to 300 seconds. Wait out the old TTL. Switch the record. Verify. Later raise the TTL again (3600 or more) to reduce query load and improve resilience. Lowering the TTL at the moment of cutover does nothing: caches already hold the old value with the old TTL.

TTLProsCons
60 to 300 sFast failover and cutoverMore queries; slightly slower first lookups
3600 s (1 h)Good default for stable recordsHour-long wait to change
86400 s (1 day)Cheapest; resilient to DNS provider hiccupsPainful to change

Negative caching: a lookup for a name that does not exist (NXDOMAIN) is also cached, for the SOA's minimum TTL. If you query a hostname before creating its record, you may keep seeing "not found" for a while.

dig: your main tool

# Full answer with all sections
dig example.com

# Just the answer
dig +short example.com
dig +short AAAA example.com
dig +short MX example.com
dig +short TXT example.com
dig +short CNAME www.example.com

# Ask a specific resolver (bypass your local cache/ISP)
dig @1.1.1.1 example.com
dig @8.8.8.8 example.com

# Ask the authoritative server directly: the source of truth, no caching
dig NS example.com +short
dig @ns1.dnsprovider.com example.com

# Follow the whole delegation chain from the root
dig +trace example.com

# Reverse lookup
dig -x 203.0.113.10 +short

Reading the full output:

;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 4321
;; ANSWER SECTION:
example.com.   287   IN   A   203.0.113.10
;;             ^^^ remaining TTL (counts down on each query to the same cache)

;; Query time: 12 msec
;; SERVER: 1.1.1.1#53(1.1.1.1)

Key statuses: NOERROR (ok, possibly with an empty answer), NXDOMAIN (name does not exist), SERVFAIL (resolver could not get a valid answer; often a broken DNSSEC setup or dead name servers), REFUSED. Alternatives: nslookup, host, and resolvectl query on systemd systems.

Setting up a domain for your app

  1. Register the domain with a registrar (Namecheap, Cloudflare Registrar, Porkbun, Route 53 Domains).
  2. Choose where DNS is hosted. The registrar's default or a dedicated provider. At the registrar, set the domain's NS records (delegation) to the provider's name servers.
  3. Create records in that provider's zone:
@     300  A      203.0.113.10        ; example.com
www   300  CNAME  example.com.        ; www.example.com
api   300  A      203.0.113.20        ; api.example.com
@     300  CAA    0 issue "letsencrypt.org"

Note: NS records at the registrar (delegation) and the records in the zone are two different things. Beginners edit the wrong place and see no effect. Check with dig NS example.com +short to see who really is authoritative.

DNS as a deployment tool

  • Cutover: point the name at the new server.
  • Weighted routing (Route 53, Cloudflare): 5 percent of answers to the new stack. A crude canary.
  • Health-checked failover: the provider stops returning an unhealthy IP.
  • Geo/latency routing: answer with the nearest region.
  • Wildcards: *.example.com catches all subdomains (useful for preview environments per pull request).
  • Split-horizon: internal resolvers return private IPs for the same name that resolves publicly elsewhere. Cloud private zones (Route 53 private hosted zones) do this.

Limit: DNS-based traffic shifting is coarse, because clients cache answers and you cannot drain instantly. Load balancers (see that lesson) are the precise tool.

Pitfalls

  • Trailing dots: in zone files example.com. is absolute; example.com without a dot gets the zone name appended (example.com.example.com.). Web UIs usually hide this, but file-based zones bite.
  • CNAME at apex or alongside MX/TXT breaks mail and verification.
  • Dangling records: a CNAME to a deleted cloud resource can be claimed by an attacker (subdomain takeover). Clean up DNS when you delete infrastructure.
  • Expired domains take everything down. Enable auto-renew and keep a valid payment method.
  • Forgetting the local cache: your machine may still hold the old answer. Flush with sudo resolvectl flush-caches (Linux) or sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder (macOS). Test with dig @1.1.1.1 instead.
  • Single DNS provider is a single point of failure for the entire company. Large organisations use two.
  • Testing before DNS is ready: use curl --resolve app.example.com:443:203.0.113.10 https://app.example.com/ or temporarily edit /etc/hosts.
DNSSEC and DoH

DNSSEC signs records so resolvers can detect tampering (a misconfiguration can make your domain fail to resolve entirely, so enable it deliberately and keep DS records in sync). DNS over HTTPS/TLS encrypts the client-to-resolver hop for privacy. Neither changes how records work.

Try it

  1. Run dig +trace github.com and identify the root, TLD and authoritative steps.
  2. Run dig github.com twice a few seconds apart and watch the TTL count down.
  3. Find a domain's mail servers (dig +short MX gmail.com), name servers and SPF record (dig +short TXT gmail.com).
  4. Compare dig @1.1.1.1 +short example.com with dig @8.8.8.8 +short example.com for a CDN-fronted site; you may see different IPs (geo routing).
  5. Test a site without DNS: curl -I --resolve example.com:443:93.184.215.14 https://example.com/.
  6. If you own a domain, create a test record test.yourdomain.com with TTL 60, change its value, and time how long dig takes to show the new value.
