HTTP and HTTPS

HTTP is the language your app, browser, reverse proxy, load balancer and CDN all speak. Knowing it well turns mysterious 502s, stale caches and CORS errors into five-minute fixes.

Why learn the protocol and not just the framework

Frameworks hide HTTP. But in production the request passes through a CDN, a load balancer and nginx before reaching your code. Each hop reads and rewrites headers, enforces timeouts and returns its own errors. To debug, you must see the raw conversation.

Anatomy of a request and response

GET /api/users/42?include=orders HTTP/1.1
Host: api.example.com
User-Agent: curl/8.7.1
Accept: application/json
Authorization: Bearer eyJhbGciOi...

HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 87
Cache-Control: private, max-age=0
ETag: "a1b2c3"

{"id":42,"name":"Ada","orders":[]}

A request has a method, a path+query, headers and an optional body. A response has a status code, headers and a body. The Host header is how one IP address serves many sites (virtual hosting): nginx picks the config by it.

Idempotency matters operationally: a load balancer or client may retry idempotent requests automatically after a failure. A retried POST can double-charge a customer unless you use an idempotency key.

Decoding the gateway errors

502: the proxy reached the upstream but got garbage or the connection was refused/reset (your app crashed or is not listening). 503: no healthy upstream, or the service is deliberately overloaded or in maintenance. 504: the upstream accepted the request but did not answer in time (slow query, timeout too short). 502 and 504 are the proxy telling you the problem is behind it. Look at the app logs.

Caching headers

Caching is the cheapest performance and scalability feature you have. HTTP defines it precisely.

# Immutable, fingerprinted assets (app.3f9c1a.js): cache a year, never revalidate
Cache-Control: public, max-age=31536000, immutable

# HTML pages: always check with the server, but allow cheap 304s
Cache-Control: no-cache
ETag: "v123"

# Per-user API data: never store in shared caches (CDN)
Cache-Control: private, no-store

# Let CDN cache 60s, browser not at all
Cache-Control: public, max-age=0, s-maxage=60

# Serve stale while refreshing in the background
Cache-Control: public, max-age=60, stale-while-revalidate=300
DirectiveMeaning
max-age=NFresh for N seconds in any cache
s-maxage=NLike max-age but only for shared caches (CDN, proxy)
no-cacheMay store, but must revalidate before each use (confusing name)
no-storeDo not store at all
public / privateShared caches allowed / browser only
immutableWill never change; skip revalidation

Revalidation: the server sends ETag: "abc" (or Last-Modified). The client later sends If-None-Match: "abc"; if unchanged the server answers 304 Not Modified with no body. Vary: Accept-Encoding tells caches the response differs per that request header; a wrong Vary causes serving the wrong variant.

Best practice: fingerprint static file names with a content hash so they can be cached forever, and keep the HTML short-lived so a deploy takes effect immediately.

Connections: keep-alive, HTTP/1.1, HTTP/2, HTTP/3

A new TCP+TLS connection costs several round trips. Keep-alive (default in HTTP/1.1) reuses a connection for many requests. Between nginx and your app, enable upstream keep-alive too, or you pay connection setup on every proxied request.

VersionTransportKey ideasWeakness
HTTP/1.1TCPText protocol, keep-alive, one request at a time per connection (browsers open ~6 connections)Head-of-line blocking at HTTP level
HTTP/2TCP + TLSBinary, multiplexed streams on one connection, header compression (HPACK)One lost TCP packet stalls all streams
HTTP/3QUIC over UDPIndependent streams, faster handshake (1-RTT, 0-RTT resumption), connection migration (Wi-Fi to cellular)UDP sometimes blocked; needs UDP 443 open

Typically TLS terminates at the CDN/load balancer/nginx which speaks HTTP/2 or 3 to browsers and plain HTTP/1.1 to your app. Your app rarely needs to care. Browsers discover HTTP/3 via the Alt-Svc response header and fall back gracefully.

HTTPS in one paragraph

HTTPS is HTTP carried inside a TLS-encrypted connection. It provides confidentiality (no eavesdropping), integrity (no tampering) and authentication (you are talking to the real example.com). It is mandatory today: browsers mark HTTP as insecure, HTTP/2 in browsers requires it, and many browser APIs only work on secure origins. The next lesson covers how TLS works. Operationally:

  • Redirect all HTTP to HTTPS (301/308).
  • Send Strict-Transport-Security: max-age=31536000; includeSubDomains once you are confident (a mistake is sticky for the max-age).
  • Mark cookies Secure.
  • Avoid mixed content (an HTTPS page loading HTTP assets gets blocked).

Behind a proxy: the scheme and client IP problem

If TLS ends at nginx and your app sees plain HTTP from 127.0.0.1, then req.protocol is http and req.ip is 127.0.0.1. Redirect loops and wrong rate limiting follow. Fix: the proxy sets X-Forwarded-* and the app trusts exactly that proxy:

// Express
app.set('trust proxy', 1);   // trust one hop (nginx). Don't use `true` blindly.
// now req.ip is the real client IP and req.secure reflects X-Forwarded-Proto

Timeouts

Every hop has them, and the smallest wins. Typical defaults: nginx proxy_read_timeout 60 s, AWS ALB idle timeout 60 s, Cloudflare 100 s. Long-running work (report generation, uploads) should return 202 Accepted and complete in a background job rather than hold a connection open. Make your app's keep-alive timeout longer than the load balancer's idle timeout, or you will see sporadic 502s when the app closes a connection the LB believes is still open (Node's server.keepAliveTimeout defaults to 5 s, a classic ALB 502 cause).

curl for HTTP debugging

curl -i https://example.com/               # include response headers
curl -I https://example.com/               # HEAD request only
curl -v https://example.com/               # verbose: TLS, request, response
curl -sS -o /dev/null -w '%{http_code} %{time_total}s\n' https://example.com/
curl -X POST https://api.example.com/items \
     -H 'Content-Type: application/json' -d '{"name":"widget"}'
curl -L https://example.com/               # follow redirects
curl --http2 -I https://example.com/       # force a protocol (also --http3 if built in)
curl -H 'Accept-Encoding: gzip' -I https://example.com/   # check compression
curl -I -H 'Origin: https://other.com' https://api.example.com/   # check CORS headers

Pitfalls

  • Returning 200 with an error body, which breaks monitoring and retries. Use correct status codes.
  • Using 301 for something you may change: browsers cache permanent redirects aggressively.
  • Caching authenticated responses on a CDN. Always set Cache-Control: private or no-store for personalised data.
  • Trusting X-Forwarded-For from the open internet: clients can forge it. Only accept it from your proxy.
  • CORS is enforced by browsers, not servers; curl working does not mean the browser will.

Try it

  1. Run curl -v https://example.com/ 2>&1 | less. Find the TLS version, the negotiated protocol (ALPN: h2), the status and the headers.
  2. Run curl -I https://github.com/ and list the security and caching headers. Which have max-age?
  3. Fetch a static asset from a big site twice with curl -I and look for Age, X-Cache or CF-Cache-Status headers that reveal CDN caching.
  4. Test revalidation: take an ETag from a response and send curl -I -H 'If-None-Match: "THE-ETAG"' URL. Expect 304.
  5. Write a 10-line Express app that returns different Cache-Control headers on two routes and observe browser behaviour in DevTools (Network tab, "Disable cache" off).
