Load Balancers

One server is a single point of failure and a scaling ceiling. A load balancer spreads traffic over many servers, removes unhealthy ones automatically, and lets you deploy without downtime.

The problem

With one app server: when it crashes, you are down; when you deploy, you are down; when traffic doubles, you are slow. Adding a second server does not help by itself, because clients need a single address to talk to. A load balancer (LB) is that address. It accepts connections and forwards each to one of several backends.

                         ┌──▶ app-1  10.0.1.11:3000   healthy
 Clients ──▶  LB ────────┼──▶ app-2  10.0.1.12:3000   healthy
 (one address)  │        └──▶ app-3  10.0.1.13:3000   FAILED health check: removed from rotation
                │
                └─ periodically probes GET /health on each backend

Benefits: availability (failed nodes bypassed), scalability (add nodes), zero-downtime deploys (drain one node at a time), TLS offload, a single place for logging and WAF rules.

Layer 4 vs Layer 7

SpeedVery fast, millions of connectionsMore CPU (parses and often terminates TLS)
FeaturesPass-through, any protocol (Postgres, MQTT, SMTP, gRPC raw)Path/host routing, redirects, header rewrite, WAF, sticky cookies, HTTP/2 to HTTP/1.1

Rule of thumb: use L7 for web apps and APIs (routing by path is invaluable: /api to one pool, / to another). Use L4 for non-HTTP protocols, extreme throughput, static IPs, or when you must preserve end-to-end TLS.

AlgorithmHowBest for / caveat

Least connectionsSend to the server with fewest active connectionsLong or uneven requests, WebSockets

Random (power of two choices)Pick two at random, take the less loadedLarge pools; avoids herd effects

Health checks

The LB is only as good as its health checks. Two kinds:

  • Passive: observe real traffic; mark a backend down after N failures (nginx max_fails).
  • Active: the LB probes an endpoint on an interval (HAProxy check, ALB target group health checks).

Typical settings: probe every 5 to 10 s, mark unhealthy after 2 to 3 failures, healthy after 2 to 5 successes, timeout 2 to 5 s.

// A useful /health endpoint (Express)
app.get('/health', async (req, res) => {
  try {
    await db.query('SELECT 1');           // can I do my job?
    res.status(200).json({ status: 'ok', version: process.env.GIT_SHA });
  } catch (e) {
    res.status(503).json({ status: 'degraded' });
  }
});
Shallow vs deep health checks

A check that only returns 200 hides a broken database connection. But a check that fails whenever any dependency (a third-party API) is down can make the LB eject every node at once, turning a partial outage into a total one. Prefer: liveness (process responds) for restart decisions, readiness (can serve traffic: DB reachable, caches warm) for LB membership, and never check non-essential dependencies.

Connection draining

When removing a node (deploy, scale-in) the LB should stop sending new requests but let in-flight ones finish: "connection draining" (ALB: deregistration delay, default 300 s; lower it to match your longest request). Combined with graceful shutdown in your app (see the zero-downtime lesson), deploys drop no requests.

Session stickiness

If the app keeps user session state in server memory, the user must keep hitting the same server, or they appear logged out. Options:

  • Sticky sessions: LB sets a cookie (ALB duration-based or app cookie; HAProxy cookie SERVERID insert) or hashes the client IP.
  • Externalise state (preferred): sessions in Redis or a database, or stateless signed tokens (JWT). Any server can then handle any request.

Stickiness hurts: uneven load, lost sessions when a node dies, awkward scaling and draining. Treat it as a stopgap and design services stateless (a core 12-factor principle).

nginx as a simple load balancer

upstream app_pool {
    least_conn;
    server 10.0.1.11:3000 weight=3 max_fails=3 fail_timeout=15s;
    server 10.0.1.12:3000 weight=1;
    server 10.0.1.13:3000 backup;          # used only if the others are down
    keepalive 64;
}
server {
    listen 80;
    location / {
        proxy_pass http://app_pool;
        proxy_next_upstream error timeout http_502 http_503;   # retry another node
        proxy_next_upstream_tries 2;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
    }
}

Open-source nginx has only passive health checks (active probes need nginx Plus). Be careful with proxy_next_upstream and non-idempotent requests: nginx does not retry POST by default after the request was sent unless you add non_idempotent.

HAProxy example

HAProxy is a dedicated, extremely efficient LB with rich active health checks and stats.

# /etc/haproxy/haproxy.cfg
global
    log /dev/log local0
    maxconn 20000

defaults
    mode http
    log global
    option httplog
    timeout connect 5s
    timeout client  30s
    timeout server  30s

frontend https_in
    bind :80
    bind :443 ssl crt /etc/haproxy/certs/example.pem alpn h2,http/1.1
    http-request redirect scheme https unless { ssl_fc }
    http-request set-header X-Forwarded-Proto https if { ssl_fc }

    acl is_api path_beg /api
    use_backend api_pool if is_api
    default_backend web_pool

backend web_pool
    balance roundrobin
    option httpchk GET /health
    http-check expect status 200
    server web1 10.0.1.11:3000 check inter 5s fall 3 rise 2
    server web2 10.0.1.12:3000 check inter 5s fall 3 rise 2

backend api_pool
    balance leastconn
    cookie SERVERID insert indirect nocache      # sticky sessions
    option httpchk GET /health
    server api1 10.0.1.21:4000 check cookie a1
    server api2 10.0.1.22:4000 check cookie a2

listen stats
    bind 127.0.0.1:8404
    stats enable
    stats uri /stats
haproxy -c -f /etc/haproxy/haproxy.cfg    # validate
sudo systemctl reload haproxy

Managed load balancers (AWS example)

ServiceLayerNotes
ALB (Application LB)L7Host/path routing, TLS via ACM certs, WebSockets, gRPC, auth via OIDC, WAF integration, target groups (instances, IPs, Lambda, containers)
NLB (Network LB)L4Static IPs, ultra-low latency, TCP/UDP/TLS
GWLBL3Insert firewall appliances

Key ALB concepts: listeners (port 443 with a certificate) have rules (if host is api.example.com or path is /img/*) that forward to target groups, each with a health check config. Put the ALB in at least two Availability Zones, targets in private subnets, and a security group allowing 80/443 from the internet while the targets allow traffic only from the ALB's security group. GCP (Cloud Load Balancing) and Azure (Application Gateway / Front Door) offer equivalents; Kubernetes Ingress and Service type LoadBalancer provision them for you.

Is the load balancer itself a single point of failure?

Yes, if you run one. Solutions: managed LBs are redundant across zones by design; self-hosted ones use two nodes with a floating IP (keepalived/VRRP), or DNS with multiple A records, or anycast. This is why teams usually pay for the managed one.

Pitfalls

  • Real client IP lost: backends see the LB's IP. Use X-Forwarded-For (L7) or the PROXY protocol (L4).
  • Idle timeout mismatches: app keep-alive shorter than LB idle timeout causes sporadic 502/504.
  • Uneven deploys: new version unhealthy but health check too shallow: LB sends traffic to broken nodes.
  • Thundering herd after restart: all nodes start cold and are marked healthy before caches/JIT are warm. Use slow-start (ALB slow start mode, HAProxy slowstart).
  • Retry storms: aggressive retries on a struggling backend amplify the overload.
  • Stateful in-memory data (uploads on local disk, in-memory sessions or caches) breaks the moment there are two servers.

Try it

  1. Start three tiny backends that print their port: for p in 3001 3002 3003; do (python3 -m http.server $p --bind 127.0.0.1 &); done (or three Node processes returning their PID).
  2. Configure the nginx upstream above with those ports. Request repeatedly: for i in $(seq 6); do curl -s localhost/ | head -1; done and watch the distribution; try weight and least_conn.
  3. Kill one backend. Observe failed requests (and then none, once nginx has marked it down or retried with proxy_next_upstream).
  4. Install HAProxy, use the config above with check, open the stats page and watch a backend flip to DOWN when stopped.
  5. Write down: which of your app's state lives in memory or on local disk and would break behind a load balancer?
