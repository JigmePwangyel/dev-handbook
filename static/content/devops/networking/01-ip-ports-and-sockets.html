IP Addresses, Ports and Sockets

Every deployment problem eventually becomes "can machine A reach machine B on port N?" This lesson gives you the mental model and the commands to answer that question in seconds instead of hours.

Why this matters

You deploy an app, open the browser and get "connection refused" or a spinning timeout. Without a networking model you can only guess. With one, you can ask precise questions: Is the process listening? On which address? Is a firewall dropping packets? Does DNS point at the right machine? Each question maps to a layer and a tool.

The layers you actually need

 Application   HTTP, SSH, Postgres protocol      (your code, nginx)
 Transport     TCP / UDP  + port numbers         (the OS kernel)
 Network       IP addresses + routing            (routers)
 Link          Ethernet / Wi-Fi frames           (switches, NICs)

The full OSI model has seven layers, but in practice you reason about four: link, IP, TCP/UDP, application. "L4 load balancer" and "L7 load balancer" (later lessons) refer to the transport and application layers.

IP addresses

An IP address identifies a network interface. It is how packets find their destination across routers.

  • IPv4: 32 bits, written 203.0.113.10. About 4.3 billion addresses, which ran out, hence NAT and IPv6.
  • IPv6: 128 bits, written 2001:db8::1. Effectively unlimited. Most clouds and CDNs support it; many home networks do too.

Public vs private addresses

Range (CIDR)Use
10.0.0.0/8Private (large networks, cloud VPCs)
172.16.0.0/12Private (Docker uses 172.17.0.0/16 by default)
192.168.0.0/16Private (home routers)

169.254.0.0/16Link-local (cloud metadata service at 169.254.169.254)

Private addresses are not routable on the internet. A NAT gateway (your home router, or a cloud NAT gateway) rewrites outgoing packets to a public address. That is why your laptop at 192.168.1.20 can browse the web but nobody can connect to it directly.

CIDR notation

10.0.1.0/24 means "the first 24 bits are the network, the last 8 bits are hosts", so 256 addresses (10.0.1.0 to 10.0.1.255). A /16 has 65,536 addresses, a /32 is exactly one host. You will see CIDR in firewall rules, security groups and VPC design.

/24256A subnet

/0All"Anywhere" (0.0.0.0/0)

Ports

An IP gets a packet to a machine. A port (0 to 65535) gets it to the right program on that machine. One process "listens" on a port; clients connect to it.

3306MySQLNever expose publicly

Ports 0 to 1023 are "privileged": on Linux only root (or a process with CAP_NET_BIND_SERVICE) may bind them. This is why you run your Node app on 3000 and let nginx (which binds 80/443) forward to it.

Sockets, TCP and UDP

A socket is the OS object that represents one end of a connection. A TCP connection is uniquely identified by a 4-tuple:

 (client IP, client port, server IP, server port)
 (198.51.100.7, 51514, 203.0.113.10, 443)

The client's port is an ephemeral port (roughly 32768 to 60999 on Linux) picked by the OS. One server port can serve thousands of clients because each connection has a different 4-tuple.

Refused vs timeout

"Refused" is good news: the network works and the machine answered, so the problem is the process. "Timeout" means something in the path is dropping your packets, almost always a firewall. Memorise this distinction; it halves your debugging time.

Listening addresses: the 0.0.0.0 trap

A server chooses which local address to bind:

  • 127.0.0.1: only reachable from the same machine. Perfect for an app behind nginx or a database that only the app uses.
  • 0.0.0.0: all IPv4 interfaces, reachable from anywhere the network allows. :: is the IPv6 equivalent.
  • A specific private IP such as 10.0.1.5: only that interface.
// Node/Express
app.listen(3000, '127.0.0.1');   // only nginx on the same box can reach it
app.listen(3000, '0.0.0.0');     // reachable from the network (needed inside Docker)

Two classic bugs: (1) the app binds 127.0.0.1 inside a Docker container, so published ports never work; (2) the database binds 0.0.0.0 on a public IP with a weak password, and gets found by scanners within hours.

Diagnostic toolbox

# What is listening on this machine? (-t tcp, -l listening, -n numeric, -p process)
sudo ss -tlnp
#  LISTEN 0 511 127.0.0.1:3000  0.0.0.0:*  users:(("node",pid=1234,fd=19))
#  LISTEN 0 511 0.0.0.0:80      0.0.0.0:*  users:(("nginx",pid=800,fd=6))

# Who is using port 3000?
sudo lsof -i :3000

# My addresses and routes
ip addr
ip route

# Can I open a TCP connection to host:port? (-z scan only, -v verbose)
nc -zv example.com 443

# Full HTTP exchange with timing
curl -v https://example.com/
curl -o /dev/null -s -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} total=%{time_total}\n' https://example.com/

# Path to a destination (where do packets stop?)
traceroute example.com      # or mtr example.com

# What is my public IP?
curl -s https://ifconfig.me

netstat is the older equivalent of ss; on macOS use lsof -iTCP -sTCP:LISTEN -n -P.

A debugging ladder

  1. Is the process up? systemctl status myapp, ss -tlnp | grep 3000.
  2. Does it answer locally? curl -i http://127.0.0.1:3000/ on the server.
  3. Does it answer from the server's public/private IP? Tests the bind address.
  4. Is the host firewall open? sudo ufw status.
  5. Is the cloud firewall open? Security group / network ACL.
  6. Does DNS point here? dig +short example.com.

Work outward from the process. The first failing step is your culprit.

Pitfalls

  • Hard-coding IPs. Cloud IPs change when instances are replaced. Use DNS names or service discovery.
  • Forgetting UDP. Opening 443/tcp but not 443/udp silently disables HTTP/3 (it falls back to HTTP/2, so it still works).
  • Port conflicts. EADDRINUSE means another process already has that port. Find it with ss or lsof.
  • Ephemeral port exhaustion. A client making huge numbers of short connections to one server can run out of source ports (TIME_WAIT pile-up). Fix with connection reuse (keep-alive, pooling).

Try it

  1. Run ip addr (Linux) or ifconfig (macOS). Identify your loopback and LAN addresses. Is your LAN address in a private range?
  2. Start a throwaway server: python3 -m http.server 8000 --bind 127.0.0.1. In another terminal run ss -tlnp | grep 8000 (or lsof -i :8000) and note the bind address.
  3. From another machine on your network (or by using your LAN IP), try to reach it. It should be refused or time out. Restart with --bind 0.0.0.0 and retry.
  4. Run nc -zv localhost 9999 (nothing is listening) and observe "refused". Compare with nc -zv -w 3 10.255.255.1 80, which should time out.
  5. Use the curl -w timing command against any site and identify which phase is slowest.
