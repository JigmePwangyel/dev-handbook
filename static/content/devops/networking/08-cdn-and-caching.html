CDNs and Caching

Physics sets a floor on latency: a round trip from Sydney to a server in Virginia costs roughly 200 ms, however fast your code is. A CDN puts copies of your content near users and absorbs traffic before it ever reaches your servers.

The problem a CDN solves

  • Latency: distance. Several round trips for TCP, TLS and HTTP add up.
  • Origin load: every image, script and font request hits your server. A traffic spike (front page of Hacker News) can topple it.
  • Bandwidth cost: egress from a cloud provider is expensive; CDN egress is usually cheaper, sometimes free.
  • Availability and attacks: DDoS traffic must be absorbed somewhere; a CDN's distributed network has far more capacity than one origin.

How a CDN works

A CDN is a globally distributed fleet of caching reverse proxies called edge servers (points of presence, PoPs). Your origin is your real server. Users are steered to a nearby edge, via anycast routing or DNS that answers with the closest PoP.

 User (Sydney) ──▶ Edge PoP (Sydney)
                      │
                      ├─ HIT:  has fresh copy → returns it in ~10 ms. Origin never sees the request.
                      │
                      └─ MISS: fetch from origin ───────────────▶ Origin (Virginia)
                               store copy (obey Cache-Control) ◀── response
                               return to user
 Next Sydney user: HIT.

Many CDNs add an intermediate shield / tiered cache layer so that dozens of edges missing at once result in one request to the origin, not dozens.

Setup in the common "proxy" model: you change your domain's DNS (or name servers) so www.example.com points at the CDN, which is configured with your origin address. Users hit the CDN; the CDN talks to you. Your origin firewall can then accept traffic only from the CDN's IP ranges.

What gets cached?

  • Static assets: JS, CSS, images, fonts, video segments, downloads. Cached by default by file extension in most CDNs.
  • HTML and API responses: only if you opt in or your headers allow it (Cache-Control: public, s-maxage=60). Hugely effective for public, read-heavy content (news, product pages, public APIs).
  • Never cache personalised or authenticated responses with shared caches. Mark them Cache-Control: private or no-store.

The cache key

The CDN decides "is this the same request?" using a cache key: normally scheme + host + path + query string. Rules matter:

  • Tracking parameters (?utm_source=...) make each URL unique and tank your hit ratio; configure the CDN to ignore them.
  • Vary: Accept-Encoding and Vary: Accept-Language multiply cache entries. Vary: Cookie effectively disables caching.
  • By default, requests with cookies or an Authorization header are often not cached; verify for your CDN.

Measure cache hit ratio (hits divided by total). For static sites aim for above 95 percent. Check responses for headers such as CF-Cache-Status: HIT (Cloudflare), X-Cache: Hit from cloudfront (CloudFront), or Age: 253 (seconds in cache).

Cache control: telling the CDN what to do

# Origin response headers

# Fingerprinted build artefacts: cache everywhere for a year
Cache-Control: public, max-age=31536000, immutable

# Public HTML or API: edge caches 5 min; browsers always revalidate
Cache-Control: public, max-age=0, s-maxage=300

# Serve stale content while refreshing, and keep serving it if origin errors
Cache-Control: public, s-maxage=60, stale-while-revalidate=300, stale-if-error=86400

# Personalised
Cache-Control: private, no-store

s-maxage targets shared caches (CDN) separately from the browser's max-age, allowing "CDN caches 5 minutes; users' browsers always ask the CDN". stale-if-error is a free resilience feature: if your origin falls over, users still see the last good copy.

Cache invalidation

"There are only two hard things in computer science: cache invalidation and naming things." When content changes, stale copies sit at hundreds of edges and in users' browsers. Strategies, best first:

  1. Cache busting by fingerprinting (best). Put a content hash in the file name: app.3f9c1a7b.js. A new build produces a new URL; old URLs stay cached harmlessly. Nothing to invalidate. Webpack, Vite, Next.js and most bundlers do this by default. Only the HTML that references the files needs a short TTL.
  2. Short TTLs for content that changes unpredictably: 30 to 300 s caps staleness and still shields the origin from spikes ("micro-caching").
  3. Purge by URL / tag / prefix / everything. Explicit API calls on content change. Tag-based purging (Cloudflare Cache-Tags, Fastly surrogate keys) lets you purge "all pages that mention product 42". Purge propagates in seconds to a minute, depending on the CDN.
  4. Versioned paths (/v2/api/...), with query strings (?v=123) as a weaker form.
# Cloudflare: purge specific URLs (API token with Cache Purge permission)
curl -X POST "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/purge_cache" \
  -H "Authorization: Bearer $CF_API_TOKEN" -H "Content-Type: application/json" \
  --data '{"files":["https://example.com/index.html","https://example.com/pricing"]}'

# Purge everything (use sparingly: the next minute hits your origin hard)
curl -X POST "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/purge_cache" \
  -H "Authorization: Bearer $CF_API_TOKEN" -H "Content-Type: application/json" \
  --data '{"purge_everything":true}'

# AWS CloudFront invalidation
aws cloudfront create-invalidation --distribution-id E123ABC --paths "/index.html" "/blog/*"
The deploy pattern for frontends

Upload hashed assets first (immutable, one-year cache), then upload the small index.html last (no-cache or a short s-maxage), and purge only index.html. Users then never see HTML pointing at assets that do not exist yet, and never see old assets that were cleaned up too early. Keep the previous build's assets around for a while: users with an old page open still request them.

Cloudflare in practice

Cloudflare is the most common starting point because the free tier is generous and setup is only a DNS change.

  1. Add your domain; Cloudflare scans existing DNS records. Change your registrar's NS to the two Cloudflare name servers.
  2. For each record, the cloud icon is Proxied (orange: traffic goes via Cloudflare, you get CDN/WAF and your origin IP is hidden) or DNS only (grey: plain DNS). Proxy web traffic; do not proxy SSH, mail or database hostnames (non-HTTP ports are not proxied on the free plan).
  3. SSL/TLS mode: use Full (strict): Cloudflare connects to your origin over HTTPS and validates the certificate (install a Let's Encrypt or Cloudflare Origin Certificate on the origin). Flexible mode sends plain HTTP to the origin and invites redirect loops and interception; avoid it.
  4. Turn on "Always Use HTTPS", HTTP/3, Brotli, and Auto Minify/Rocket features as appropriate. Add Cache Rules (what to cache, edge TTL, bypass for /admin and /api).
  5. Lock the origin: allow 80/443 only from Cloudflare's published IP ranges (cloudflare.com/ips), or use Authenticated Origin Pulls / Cloudflare Tunnel (cloudflared) so the origin needs no inbound ports at all.

Note: by default Cloudflare caches by file extension (static assets), not HTML. To cache HTML, add a Cache Rule ("Eligible for cache") and set edge TTL or respect origin headers.

Other CDNs: Amazon CloudFront (tight AWS integration, S3 origins with Origin Access Control), Fastly (instant purge, VCL/Compute programmability), Akamai (enterprise), Bunny.net (cheap, simple), Vercel/Netlify (built in).

More than caching

  • TLS termination near the user: the expensive handshake is short-haul; the CDN reuses long-lived connections to the origin.
  • DDoS mitigation and WAF: block bad traffic at the edge; rate limiting; bot management.
  • Image optimisation: resizing and converting to WebP/AVIF per device.
  • Edge compute (Cloudflare Workers, CloudFront Functions/Lambda@Edge, Fastly Compute): run small code at the edge for redirects, A/B tests, auth checks, header rewriting.
  • Origin failover and load balancing across origins.

Every layer is a place where stale data can hide. When "my change does not show up", walk the layers from the browser inwards: hard-refresh, curl -I to see the CDN status header, curl the origin directly, then check app caches.

Pitfalls

  • Caching a response that contains user data and serving it to others. This is a serious security incident. Default to private for anything personalised and test with two accounts.
  • Caching error pages: a transient 500 cached for an hour. Make sure errors are not cacheable, or use short negative TTLs.
  • Long TTL on non-fingerprinted files (style.css cached for a year, unfixable except by purge).
  • Origin IP leaks (old DNS records, mail headers) let attackers bypass the CDN. Firewall the origin to CDN ranges.
  • Purging everything during peak: cold cache plus full traffic equals an origin outage ("cache stampede"). Use request coalescing/tiered caching and purge selectively.
  • Treating CDN as a fix for a slow app: dynamic, uncacheable requests still go to your origin.
  • Cookies on static domains can make assets uncacheable. Serve static content from cookieless paths/hosts.

Try it

  1. Run curl -sI https://www.cloudflare.com/ | grep -iE 'cf-cache-status|age|cache-control|server'. Run it twice and watch Age.
  2. Compare headers for an HTML page versus a hashed asset (.js) on a large site. How do their Cache-Control values differ and why?
  3. Put a free Cloudflare account in front of a domain pointing at a small VPS. Request a static file twice and confirm cf-cache-status: HIT on the second.
  4. Change the file on the origin. Request it again: you get the old content. Purge that URL through the dashboard or API and fetch again.
  5. Add a hashed filename to a test asset instead of purging, and notice no purge is required.
  6. Restrict your origin's firewall (ufw allow from <CF range> to any port 443) and confirm direct access to the origin IP fails while the proxied domain works.
