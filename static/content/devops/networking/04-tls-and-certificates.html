TLS and Certificates

TLS is what makes the padlock appear. Operationally it is about one thing: getting a valid certificate onto your server and renewing it before it expires. Expired certificates are among the most common, most embarrassing and most preventable outages.

The problem TLS solves

Plain HTTP crosses many machines you do not control: Wi-Fi routers, ISPs, corporate proxies. Anyone along the path can read passwords and cookies, or alter the page. TLS (Transport Layer Security, the successor to SSL) gives you three guarantees:

  • Confidentiality: traffic is encrypted.
  • Integrity: tampering is detected.
  • Authentication: the server proves it is really example.com. Without this, an attacker could encrypt traffic to themselves and relay it (man-in-the-middle).

Authentication is the job of certificates.

Key ideas: asymmetric and symmetric crypto

  • Asymmetric (public/private key pairs): what the public key encrypts or verifies, only the private key can decrypt or sign. Slow, but solves "how do two strangers agree on a secret".
  • Symmetric (AES, ChaCha20): one shared key, very fast. Used for the bulk of the data.

TLS uses asymmetric techniques during the handshake to authenticate the server and agree on a shared secret, then switches to symmetric encryption.

The TLS 1.3 handshake

 Client                                            Server
   │── ClientHello ───────────────────────────────▶│  supported versions/ciphers,
   │     (SNI: example.com, key share, ALPN h2)    │  SNI = which hostname I want
   │                                               │
   │◀─ ServerHello (chosen cipher, key share) ─────│  both sides can now derive keys
   │◀─ {Certificate chain}  (encrypted) ───────────│  "here is my proof of identity"
   │◀─ {CertificateVerify}  (signature) ───────────│  proves I own the private key
   │◀─ {Finished} ─────────────────────────────────│
   │                                               │
   │── {Finished} ────────────────────────────────▶│
   │══ encrypted HTTP request/response ═══════════│

TLS 1.3 needs one round trip (TLS 1.2 needs two). The key agreement uses ephemeral Diffie-Hellman, which gives forward secrecy: even if the server's private key leaks later, recorded past traffic cannot be decrypted. SNI (Server Name Indication) is the hostname sent in the clear in ClientHello, which lets one IP host many certificates.

Disable TLS 1.0/1.1 (and SSLv3). Allow TLS 1.2 and 1.3.

Certificates and the chain of trust

A certificate is a signed statement: "this public key belongs to example.com", signed by a Certificate Authority (CA). Your browser/OS ships with a trust store of root CA certificates. Roots do not sign server certificates directly; they sign intermediate CAs, which sign yours:

 Root CA (in browser trust store, offline, long-lived)
    └── Intermediate CA (signs leaf certs)
           └── Leaf certificate: example.com, www.example.com   (yours, 90 days)

The server must send the leaf plus intermediates (the "full chain"). Missing intermediates is a common bug: it works in Chrome (which can fetch them) but fails in curl, Java or mobile apps.

A leaf certificate contains: the subject names (Subject Alternative Names, SANs, are what browsers check), the public key, validity dates, and the issuer's signature. Validation checks: signature chain to a trusted root, the name matches the host, the date is valid, not revoked.

Let's Encrypt and ACME

Let's Encrypt is a free, automated, non-profit CA. It uses the ACME protocol: your server proves it controls a domain by completing a challenge, and the CA issues a certificate with a short lifetime (90 days; the industry is moving toward even shorter lifetimes, so automation is not optional).

ChallengeHowUse when
HTTP-01CA fetches http://example.com/.well-known/acme-challenge/TOKEN on port 80Single public web server. Port 80 must be reachable. No wildcards.
DNS-01You publish a TXT record _acme-challenge.example.comWildcards; servers not publicly reachable. Needs DNS provider API access.
TLS-ALPN-01Special handshake on 443Port 80 unavailable

Rate limits exist (for example, a limited number of certificates per registered domain per week). Use the staging environment (--staging) while experimenting so you do not get locked out.

certbot on Ubuntu with nginx

# Prerequisites: DNS A record points to this server; ports 80 and 443 are open.
sudo apt update
sudo apt install -y certbot python3-certbot-nginx

# Obtain a cert AND let certbot edit your nginx server block
sudo certbot --nginx -d example.com -d www.example.com \
     --redirect --agree-tos -m you@example.com

# Or obtain only (you edit nginx yourself)
sudo certbot certonly --nginx -d example.com -d www.example.com

# Without a web server on the box (standalone mode: certbot binds port 80 briefly)
sudo certbot certonly --standalone -d example.com

# Wildcard via DNS-01 (example with the Cloudflare plugin)
sudo apt install -y python3-certbot-dns-cloudflare
sudo certbot certonly --dns-cloudflare \
     --dns-cloudflare-credentials /root/.secrets/cloudflare.ini \
     -d example.com -d '*.example.com'

Files land in /etc/letsencrypt/live/example.com/:

FileContains
fullchain.pemYour leaf cert plus intermediates. Use as ssl_certificate.
privkey.pemPrivate key. Use as ssl_certificate_key. Guard it; mode 600/root only.
cert.pem, chain.pemSeparate pieces (rarely needed)

These are symlinks into /etc/letsencrypt/archive/; always reference the live/ paths so renewals are picked up.

The nginx side

server {
    listen 443 ssl;
    listen 443 quic reuseport;          # HTTP/3 (nginx 1.25+), also open UDP 443
    http2 on;                           # nginx 1.25.1+ syntax
    server_name example.com www.example.com;

    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_session_cache   shared:SSL:10m;
    ssl_session_timeout 1d;
    add_header Strict-Transport-Security "max-age=31536000" always;
    add_header Alt-Svc 'h3=":443"; ma=86400' always;
    # ... location blocks ...
}
server {
    listen 80;
    server_name example.com www.example.com;
    return 301 https://$host$request_uri;
}

Renewal

The Ubuntu package installs a systemd timer (or cron job) that runs certbot renew twice a day. It renews only certificates within 30 days of expiry.

systemctl list-timers | grep certbot        # confirm the timer exists
sudo certbot renew --dry-run                # simulate renewal against staging: DO THIS
sudo certbot certificates                   # list certs and expiry dates

# Reload nginx after a successful renewal so it loads the new file
sudo tee /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh <<'EOF'
#!/bin/sh
systemctl reload nginx
EOF
sudo chmod +x /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh

The nginx plugin normally reloads nginx automatically, but a deploy hook makes it explicit and works for any setup. A server that renews the file but never reloads keeps serving the old, soon-expired certificate.

Why renewals fail in practice

Port 80 got firewalled or redirected oddly; DNS no longer points to this server; the DNS API token expired (DNS-01); nginx config changed so the challenge location is shadowed; disk full; the timer was never enabled. Always alert on days until expiry (monitoring a probe such as openssl s_client, Prometheus blackbox exporter, or your uptime tool) rather than trusting that renewal works.

Inspecting certificates

# What does the server present? (expiry, issuer, SANs)
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName

# Only the expiry
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null \
  | openssl x509 -noout -enddate

# Is the chain complete?
openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null

# Verbose TLS info via curl
curl -vI https://example.com/ 2>&1 | grep -iE 'TLS|subject|issuer|expire'

# Generate a self-signed cert for local testing
openssl req -x509 -newkey rsa:2048 -nodes -days 365 \
  -keyout dev.key -out dev.crt -subj "/CN=localhost"

Managed options (AWS ACM, Cloudflare, Caddy's automatic HTTPS, Kubernetes cert-manager) automate everything in this lesson. The concepts remain the same when they break.

Pitfalls and best practices

  • Serve fullchain.pem, not cert.pem.
  • Protect and never commit private keys. If one leaks, revoke and reissue.
  • Do not rely on email expiry warnings; monitor expiry yourself.
  • Add a CAA DNS record to restrict who can issue for your domain.
  • Clients with wrong clocks see "certificate not yet valid / expired" errors. Run NTP (chrony) on servers.
  • Pinning certificates in mobile apps without a rotation plan creates outages when certs change.
  • Internal hostnames (db.internal) cannot get public certs; use a private CA (step-ca, Vault PKI, cloud private CA).

Try it

  1. Run the openssl s_client command against three sites. Compare issuers and expiry dates. How many days remain on each?
  2. Count the certificates in the chain with -showcerts. Which one is the leaf?
  3. On a VPS with a real domain: install certbot, run sudo certbot --nginx --staging -d yourdomain.com first, then repeat without --staging.
  4. Run sudo certbot renew --dry-run and read the output. Then run systemctl list-timers and find the renewal timer.
  5. Locally: generate a self-signed cert, point an nginx server block at it, and observe the browser warning and what curl -k does differently.
  6. Run curl https://expired.badssl.com/ and curl https://self-signed.badssl.com/ to see the exact error messages you would see in production.
