Container Registries

An image on your laptop helps nobody else. A registry is the server that stores and distributes images, the "package repository" of the container world. Your CI pushes to it; your servers, Kubernetes clusters and teammates pull from it. How you tag, secure and scan what lives there decides how safe and repeatable your deployments are.

How registries work

  CI pipeline                     Registry                        Production host
 ┌───────────┐  docker push   ┌──────────────────┐  docker pull  ┌───────────────┐
 │ build img │───────────────▶│ repo: acme/api   │──────────────▶│ run container │
 └───────────┘                │  tags: 1.4.2,... │               └───────────────┘
                              │  blobs (layers)  │
                              └──────────────────┘

Registries speak the OCI Distribution API over HTTPS. An image reference is registry-host/namespace/repo:tag. When the host is omitted, Docker assumes Docker Hub: nginx means docker.io/library/nginx:latest. Pushes upload only layers the registry does not already have (by digest), so repeated pushes are fast.

Choosing a registry

RegistryHostNotes
Docker Hubdocker.ioLargest public catalog and official images. Anonymous and free-tier pulls are rate-limited, which can break CI at scale. Private repos on paid plans.
GitHub Container Registryghcr.ioTied to GitHub orgs/repos; authenticates with GITHUB_TOKEN in Actions; free for public images.
GitLab Container Registryregistry.gitlab.comBuilt into each GitLab project.
Amazon ECR<acct>.dkr.ecr.<region>.amazonaws.comIAM-based auth, same-region pull is fast and cheap, built-in scanning, lifecycle policies, replication.
Google Artifact Registry<region>-docker.pkg.devGCP's registry (successor to GCR). IAM auth.
Azure Container Registry<name>.azurecr.ioEntra ID auth, geo-replication.
Self-hostedyour ownHarbor (full-featured: RBAC, scanning, replication), the minimal registry:2/Distribution, Nexus, Artifactory.

Rule of thumb: put images in the registry closest to where they run (ECR for AWS, Artifact Registry for GCP) for speed, IAM integration and lower egress cost. Use GHCR when your code and CI are on GitHub and you deploy anywhere.

Authentication and push/pull

# Docker Hub
docker login -u myuser                    # prompts for a personal access token (not your password)

# GHCR (use a PAT with write:packages, or GITHUB_TOKEN in Actions)
echo "$GHCR_TOKEN" | docker login ghcr.io -u myuser --password-stdin

# AWS ECR (token valid 12 hours)
aws ecr get-login-password --region eu-west-1 \
  | docker login --username AWS --password-stdin 123456789012.dkr.ecr.eu-west-1.amazonaws.com
aws ecr create-repository --repository-name acme/api

# Tag and push
docker tag myapp:1.4.2 ghcr.io/acme/api:1.4.2
docker push ghcr.io/acme/api:1.4.2
docker pull ghcr.io/acme/api:1.4.2
Credentials are stored in ~/.docker/config.json

Without a credential helper that file holds a base64 (not encrypted) token. Use --password-stdin so secrets stay out of shell history, prefer short-lived tokens or OIDC in CI, and configure a credential store (osxkeychain, pass, ecr-login).

Running your own registry

docker run -d -p 5000:5000 --restart always --name registry \
  -v registry-data:/var/lib/registry registry:2
docker tag myapp:1.0 localhost:5000/myapp:1.0
docker push localhost:5000/myapp:1.0
curl http://localhost:5000/v2/_catalog

This is fine for local testing. For anything shared, you need TLS (Docker refuses plain HTTP except for localhost unless configured as insecure-registries), authentication and garbage collection. At that point use Harbor or a managed registry.

Tagging strategy

Tags are mutable pointers (see the layers lesson), so a deliberate scheme prevents confusion and enables rollbacks.

TagExamplePurpose
Git SHAapi:3f2a9c1Traceable to an exact commit; unique per build. Best for deploys.
Semantic versionapi:1.4.2, 1.4, 1Release tags for humans; moving 1.4 follows patches.
Branch/envapi:main, api:stagingMoving pointers; convenient but never the sole source of truth.
PR/previewapi:pr-123Ephemeral test environments.
latestapi:latestAvoid deploying it. It tells you nothing about what is running.
Build once, promote the same image

Build an image once in CI, tag it with the commit SHA, test it, then promote by adding tags (staging, 1.4.2, prod) to that same digest. Never rebuild for production: a rebuild is a different artifact that was never tested. Deploy by digest or immutable tag. Enable tag immutability on ECR/Artifact Registry for release tags so they cannot be overwritten.

# Promote without rebuilding (copies manifest, no layer re-upload)
docker buildx imagetools create \
  --tag ghcr.io/acme/api:1.4.2 \
  --tag ghcr.io/acme/api:prod \
  ghcr.io/acme/api:3f2a9c1

Pushing from CI (GitHub Actions)

name: build-and-push
on:
  push:
    branches: [main]
    tags: ["v*"]

permissions:
  contents: read
  packages: write            # lets GITHUB_TOKEN push to ghcr.io

jobs:
  image:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - id: meta
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=sha
            type=semver,pattern={{version}}
            type=ref,event=branch
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          platforms: linux/amd64,linux/arm64
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
          provenance: true
          sbom: true

Pin third-party actions to a commit SHA in sensitive pipelines. For AWS, use GitHub's OIDC and an IAM role (aws-actions/configure-aws-credentials) instead of long-lived access keys.

Image scanning

Images contain OS packages and language libraries that accumulate known vulnerabilities (CVEs). Scanners compare the image's package inventory against vulnerability databases.

trivy image ghcr.io/acme/api:1.4.2
trivy image --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 ghcr.io/acme/api:1.4.2
docker scout cves ghcr.io/acme/api:1.4.2       # Docker Scout
grype ghcr.io/acme/api:1.4.2                   # Anchore Grype
  • Scan in CI to fail the build on new critical findings, and continuously in the registry (ECR enhanced scanning, Harbor, GHCR with Dependabot/Trivy), because new CVEs are published against images you built months ago.
  • Use --ignore-unfixed to focus on actionable issues; track accepted risks in an ignore file with expiry dates.
  • Most fixes come from rebuilding on a newer base image. Automate with Renovate or Dependabot bumps.

Signing and provenance

Scanning tells you what is in an image; signing tells you who built it. Tools like Sigstore cosign sign images (keyless, using your CI's OIDC identity), and Kubernetes admission policies can then refuse unsigned images. Attach an SBOM (software bill of materials) and build provenance attestations with BuildKit's --sbom and --provenance.

Housekeeping

  • Registries grow forever. Set lifecycle/retention policies: e.g. ECR rule "expire untagged images after 7 days; keep last 30 tagged pr-*".
  • Use per-repo, least-privilege tokens: CI can push, production hosts can only pull.
  • Docker Hub rate limits: authenticate pulls, or mirror base images into your own registry (pull-through cache) so an outage or limit upstream does not stop your deploys.
  • Do not put secrets in images. Public images are world-readable; "private" images are one misconfiguration away.

Try it

  1. Run a local registry:2, push an image tagged localhost:5000/hello:1 and list it via the /v2/_catalog endpoint.
  2. Create a free GHCR or Docker Hub repo, log in with a token and push an image tagged both with a version and a short git SHA. Confirm both tags point to the same digest.
  3. Run trivy image node:22 and trivy image node:22-slim. Compare vulnerability counts.
  4. Write the GitHub Actions workflow above for a sample repo and watch the image appear in the Packages tab.
