Multi-Stage Builds and Optimization

Compilers, dev dependencies and build tools are needed to build your app but are dead weight (and attack surface) when you run it. Multi-stage builds let one Dockerfile use a fat image to build and a tiny image to ship. Combine that with smart cache ordering, BuildKit features and multi-arch builds, and you get fast builds and small, safe images.

The problem

A single-stage Go or Node build leaves behind everything it used: the 800 MB Go toolchain, gcc, node_modules/.cache, TypeScript sources, test files. Before multi-stage, teams maintained two Dockerfiles plus a shell script to copy artifacts between them. Now it is built in.

How multi-stage works

Each FROM starts a new stage with a fresh filesystem. COPY --from=<stage> pulls specific files from an earlier stage. Only the last stage becomes the final image (unless you pick another with --target); earlier stages are discarded.

 Stage "deps"          Stage "build"              Stage "runtime" (final)
 ┌────────────────┐    ┌───────────────────┐     ┌─────────────────────┐
 │ node:22        │    │ FROM deps         │     │ node:22-slim        │
 │ npm ci (all)   │───▶│ COPY src          │──┐  │ COPY --from=build   │
 └────────────────┘    │ npm run build     │  └─▶│   /app/dist         │
                       └───────────────────┘     │ COPY prod node_mods │
      discarded              discarded           └─────────────────────┘
                                                   ← this is what ships

Node.js with TypeScript

# syntax=docker/dockerfile:1
FROM node:22-slim AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci

FROM deps AS build
COPY . .
RUN npm run build                      # tsc -> /app/dist

FROM node:22-slim AS prod-deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci --omit=dev

FROM node:22-slim AS runtime
ENV NODE_ENV=production
WORKDIR /app
COPY --from=prod-deps /app/node_modules ./node_modules
COPY --from=build /app/dist ./dist
COPY package.json ./
USER node
CMD ["node", "dist/server.js"]

Useful targets

Add a test or dev stage and select it with --target:

FROM build AS test
RUN npm test

# docker build --target test .          # run tests in CI, never ships
# docker build --target runtime -t myapp .

Choosing a base image

BaseProsCons
Full (node:22, python:3.13)Has compilers and tools; easy debuggingLarge (~1 GB), many CVEs
Slim (-slim, Debian)glibc, small, broad compatibility; default sensible choiceNo build tools; needs apt for native deps
Alpine (-alpine)Tiny (musl libc, BusyBox), quick pullsmusl differences cause subtle bugs: Python wheels often must compile from source (slow), DNS and performance quirks, some native Node modules fail
Distroless (gcr.io/distroless/*)No shell, no package manager; minimal attack surface; :nonroot tagsCannot docker exec ... sh; debugging needs :debug variants or ephemeral containers

Rule of thumb

Start with -slim. Move to distroless or scratch for compiled languages when you want minimal size and attack surface. Use Alpine when you understand the musl trade-offs. Smaller is not automatically better: an image that breaks in production is more expensive than 100 MB.

Layer cache ordering

Order instructions from least to most frequently changing. Dependencies change weekly, source changes every commit:

# Python
COPY requirements.txt .
RUN pip install -r requirements.txt     # cached until requirements change
COPY . .                                # busts only layers after it

Apply the same logic to system packages (top), language dependencies (middle), source (bottom), build step (end). Copy only what each step needs, e.g. COPY go.mod go.sum ./ before go mod download.

BuildKit

BuildKit is the modern build engine and the default since Docker 23. It builds independent stages in parallel, skips stages the target does not need, and offers powerful mounts. Enable features with the first line # syntax=docker/dockerfile:1. Use docker buildx build for the extended CLI.

Cache mounts

Layer caching is all-or-nothing: if package.json changes, npm ci re-downloads everything. A cache mount persists a directory across builds without becoming part of the image:

RUN --mount=type=cache,target=/root/.cache/pip pip install -r requirements.txt
RUN --mount=type=cache,target=/go/pkg/mod --mount=type=cache,target=/root/.cache/go-build \
    go build -o /out/server ./cmd/server
RUN --mount=type=cache,target=/var/cache/apt --mount=type=cache,target=/var/lib/apt \
    apt-get update && apt-get install -y --no-install-recommends libpq5

Secret mounts

Need a private npm token at build time? Never use ARG or COPY. Mount it as a file that exists only during that one RUN and is never written to a layer:

RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci

# docker build --secret id=npmrc,src=$HOME/.npmrc -t myapp .

Similarly --mount=type=ssh forwards your SSH agent for private git dependencies.

Bind mounts and heredocs

RUN --mount=type=bind,source=requirements.txt,target=requirements.txt \
    pip install -r requirements.txt            # no COPY layer needed

RUN <<EOF
set -e
apt-get update
apt-get install -y --no-install-recommends curl
rm -rf /var/lib/apt/lists/*
EOF

CI cache export

CI runners start empty, so the cache is lost each run. Export it:

docker buildx build \
  --cache-from type=registry,ref=ghcr.io/acme/myapp:buildcache \
  --cache-to   type=registry,ref=ghcr.io/acme/myapp:buildcache,mode=max \
  -t ghcr.io/acme/myapp:1.4.2 --push .
# On GitHub Actions: --cache-from type=gha --cache-to type=gha,mode=max

Multi-architecture images

Apple Silicon laptops and AWS Graviton servers are arm64; most older servers are amd64. An image built for one will not run natively on the other. Build one tag that serves both:

docker buildx create --name multi --use
docker buildx build --platform linux/amd64,linux/arm64 \
  -t ghcr.io/acme/myapp:1.4.2 --push .
docker buildx imagetools inspect ghcr.io/acme/myapp:1.4.2   # shows both platforms

Pushing creates a manifest list; clients automatically pull the matching platform. Non-native platforms build under QEMU emulation (slow for compiled languages). Faster: cross-compile in the build stage using FROM --platform=$BUILDPLATFORM and the TARGETARCH arg:

FROM --platform=$BUILDPLATFORM golang:1.24 AS build
ARG TARGETOS TARGETARCH
RUN GOOS=$TARGETOS GOARCH=$TARGETARCH CGO_ENABLED=0 go build -o /out/server .

Measuring the result

docker build -t myapp:fat -f Dockerfile.single .
docker build -t myapp:slim .
docker images myapp
dive myapp:slim                    # visualize wasted space per layer

Pitfalls and trade-offs

  • Forgetting runtime-only needs when going distroless/scratch: CA certificates, /etc/passwd, timezone data, shared libraries (a dynamically linked Go binary fails on scratch; set CGO_ENABLED=0).
  • Cache mounts are not shared by default across CI runners; they speed local builds more than ephemeral CI.
  • Over-optimizing: debugging a shell-less image is harder. Keep a debug target.
  • Alpine + Python: often slower and bigger once compilers are added. Prefer python:3.13-slim.
  • Cache never refreshes: a cached apt-get update layer hides security fixes. Rebuild with --pull --no-cache on a schedule.

Try it

  1. Write a tiny Go "hello server". Build it single-stage (FROM golang) and multi-stage with distroless. Compare docker images sizes.
  2. Add a cache mount to a Python Dockerfile, change requirements.txt by one line and compare the second build time with and without the mount.
  3. Try docker run --rm -it your-distroless-image sh and read the error. Then build the :debug variant and retry.
  4. Run docker buildx build --platform linux/amd64,linux/arm64 . (without --push use --output type=image,push=false or a local registry) and inspect the result.
