Writing Dockerfiles

A Dockerfile is a text recipe: start from a base image, then run a series of instructions, each producing a layer. Writing a good one is mostly about knowing what each instruction really does, ordering them for the build cache, and keeping the result small, secure and well-behaved at shutdown.

Anatomy of a Dockerfile

# syntax=docker/dockerfile:1
# base image (required, first)
FROM node:22-slim
# set and create working directory
WORKDIR /app
# copy files from build context
COPY package*.json ./
# execute a command at BUILD time
RUN npm ci --omit=dev
COPY . .
# environment variable (build + runtime)
ENV NODE_ENV=production
# documentation only
EXPOSE 3000
# drop root
USER node
# default command at RUN time
CMD ["node", "server.js"]

Build and run it:

docker build -t myapp:1.0 .          # "." is the build context
docker run -d -p 3000:3000 myapp:1.0

ENTRYPOINT vs. CMD

Both define what runs when the container starts. The distinction is who can override what.

  • ENTRYPOINT: the program. Overridden only with --entrypoint.
  • CMD: default arguments to the entrypoint (or the whole command if there is no entrypoint). Replaced by anything you put after the image name in docker run.
Dockerfiledocker run imgdocker run img --foo
CMD ["node","server.js"]node server.jsruns --foo as the command (error!)
ENTRYPOINT ["node"]nodenode --foo
ENTRYPOINT ["node"]
CMD ["server.js"]		node server.jsnode --foo

A common pattern is an entrypoint script that prepares the environment, then hands over to the real process:

#!/bin/sh
# docker-entrypoint.sh
set -e
echo "Running migrations..."
node migrate.js
exec "$@"      # replace the shell with the CMD so signals reach the app
COPY docker-entrypoint.sh /usr/local/bin/
ENTRYPOINT ["docker-entrypoint.sh"]
CMD ["node", "server.js"]

Exec form vs. shell form

CMD ["node", "server.js"]     # exec form (JSON array): node IS PID 1
CMD node server.js            # shell form: /bin/sh -c "node server.js", sh is PID 1
Always use exec form for CMD and ENTRYPOINT

In shell form, sh is PID 1 and does not forward SIGTERM to your app. docker stop then waits 10 seconds and kills it forcibly, losing graceful shutdown (open requests dropped, DB connections not closed). Exec form makes your app PID 1 so it receives signals. Also note PID 1 has special signal semantics: handle SIGTERM explicitly in your code, or run with docker run --init (adds a tiny init, tini) to reap zombies and forward signals.

Build context and .dockerignore

The . in docker build . is the build context: the directory whose contents are sent to the builder. COPY can only see files inside it. Sending a context that includes node_modules, .git and build output is slow and pollutes the cache (any change in those files invalidates COPY . .). It can also leak secrets such as .env into the image.

# .dockerignore
.git
node_modules
npm-debug.log
dist
coverage
.env
.env.*
*.md
Dockerfile
docker-compose*.yaml
.DS_Store
__pycache__
*.pyc
.venv

Layer-friendly RUN

# Bad: three layers, cache goes stale, apt lists left behind
RUN apt-get update
RUN apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*

# Good: one layer, no leftovers, no recommended extras
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl ca-certificates \
 && rm -rf /var/lib/apt/lists/*

Full example: Node.js

# syntax=docker/dockerfile:1
FROM node:22-slim

ENV NODE_ENV=production
WORKDIR /app

# 1. dependency manifests first -> cached until they change
COPY package.json package-lock.json ./
RUN npm ci --omit=dev

# 2. application code
COPY --chown=node:node . .

# built-in unprivileged user in node images
USER node
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s \
  CMD node -e "fetch('http://localhost:3000/health').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"
CMD ["node", "server.js"]

npm ci installs exactly what the lockfile says (reproducible, faster than npm install). The healthcheck uses Node itself because slim images have no curl.

Full example: Python (FastAPI)

# syntax=docker/dockerfile:1
FROM python:3.13-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PIP_NO_CACHE_DIR=1

WORKDIR /app

# Create unprivileged user
RUN useradd --create-home --uid 10001 appuser

COPY requirements.txt .
RUN pip install -r requirements.txt

COPY --chown=appuser:appuser . .
USER appuser

EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

PYTHONUNBUFFERED=1 makes logs appear immediately in docker logs instead of being buffered. Binding to 0.0.0.0 is essential: 127.0.0.1 inside a container is reachable only from inside that container, so published ports would not work.

Full example: Go (static binary)

# syntax=docker/dockerfile:1
FROM golang:1.24 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o /out/server ./cmd/server

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/server /server
EXPOSE 8080
ENTRYPOINT ["/server"]

Go compiles to a single static binary, so the final image can be ~10 MB with no shell or package manager. The multi-stage pattern is explained in the next lesson.

Configuration: ENV vs. ARG vs. runtime

# build-time only
ARG APP_VERSION=dev
# promote to runtime if needed
ENV APP_VERSION=$APP_VERSION
# docker build --build-arg APP_VERSION=1.4.2 -t myapp:1.4.2 .

Environment-specific values (database URLs, API keys) belong at run time (-e, --env-file, Compose, orchestrator secrets), not in the image. The image should be identical in every environment; only configuration varies. This is the build-once, deploy-anywhere principle.

Pitfalls

  • Running as root because nobody added USER.
  • COPY . . before installing dependencies, destroying the cache.
  • Secrets via ARG/ENV/COPY. They persist in layers and metadata. Use BuildKit secret mounts (next lesson).
  • Using latest base images, so builds change without you touching anything.
  • Multiple processes in one container (app + cron + ssh). Split them.
  • Forgetting .dockerignore.
  • Apps that log to files instead of stdout/stderr, so docker logs shows nothing.
  • apt-get upgrade in Dockerfiles: non-reproducible. Bump the base image instead.

Linting

Run hadolint Dockerfile locally or in CI. It flags unpinned versions, missing --no-install-recommends, shell-form CMD and dozens of other issues. Recent Docker also has docker build --check for built-in lint rules.

Try it

  1. Create a minimal Express or FastAPI "hello" app and write the Dockerfile above. Build and run it, then hit it with curl.
  2. Change one line of source and rebuild. Which steps say CACHED? Now change package.json and rebuild; what is different?
  3. Switch CMD to shell form and time docker stop. Switch back and compare.
  4. Add .dockerignore and compare the "transferring context" size in the build output before and after.
  5. Override the command: docker run --rm myapp:1.0 node -v. Then use --entrypoint sh to get a shell.
