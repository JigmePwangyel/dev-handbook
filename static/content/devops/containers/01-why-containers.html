Why Containers?

Containers exist to solve one stubborn problem: software that behaves differently depending on where it runs. A container packages your application together with everything it needs, then runs it as an isolated process on a shared kernel. It is not magic and it is not a tiny virtual machine, and once you see what it really is, most of Docker stops being mysterious.

The problem: "works on my machine"

Imagine a Node.js API. On your laptop it runs on Node 22, macOS, with a globally installed libvips, an .env file you forgot to commit, and PostgreSQL 16. The production server runs Ubuntu 22.04, Node 18 installed years ago, no libvips, and a different locale. The code is identical, yet:

  • A native dependency fails to compile because the system library is missing or a different version.
  • A date-formatting bug appears because of a different timezone or ICU version.
  • Two apps on the same server need Python 3.9 and Python 3.12 and fight over the system interpreter.
  • A new teammate spends two days following an outdated "setup" wiki page.
  • Staging passes and production fails, and nobody can say what differs between them.

Without containers the usual workarounds are long README setup guides, configuration-management scripts that try to converge a server into a known state, or per-language version managers (nvm, pyenv, rbenv, virtualenv). Each solves one slice. None of them ships the whole environment (OS libraries, runtime, app, config defaults) as one artifact.

The container idea

Build the environment once, as an immutable image. Run that exact image on your laptop, in CI, in staging and in production. If it works in one place, it works in all of them, because the filesystem the process sees is byte-for-byte the same.

Virtual machines vs. containers

Before containers, the standard answer to isolation was the virtual machine. A hypervisor (KVM, VMware, Hyper-V, Xen) emulates hardware, and each VM boots a full guest operating system with its own kernel.

The trade-off is real: containers give up some isolation strength in exchange for speed and density. This is why multi-tenant clouds that run untrusted code (AWS Lambda, Fargate) wrap containers in micro-VMs such as Firecracker. For your own trusted services, plain containers are the norm. Containers and VMs also combine: most production containers run inside VMs (EC2 instances, GCE nodes).

What a container really is

There is no "container" object in the Linux kernel. A container is an ordinary Linux process (plus its children) that the kernel has been told to lie to and to limit. Three kernel features do nearly all the work.

1. Namespaces: what a process can see

A namespace gives a process its own private view of one kind of system resource.

NamespaceIsolatesEffect inside the container
pidProcess IDsYour app is PID 1; it cannot see host processes
netNetwork stackOwn interfaces, IP, routing table, ports
mntMount pointsOwn root filesystem (/)
utsHostnameOwn hostname
ipcShared memory, semaphoresPrivate IPC
userUID/GID mappingRoot inside can map to unprivileged outside
cgroupcgroup viewOwn view of resource hierarchy

2. cgroups: how much a process can use

Control groups limit and account for CPU, memory, I/O and process counts. When you run docker run --memory=256m --cpus=0.5, Docker simply writes those numbers into a cgroup. If the process exceeds the memory limit, the kernel's OOM killer terminates it (you will meet this as exit code 137).

3. Union filesystems: what files it has

An image is a stack of read-only filesystem layers. At run time the container runtime merges them with a union/overlay filesystem (overlay2 on modern Linux) and adds a thin writable layer on top. Many containers can share the same underlying read-only layers, which is why starting a container is nearly instant and storage is cheap. Layers are covered in depth in the images lesson.

Seeing it with your own eyes

You can build a crude container by hand on any Linux box, with no Docker at all:

# Run bash in new PID, mount and UTS namespaces (needs root)
sudo unshare --pid --fork --mount-proc --uts bash

# Inside the new shell:
hostname demo          # changes hostname only inside this namespace
ps aux                 # shows only a couple of processes, bash is PID 1
exit

Now with Docker, see the same truth from the host side:

docker run -d --name web nginx:1.27
docker top web                 # the processes, as seen from the host
ps aux | grep "nginx: master"  # the SAME process is visible on the host, with a normal PID
docker exec web ps aux         # inside the container the master is PID 1

The same process has two PIDs depending on which namespace you ask. That is the whole trick.

Docker Desktop on Mac and Windows

The Linux kernel features above do not exist on macOS or Windows. Docker Desktop transparently runs a small Linux VM (using Apple Virtualization framework or WSL 2) and runs your containers inside it. So "containers share the host kernel" really means "share the Linux VM's kernel" on those platforms.

What you get from containers

  • Reproducibility. The image is immutable. Same bytes, same behavior.
  • Isolation of dependencies. Two apps with conflicting library versions coexist peacefully.
  • Fast onboarding. docker compose up replaces a 30-step setup document.
  • Efficient resource use. Many more workloads per server than with VMs.
  • A universal deployment unit. Kubernetes, ECS, Cloud Run, Fly.io and Nomad all consume the same OCI image format.
  • Easy rollback. Deploying a version means running image tag X; rolling back means running tag X-1.

What containers do NOT give you

  • Not a security sandbox by default. A root process in a default container is far more powerful than people assume. See the security lesson.
  • Not persistence. The writable layer disappears with the container. Data needs volumes.
  • Not orchestration. Docker alone does not restart across machines, scale or load balance. That is Kubernetes' job.
  • Not a fix for bad architecture. A tangled app in a container is a tangled app in a container.
  • Not portable across CPU architectures. An arm64 image will not run natively on amd64; see multi-arch builds.
Common misconception

"Containers are lightweight VMs." Thinking this way leads to SSH-ing into containers, running several services in one, and treating them as pets. Treat a container as a single process with a packaged filesystem: disposable, replaceable, one concern each.

A quick mental model

  • Image: the recipe-plus-ingredients, a read-only template (like a class).
  • Container: a running (or stopped) instance of an image (like an object).
  • Registry: a server where images are stored and shared (like a package repository).
  • Dockerfile: the text recipe for building an image.

Try it

  1. Install Docker (next lesson) and run docker run --rm alpine cat /etc/os-release. Compare with your host OS. Why does it say Alpine?
  2. Run docker run --rm alpine uname -r and uname -r on your host (on Linux). Are the kernel versions identical? Why?
  3. Run docker run -d --name sleeper alpine sleep 600, then find its PID on the host with docker inspect -f '{{.State.Pid}}' sleeper. On Linux, inspect /proc/<pid>/ns/ to see its namespaces.
  4. Run docker run --rm --memory=10m alpine sh -c 'head -c 50m /dev/zero | tail' and observe it get killed. You just met cgroups.
