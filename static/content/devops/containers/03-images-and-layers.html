Images and Layers

An image is not one big file. It is an ordered stack of immutable, content-addressed layers plus a small piece of JSON metadata. Understanding layers explains why builds are sometimes instant and sometimes slow, why pulls reuse downloads, why deleting a file in a later step does not shrink your image, and why tags are not the same as versions.

What is inside an image

An OCI image consists of three things:

  • Layers: compressed tar archives, each holding the filesystem changes from one build step (files added, modified or deleted).
  • Config: JSON with the default command, environment variables, exposed ports, working directory, user, architecture and the ordered list of layer hashes.
  • Manifest: JSON that lists the config and layers by digest. A registry stores and serves these.

Content-addressable storage

Every layer, config and manifest is named by the SHA-256 hash of its content, written sha256:ab12.... This one design choice gives you a lot:

  • Deduplication. If ten images share the same Debian base layer, it is stored once on disk and downloaded once.
  • Integrity. A pulled layer is verified against its hash. Tampering or corruption is detected.
  • Immutability. You cannot change a layer; changing content changes the hash, making it a different layer.
  • Cheap pushes. The registry says "I already have that digest" and the push skips it.
docker pull python:3.13-slim
# 3.13-slim: Pulling from library/python
# a2318d6c47ec: Pull complete
# ...
docker pull python:3.12-slim      # shared layers say "Already exists"

Copy-on-write at runtime

When a container starts, the runtime stacks the read-only layers with an overlay filesystem and adds an empty writable layer. If the container modifies a file from a lower layer, the file is first copied up into the writable layer and changed there. Lower layers are never touched. Deleting a file adds a "whiteout" marker in the upper layer that hides it.

Deleting in a later layer does not shrink the image

If layer 3 downloads a 500 MB archive and layer 4 runs rm on it, the image still contains the 500 MB in layer 3. The deletion is only a whiteout on top. Combine download, use and cleanup in the same RUN instruction, or use multi-stage builds. This also means a secret you COPY and then delete is still extractable from the image.

Tags vs. digests

A full image reference looks like this:

 registry.example.com / team / myapp : 1.4.2 @ sha256:9f86d0…
 └──── registry ────┘  └repo┘ └name┘  └tag┘   └────digest────┘
TagDigest
What it isA human-friendly, mutable pointerThe hash of the manifest, immutable
Examplenginx:1.27nginx@sha256:…
Can change meaning?Yes: the publisher can re-push 1.27 with a security patch, or latest with anythingNever
Use forReadability, developmentReproducible, auditable production deploys

If you omit a tag, Docker assumes :latest. That is not "the newest", it is merely the default tag name, and publishers may not even maintain it. Always specify tags explicitly.

docker images --digests nginx
docker inspect --format '{{index .RepoDigests 0}}' nginx:1.27
# In a Dockerfile, pin tag AND digest (tag is for humans, digest is enforced)
FROM nginx:1.27@sha256:<digest-here>

Multi-architecture images have a top-level "index" (manifest list) whose digest points to per-platform manifests. Pulling by tag on an ARM Mac and an x86 server resolves to different manifests under the same tag.

Inspecting layers

docker history myapp:1.4
# IMAGE         CREATED        CREATED BY                                      SIZE
# 3f1c...       2 minutes ago  CMD ["node" "server.js"]                         0B
# 8a2b...       2 minutes ago  COPY . . # buildkit                              1.2MB
# c7d9...       3 minutes ago  RUN npm ci --omit=dev                            85MB
# e01a...       3 minutes ago  COPY package*.json ./                            4kB
# ...           2 weeks ago    /bin/sh -c #(nop)  CMD ["node"]                  0B

docker history --no-trunc --format '{{.Size}}\t{{.CreatedBy}}' myapp:1.4
docker image inspect myapp:1.4 | less      # full config, layer digests, env
docker save myapp:1.4 | tar -tv | head     # raw layer tarballs
docker system df -v                        # image sizes and shared sizes

For a more visual exploration use the open-source tool dive, which shows each layer's file changes and flags wasted space.

The build cache

When you run docker build, each Dockerfile instruction produces a layer. Docker reuses a cached layer if:

  1. The instruction text is identical, and
  2. The parent layer is the same cached layer, and
  3. For COPY/ADD, the content checksums of the copied files are unchanged.

Crucially, the moment one layer is invalidated, every layer after it is rebuilt. That makes instruction order the single biggest build-speed lever:

# SLOW: any source edit invalidates npm install
COPY . .
RUN npm ci

# FAST: dependencies reinstall only when package files change
COPY package.json package-lock.json ./
RUN npm ci
COPY . .

RUN instructions are cached by their text, not their effect. RUN apt-get update can stay cached for months and then install stale package lists. That is why you chain apt-get update && apt-get install in one RUN, and why CI builds sometimes use --no-cache or --pull on a schedule to pick up security patches.

Working with images

docker tag myapp:1.4 myapp:latest         # add another tag to the same image ID
docker tag myapp:1.4 ghcr.io/acme/myapp:1.4
docker rmi myapp:latest                   # removes the tag; layers stay while another tag uses them
docker image prune                        # remove dangling (untagged) images
docker image prune -a --filter "until=168h"   # unused images older than a week
docker save -o myapp.tar myapp:1.4        # export to a file (air-gapped transfer)
docker load -i myapp.tar

"Dangling" images are untagged leftovers, often the previous build of a tag you just rebuilt.

Mental model

Think of an image like a Git repository: layers are commits (immutable, hashed, shared), tags are branches (movable pointers), and the digest is the commit SHA. Production should deploy SHAs; humans read branches.
