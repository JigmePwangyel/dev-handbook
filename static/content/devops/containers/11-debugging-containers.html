Debugging Containers

Containers fail in a small number of recurring ways: the process exits, gets killed, cannot reach something, or runs but behaves differently than on your laptop. A systematic routine, check the state, read the logs, inspect the config, get inside, compare environments, resolves most problems in minutes.

The debugging routine

  1. docker ps -a            Is it running? Exited? Restarting? What exit code?
        │
  2. docker logs             What did the process say before it died?
        │
  3. docker inspect          What config did Docker really apply? (env, mounts, ports, health)
        │
  4. docker exec / run       Get inside; test DNS, ports, files, permissions
        │
  5. docker events / stats   Resource pressure? OOM? Daemon-level problems?

Step 1: state and exit codes

docker ps -a --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
# NAMES  STATUS                      PORTS
# api    Restarting (1) 5 seconds ago
# db     Up 2 hours (healthy)        5432/tcp
# job    Exited (137) 3 minutes ago

docker inspect api --format '{{.State.ExitCode}} oom={{.State.OOMKilled}} err={{.State.Error}}'
docker inspect api --format '{{json .State.Health}}' | jq
Exit codeMeaningTypical cause
0Clean exitThe command finished. Expected for batch jobs; for a server it means the main process returned (e.g. daemonized itself, or CMD is a short script)
1Application errorUncaught exception, bad config, failed DB connection. Read the logs
2Shell misuse / bad usageWrong command-line arguments

126Command found but not executableMissing chmod +x on entrypoint script, wrong architecture binary
127Command not foundTypo, binary missing in slim/distroless image, CRLF line endings in script (#!/bin/sh^M)
130SIGINT (128+2)Ctrl+C
137SIGKILL (128+9)OOM kill, or docker stop timeout then forced kill, or docker kill

The rule: exit codes above 128 mean "killed by signal (code minus 128)".

Step 2: logs

docker logs api                         # everything since start
docker logs -f --tail 200 api           # follow, last 200 lines
docker logs --since 10m --timestamps api
docker compose logs -f --tail 50 api db # several services interleaved
docker logs api 2>&1 | grep -i error     # stderr is a separate stream
  • Empty logs? The app may write to a file instead of stdout/stderr, or output is buffered (set PYTHONUNBUFFERED=1). Link log files to /dev/stdout (nginx images do) or reconfigure the logger.
  • Logs vanish on docker rm. The default json-file driver stores them per container. In production ship logs elsewhere (Loki, CloudWatch, ELK).
  • Logs eating the disk? Default json-file has no rotation. Set max-size and max-file in daemon.json or Compose logging.options.

Step 3: inspect

docker inspect api | less
docker inspect -f '{{range .Config.Env}}{{println .}}{{end}}' api     # effective env vars
docker inspect -f '{{json .Mounts}}' api | jq                          # actual mounts
docker inspect -f '{{json .NetworkSettings.Networks}}' api | jq        # IPs, networks
docker inspect -f '{{.HostConfig.Memory}} {{.HostConfig.RestartPolicy.Name}}' api
docker port api                                                         # published ports
docker compose config                                                   # resolved Compose file

Much "it works locally" turns out to be a different environment variable, a missing mount or a wrong network, visible instantly here.

Step 4: get inside

docker exec -it api sh                  # shell in a running container (try bash if sh is minimal)
docker exec api env                     # environment
docker exec api ls -la /app             # are the files there? permissions?
docker exec api cat /etc/resolv.conf
docker exec -u 0 -it api sh             # as root (to install debugging tools temporarily)

When it crashes immediately (so you cannot exec)

# Override entrypoint to keep it alive and look around
docker run --rm -it --entrypoint sh myapp:1.4.2
docker run --rm -it --entrypoint sh --env-file .env myapp:1.4.2   # same env as the real thing
# Then run the real command manually and watch it fail:
/ # node server.js

# Inspect the filesystem of an exited container
docker commit api debug-snapshot && docker run --rm -it --entrypoint sh debug-snapshot
docker cp api:/app/error.log .          # works on stopped containers too

Shell-less and distroless images

There is no sh to exec into. Options: use the :debug tag of distroless (it includes BusyBox), or attach a sidecar that shares the target's namespaces:

docker run --rm -it --pid=container:api --network=container:api nicolaka/netshoot
# Now you see api's processes and network, and have curl, dig, tcpdump, ss, etc.
docker debug api                         # Docker Desktop/Subscription: injects a toolbox shell
kubectl debug -it pod/api --image=busybox --target=api     # Kubernetes ephemeral containers

Common failures and fixes

Exit 137 and OOM

docker inspect api --format '{{.State.OOMKilled}}'      # true => out of memory
docker stats                                             # live CPU / mem / net / IO per container
dmesg -T | grep -i -E 'killed process|out of memory'    # kernel's view (on the host)

If OOMKilled is true, the process exceeded its cgroup memory limit (or the host ran out). Fix by finding the leak or raising the limit; configure the runtime (e.g. Node --max-old-space-size below the limit, JVM -XX:MaxRAMPercentage=75). If OOMKilled is false, the 137 came from a stop timeout: the app ignored SIGTERM, so check exec-form CMD and signal handlers.

Crash loops (Restarting...)

With restart: always a failing container flaps forever, and Docker backs off exponentially between tries. Read docker logs for the last attempt, check the exit code, and temporarily disable the restart policy (docker update --restart=no api) to make it stay failed for investigation. Typical causes: missing env var, DB not ready, wrong file permissions after switching to a non-root user, a port already in use, or migration failures.

Permission denied

Non-root user cannot write to a volume or bind mount (owned by root or a host UID). Fix ownership at build (COPY --chown, chown in the Dockerfile before USER), run with a matching --user, or use chown in an init step. On SELinux hosts add :z to mounts.

docker network inspect appnet | jq '.[0].Containers'

"exec format error"

The image architecture does not match the host (arm64 image on amd64 or vice versa), or the entrypoint script has no shebang. Check docker image inspect --format '{{.Architecture}}' img, rebuild for the right platform with --platform.

Works on my machine, not in the container

  • File missing: .dockerignore excluded it, or COPY path is wrong. docker run --rm img ls -R /app.
  • Case-sensitive paths: macOS is case-insensitive, Linux containers are not.
  • Different env: compare docker exec api env with your local environment.
  • Dev dependencies omitted (npm ci --omit=dev) but code needs them at runtime.
  • Time zone, locale, missing CA certificates (slim/scratch) for outbound HTTPS.
  • Stale image: you changed code but ran an old build. Rebuild, check docker images timestamps, or use --no-cache.

Build failures

docker build --progress=plain --no-cache .          # full unfolded output
docker build --target build -t dbg . && docker run --rm -it dbg sh   # stop at a stage and poke around
docker builder prune                                # clear a corrupted/huge build cache

Disk space

docker system df -v          # who is using space
docker system prune -a       # unused images/containers/networks (careful)
docker volume ls -f dangling=true

Daemon-level tools

docker events                       # live stream: create, start, die, oom, health_status
docker stats --no-stream            # snapshot of resource use
docker top api                      # processes in the container, from the host
sudo journalctl -u docker -f        # daemon logs (Linux systemd)
docker info                         # storage driver, cgroup version, warnings
Habits that make debugging easy
  • Log to stdout/stderr in structured form, include a version and request ID.
  • Add a /health endpoint and HEALTHCHECK; Docker then reports (healthy) or (unhealthy) in docker ps.
  • Keep a debug build target or tag with a shell and tools; ship the minimal one.
  • Do not "fix" a running container by hand. If you change it by exec, you lose that change on the next deploy. Reproduce, fix the Dockerfile or config, rebuild.

Try it

  1. Run docker run -d --name oom --memory=20m python:3.13-slim python -c "x=bytearray(200*1024*1024)". Find the exit code and confirm OOMKilled=true with inspect.
  2. Run docker run --name bad alpine nonexistent-cmd and read exit code 127 (or 126 for a non-executable file).
  3. Start a container that logs to a file only (e.g. sh -c 'echo hi > /tmp/x.log; sleep 100') and observe empty docker logs. Then redirect to stdout.
  4. Put two containers on the default bridge, show that name lookup fails, then fix it with a user-defined network. Use nicolaka/netshoot to diagnose.
  5. Make a crash-looping Compose service (command: ["sh","-c","exit 1"], restart: always), and practice the routine: ps, logs, inspect, stop the loop.
