Container Security and Best Practices

Containers share the host kernel, so their isolation is thinner than a VM's, and default settings are permissive. Security here is mostly about shrinking what a compromised process can do: run as an unprivileged user, drop capabilities, make the filesystem read-only, cap resources, keep secrets out of images and keep the contents patched.

The threat model

Assume your application will eventually be exploited (a vulnerable library, an injection bug). The question is what the attacker gets next:

  • Root inside the container, then escape to the host via a kernel bug or misconfiguration.
  • Network access to other containers, the cloud metadata service (169.254.169.254, which holds IAM credentials) or the Docker socket.
  • Secrets baked into image layers or environment variables.
  • A vulnerable or malicious base image or dependency (supply chain).

Defense in depth: each control below removes one rung from the attacker's ladder.

1. Run as a non-root user

By default the process in a container is root (UID 0). Container root is not host root, but it is dangerously close: with a kernel bug, a writable host mount or an extra capability, it can become host root. And inside the container root can modify everything the app can see.

# Debian/Ubuntu-based
RUN groupadd --system --gid 10001 app && useradd --system --uid 10001 --gid app --no-create-home app
USER 10001:10001

# Alpine
RUN addgroup -S -g 10001 app && adduser -S -u 10001 -G app app
USER app

# Many images ship one: node has "node", distroless has ":nonroot" (UID 65532), nginx-unprivileged
FROM gcr.io/distroless/static-debian12:nonroot

Use a numeric UID so Kubernetes' runAsNonRoot check can verify it. Non-root processes cannot bind ports below 1024; listen on 8080 and map it with -p 80:8080. Enforce at run time with --user 10001.

2. Read-only root filesystem

docker run --read-only --tmpfs /tmp --tmpfs /run -v appdata:/data myapp:1.4.2

If an attacker cannot write to the filesystem, they cannot drop tools or modify your code. Give the app only the writable spots it really needs (tmpfs for temp files, one volume for data).

3. Drop capabilities and block privilege escalation

Linux splits root's power into ~40 capabilities. Docker grants a default subset (including NET_RAW, CHOWN, SETUID). A typical web app needs none.

docker run \
  --cap-drop ALL \
  --cap-add NET_BIND_SERVICE \
  --security-opt no-new-privileges:true \
  myapp:1.4.2

NET_BIND_SERVICE is only needed to bind ports below 1024. no-new-privileges stops setuid binaries from gaining privileges. Docker's default seccomp profile (blocks ~44 dangerous syscalls) and AppArmor/SELinux profiles are enabled by default; do not disable them (--security-opt seccomp=unconfined).

Never do these
  • --privileged: gives nearly all capabilities and device access; equals root on the host.
  • Mounting /var/run/docker.sock: lets the container control Docker, hence the host.
  • Mounting /, /etc or /proc from the host.
  • --network host / --pid host without a specific reason.

Rootless Docker/Podman and user namespace remapping (userns-remap) go further: container "root" maps to an unprivileged host UID, so even an escape lands as a nobody.

4. Resource limits

Without limits, one runaway or compromised container can starve the host (memory leak, fork bomb, crypto-miner).

docker run --memory=512m --memory-swap=512m --cpus=1.5 --pids-limit=200 \
           --ulimit nofile=4096:4096 myapp:1.4.2

Exceeding the memory limit gets the process OOM-killed (exit code 137): size limits from measured usage plus headroom, and make runtimes aware of the limit (modern JVMs and Go respect cgroup limits; Node needs --max-old-space-size tuned below the container limit).

5. Secrets

MethodVerdict
Hardcoded in code or Dockerfile (ENV, ARG, COPY .env)Never. Lives in layers and docker history/inspect forever.
Environment variable at run timeAcceptable for low-risk setups. Visible in docker inspect, /proc, crash dumps and child processes.
File mounted at run time (/run/secrets/x, Compose/Swarm secrets, Kubernetes Secret volumes)Better. Not in the image, not in inspect. Many images support *_FILE variables.
Secret manager fetched at start (Vault, AWS Secrets Manager, SSM, external-secrets operator)Best. Central rotation, audit logs, short-lived credentials.
Build-time secretsUse BuildKit --mount=type=secret, never ARG.

If a secret ever entered an image or a Git repository, treat it as leaked and rotate it. Deleting the layer or commit does not un-leak it.

6. Image hygiene: minimal, pinned, scanned

  • Minimal base: slim, distroless or scratch. Fewer packages, fewer CVEs, no shell for attackers.
  • Pin versions: FROM node:22.11-slim, ideally with @sha256: digest, and automate bumps with Renovate or Dependabot. Pin OS and language packages too (lockfiles, npm ci, pip --require-hashes).
  • Use trusted sources: Docker Official Images, verified publishers, your own mirrored base images. A random Hub image is arbitrary code running in your infrastructure.
  • Rebuild regularly: a weekly scheduled build picks up base image patches even when your code does not change.

Scanning with Trivy

trivy image myapp:1.4.2                                   # OS + language package CVEs
trivy image --severity HIGH,CRITICAL --exit-code 1 --ignore-unfixed myapp:1.4.2   # CI gate
trivy fs .                                                # scan source dependencies
trivy config .                                            # lint Dockerfile, Compose, Kubernetes, Terraform
trivy image --scanners secret myapp:1.4.2                 # hunt for leaked secrets in layers
trivy image --format cyclonedx -o sbom.json myapp:1.4.2   # produce an SBOM
# GitHub Actions step
- uses: aquasecurity/trivy-action@0.28.0
  with:
    image-ref: ghcr.io/acme/api:${{ github.sha }}
    severity: CRITICAL,HIGH
    ignore-unfixed: true
    exit-code: "1"

A scan is a snapshot: schedule re-scans of what is already deployed. Not every CVE is exploitable in your context; triage, but do not ignore everything. Complement with hadolint (Dockerfile lint) and Docker Bench for Security / CIS Docker Benchmark checks on hosts.

7. Protect the daemon and the host

  • Keep Docker and the kernel patched; most container escapes are kernel or runtime CVEs.
  • Restrict membership in the docker group (it equals root).
  • Never expose the daemon on TCP (-H tcp://0.0.0.0:2375) without mutual TLS. Open Docker ports on the internet are routinely hijacked for crypto-mining.
  • Block containers from the cloud metadata endpoint (enforce IMDSv2 with hop limit 1 on AWS) so a compromised container cannot steal the instance's IAM role.
  • Run untrusted code in stronger sandboxes (gVisor, Kata Containers, Firecracker microVMs).

A hardened run command

docker run -d --name api \
  --user 10001:10001 \
  --read-only --tmpfs /tmp \
  --cap-drop ALL --security-opt no-new-privileges:true \
  --memory 512m --cpus 1 --pids-limit 200 \
  --restart unless-stopped \
  -p 127.0.0.1:8080:8080 \
  -e DATABASE_URL_FILE=/run/secrets/dburl \
  -v "$PWD/secrets/dburl":/run/secrets/dburl:ro \
  ghcr.io/acme/api@sha256:<digest>

The same in Compose:

services:
  api:
    image: ghcr.io/acme/api:1.4.2
    user: "10001:10001"
    read_only: true
    tmpfs: [/tmp]
    cap_drop: [ALL]
    security_opt: ["no-new-privileges:true"]
    mem_limit: 512m
    cpus: 1
    pids_limit: 200

Security is a trade-off with convenience

Read-only filesystems, distroless images and dropped capabilities make debugging and onboarding harder. Adopt them progressively: non-root and pinned versions first (nearly free), then scanning, then read-only and capabilities. Verify each step with tests so hardening does not break production at 3 a.m.

Try it

  1. Run docker run --rm alpine id, then docker run --rm --user 10001 alpine id. Then try docker run --rm --read-only alpine touch /x and read the error.
  2. Run docker run --rm alpine sh -c 'cat /proc/self/status | grep Cap' with and without --cap-drop ALL and compare.
  3. Scan an old image such as node:16 with Trivy and a current node:22-slim. Count criticals.
  4. Take a Dockerfile from your own project and apply items 1, 2, 3 and 10 from the list. Rescan and compare size and CVE counts.
