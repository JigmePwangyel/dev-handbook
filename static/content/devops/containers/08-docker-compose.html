Docker Compose

Real applications are several containers: an API, a database, a cache, a reverse proxy. Starting each with a long docker run line, creating networks and volumes by hand and remembering the order is error-prone. Compose lets you describe the whole stack in one YAML file and manage it with a single command.

Why Compose

  • Declarative: the file is the documentation and the source of truth. Check it into Git.
  • One command: docker compose up creates the network, volumes and containers in dependency order.
  • Service discovery: each service name becomes a DNS name on the project network.
  • Reproducible dev environments: a new teammate clones the repo and runs one command.

Compose is the V2 plugin invoked as docker compose (with a space). The old Python docker-compose binary is end-of-life. The file is named compose.yaml (preferred) or docker-compose.yml, and the old top-level version: key is obsolete: omit it.

A complete example: app + Postgres + Redis + nginx

name: shop                                # project name (prefixes networks/volumes)

services:
  nginx:
    image: nginx:1.27-alpine
    ports:
      - "80:80"
    volumes:
      - ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      api:
        condition: service_healthy
    networks: [front]
    restart: unless-stopped

  api:
    build:
      context: ./api
      target: runtime
    image: shop/api:dev
    environment:
      NODE_ENV: production
      PORT: 3000
      REDIS_URL: redis://cache:6379
      DATABASE_URL: postgres://app:${DB_PASSWORD}@db:5432/shop
    env_file:
      - .env                              # extra vars, lower priority than "environment"
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_started
    healthcheck:
      test: ["CMD", "node", "-e", "fetch('http://localhost:3000/health').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"]
      interval: 10s
      timeout: 3s
      retries: 5
      start_period: 15s
    networks: [front, back]
    restart: unless-stopped

  db:
    image: postgres:16
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${DB_PASSWORD:?DB_PASSWORD must be set}
      POSTGRES_DB: shop
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./db/init:/docker-entrypoint-initdb.d:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d shop"]
      interval: 5s
      timeout: 3s
      retries: 10
    networks: [back]
    restart: unless-stopped

  cache:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - redisdata:/data
    networks: [back]
    restart: unless-stopped

volumes:
  pgdata:
  redisdata:

networks:
  front:
  back:

And the nginx config the proxy mounts, forwarding to the API by service name:

# nginx/default.conf
server {
  listen 80;
  location / {
    proxy_pass http://api:3000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  }
}
 Internet ─:80─▶ [nginx] ── front ── [api] ── back ──┬─▶ [db]    (pgdata volume)
                                                     └─▶ [cache] (redisdata volume)
 Only nginx publishes a port. db and cache are unreachable from outside.

Key concepts in that file

Healthchecks and depends_on

Plain depends_on: [db] only waits until the db container has started, not until Postgres accepts connections. The app then crashes with "connection refused". Using condition: service_healthy waits for the healthcheck to pass. Conditions are service_started (default), service_healthy and service_completed_successfully (for one-shot init jobs such as migrations). Your app should still retry connections on startup, since databases restart at any time.

Environment variables and env files

  • environment: sets variables directly; values can interpolate from your shell or .env: ${VAR}, ${VAR:-default}, ${VAR:?error message}.
  • A file named .env next to compose.yaml is read automatically for interpolation in the compose file. env_file: injects variables into the container. They are different mechanisms.
  • Never commit real secrets. Commit a .env.example and gitignore .env.
  • Precedence (high to low): docker compose run -e, shell environment, environment:, env_file:, image ENV.

Secrets

services:
  db:
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets: [db_password]
secrets:
  db_password:
    file: ./secrets/db_password.txt        # mounted at /run/secrets/db_password

Profiles

Profiles make services optional so they do not start by default:

services:
  adminer:
    image: adminer
    profiles: ["debug"]
    ports: ["8081:8080"]
  migrate:
    build: ./api
    command: ["node", "migrate.js"]
    profiles: ["tools"]
    depends_on:
      db: { condition: service_healthy }

# docker compose up -d                       # core services only
# docker compose --profile debug up -d       # + adminer
# docker compose run --rm migrate            # explicit run of a profiled service

Dev vs. prod: override files

Compose merges compose.yaml with compose.override.yaml automatically. Put production-safe defaults in the base and developer conveniences in the override; or use explicit files per environment.

# compose.override.yaml  (auto-loaded in dev)
services:
  api:
    build:
      target: dev
    command: ["npm", "run", "dev"]
    volumes:
      - ./api:/app                  # live code via bind mount
      - /app/node_modules
    ports:
      - "3000:3000"
      - "9229:9229"                 # node debugger
    environment:
      NODE_ENV: development
  db:
    ports:
      - "127.0.0.1:5432:5432"       # let your local psql connect

# compose.prod.yaml
services:
  api:
    image: ghcr.io/acme/shop-api:${TAG:?set TAG}   # pull a built image, never build in prod
    restart: always
    deploy:
      resources:
        limits: { cpus: "1.0", memory: 512M }
    logging:
      driver: json-file
      options: { max-size: "10m", max-file: "3" }

# Production invocation (skips the override file):
# docker compose -f compose.yaml -f compose.prod.yaml up -d

Merge rules: scalars are replaced, maps are merged, lists such as ports and volumes are appended. Run docker compose config to see the final merged result, which is the best debugging tool for override confusion.

For hot reload without bind mounts, Compose has develop: watch: with docker compose watch, which syncs or rebuilds on file changes (and avoids many bind mount performance issues on Mac).

Common commands

CommandDoes
docker compose up -dCreate and start everything in the background
docker compose up -d --buildRebuild images first
docker compose up -d --waitBlock until services are healthy (great in CI)
docker compose psStatus and health of services
docker compose logs -f apiFollow one service's logs
docker compose exec api shShell in a running service
docker compose run --rm api npm testOne-off container from a service definition
docker compose build [--no-cache]Build images
docker compose pullPull newer images
docker compose restart apiRestart one service
docker compose stop / startStop/start without removing
docker compose downStop and remove containers and networks (volumes kept)
docker compose down -vAlso delete named volumes (data loss!)
docker compose configValidate and print resolved config
docker compose up -d --scale worker=3Run multiple replicas (service must not publish a fixed host port)

Pitfalls and best practices

  • Do not use Compose as a production orchestrator for critical multi-host systems. It is excellent for dev, CI and small single-host deployments; for rolling updates, self-healing across machines and autoscaling, move to Kubernetes or a managed container service.
  • Pin image tags, same rule as everywhere.
  • Do not publish every port. Only the entry point needs to be public; internal services reach each other via the network.
  • YAML indentation errors: use docker compose config to catch them.
  • .env quoting: values are taken literally; quotes and trailing spaces can end up in the value.
  • Changed Dockerfile but no effect: you need --build or docker compose build.
  • Stale data after changing init scripts: files in docker-entrypoint-initdb.d only run on an empty data volume. Remove the volume to re-run.
  • Set name: or use -p so two checkouts of the same repo do not collide on project names.

Try it

  1. Write the compose file above for a small app of your own (any API that reads DATABASE_URL). Add a .env with DB_PASSWORD.
  2. Run docker compose up -d --wait, then docker compose ps. Stop the db with docker compose stop db and watch the api's health respond.
  3. Remove the condition: service_healthy and see whether the API fails on a cold start. Put it back.
  4. Add a compose.override.yaml with a bind mount and inspect the merge with docker compose config.
  5. Run docker compose down, then up again: is the data still there? Now try down -v.
