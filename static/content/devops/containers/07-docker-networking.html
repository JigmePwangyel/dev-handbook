Docker Networking

Every container gets its own network namespace: its own IP address, interfaces and ports. Docker's job is to wire those namespaces together and to the outside world. Most "my containers cannot talk to each other" problems come down to five ideas: network drivers, user-defined networks with built-in DNS, port publishing, localhost meaning something different inside a container, and bind addresses.

How it works under the hood

On Linux, Docker creates a virtual bridge (docker0), then for each container a veth pair: one end inside the container's namespace (eth0), the other attached to the bridge. Outbound traffic is NAT'd (masqueraded) through the host with iptables/nftables rules, and published ports are implemented as DNAT rules.

  Container A (172.18.0.2)   Container B (172.18.0.3)
        eth0 ─┐                    eth0 ─┐
              │ veth                     │ veth
        ┌─────┴────────────────────┬─────┴──────┐
        │         bridge (172.18.0.1)           │   ← Docker network "appnet"
        └───────────────┬───────────────────────┘
                        │ NAT / iptables
                  Host eth0 (192.168.1.50) ──▶ Internet
        host:8080 ──DNAT──▶ container A:80   (port publishing)

The default bridge vs. user-defined bridges

Containers started without --network join the legacy default bridge. It works, but containers there can reach each other only by IP address (which changes on every restart) and all share one flat network. User-defined bridge networks fix both:

  • Automatic DNS: containers resolve each other by name (or service alias) via Docker's embedded DNS server at 127.0.0.11.
  • Better isolation: only containers on the same network can talk.
  • Live attach/detach without restarting.
docker network create appnet
docker run -d --name db  --network appnet -e POSTGRES_PASSWORD=pw postgres:16
docker run -d --name api --network appnet -e DATABASE_URL=postgres://postgres:pw@db:5432/postgres myapp:1.0
#                                                                              ^^ resolved by name

docker exec api getent hosts db          # 172.18.0.2  db
docker exec api ping -c1 db
docker network connect appnet other      # attach a running container
docker network rm appnet
Always use a user-defined network

Docker Compose does this for you automatically: each project gets its own network and each service name becomes a DNS name. That is why your app connects to host db or redis instead of an IP.

Port publishing

A container's ports are private to its network by default. -p publishes them on the host so outside clients can reach them.

-p 8080:80                 # host 8080 -> container 80, on ALL host interfaces (0.0.0.0)
-p 127.0.0.1:8080:80       # only reachable from the host itself
-p 8080:80/udp             # UDP
-p 3000-3005:3000-3005     # ranges
-p 80                      # random host port; find it with: docker port web
-P                         # publish all EXPOSEd ports to random host ports

EXPOSE in a Dockerfile is just documentation; only -p/-P actually publishes.

Published ports bypass your firewall

Docker inserts its own iptables rules ahead of ufw/firewalld rules. -p 5432:5432 on a cloud VM exposes Postgres to the internet even if ufw says "deny". Bind to 127.0.0.1 for anything not meant to be public, put only your reverse proxy on public ports, and use cloud security groups as the real perimeter.

"localhost" inside a container is the container itself

The single most common networking bug: your API container uses localhost:5432 to reach Postgres. That points at the API container's own loopback, where nothing listens. Use the service name (db:5432). Also note that between containers you use the container's internal port (5432), not the host-published one.

Bind to 0.0.0.0, not 127.0.0.1

If your app listens only on 127.0.0.1 inside the container, traffic arriving via the bridge (or a published port) is refused. Configure the server to listen on 0.0.0.0 (e.g. uvicorn --host 0.0.0.0, app.listen(3000, '0.0.0.0')).

Putting it together: three-tier example

docker network create front
docker network create back

docker run -d --name db    --network back  postgres:16
docker run -d --name api   --network back  myapi:1.0
docker network connect front api              # api is on BOTH networks
docker run -d --name proxy --network front -p 80:80 nginx:1.27
# proxy can reach api (front) but NOT db; db is invisible from the proxy.
 Internet ──:80──▶ [proxy] ── front ──▶ [api] ── back ──▶ [db]
                      proxy cannot see db  ────────────╳

Segmenting networks like this is cheap defense in depth. For a stronger variant, docker network create --internal back blocks all outbound internet access from that network.

DNS details

  • On user-defined networks, name resolution uses the embedded DNS server; unresolved names are forwarded to the host's DNS.
  • Add aliases: docker run --network appnet --network-alias cache redis. Multiple containers sharing an alias get round-robin DNS.
  • Override DNS: --dns 1.1.1.1; add static entries with --add-host name:ip.
  • Corporate VPN or split-horizon DNS often breaks name resolution inside containers. Check docker exec c cat /etc/resolv.conf.

Host networking and its trade-offs

--network host removes the NAT hop and the namespace boundary: no -p needed, slightly better throughput and latency, ability to bind many ports. In exchange you lose port isolation (two containers cannot both listen on 80), and the container can see and bind host interfaces. It is useful for network monitoring agents or high-throughput proxies; avoid for ordinary apps.

IPv6 and custom subnets

docker network create --subnet 10.50.0.0/24 --gateway 10.50.0.1 appnet
docker network create --ipv6 --subnet 2001:db8:1::/64 v6net
docker network inspect appnet --format '{{range .Containers}}{{.Name}} {{.IPv4Address}}{{"\n"}}{{end}}'

If your corporate network or VPN uses the same private ranges Docker picks by default (172.17-31.x), routing silently breaks. Define default-address-pools in /etc/docker/daemon.json to avoid overlaps.

Pitfalls

  • Default bridge: no name resolution. Use a user-defined network.
  • Using the host-published port between containers.
  • Starting the app before the DB is ready (see Compose healthchecks).
  • Port already allocated: another process or container holds the host port; lsof -i :8080 or docker ps.
  • Docker Desktop's host mode behaves differently from Linux since the engine runs in a VM.

Try it

  1. Start two alpine containers on the default bridge and try ping by name (fails) and by IP (works). Repeat on a user-defined network.
  2. Run nginx with -p 127.0.0.1:8080:80, then try reaching it from another machine or via your LAN IP and see it refused. Compare with -p 8080:80.
  3. Run docker run --rm --network host alpine ip addr and compare with the default. What changed?
  4. Build the front/back network example and prove with docker exec proxy ping db that isolation works.
