Volumes and Data Persistence

A container's writable layer is born with the container and dies with it. Delete the container and every file it wrote is gone. That is perfect for stateless web apps and disastrous for databases. Volumes and mounts are how you attach durable storage to disposable containers.

The problem

docker run -d --name db -e POSTGRES_PASSWORD=pw postgres:16
# ... create tables, insert data ...
docker rm -f db
docker run -d --name db -e POSTGRES_PASSWORD=pw postgres:16
# all your data is gone

Container filesystems are also slower (copy-on-write overlay) and cannot be shared easily between containers. Docker offers three ways to mount something from outside the writable layer into a container.

              Docker host
 ┌──────────────────────────────────────────────┐
 │  Container                                   │
 │   /var/lib/postgresql/data ◀── volume        │──▶ /var/lib/docker/volumes/pgdata/_data
 │   /app (source code)       ◀── bind mount    │──▶ /home/you/project  (any host path)
 │   /run/secrets, /tmp       ◀── tmpfs         │──▶ host RAM only (never on disk)
 └──────────────────────────────────────────────┘

Named volumes

docker volume create pgdata
docker run -d --name db \
  -e POSTGRES_PASSWORD=pw \
  -v pgdata:/var/lib/postgresql/data \
  postgres:16

docker rm -f db                       # container gone...
docker run -d --name db2 -e POSTGRES_PASSWORD=pw \
  -v pgdata:/var/lib/postgresql/data postgres:16   # ...data is back

docker volume ls
docker volume inspect pgdata          # shows Mountpoint
docker volume rm pgdata               # permanent delete
docker volume prune                   # remove volumes not used by any container

The -v name:/path form creates the volume automatically if it does not exist. The modern, explicit syntax is --mount, which errors on typos rather than silently creating things:

docker run --mount type=volume,source=pgdata,target=/var/lib/postgresql/data postgres:16
docker run --mount type=bind,source="$PWD",target=/app,readonly node:22-slim ls /app
-v pitfall

If you write -v ./data:/data with a path, you get a bind mount. If you write -v data:/data with a bare name, you get a named volume. A missing ./ changes the semantics entirely, and with -v a mistyped host path is silently created as an empty directory owned by root. Prefer --mount in scripts.

Bind mounts for development

Mount your source directory into the container so edits on the host appear instantly, enabling hot reload without rebuilding:

docker run --rm -it -p 3000:3000 \
  -v "$PWD":/app \
  -v /app/node_modules \
  node:22-slim sh -c "cd /app && npm run dev"

The second -v creates an anonymous volume that masks the host node_modules. The trick of masking /app/node_modules stops your macOS-built native modules from overriding the Linux ones installed in the image.

Bind mount gotchas
  • Permissions/ownership: files are owned by your host UID. A container running as a different UID may be unable to write. Match with --user "$(id -u):$(id -g)" or fix with chown.
  • Performance on Mac/Windows: file sharing across the VM boundary is slow for large trees (many small files such as node_modules). Use named volumes for dependency dirs; Docker Desktop's VirtioFS and Compose watch help.
  • Host content hides image content: mounting an empty dir over /app makes the code baked into the image invisible.
  • SELinux (Fedora/RHEL): add :z or :Z to the mount, e.g. -v "$PWD":/app:z.
  • Use :ro for anything the container should not modify.

tmpfs

docker run --rm --tmpfs /tmp:rw,size=64m,mode=1777 alpine df -h /tmp
docker run --read-only --tmpfs /tmp --tmpfs /run myapp   # read-only root + writable scratch

tmpfs data lives in RAM and vanishes when the container stops. Use it for temp files that must never touch disk, and in tandem with --read-only for hardening.

Persisting a real database

docker run -d --name pg \
  --restart unless-stopped \
  -e POSTGRES_USER=app \
  -e POSTGRES_PASSWORD_FILE=/run/secrets/pgpass \
  -e POSTGRES_DB=appdb \
  -v pgdata:/var/lib/postgresql/data \
  -p 127.0.0.1:5432:5432 \
  postgres:16

psql -h 127.0.0.1 -U app appdb      # connect from the host

Notes: bind published DB ports to 127.0.0.1 unless remote access is truly required (a plain -p 5432:5432 exposes it on every interface, and Docker bypasses most host firewall rules). Pin the major version: pointing a newer Postgres at an older data directory fails, and upgrades require pg_upgrade or dump/restore.

Backup and restore

Volumes are just directories, so you can archive them with a throwaway container that mounts the volume plus a host directory:

# Backup volume "pgdata" to ./backup/pgdata-2026-10-05.tgz
docker run --rm \
  -v pgdata:/source:ro \
  -v "$PWD/backup":/backup \
  alpine tar czf /backup/pgdata-$(date +%F).tgz -C /source .

# Restore into a (new) volume
docker volume create pgdata-restored
docker run --rm \
  -v pgdata-restored:/target \
  -v "$PWD/backup":/backup:ro \
  alpine tar xzf /backup/pgdata-2026-10-05.tgz -C /target
File-level copies of live databases can be corrupt

Tarring a running Postgres data directory may capture a half-written state. For databases prefer logical backups, which are consistent and portable across versions:

docker exec pg pg_dump -U app -Fc appdb > appdb.dump          # backup
docker exec -i pg pg_restore -U app -d appdb --clean < appdb.dump   # restore
# MySQL: docker exec db mysqldump -u root -p"$PW" --all-databases > all.sql

Also test restores regularly. An untested backup is a hope, not a backup.

Sharing and copying data

docker run -v shared:/data writer ...      # several containers can mount one volume
docker run -v shared:/data:ro reader ...   # read-only for the consumer
docker cp web:/etc/nginx/nginx.conf ./nginx.conf   # one-off copy out of a container
docker cp ./index.html web:/usr/share/nginx/html/
docker run --rm -v pgdata:/d alpine ls -la /d      # peek into a volume

Concurrent writers to the same volume need application-level coordination. Two Postgres instances on one data directory will destroy it.

Volumes in production

  • Single host: named volumes on a fast local disk, with scheduled backups shipped off-host (S3, etc.).
  • Orchestrators: Kubernetes uses PersistentVolumes backed by cloud disks (EBS, GCE PD). The volume lives independently of any node.
  • Managed databases (RDS, Cloud SQL) are often the better answer: "databases in containers" in production means you own backups, upgrades, failover and tuning. Containerized databases shine in dev, CI and test.
  • Volume drivers (NFS, cloud storage) exist but network filesystems often have poor locking and latency characteristics for databases.

Design principle: keep containers stateless

Treat state as an external dependency: databases, object storage (S3), caches. A stateless container can be killed, rescheduled and scaled freely. Write logs to stdout, uploads to object storage, sessions to Redis. Where state must be local, make the volume explicit and documented.

Pitfalls

  • docker compose down -v deletes your named volumes. Know before you type the -v.
  • docker system prune --volumes removes unused volumes, including a stopped DB's data.
  • Anonymous volumes (from VOLUME in a Dockerfile or -v /path) pile up as random-hash names. Name your volumes.
  • Changing POSTGRES_PASSWORD on an existing volume has no effect; init variables apply only when the data directory is empty.

Try it

  1. Run Postgres with a named volume, create a table, remove the container, start a new one on the same volume and confirm the table survived.
  2. Repeat without a volume and watch the data vanish.
  3. Bind-mount a folder with an index.html into nginx (-v "$PWD/site":/usr/share/nginx/html:ro), edit the file and refresh the browser.
  4. Back up the volume with the tar command and a pg_dump. Restore the dump into a fresh container.
