The Twelve-Factor App

The twelve-factor methodology (written by Heroku engineers around 2011) is still the best short checklist for building applications that are easy to deploy, scale and operate. Almost every modern platform, from Docker to Kubernetes, assumes your app follows it.

Why it matters

An app that is painful to deploy is usually painful for a reason: config baked into the build, state stored on local disk, logs written to files nobody reads, or a startup procedure that only one person understands. The twelve factors are a set of constraints that remove those reasons. If you follow them, the same artifact runs on your laptop, in CI, in staging and in production, and you can run 1 or 50 copies of it.

        one codebase ──▶ build once ──▶ release = build + config ──▶ run N stateless processes
                                              ▲                              │
                                    env vars (per environment)               ├──▶ backing services (DB, cache, queue) via URL
                                                                             └──▶ logs to stdout ──▶ platform collects them

The twelve factors

I. Codebase: one codebase tracked in version control, many deploys

One app = one repo. Staging and production are different deploys of the same commit lineage, not different repos or long-lived forks. If two apps share code, extract a library and depend on it. Anti-pattern: a prod branch that diverges from main with hand edits.

II. Dependencies: explicitly declare and isolate

Never rely on a system-wide package happening to be installed. Declare everything in a manifest and lock exact versions.

# Node: package.json + package-lock.json, install reproducibly
npm ci

# Python: pin hashes
pip install --require-hashes -r requirements.txt

# Container: the image itself is the isolation boundary
FROM node:22-alpine
COPY package*.json ./
RUN npm ci --omit=dev

Commit the lockfile. npm install may change versions; npm ci will not.

III. Config: store config in the environment

Config is anything that varies between deploys: database URLs, API keys, feature flags, hostnames. It must not live in the code. The litmus test: could you open-source the repo right now without leaking credentials?

// config.js - read once, validate, fail fast
const required = ['DATABASE_URL', 'SESSION_SECRET'];
for (const k of required) {
  if (!process.env[k]) throw new Error(`Missing env var ${k}`);
}
export const config = {
  port: Number(process.env.PORT ?? 3000),
  databaseUrl: process.env.DATABASE_URL,
  logLevel: process.env.LOG_LEVEL ?? 'info',
};
Avoid "config files per environment"

Files like config.production.json checked into git grow combinatorially and tempt people to commit secrets. Env vars are language-agnostic and easy to change per deploy without a rebuild.

IV. Backing services: treat them as attached resources

Postgres, Redis, S3, an SMTP provider: all are reached through a URL and credentials in config. Swapping a local Postgres for a managed RDS instance should require changing DATABASE_URL and nothing else. Code that hardcodes localhost:5432 violates this factor.

V. Build, release, run: strictly separate stages

StageWhat happensOutput
BuildCompile code, fetch dependenciesImmutable artifact (image tagged with commit SHA)
ReleaseCombine build with environment configNumbered release you can roll back to
RunStart processes from a releaseRunning app

Never edit code on a running server. Rollback becomes "run the previous release", not "hope you remember what you changed".

VI. Processes: execute the app as one or more stateless processes

Any data that must outlive a request goes in a backing service, never in process memory or local disk. "Sticky sessions" (the load balancer pins a user to one server because the session lives in RAM) are a smell; store sessions in Redis or use signed tokens. A stateless process can be killed, restarted or duplicated freely, and that property underpins autoscaling and rolling deploys.

In-memory caches are fine as an optimisation, as long as losing them is harmless.

VII. Port binding: export services via port binding

The app is self-contained: it embeds an HTTP server and listens on $PORT. It does not depend on being injected into Apache or Tomcat at runtime. A reverse proxy or load balancer then routes to that port.

VIII. Concurrency: scale out via the process model

Scale by running more processes, and by running different process types for different workloads: web, worker, scheduler. Horizontal scaling beats making one process enormous.

# Procfile style - same image, different command
web:    node dist/server.js
worker: node dist/worker.js
cron:   node dist/scheduler.js

IX. Disposability: fast startup and graceful shutdown

Processes get killed constantly (deploys, autoscaling, node failures). Start in seconds, and on SIGTERM stop accepting new work, finish in-flight requests, then exit.

process.on('SIGTERM', () => {
  console.log('SIGTERM received, draining');
  server.close(async () => {   // stops new connections, waits for in-flight
    await db.end();
    process.exit(0);
  });
  setTimeout(() => process.exit(1), 25_000).unref(); // hard stop before the platform's SIGKILL
});

Workers must make jobs idempotent or re-queueable, because a killed worker means a job is retried.

X. Dev/prod parity: keep environments as similar as possible

Historically there were three gaps: time (code took weeks to ship), people (devs write, ops deploy) and tools (SQLite locally, Postgres in prod). Close them: deploy often, own what you ship, and run the same Postgres major version locally via Docker Compose.

XI. Logs: treat logs as event streams

The app writes unbuffered events to stdout, one per line, ideally as JSON. It does not manage log files, rotation or shipping. The platform (Docker, systemd, Kubernetes) captures the stream and forwards it to Loki, CloudWatch or Elasticsearch.

{"ts":"2026-10-05T10:21:07Z","level":"error","msg":"payment failed","order_id":9123,"trace_id":"a1b2c3"}

XII. Admin processes: run one-off tasks as one-off processes

Migrations, data fixes and REPL sessions run from the same codebase, release and config as the app, in a throwaway process: docker compose run --rm app node dist/migrate.js or a Kubernetes Job. Do not SSH in and run ad-hoc scripts against production from your laptop copy of the code.

Beyond the original twelve

Modern authors (see Kevin Hoffman's "Beyond the Twelve-Factor App") add three more, which matter in 2026:

  • API first: define contracts (OpenAPI) before implementation.
  • Telemetry: expose metrics, traces and health endpoints (/healthz, /metrics), not only logs.
  • Authentication and authorization: build security in from the start, not as an afterthought.

Trade-offs and honesty

Not every factor is absolute. Some apps legitimately hold state (databases, game servers, WebSocket hubs). The point is to be deliberate: isolate the stateful part, and keep everything else disposable. Env vars also have limits: they are visible to child processes and sometimes leak through crash dumps, so for high-value secrets prefer mounted files or a secret manager (next lesson).

Try it

  1. Pick one of your own apps and score it 0 or 1 against each factor. Which three failures would hurt most in production?
  2. Remove every hardcoded URL or key from it and read them from env vars with fail-fast validation.
  3. Add a SIGTERM handler, run it in Docker and confirm docker stop returns in under a second instead of waiting 10 seconds for SIGKILL.
