Scaling Patterns

Scaling means keeping latency and error rates acceptable as load grows. There is no single trick; there is a toolbox, and a rule: measure first, then apply the cheapest pattern that removes the actual bottleneck. This lesson walks through the toolbox from cheap to expensive.

Vertical vs horizontal

Vertical (scale up)Horizontal (scale out)
HowBigger machineMore machines behind a load balancer
ProsNo code changes, simplestNo hard ceiling, resilient to node failure
ConsCeiling, downtime to resize, single point of failureRequires stateless design (12-factor), more moving parts

Scale up first while it is cheap (a bigger instance is far less work than a distributed system), but design the app stateless so scaling out stays possible.

The request path and where to relieve it

 User ─▶ CDN ─▶ Load balancer ─▶ App (stateless) ─▶ Cache (Redis) ─▶ DB primary
  ▲        │                          │                              └▶ DB read replicas
  │ edge   │ static + cacheable       └▶ Queue ─▶ Workers (async, slow work)
  └ cache hit returns here; the closer to the user, the cheaper

1. Caching layers

The fastest request is one you never serve. Layer caches from the edge inward:

LayerExampleNotes
BrowserCache-Control: max-age=31536000, immutable on hashed assetsFree; use content-hashed filenames
CDNCloudflare, CloudFront, FastlyStatic files and cacheable API/HTML responses
Reverse proxynginx proxy_cache, VarnishMicro-caching (1-5s) can absorb spikes
ApplicationRedis/Memcached cache-asideQuery results, rendered fragments
DatabaseBuffer cache, materialized viewsPrecompute expensive aggregates

Every cache adds an invalidation problem. Use TTLs, version keys (product:v3:42) and stale-while-revalidate (Cache-Control: max-age=60, stale-while-revalidate=300) to make staleness a conscious, bounded choice.

2. CDN

A CDN caches content at edge locations near users, cutting latency and shielding your origin. Beyond static assets it provides TLS termination, DDoS absorption and a WAF. Tips:

  • Cache by URL; avoid putting per-user data in cacheable responses (Vary and Set-Cookie can accidentally disable or poison the cache).
  • Purge by tag or version the URL instead of purging everything.
  • Lock the origin so it only accepts traffic from the CDN, otherwise attackers bypass it.

3. Queues and workers: async processing

Do only what the user must wait for inside the request. Everything else (sending email, resizing images, generating PDFs, webhooks, syncing to third parties) goes on a queue and is handled by workers.

 POST /orders ─▶ API: validate, write order, enqueue "send_receipt" ─▶ 202/201 in 40 ms
                                         │
                                  [ queue: SQS / RabbitMQ / Redis (BullMQ) / Kafka ]
                                         │
                              worker pool (scale independently) ─▶ email provider

// producer
await queue.add('send_receipt', { orderId }, { attempts: 5, backoff: { type: 'exponential', delay: 2000 } });
// consumer
new Worker('default', async job => sendReceipt(job.data.orderId), { concurrency: 10 });

Rules for reliable async work:

  • At-least-once delivery is the norm, so jobs must be idempotent (processing twice has the same effect as once). Use an idempotency key or a "processed" record.
  • Retry with exponential backoff and jitter; after N attempts send to a dead-letter queue and alert.
  • Write the DB row and enqueue atomically, using the transactional outbox pattern, or you lose jobs when one succeeds and the other fails.
  • Autoscale workers on queue depth / age of oldest message, not CPU (KEDA does this on Kubernetes).

4. Read replicas

Most apps are read-heavy. Route reports, search and list pages to async replicas (see the databases lesson), mindful of replication lag. Replicas scale reads only; writes still go to one primary.

5. Sharding: the last resort

When a single primary cannot handle write volume or dataset size, you split data across multiple databases by a shard key (for example tenant_id or hash of user_id).

StrategyHowTrade-off
RangeUsers A-M on shard 1Hot spots if data is skewed
Hashhash(id) % N or consistent hashingEven spread; range queries and resharding are harder
Directory / tenantLookup table maps tenant to shardFlexible; extra lookup

Costs: cross-shard joins and transactions become hard or impossible, resharding is painful, operations multiply. Before sharding try: better indexes, partitioning (PARTITION BY, single node), archiving old data, bigger hardware, or a distributed SQL database (CockroachDB, Citus, Vitess, Aurora Limitless) that does it for you.

6. Rate limiting and load shedding

Capacity is finite. Decide who gets served when demand exceeds it, rather than letting everyone fail equally.

  • Rate limiting caps requests per client/key/IP. Algorithms: fixed window (simple, bursty at edges), sliding window, token bucket (allows bursts, most popular), leaky bucket.
  • Return 429 Too Many Requests and Retry-After; expose limits in headers.
  • Use a shared store (Redis) so limits hold across replicas.
-- Redis fixed-window counter (atomic via Lua or INCR+EXPIRE)
INCR rl:user:42:2026-10-05T10:21
EXPIRE rl:user:42:2026-10-05T10:21 60
-- if value > 100 -> 429

7. Backpressure

Backpressure is a downstream system telling upstream "slow down" instead of silently buffering until it dies. Without it, a slow database causes app threads to pile up, memory balloons, timeouts trigger retries, retries add load, and you get a retry storm (metastable failure).

  • Bounded queues: reject or drop when full instead of growing without limit.
  • Timeouts everywhere: every outbound call has a deadline shorter than the caller's.
  • Retries with budgets: exponential backoff, jitter, cap on total retries.
  • Circuit breakers: stop calling a failing dependency for a cool-off period and fail fast.
  • Load shedding: return 503 early when overloaded and protect the critical paths (checkout over recommendations).
  • Autoscaling lag: new instances take minutes; queue and shed in the meantime.

Choosing a pattern

SymptomLikely first move
High TTFB for static assets worldwideCDN, compression, HTTP/2/3
DB CPU high on repeated identical queriesCache-aside, fix N+1
Requests slow because of email/PDF/API callsQueue + workers
DB CPU high, mostly SELECTs of varied queriesIndexes, read replicas
Primary write-saturatedBatch writes, partitioning, bigger instance, then sharding
Traffic spikes/abuseRate limits, autoscaling, shedding
Premature scaling is its own failure

A single well-indexed Postgres on a decent instance with a CDN in front serves a startling amount of traffic. Add complexity when metrics demand it, and keep the system simple enough that you can explain it in five minutes.

Try it

  1. Add proxy_cache with a 5-second TTL to an nginx in front of a slow endpoint and compare p95 latency under load.
  2. Build a tiny queue worker (BullMQ or Celery) where a job randomly fails; confirm retries, backoff and a dead-letter path work and that the job is idempotent.
  3. Implement a token-bucket limiter in Redis and demonstrate 429 responses with hey or k6.
