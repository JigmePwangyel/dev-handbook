Databases in Production

Your stateless app servers are cattle; the database is the one pet you cannot lose. It is usually the first bottleneck, the hardest thing to scale and the source of the worst outages. This lesson covers connection management, replicas, indexes, safe migrations, the managed-vs-self-hosted decision and caching, with Postgres as the running example.

1. Connections are expensive: pooling

A Postgres connection is a whole OS process using several MB of RAM. The default max_connections is 100. If you run 20 app replicas each with a pool of 10, you are already at 200 and the database falls over. Scaling the app can take down the DB.

 app pod ─┐                                     ┌─ pg conn 1
 app pod ─┤ 200 client conns ─▶ [ PgBouncer ] ─┼─ pg conn 2     (e.g. 20 real server connections)
 app pod ─┘                                     └─ pg conn ...
  • In-app pool (node-postgres Pool, HikariCP, SQLAlchemy): size it small. A common formula is connections = (cores * 2) + disks on the DB, shared across all app instances.
  • External pooler (PgBouncer, RDS Proxy, Supavisor): multiplexes many clients onto few server connections. Use pool_mode = transaction; note it breaks session features such as SET, advisory locks and (older) prepared statements.
# pgbouncer.ini
[databases]
app = host=10.0.0.5 port=5432 dbname=app
[pgbouncer]
pool_mode = transaction
max_client_conn = 1000
default_pool_size = 20
auth_type = scram-sha-256
Symptom: "remaining connection slots are reserved"

Usually a leak (connections not released) or too many replicas times pool size. Check SELECT state, count(*) FROM pg_stat_activity GROUP BY 1;. Set idle_in_transaction_session_timeout and statement_timeout so a stuck client cannot hold resources forever.

2. Replication and read replicas

A primary handles writes and streams its write-ahead log (WAL) to replicas. Replicas provide two different things, which people confuse:

PurposeMechanismNotes
High availabilityStandby that can be promoted (synchronous or async)Failover automation: Patroni, RDS Multi-AZ, Cloud SQL HA
Read scalingAsync replicas serving read-only queriesReads may be stale (replication lag)

The classic bug: a user submits a form (write to primary), the next page reads from a replica that has not caught up, and the data "disappears". Mitigate by reading from the primary right after writes ("read your writes"), or routing only reports and search to replicas. Monitor lag: SELECT now() - pg_last_xact_replay_timestamp(); on the replica.

3. Indexes

An index trades write speed and disk for read speed. Without one, Postgres scans the whole table.

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE customer_id = 42 ORDER BY created_at DESC LIMIT 20;
-- "Seq Scan on orders" on a big table = missing index

CREATE INDEX CONCURRENTLY idx_orders_customer_created
  ON orders (customer_id, created_at DESC);
  • CONCURRENTLY is mandatory in production. A plain CREATE INDEX takes a lock that blocks writes for the entire build. The concurrent variant takes longer, cannot run inside a transaction and can leave an INVALID index if it fails (drop and retry).
  • Column order matters in composite indexes: equality columns first, then range/sort columns.
  • Index foreign keys; Postgres does not do it for you.
  • Find unused indexes with pg_stat_user_indexes (idx_scan = 0) and slow queries with the pg_stat_statements extension.

4. Safe schema migrations

Use a migration tool (Flyway, Liquibase, Alembic, Prisma Migrate, golang-migrate, Rails/Django migrations): versioned, in git, applied in CI/CD, never by hand. The danger is that during a rolling deploy old and new code run against the same schema simultaneously, and some DDL takes long locks.

The expand / contract pattern

Never make a breaking change in one step. Rename a column in phases:

  1. Expand: add the new column (nullable). Deploy code that writes to both.
  2. Backfill old rows in small batches (not one giant UPDATE).
  3. Deploy code that reads from the new column.
  4. Contract: stop writing the old column, then drop it in a later release.

Dangerous operations and their safe forms

RiskyWhySafer
CREATE INDEXBlocks writesCREATE INDEX CONCURRENTLY
ALTER TABLE ... ADD COLUMN ... DEFAULT x (PG < 11)Rewrote whole tablePG 11+ is instant for constant defaults; otherwise add nullable, backfill
ALTER COLUMN TYPETable rewrite under lockNew column + backfill + swap
ADD CONSTRAINT FOREIGN KEY / CHECKFull scan under lockAdd NOT VALID, then VALIDATE CONSTRAINT
SET NOT NULLFull scanAdd valid CHECK (col IS NOT NULL) first, then SET NOT NULL
Dropping a column still read by old codeErrors during rolloutStop using it first, drop later
-- always protect yourself from queueing behind a long transaction
SET lock_timeout = '3s';
SET statement_timeout = '60s';
ALTER TABLE orders ADD COLUMN currency text;

Why lock_timeout: an ALTER waits for a lock, and while it waits every other query queues behind it, so a quick DDL stuck behind a long-running transaction can stall the whole application. Fail fast and retry.

Also: test migrations against a copy of production-sized data, take a backup first, and keep migrations backward compatible so you can roll back the app without rolling back the schema. Run them as a separate pipeline step (a one-off job) rather than at app startup when you have many replicas.

Default advice: use managed unless you have a specific reason and a person who knows how to run databases. The price premium is almost always smaller than one bad weekend. Whichever you pick, a database on the same VPS as the app is acceptable only for small projects, with off-box backups.

6. Caching with Redis

Caching removes load from the database for data that is read often and changes rarely. The standard pattern is cache-aside:

async function getProduct(id) {
  const key = `product:${id}`;
  const hit = await redis.get(key);
  if (hit) return JSON.parse(hit);

  const row = await db.query('SELECT * FROM products WHERE id=$1', [id]);
  // TTL with jitter avoids many keys expiring in the same second
  await redis.set(key, JSON.stringify(row), 'EX', 300 + Math.floor(Math.random()*60));
  return row;
}
// on update: DEL product:{id}  (invalidate)
  • Always set a TTL, so stale data and memory growth are bounded. Configure maxmemory and maxmemory-policy allkeys-lru for caches.
  • Cache stampede: a hot key expires and 1000 requests hit the DB simultaneously. Use jittered TTLs, request coalescing or a short lock.
  • Invalidation is the hard part: prefer short TTLs plus explicit deletes on writes over elaborate schemes.
  • Do not treat a cache as the source of truth unless you configure persistence deliberately (AOF/RDB) and accept the trade-offs. Never expose Redis publicly; require auth and TLS.
  • Redis also serves as a session store, rate-limit counter and job queue backend.

7. Operational basics

  • Monitor: connections, replication lag, disk space (a full disk is the classic outage), cache hit ratio, slow queries, locks, autovacuum and transaction ID age.
  • Private network only; TLS to the database; per-service credentials with least privilege.
  • Alert on disk at 70-80%, not 95%.
  • Run EXPLAIN on new queries in code review; add an ORM N+1 detector.
Rule of thumb

Scale the database in this order: fix queries and indexes, add pooling, cache, add read replicas, scale up the instance, and only then consider sharding. Each step is cheaper than the next.
