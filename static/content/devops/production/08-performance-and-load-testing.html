Performance and Load Testing

You do not know how your system behaves under load until you load it. Load testing finds the breaking point before your customers do, and gives you the numbers needed for capacity planning. This lesson shows how to test with k6, how to read the results and how to hunt the bottleneck.

Types of performance tests

TypeShapeQuestion
Smoke1-2 users, 1 minuteDoes the script and system work at all?
LoadExpected peak, sustained 10-30 minDo we meet our SLOs at normal peak?
StressRamp beyond peak until failureWhere does it break and how (gracefully or catastrophically)?
SpikeSudden jump 10x then backDo autoscaling, queues and caches cope?
SoakModerate load for hoursMemory leaks, connection leaks, disk growth?

Metrics that matter

  • Throughput: requests per second.
  • Latency percentiles: p50, p95, p99. Averages hide pain; if p99 is 8 seconds, one in a hundred users is suffering, and with many requests per page view that is most of your users.
  • Error rate: non-2xx and timeouts.
  • Saturation: CPU, memory, connections, queue depth, disk IO. (This is the Google SRE "four golden signals": latency, traffic, errors, saturation.)
Latency rises non-linearly

Latency stays flat as load increases, then curves up sharply as a resource saturates (the "knee"). Operating near 100% utilisation of anything means queueing delay explodes. Plan to run steady-state at 50-70% of the knee.

k6 in practice

k6 (Grafana Labs) scripts tests in JavaScript, runs as a single fast binary, and supports thresholds that make CI fail when performance regresses.

// load-test.js
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '2m', target: 50 },    // ramp up to 50 virtual users
    { duration: '10m', target: 50 },   // hold
    { duration: '1m', target: 0 },     // ramp down
  ],
  thresholds: {
    http_req_failed:   ['rate<0.01'],            // under 1% errors
    http_req_duration: ['p(95)<300', 'p(99)<800'], // latency SLO in ms
  },
};

export default function () {
  const res = http.get(`${__ENV.BASE_URL}/api/products`);
  check(res, {
    'status is 200': (r) => r.status === 200,
    'body not empty': (r) => r.body.length > 0,
  });
  sleep(1);   // think time: real users pause
}
k6 run -e BASE_URL=https://staging.example.com load-test.js
# stream results to Prometheus/Grafana for correlation with server metrics
k6 run --out experimental-prometheus-rw load-test.js

Sample output includes http_req_duration ... avg=120ms p(90)=210ms p(95)=290ms and a threshold pass/fail. For realistic modelling prefer the open model (arrival-rate executors such as constant-arrival-rate) over fixed virtual users: real traffic does not slow down just because your server did, whereas closed-model tests politely back off and hide overload ("coordinated omission").

scenarios: {
  steady: { executor: 'constant-arrival-rate', rate: 200, timeUnit: '1s',
            duration: '10m', preAllocatedVUs: 100, maxVUs: 500 },
}

Rules for valid tests

  • Test a production-like environment: same instance sizes, same data volume (a 100-row test DB lies), same config. Never casually load-test production or third-party services you do not own.
  • Run the generator on a separate machine, close to the target; check it is not itself the bottleneck (CPU).
  • Use realistic traffic mixes and varied data (cache-busting parameters, many users), or you test your cache and not your system.
  • Warm up first; JIT, caches and connection pools matter.
  • Change one thing at a time and keep results in version control.
  • Put a quick test in CI with strict thresholds to catch regressions (a smoke-level performance gate).

Bottleneck hunting

While the test runs, watch the system side. The methodology of Brendan Gregg's USE method is the shortcut: for every resource check Utilisation, Saturation, Errors.

Symptom during testProbable bottleneckTools
App CPU at 100%, latency upCPU-bound code, JSON/serialisation, regex, logging volumetop, flame graphs (perf, pprof, clinic.js, py-spy)
App CPU low, latency highWaiting: DB, downstream API, locks, pool exhaustionTracing (OpenTelemetry), pool metrics
DB CPU highMissing index, N+1 queries, heavy aggregatespg_stat_statements, EXPLAIN ANALYZE
DB connections maxedPool too large/small, leakspg_stat_activity, PgBouncer stats
Memory climbingLeak, unbounded cache, GC pressureHeap snapshots, free -m, GC logs
Disk await highIO-bound DB or loggingiostat -x 1
Errors with low resource useLimits: file descriptors, net.core.somaxconn, worker threads, rate limiterulimit -n, ss -s, nginx error log
Latency spikes at regular intervalsGC pauses, cron jobs, checkpointing, DNSCorrelate timestamps
# a quick host-level look while the test runs
vmstat 1          # r (run queue) > cores = CPU saturation; si/so = swapping
iostat -x 1       # %util and await for disks
ss -s             # socket counts; TIME_WAIT piles
pidstat -u -r 1   # per-process CPU / memory

Method: find the first saturated resource, fix or relieve it, rerun, and expect the bottleneck to move somewhere else. Stop when you meet the target with headroom. The slowest code is rarely where you guess, so profile instead of speculating.

Capacity planning

  1. Define targets: peak requests per second, latency SLO, growth forecast (for example 3x in a year), and event peaks (marketing launch, Black Friday).
  2. Measure unit capacity: with a load test, find the throughput a single instance sustains while meeting the SLO (say 220 rps per app instance).
  3. Compute: instances = peak rps / (unit capacity * target utilisation) plus redundancy.
peak = 1500 rps;  unit = 220 rps;  target utilisation = 65%
instances = 1500 / (220 * 0.65) = 10.5  -> 11
+ N+1 (survive losing one) -> 12 instances
  1. Find the next constraint: 12 app instances times pool of 10 means 120 DB connections. Does the DB cope? Do the same maths for DB, cache, bandwidth, third-party API quotas and your cloud account limits.
  2. Revisit regularly: re-test after significant releases and track trends from monitoring to see when you will hit limits (disk fill date, connection trend).

Use autoscaling to absorb variance, but keep minimums high enough for a sudden spike while new capacity boots, and set maximums so a bug or attack cannot create an enormous bill.

Pitfalls

Testing from your laptop over Wi-Fi, testing with one URL, ignoring think time, testing an empty database, trusting averages, and treating one passing run as proof. Also: a load test hitting a CDN-cached page measures the CDN.

Try it

  1. Run the capstone API locally (or any service) and write a k6 script with thresholds. Run it at 10, 50 and 100 VUs and plot where p95 starts to climb.
  2. While running, watch docker stats and pg_stat_activity. Identify the first resource to saturate.
  3. Fix it (an index, a pool size, caching) and rerun. Record the improvement and compute how many instances you would need for 1000 rps.
