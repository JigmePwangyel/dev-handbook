Production Readiness Checklist

"Are we ready to go live?" is answered best with a checklist, not a feeling. Airline pilots use them because memory fails under pressure; so do mature engineering teams. Use this as a launch review: every row should be a tick, a conscious "not needed, because...", or a tracked ticket with an owner.

How to use this page

  • Run it as a review meeting 1-2 weeks before launch, not the night before.
  • Be honest about "partial". The goal is visible risk, not a perfect score.
  • Adapt by criticality: an internal tool needs a lighter pass than a payment service.
  • Re-run it after major architectural changes. Keep it in the repo and evolve it after each incident ("what would have caught this?").

8. Final go-live gate

  1. Dry run of the full deploy in staging, including rollback.
  2. Load test passed on production-like environment.
  3. Restore drill completed this quarter.
  4. No open critical security findings; no known data-loss bugs.
  5. Dashboards and alerts live before traffic, not after.
  6. Rollback owner and decision criteria named ("if error rate > 2% for 5 min we roll back").
  7. Staged traffic: internal users, then 1%, 10%, 50%, 100%, watching metrics at each step.
After launch

Hypercare for the first days: watch dashboards, hold a short daily review, and capture surprises as checklist improvements. Production readiness is not a one-time gate but a habit.

Scale the checklist to the stakes

A hobby project may take only the bold basics: HTTPS, backups with a restore test, an uptime check, secrets out of git, and a rollback path. Add rows as the consequences of failure grow.

Try it

  1. Copy this checklist into a spreadsheet and score a real service you run: 0 = absent, 1 = partial, 2 = done. Sort by lowest score times business impact.
  2. Pick the top three gaps and write tickets with owners and dates.
  3. Run a 30-minute game day: kill one instance and break one dependency in staging. Did alerts fire? Did the runbook work?
