Server and Application Hardening

A public server is probed within minutes of getting an IP address. Hardening is the unglamorous work of shrinking what an attacker can reach and limiting what they can do if they get in. Most of it is a one-time checklist plus automation.

The mindset: defense in depth

 Internet ─▶ [ Firewall / security group ] ─▶ [ Reverse proxy: TLS, headers, rate limit ]
          ─▶ [ App: validation, authn/z ] ─▶ [ DB: least-privilege user, private network ]
              each layer assumes the previous one has failed

No single control is enough. Assume any layer can be bypassed and make sure the next one still limits the damage ("blast radius").

1. Patching the operating system

Unpatched known vulnerabilities are the most common entry point. Automate security updates and reboot when kernels change.

# Debian/Ubuntu: unattended security upgrades
sudo apt install unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades
# check status / pending reboot
cat /var/run/reboot-required
sudo needrestart

For containers, patching means rebuilding images regularly on updated base images (a weekly scheduled CI build) and redeploying. Live-patching a container is an anti-pattern.

2. SSH hardening

Put these in /etc/ssh/sshd_config.d/99-hardening.conf:

PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
AllowUsers deploy alice
MaxAuthTries 3
LoginGraceTime 20
X11Forwarding no
sudo sshd -t                 # validate config BEFORE reloading
sudo systemctl reload ssh    # keep your current session open and test a second one
Do not lock yourself out

Always keep an existing session open while testing a new SSH config in a second terminal. Know your provider's recovery console before you need it.

Use ed25519 keys (ssh-keygen -t ed25519) with a passphrase or hardware key. Optionally move SSH off port 22 (reduces log noise, not real security) or, better, reach servers only through a VPN/bastion or a tool like Tailscale or AWS SSM Session Manager so port 22 is not public at all.

3. Firewall

Default deny inbound, open only what you serve.

sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 22/tcp      # or restrict: ufw allow from 203.0.113.7 to any port 22
sudo ufw allow 80,443/tcp
sudo ufw enable
sudo ufw status verbose
Docker bypasses ufw

Published container ports (-p 5432:5432) are added to iptables ahead of ufw rules and are exposed to the world. Bind to localhost (127.0.0.1:5432:5432) or do not publish at all and use internal networks. Also use your cloud security group as the primary firewall.

4. fail2ban

Bans IPs that repeatedly fail authentication by parsing logs and adding firewall rules.

sudo apt install fail2ban
# /etc/fail2ban/jail.local
[sshd]
enabled  = true
maxretry = 5
findtime = 10m
bantime  = 1h

sudo systemctl enable --now fail2ban
sudo fail2ban-client status sshd

With key-only SSH it mostly reduces noise, but it is also useful on nginx login endpoints (nginx-limit-req jail).

5. Least privilege

  • Run apps as a dedicated unprivileged user, never root. In containers add USER node (or a numeric UID) and prefer --read-only filesystems.
  • Give the DB user used by the app only SELECT/INSERT/UPDATE/DELETE on its schema, with a separate migration user for DDL.
  • Use sudo with specific commands rather than full access; log it.
  • systemd sandboxing makes a cheap extra layer:
[Service]
User=app
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true
ReadWritePaths=/var/lib/app
CapabilityBoundingSet=
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX

Check how you are doing with systemd-analyze security app.service.

6. Reduce attack surface

  • Remove unused packages and services (ss -tlnp shows what is listening).
  • Databases and caches listen on private interfaces only. A public Redis with no password is mining malware's favourite target.
  • Use minimal images (distroless, alpine, -slim).
  • Enable audit logs and send them off the box so an intruder cannot erase them.

7. OWASP Top 10: the application basics

The OWASP Top 10 lists the most common web risks. A practical translation:

Broken access controlUser A fetches /orders/123 belonging to B (IDOR)Check ownership server-side on every request
Cryptographic failuresPlain HTTP, weak hashing, secrets in URLsTLS everywhere, argon2/bcrypt for passwords
InjectionSQL/command/template injectionParameterised queries, never string-concat input
Insecure designNo rate limits, no abuse thinkingThreat model early
Security misconfigurationDebug on, default creds, open bucketsIaC + config scanning
Vulnerable componentsOld libraries with CVEsDependency scanning (next lesson)
Authentication failuresCredential stuffing, weak sessionsMFA, lockout/rate limits, secure cookies
Integrity failuresUnsigned updates, tampered pipelinesSigning, pinned dependencies

// SQL injection: wrong vs right
db.query("SELECT * FROM users WHERE email = '" + email + "'");   // WRONG
db.query("SELECT * FROM users WHERE email = $1", [email]);       // right

8. Security headers (set at nginx or in the app)

add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "DENY" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Content-Security-Policy "default-src 'self'; img-src 'self' data:; frame-ancestors 'none'" always;
add_header Permissions-Policy "geolocation=(), camera=()" always;
server_tokens off;

Test with curl -I https://example.com or securityheaders.com. Roll out CSP in Content-Security-Policy-Report-Only mode first so you do not break the site. Set cookies with Secure; HttpOnly; SameSite=Lax.

9. Rate limiting and abuse control

http {
  limit_req_zone $binary_remote_addr zone=login:10m rate=5r/m;
  limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;
  server {
    location /login { limit_req zone=login burst=5 nodelay; proxy_pass http://app; }
    location /api/  { limit_req zone=api burst=20;          proxy_pass http://app; }
  }
}

Limit at the edge (CDN/WAF), at nginx and, for per-user logic, in the app (token bucket in Redis). Return 429 with Retry-After. Behind a proxy make sure you key on the real client IP (X-Forwarded-For from a trusted proxy only), otherwise everyone shares one bucket or attackers spoof it.

10. Verify, continuously

  • lynis audit system gives a hardening report for Linux hosts; CIS Benchmarks are the detailed standard.
  • nmap -sV yourserver from outside: does the list of open ports match your intent?
  • Run OWASP ZAP baseline scan against staging in CI.
  • Enable cloud-native detection (GuardDuty, Security Hub) if on AWS.

Trade-offs

Every control costs convenience. Strict CSP breaks inline scripts; read-only filesystems break apps that write temp files; aggressive rate limits block users behind shared NAT. Roll out in report-only or monitor mode, measure, then enforce.

Try it

  1. On a throwaway VPS apply the SSH config, ufw rules and fail2ban above. From another machine confirm password login is refused.
  2. Run sudo lynis audit system and fix the top three suggestions.
  3. Add the headers to nginx and grade the site; then add a login rate limit and prove it with a loop of curl requests that start returning 429.
