DevSecOps and Supply Chain Security

Your application is perhaps 10% code you wrote and 90% code you imported, plus a base image, a build system and a pipeline. Attackers know it: compromising one popular package or one CI token reaches thousands of victims. DevSecOps means building security checks into the pipeline so they run on every change, not once a year.

Why "shift left"

A vulnerability found in a pull request costs minutes to fix. The same flaw found in production costs an incident. Automated checks in CI give fast feedback to the developer who just wrote the code, while it is still in their head.

Dependency scanning in practice

Enable Dependabot or Renovate so you receive automated update PRs. A minimal .github/dependabot.yml:

version: 2
updates:
  - package-ecosystem: npm
    directory: /
    schedule: { interval: weekly }
    groups:
      minor-and-patch:
        update-types: [minor, patch]
  - package-ecosystem: docker
    directory: /
    schedule: { interval: weekly }
  - package-ecosystem: github-actions
    directory: /
    schedule: { interval: weekly }

And a CI gate that fails on serious findings:

- name: Scan image
  uses: aquasecurity/trivy-action@0.28.0
  with:
    image-ref: ghcr.io/acme/api:${{ github.sha }}
    severity: CRITICAL,HIGH
    ignore-unfixed: true
    exit-code: 1
Triage, do not drown

Scanners produce noise. Prioritise: is it reachable by your code, is a fix available, is it exploitable in your context? Use ignore-unfixed, VEX statements or documented ignore files with expiry dates. A gate nobody trusts gets disabled.

Pinning: make builds reproducible and tamper-evident

  • Lockfiles: commit them, install with npm ci/pip --require-hashes/go.sum verification.
  • Base images by digest: tags are mutable, digests are not.
  • GitHub Actions by commit SHA: a tag like @v4 can be moved by a compromised maintainer (this happened in the 2025 tj-actions/changed-files incident, which leaked secrets from thousands of repos).
FROM node:22-alpine@sha256:3a4c...e91f      # digest pin; Renovate can bump it

- uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683   # v4.2.2

Trade-off: pinning stops silent changes but also stops silent security fixes, so pair it with automated update PRs.

SBOM: a bill of materials

A Software Bill of Materials lists every component in an artifact. When the next Log4Shell lands, you query SBOMs instead of grepping repos. Common formats: SPDX and CycloneDX.

syft ghcr.io/acme/api:1.4.0 -o spdx-json > sbom.spdx.json
grype sbom:sbom.spdx.json --fail-on high
# Attach it to the image in the registry
cosign attest --yes --predicate sbom.spdx.json --type spdxjson ghcr.io/acme/api@sha256:...

Regulation is pushing this: US executive order 14028 and the EU Cyber Resilience Act both expect SBOMs for many products.

Signing images with cosign (Sigstore)

Scanning tells you what is inside. Signing tells you who built it and that it was not altered. Sigstore's keyless signing ties a signature to an OIDC identity (for example "the GitHub workflow in repo acme/api on main") and records it in a public transparency log, so you manage no long-lived signing keys.

# in CI (needs permissions: id-token: write, packages: write)
cosign sign --yes ghcr.io/acme/api@${DIGEST}

# verify anywhere
cosign verify ghcr.io/acme/api@${DIGEST} \
  --certificate-identity-regexp '^https://github.com/acme/api/.github/workflows/release.yml@refs/heads/main$' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

Enforce verification at deploy time with a Kubernetes admission controller (Kyverno verifyImages, Sigstore policy-controller, or Ratify). Sign the digest, never the tag.

SLSA: a maturity framework for build integrity

SLSA ("salsa", Supply-chain Levels for Software Artifacts) defines increasing guarantees about how an artifact was built.

Build levelMeaningHow to get it
L1Build is scripted and provenance existsAny CI that emits provenance
L2Hosted build platform signs provenanceGitHub Actions + actions/attest-build-provenance
L3Hardened, isolated builds; provenance cannot be forged by the build's own stepsslsa-github-generator reusable workflows

Provenance is a signed statement: "this digest was built from commit X of repo Y by workflow Z". A consumer can verify it with gh attestation verify or slsa-verifier.

Hardening the pipeline itself

  • Set the workflow permissions: to read-only by default; grant write per job.
  • Protect main: required reviews, required status checks, no force pushes, signed commits if you need them.
  • Never use pull_request_target with checkout of untrusted PR code; never interpolate untrusted input (${{ github.event.pull_request.title }}) into shell commands.
  • Use ephemeral runners for untrusted builds; self-hosted runners that persist between jobs can be poisoned.
  • Use OIDC to cloud instead of stored keys; require approvals on the production environment.

Dependency hygiene

  • Beware typosquatting and dependency confusion (an attacker publishes a public package with your internal package's name). Use scoped names and registry config that pins internal scopes.
  • Be wary of install scripts: npm ci --ignore-scripts where feasible.
  • Prefer fewer, well-maintained dependencies. Every one is trust you extend.
  • Delay adopting brand new releases a few days (Renovate minimumReleaseAge); most malicious versions are yanked quickly.

A sensible starting pipeline

  1. Day 1: Dependabot + secret scanning + push protection (free on GitHub).
  2. Week 1: Trivy on image and IaC in CI, failing on critical.
  3. Month 1: SBOM and provenance generated on release.
  4. Quarter 1: cosign signing and cluster-side verification; SHA-pinned actions.
Security is a process, not a gate

The goal is not zero findings; it is a pipeline that makes the secure path the easy path, keeps fix time short, and lets you answer "are we affected?" within an hour of a new CVE.

Try it

  1. Run trivy image node:22 and compare with trivy image node:22-alpine and a distroless image. Note the difference in findings.
  2. Generate an SBOM with syft for one of your images and query it for a package: grype sbom:./sbom.json.
  3. Sign a test image in GHCR using keyless cosign from a GitHub Action, then verify it from your laptop.
