Secrets Management

Passwords, API keys, tokens, private keys and certificates are the keys to your kingdom. Most real-world breaches involve a leaked credential rather than a clever exploit. This lesson covers where secrets should live, how to hand them to applications, how to rotate them and what to do the minute one leaks.

Why it is hard

A secret has to be readable by the running application, yet unreadable by almost everyone and everything else. It must travel from a human or a generator to a process, through CI, containers and logs, without being copied somewhere it should not be. Every extra copy is another place it can leak.

Where secrets leak most often

  • Committed to git (including in history after being "deleted").
  • Baked into a Docker image layer (ENV API_KEY=... or COPY .env). Anyone who can pull the image can read it with docker history or by extracting layers.
  • Printed in CI logs, crash dumps, error pages or debug endpoints.
  • Shared in Slack, tickets and wikis.
  • Over-broad long-lived keys on developer laptops.
Deleting a commit does not delete the secret

Once pushed, assume it is compromised: bots scrape public GitHub in seconds. Rewriting history is cleanup, not remediation. The remediation is always to revoke and rotate.

Level 1: .env done properly

# .gitignore
.env
.env.*
!.env.example

# .env.example (committed - names only, no values)
DATABASE_URL=
SESSION_SECRET=

# on the server
chmod 600 /opt/app/.env
chown deploy:deploy /opt/app/.env

In Docker Compose pass it with env_file: .env. Prefer Docker/Compose secrets (mounted as files under /run/secrets/) for sensitive values, since environment variables show up in docker inspect and /proc/<pid>/environ.

Level 3: SOPS, encrypted secrets in git

Mozilla SOPS encrypts the values in YAML/JSON/dotenv files while leaving keys readable, so diffs and code review still work. It encrypts with age, AWS KMS, GCP KMS or Azure Key Vault keys.

# one-time: generate an age key (keep the private key out of git!)
age-keygen -o ~/.config/sops/age/keys.txt
# prints: Public key: age1ql3z7hjy54pw3hyww5ayyfg7zqgvc7w3j2elw8zmrj2kg5sfn9aqmcac8p

# .sops.yaml - which files get which keys
creation_rules:
  - path_regex: secrets/.*\.yaml$
    age: age1ql3z7hjy54pw3hyww5ayyfg7zqgvc7w3j2elw8zmrj2kg5sfn9aqmcac8p

sops secrets/prod.yaml            # opens editor, saves encrypted
sops -d secrets/prod.yaml         # decrypt to stdout
sops exec-env secrets/prod.env ./start.sh   # run a command with decrypted env

The encrypted file is safe to commit. Only holders of the private key (or KMS permission) can decrypt. Combine with Flux or Argo CD plugins for Kubernetes, or Bitnami Sealed Secrets / External Secrets Operator as alternatives.

Level 4: central secret managers

AWS Secrets Manager

aws secretsmanager create-secret --name prod/app/db \
  --secret-string '{"username":"app","password":"s3cr3t"}'

aws secretsmanager get-secret-value --secret-id prod/app/db \
  --query SecretString --output text

Access is controlled by IAM: attach a policy allowing secretsmanager:GetSecretValue on that one ARN to the role of your EC2 instance, ECS task or EKS service account. No static AWS key is needed; the SDK picks up role credentials automatically. Secrets Manager supports automatic rotation via Lambda (native for RDS). Cheaper alternative for plain config: SSM Parameter Store (SecureString).

HashiCorp Vault (and its open-source fork OpenBao)

Vault is a self-hosted (or HCP-managed) secrets engine with identity-based access, full audit logging and, importantly, dynamic secrets: it creates a fresh database user on demand with a TTL and deletes it afterwards.

vault kv put secret/app/stripe api_key=sk_live_xxx
vault kv get -field=api_key secret/app/stripe

# Dynamic Postgres credentials, valid 1 hour
vault read database/creds/app-role
# Key             Value
# lease_duration  1h
# username        v-approle-app-x8Zk
# password        A1a-...random...

Apps authenticate to Vault with a platform identity (Kubernetes service account, AWS IAM, AppRole, OIDC) and receive a token, never a long-lived password. Costs: you must run, unseal, back up and upgrade Vault (or pay for HCP).

Secrets in CI/CD

  • Prefer OIDC federation over stored cloud keys: GitHub Actions requests a short-lived token and assumes an AWS role. Nothing long-lived sits in repo settings.
  • Scope secrets to environments (production environment with required reviewers).
  • Do not echo them; masking only works for exact matches and can be bypassed by transformations such as base64.
  • Never expose secrets to workflows triggered by forks' pull requests.
permissions:
  id-token: write   # needed for OIDC
  contents: read
steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123456789012:role/gha-deploy
      aws-region: eu-west-1

Rotation

Rotation limits the damage window and proves you can replace a secret without an outage, which is exactly what you need during an incident. A safe pattern for a database password is two-user alternation: two valid users, rotate the idle one, switch the app over, then rotate the other. The cruder pattern (change password, restart app) causes downtime between the two steps.

  1. Make the app reload secrets without a restart, or perform rolling restarts.
  2. Automate rotation on a schedule (90 days is common; shorter for high-value keys).
  3. Rotate on personnel changes and after any suspected exposure.

Leak response runbook

  1. Revoke first. Disable the key at the provider (GitHub token settings, AWS IAM, Stripe dashboard). Speed matters more than tidiness.
  2. Issue a replacement and deploy it.
  3. Audit usage: CloudTrail, provider logs. Look for access between the leak and revocation time.
  4. Remove from history (git filter-repo, BFG) and from image layers; force-push and tell collaborators to re-clone.
  5. Find the cause: add a pre-commit scanner so it cannot recur, and write a blameless postmortem.
# Prevent: scan before commit and in CI
gitleaks detect --source . --verbose
trufflehog git file://. --only-verified
# GitHub also offers push protection and secret scanning on repos
Principles to remember

Least privilege (each app gets only its own secrets), short lifetimes, no human ever needs to see a production secret in routine work, and everything auditable. The best secret is one that does not exist because the workload uses identity (IAM roles, workload identity) instead.

Try it

  1. Install gitleaks and run it against your oldest personal repo. Revoke anything it finds.
  2. Create an age key, write a small secrets.yaml, encrypt it with SOPS and commit it. Decrypt it on another machine using only the key.
  3. Run docker history --no-trunc on one of your images and check no secret appears in a layer.
