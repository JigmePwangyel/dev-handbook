Environments: Dev, Staging, Production

An environment is a complete, isolated copy of "your system running somewhere": its own servers, database, config and secrets. Having more than one is how teams change software without gambling with real users.

Why multiple environments exist

Imagine you only have production. Every experiment, every half-finished feature, every database migration runs against real customer data. A typo in a migration drops a table and customers see errors. So you add a second place to try things first. Then you notice that place needs to resemble production or its results are meaningless. That tension, isolated enough to be safe, similar enough to be trustworthy, drives everything in this lesson.

Environment parity

The more staging differs from production, the less a green staging result tells you. The Twelve-Factor App calls this dev/prod parity. Differences that commonly bite:

  • Different database engines. SQLite locally, PostgreSQL in production. SQL dialects, locking and JSON behaviour differ. Run the same engine and major version everywhere.
  • Different OS or runtime versions. macOS laptop, Debian server, Node 18 vs 22. Containers fix most of this.
  • Different topology. One staging server vs. three behind a load balancer in prod hides session, caching and race-condition bugs.
  • Different data volume. A query that is instant on 100 rows takes minutes on 50 million.
  • Different network. Prod sits behind HTTPS and a CDN; dev talks plain HTTP on localhost, so cookie flags and CORS issues only appear in prod.
Parity is a spectrum, not a switch

You rarely afford a full-size staging. Keep kind identical (same engines, versions, OS image, deploy method) and let scale differ (smaller instances, fewer replicas). Deploying to staging with the exact same pipeline and artifact as production is the single most valuable parity rule.

Configuration per environment

Code is the same everywhere; configuration is what differs: database URL, API keys, log level, feature flags, the public hostname. The rule: build once, configure at deploy time. If you rebuild per environment, what you tested is not what you shipped.

Environment variables

The simplest, most portable mechanism. Every language reads them and every platform (systemd, Docker, Kubernetes, PaaS) can set them.

# Node
const dbUrl = process.env.DATABASE_URL;
if (!dbUrl) throw new Error("DATABASE_URL is required");

# Python
import os
db_url = os.environ["DATABASE_URL"]   # KeyError if missing = fail fast

.env files

# .env.development  (committed is OK only if it holds NO secrets)
DATABASE_URL=postgres://app:app@localhost:5432/app_dev
LOG_LEVEL=debug

# .env.production   (NEVER commit; generated or injected by the platform)
DATABASE_URL=postgres://app:S3cr3t@db.internal:5432/app
LOG_LEVEL=info

Add real .env files to .gitignore and commit a .env.example with dummy values so newcomers know which variables exist.

Build-time constantspublic API base URL for a frontendBuild variables (note: baked into the bundle, so not secret and not changeable without rebuild)
Never branch on environment name in code

if (env === "production") { ... } scattered through the code means production-only paths that are never tested in staging. Drive behaviour from named settings (EMAIL_PROVIDER=smtp) rather than "which environment am I".

Data in non-production environments

  • Synthetic/seed data: safe, reproducible, but may not exercise odd real-world shapes.
  • Anonymised production snapshot: realistic. Must scrub emails, names, payment data; GDPR and similar laws still apply to copies. Automate the scrub, never copy raw prod data to a laptop.
  • Isolation of side effects: staging must not send real emails, charge real cards or call production webhooks. Use sandbox keys (Stripe test mode), a mail catcher (Mailpit), and separate accounts.

Promotion: one artifact, many environments

 commit abc123 ──▶ build ──▶ artifact app:abc123 ─┬─▶ deploy to staging  (config: staging)
                                                  └─▶ deploy to prod     (config: production)
                     same bytes, different config

Tag artifacts with the commit SHA or a version, never "latest". Promoting means "deploy that exact tag to the next environment". Rollback is deploying the previous tag.

Preview (ephemeral) environments

A long-lived shared staging becomes a queue: "who is testing on staging?" Preview environments solve it by creating a throwaway environment per pull request with its own URL (e.g. pr-482.preview.example.com), torn down on merge.

  • Reviewers and designers click a link instead of checking out a branch.
  • Platforms: Vercel, Netlify, Cloudflare Pages (frontends); Render, Fly.io, Railway; self-built with Kubernetes namespaces or Docker Compose plus a wildcard DNS/reverse proxy.
  • Pitfalls: cost (auto-expire them), shared databases (give each preview its own schema or a seeded copy), and secrets exposure (never give previews production credentials, especially for PRs from forks).

How many environments do you need?

Team / productReasonable setup
Solo projectLocal + production (with CI tests). Preview deploys if available.
Small team SaaSLocal, CI, PR previews, production. Staging optional.
Regulated / largeLocal, CI, dev, QA, staging, production, plus a DR region.

More environments mean more cost and more drift. Add one only when it removes a real risk.

Pitfalls

  • Config drift: someone hand-edits a staging server. Fix: manage config as code (later: IaC).
  • Staging used as a dumping ground: multiple half-merged features make results meaningless.
  • Secrets copy-pasted between environments: a staging leak becomes a production breach. Use distinct credentials per environment.
  • "Test in prod" fear: some testing in production is healthy (feature flags, canaries, synthetic checks) when done deliberately. Later lessons cover it.

Try it

  1. Take any small app and read all its config from environment variables. Make it crash at startup with a clear message when one is missing.
  2. Create .env.example, add .env to .gitignore, and run the app with set -a; source .env; set +a; node app.js (or your language equivalent).
  3. List every difference between your laptop and what you imagine production to be (OS, versions, DB, network). Which would you eliminate first?
