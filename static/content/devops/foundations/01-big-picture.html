The Big Picture: How Software Reaches Users

You wrote code on your laptop and it works. Between that and a stranger using it at 3 a.m. there is a long chain: build, package, ship, run, expose, monitor. DevOps is the discipline of making that chain fast, repeatable and safe.

What "deployment" actually means

Deploying is taking a version of your software and making it the thing that real users hit. Concretely that means:

  1. Get the code/artifact onto a machine (physical, virtual, or a container host) that is reachable from the internet.
  2. Install its runtime and dependencies (Node, JVM, Python, libraries).
  3. Supply configuration and secrets (DB URL, API keys) without baking them into code.
  4. Start the process and keep it running (restart on crash, on reboot).
  5. Route traffic to it (DNS, TLS certificate, reverse proxy).
  6. Verify it works, and be able to undo it if it doesn't.
The core insight

"It works on my machine" is the root problem DevOps solves. Your laptop and the server differ in OS, versions, config and data. Everything in this handbook — CI/CD, containers, IaC — exists to make environments identical, automated and reproducible.

Roles and vocabulary

  • Dev writes features; Ops keeps systems running. Historically they were separate teams with opposing incentives (change vs. stability). DevOps merges the responsibilities.
  • SRE (Site Reliability Engineering): Google's take — treat operations as a software problem with measurable reliability targets.
  • Platform engineering: build internal tooling so product developers can deploy themselves.
