The Request Lifecycle

What really happens between typing a URL and seeing a page? Knowing every hop tells you where to look when something breaks, and which DevOps tool lives at which hop.

Why this matters

"The site is down" can mean DNS is wrong, a certificate expired, the load balancer has no healthy backends, the app crashed, or the database is out of connections. Each has a different symptom and a different owner. A mental model of the path lets you bisect: where does the request stop?

Step by step

1. DNS: name to address

Computers route by IP, humans type names. The browser asks a resolver (usually your ISP's or 1.1.1.1 / 8.8.8.8), which walks root, .com, then the domain's authoritative nameserver. Answers are cached for the record's TTL. Pitfall: lowering a record's TTL after you need a change is too late, so lower it before migrations.

dig +short app.example.com          # the A record
dig app.example.com +trace          # watch the delegation chain
curl -v https://app.example.com 2>&1 | head -30   # connect, TLS, headers

2. TCP and TLS

The client opens a TCP connection to port 443 (HTTP is 80), then performs the TLS handshake: the server presents a certificate, the client verifies it was issued by a trusted authority for that hostname and not expired, and both derive session keys. Expired certificates are one of the most common production outages. HTTP/3 uses QUIC over UDP but the idea is the same.

3. CDN and edge

Static assets and cacheable responses can be served from a node near the user (Cloudflare, CloudFront, Fastly), never reaching your servers. It lowers latency and absorbs traffic spikes and attacks.

4. Load balancer

Spreads requests across several identical backends and removes unhealthy ones (via health checks like GET /healthz). This is how you scale horizontally and deploy with no downtime.

5. Reverse proxy

nginx, Caddy, Traefik or HAProxy sits in front of apps: terminates TLS, routes by host/path (/api to service A, / to service B), compresses, rate-limits, adds headers. Your app listens on a private port (3000) and never faces the internet directly.

6. The application

Your code parses the request, authenticates, runs logic, and talks to backing services. Most time is usually spent waiting on I/O, not computing.

7. Data layer

Typically a relational database, often fronted by a cache. Databases are the hardest tier to scale and to change safely, because they hold state.

8. The response

A status code (200, 301, 404, 500, 503) and body flow back. Each layer can modify or replace it: a proxy returns 502 Bad Gateway when the app is down, a load balancer 503 when no backend is healthy, a gateway 504 on timeout.

Architectures: how the app tier is organised

Tiers

A 3-tier design separates presentation (frontend), logic (API) and data (database). Each tier can be scaled and secured independently; the database sits in a private network unreachable from the internet.

Monolith vs microservices

MonolithMicroservices
ShapeOne deployable containing everythingMany small services, each owning its data
DeploySimple: one artifactMany pipelines, versioning between services
ScalingScale the whole thingScale only hot services
FailureOne bug can take down allIsolation, but cascading failures over the network
DebuggingOne stack traceNeed distributed tracing
Team fitSmall teamsMany teams needing autonomy
Start with a well-structured monolith

Microservices trade code complexity for operational complexity. Most products should split only when team size or scaling pain demands it. A "modular monolith" keeps the option open.

Stateless vs stateful

A stateless process keeps nothing between requests that another instance couldn't reconstruct. Any request can go to any instance, so you can add, kill and replace instances freely. That property is what makes load balancing, autoscaling, rolling deploys and containers easy.

State still exists, so push it to dedicated places:

StateWhere it lives
User sessionsSigned cookie/JWT, or Redis
Uploaded filesObject storage (S3), not local disk
Business dataDatabase
Background workQueue (SQS, RabbitMQ, Redis)
The local-disk trap

An app that saves uploads to ./uploads works on one server and silently breaks behind a load balancer: the next request lands on a server without the file. Treat the app's filesystem as disposable.

Synchronous vs asynchronous

Slow work (sending email, resizing images) should not block the response. Put a message on a queue, return 202 Accepted, and let a worker process it. Workers are separate processes you must also deploy and monitor.

Try it

  1. Run curl -v https://example.com and identify: the resolved IP, TLS version, certificate subject, status line, and headers.
  2. Run dig +trace example.com and name each server in the chain.
  3. Use browser DevTools (Network tab) on a site you like. Which requests came from a CDN? (Look for cf-cache-status, x-cache, age headers.)
  4. Draw your own app's path from browser to database. Mark which parts are stateful.
