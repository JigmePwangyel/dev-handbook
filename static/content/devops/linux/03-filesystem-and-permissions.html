Filesystem and Permissions

Linux treats almost everything as a file and controls access with a simple owner/group/other permission model. Most "permission denied" errors, and a large share of security incidents, trace back to this lesson.

The filesystem hierarchy

Linux has one tree rooted at / (no drive letters). The Filesystem Hierarchy Standard (FHS) says what lives where, so you always know where to look.

 /
 ├── bin, sbin, lib  ─ essential programs/libs (often symlinks into /usr)
 ├── etc/            ─ system-wide configuration (text files)
 ├── home/alice      ─ users' personal files
 ├── root/           ─ root's home
 ├── var/
 │   ├── log/        ─ logs
 │   ├── lib/        ─ persistent app state (databases, docker)
 │   └── www/        ─ conventional web content
 ├── opt/            ─ self-contained third-party software
 ├── srv/            ─ data served by this host
 ├── usr/            ─ installed programs (usr/bin, usr/local)
 ├── tmp/            ─ temporary files (cleared on reboot)
 ├── dev/            ─ device files (/dev/null, /dev/sda)
 ├── proc, sys/      ─ virtual: kernel and process info
 └── run/            ─ runtime data (PID files, sockets)
PathWhat you do there
/etcEdit configs: /etc/nginx/, /etc/ssh/sshd_config, /etc/systemd/system/
/var/logRead logs
/var/libData that must survive (back it up)
/opt or /srvPut your deployed app, e.g. /opt/myapp
/tmpScratch; never store anything important
/proccat /proc/cpuinfo, /proc/meminfo: live kernel info

Disks and mounts

df -h              # free space per mounted filesystem
lsblk              # block devices and mount points
mount | column -t  # what is mounted where
du -sh /var/*      # size of each directory
cat /etc/fstab     # filesystems mounted at boot

Adding a disk means formatting (mkfs.ext4), mounting it at a directory (mount /dev/sdb1 /data) and adding it to /etc/fstab (use the UUID from blkid) to persist across reboots. Running out of space, or of inodes (df -i), is a classic outage.

Users and groups

Every process and file belongs to a user (a number, the UID) and a group (GID). root (UID 0) bypasses all permission checks. Service accounts (www-data, postgres) exist so each daemon runs with minimal privileges: if nginx is compromised, the attacker is not root.

whoami; id               # uid=1000(deploy) gid=1000(deploy) groups=1000(deploy),27(sudo)
cat /etc/passwd          # user list (name:x:uid:gid:comment:home:shell)
cat /etc/group           # groups
getent passwd deploy

sudo adduser alice                  # interactive, creates home (Debian/Ubuntu)
sudo useradd -m -s /bin/bash bob    # low-level, portable
sudo usermod -aG docker alice       # ADD to group (-a is crucial; without it groups are replaced)
sudo passwd -l bob                  # lock the password
sudo userdel -r bob                 # delete user and home
sudo useradd --system --no-create-home --shell /usr/sbin/nologin myapp   # service account
Group membership needs a new login

After usermod -aG docker alice, alice must log out and in (or newgrp docker). Also note: membership in docker is effectively root access.

Add digits per class: rwx = 7, r-x = 5, r-- = 4. So rwxr-xr-- is 754.

Changing permissions and ownership

chmod 755 deploy.sh        # rwxr-xr-x   scripts, directories
chmod 644 index.html       # rw-r--r--   normal files
chmod 600 ~/.ssh/id_ed25519  # rw-------  private keys (ssh insists)
chmod 700 ~/.ssh           # rwx------
chmod +x script.sh         # symbolic: add execute
chmod u+w,g-w,o-rwx file   # user add write, group remove write, other remove all
chmod -R 750 /opt/myapp    # recursive (careful!)

sudo chown deploy:www-data /opt/myapp -R   # owner and group
sudo chgrp www-data /var/www/site
ModeTypical use
600Private keys, secret env files
640Config readable by a service group
644Public files, most configs
700 / 750Private / group-shared directories
755Executables, public dirs
777Almost never. Anyone can modify. A symptom of not understanding the real problem.
Never chmod 777 to "fix" it

When you hit "permission denied", find out who is running the process (ps -o user,cmd -p PID) and give that user or its group the minimal access needed. Check every directory on the path: you need x on each parent. namei -l /path/to/file shows the permissions along the entire path.

Special bits and umask

  • setuid (4755): executable runs as its owner (how sudo and passwd work). Audit with find / -perm -4000 2>/dev/null.
  • setgid on a directory (2775): new files inherit the directory's group; great for shared project folders.
  • sticky bit (1777, as on /tmp): users can delete only their own files.
  • umask: default mask subtracted from new files; 022 gives 644 files / 755 dirs, 077 gives private.
  • ACLs (setfacl -m u:alice:rx dir) provide per-user rules beyond owner/group/other.

sudo: controlled root

Logging in as root is dangerous: no audit trail of who did what, and a typo has no guardrail. sudo runs one command with root rights, after your own password, and logs it (/var/log/auth.log or the journal).

sudo apt update           # one command as root
sudo -i                   # root shell (use sparingly)
sudo -u postgres psql     # run as another user
sudo -l                   # what may I run?
sudo visudo               # safely edit /etc/sudoers (syntax-checked)
sudo visudo -f /etc/sudoers.d/deploy

# /etc/sudoers.d/deploy : let the deploy user restart only one service, no password
deploy ALL=(root) NOPASSWD: /bin/systemctl restart myapp, /bin/systemctl status myapp

Principle of least privilege: give people and services only what they need. Automation users get narrow sudo rules, not blanket NOPASSWD: ALL.

Putting it together: a deploy directory

sudo useradd --system --home /opt/myapp --shell /usr/sbin/nologin myapp
sudo mkdir -p /opt/myapp/releases /etc/myapp
sudo chown -R deploy:myapp /opt/myapp      # deployer owns, app group reads
sudo chmod -R 750 /opt/myapp
sudo chmod 2770 /opt/myapp/releases        # setgid: new releases keep group myapp
echo 'DATABASE_URL=...' | sudo tee /etc/myapp/env >/dev/null
sudo chown root:myapp /etc/myapp/env
sudo chmod 640 /etc/myapp/env              # app can read secrets, others cannot

Try it

  1. Create a user alice. As alice, try to read a file you made with mode 600 owned by you. Observe the error, then fix with a group and mode 640.
  2. Run namei -l /etc/ssh/sshd_config and explain each permission on the path.
  3. Make a shared directory /srv/team with setgid so files created by any member are group-writable by the group.
  4. Find the biggest consumer of disk in /var and check df -i for inode usage.
