Processes and systemd

Your app on a server is a process. Production means that process starts at boot, restarts on crash, runs as the right user, has its logs captured and can be stopped cleanly. On modern Linux, systemd does all of that.

Why you need a process manager

If you start your app with node server.js over SSH it dies when you log out, does not restart when it crashes, does not start after a reboot, and its output vanishes. You could run it with nohup or tmux, but that is a hack. A service manager supervises it properly. On virtually every mainstream distro that is systemd (PID 1, the first process; it starts everything else).

Processes 101

A process is a running program with a PID, an owner, memory, open files and a parent (PPID). Programs start other programs, forming a tree rooted at PID 1.

ps aux                     # every process (BSD style)
ps -ef --forest            # tree view with parent relationships
ps -o pid,ppid,user,%cpu,%mem,etime,cmd -p 1234
pgrep -a nginx             # find PIDs by name
pstree -p                  # tree
top                        # live view (q quits); htop is friendlier
lsof -p 1234               # files and sockets a process has open
lsof -i :3000              # who is using port 3000?
ss -tlnp                   # listening TCP ports with owning process (needs sudo for others)

Process states in ps: R running, S sleeping, D uninterruptible I/O wait (often a stuck disk/NFS), Z zombie (finished, parent has not collected it), T stopped.

Handle SIGTERM in your app

Deploys, systemd and Kubernetes all stop apps by sending SIGTERM, then SIGKILL after a timeout. If your app ignores SIGTERM, in-flight requests are cut off on every deploy. Listen for it, stop accepting new connections, finish current work, then exit. Containers have a twist: if your app is PID 1 it must handle signals itself (or use tini/--init).

// Node.js graceful shutdown
process.on("SIGTERM", () => {
  server.close(() => { db.end().then(() => process.exit(0)); });
  setTimeout(() => process.exit(1), 10000).unref();   // hard stop after 10s
});

systemd basics

systemd manages units; the most common is a .service. Others: .timer (scheduling), .socket, .mount, .target (groups of units, like "multi-user").

systemctl status nginx          # state, recent logs, PID, memory
sudo systemctl start nginx
sudo systemctl stop nginx
sudo systemctl restart nginx    # stop then start (brief downtime)
sudo systemctl reload nginx     # re-read config without dropping connections, if supported
sudo systemctl enable nginx     # start at boot
sudo systemctl enable --now nginx   # enable and start together
sudo systemctl disable nginx
systemctl is-active nginx; systemctl is-enabled nginx
systemctl list-units --type=service --state=running
systemctl --failed              # what is broken?

enable and start are independent: enabled means "at boot", started means "now".

Writing a unit file for your app

Suppose a Node app lives in /opt/myapp, runs node server.js on port 3000, and reads config from /etc/myapp/env. Create /etc/systemd/system/myapp.service (your own units go in /etc/systemd/system; packages use /usr/lib/systemd/system).

[Unit]
Description=My App (Node.js)
Documentation=https://example.com/docs
After=network-online.target postgresql.service
Wants=network-online.target

[Service]
Type=simple
User=myapp
Group=myapp
WorkingDirectory=/opt/myapp/current
EnvironmentFile=/etc/myapp/env
ExecStart=/usr/bin/node server.js
Restart=on-failure
RestartSec=3
# Stop behaviour
KillSignal=SIGTERM
TimeoutStopSec=30

# Hardening (cheap, big security win)
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true
ReadWritePaths=/var/lib/myapp
# Resource limits
LimitNOFILE=65535
MemoryMax=512M

[Install]
WantedBy=multi-user.target
DirectiveWhy
After=/Wants=Ordering and soft dependency (start after the network and DB)
User=Never run apps as root
EnvironmentFile=Config and secrets outside the unit (mode 640, root:myapp)
ExecStart=Absolute path to the binary; systemd does not use your shell or PATH like you do
Restart=on-failureAuto-restart on crash; always also restarts after clean exit
Type=simple (foreground process), forking (old-style daemons), oneshot (run and exit)
WantedBy=multi-user.targetWhat enable hooks into

Activate it:

sudo systemctl daemon-reload          # REQUIRED after creating/editing unit files
sudo systemctl enable --now myapp
systemctl status myapp
systemd-analyze verify /etc/systemd/system/myapp.service   # lint
sudo systemctl edit myapp             # drop-in override without editing the original
systemd-analyze security myapp        # hardening score
Common unit mistakes
  • Forgetting daemon-reload after edits.
  • Relative paths in ExecStart, or shell syntax (&&, $VAR expansion, pipes). Wrap in /bin/sh -c '...' if you truly need it.
  • Quotes in EnvironmentFile are handled differently than in a shell; use plain KEY=value.
  • ProtectSystem=strict makes the filesystem read-only, so list writable paths in ReadWritePaths.

Reading logs with journalctl

systemd captures stdout and stderr of services into the journal. Your app need only log to stdout (a 12-factor best practice).

journalctl -u myapp                    # all logs for the unit
journalctl -u myapp -f                 # follow live
journalctl -u myapp -n 100 --no-pager  # last 100 lines
journalctl -u myapp --since "1 hour ago"
journalctl -u myapp --since "2026-10-05 09:00" --until "09:30"
journalctl -u myapp -p err             # only errors and worse
journalctl -b                          # this boot; -b -1 = previous boot
journalctl -u myapp -o json-pretty | head
journalctl --disk-usage; sudo journalctl --vacuum-time=14d

Alternatives and context

The concepts carry over: a declared command, a user, env vars, restart policy, health, graceful stop, captured logs.

Zero-downtime-ish restarts

A plain restart drops requests for a moment. Options: reload where supported (nginx), run two instances behind a proxy and restart one at a time, or socket activation. The Deploy section builds proper strategies on this.

Try it

  1. Create a trivial server: python3 -m http.server 8000 --directory /srv/demo. Write a unit for it (user nobody is fine for the exercise), enable and start it.
  2. Find its PID with systemctl status, then kill -9 it. Watch systemd restart it (Restart=always). Look at the restart in journalctl -u.
  3. Reboot the VM and confirm it came back by itself.
  4. Run systemd-analyze security on your unit, add two hardening options, and re-score.
