SSH: Secure Remote Access

SSH is the front door to every server you will ever manage, and also what CI systems use to deploy. Understanding keys, the client config file, tunnels and hardening will save you hours and protect you from the most common attacks.

Why SSH, and why keys

Older tools (telnet, rsh, FTP) sent everything, including passwords, in clear text. SSH encrypts the session and authenticates both sides. Passwords work, but any server on the internet gets thousands of password-guessing attempts per day (check sudo journalctl -u ssh | grep "Failed password" | wc -l). Public-key authentication replaces guessable secrets with cryptography that cannot be brute-forced.

How key authentication works

 Your laptop                                     Server
 ~/.ssh/id_ed25519       (private: NEVER share)
 ~/.ssh/id_ed25519.pub   (public: copy anywhere) ──▶ ~/.ssh/authorized_keys

 1. client: "I'd like to log in as deploy, here is my public key"
 2. server: finds that key in authorized_keys, sends a random challenge
 3. client: signs the challenge with the private key (key never leaves laptop)
 4. server: verifies signature with public key ──▶ access granted

Also, on first connection the client records the server's host key in ~/.ssh/known_hosts. If it later changes you get a loud REMOTE HOST IDENTIFICATION HAS CHANGED warning: either the server was rebuilt or someone is intercepting. Verify before removing the old entry (ssh-keygen -R host).

Generating and installing keys

ssh-keygen -t ed25519 -C "jane@work-laptop"
# Enter a passphrase! It encrypts the private key on disk.

ssh-copy-id deploy@203.0.113.10        # appends your public key to authorized_keys
# manual equivalent:
cat ~/.ssh/id_ed25519.pub | ssh deploy@203.0.113.10 \
  'mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys'

ssh-agent: type the passphrase once

eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519       # macOS: ssh-add --apple-use-keychain
ssh-add -l                      # loaded keys
ssh -A bastion                  # agent forwarding: convenient but risky; prefer ProxyJump

The client config file

Stop typing long commands. ~/.ssh/config (mode 600) defines aliases and defaults.

Host web1
    HostName 203.0.113.10
    User deploy
    Port 22
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes

Host db1
    HostName 10.0.1.5            # private IP, reachable only via bastion
    User admin
    ProxyJump bastion            # hop through bastion automatically

Host bastion
    HostName bastion.example.com
    User jump

Host *
    ServerAliveInterval 30       # keep idle connections from dropping
    ServerAliveCountMax 3
    AddKeysToAgent yes
    ControlMaster auto           # reuse one connection for many sessions (fast)
    ControlPath ~/.ssh/cm-%r@%h:%p
    ControlPersist 10m
ssh web1                         # that's it
ssh db1                          # transparently via bastion
ssh -v web1                      # verbose debugging (-vvv for more)

Running commands and copying files

ssh web1 'uptime; df -h /'                  # run and return
ssh web1 'sudo systemctl restart myapp'
ssh -t web1 'sudo -i'                        # -t allocates a TTY for interactive programs

scp app.tar.gz web1:/tmp/                    # simple copy
scp -r ./dist web1:/var/www/site/

rsync -avz --delete --progress ./dist/ web1:/var/www/site/
#  -a archive (perms, times, recursion)  -v verbose  -z compress
#  --delete  remove remote files not present locally (mirror)  --dry-run to preview
rsync -avz -e "ssh -p 2222" ./ web1:/opt/myapp/   # custom SSH options
rsync -avz --exclude node_modules --exclude .git ./ web1:/opt/myapp/
Prefer rsync over scp

rsync copies only the differences, resumes interrupted transfers and has --dry-run. Mind the trailing slash: ./dist/ copies the contents, ./dist copies the directory itself.

Tunnels (port forwarding)

SSH can carry other traffic through its encrypted connection, so you can reach services that are not exposed to the internet.

# Local forward: make remote DB reachable at localhost:5433 on my laptop
ssh -L 5433:localhost:5432 web1 -N
psql -h localhost -p 5433 -U app mydb

# Reach a private DB that web1 can see but you cannot
ssh -L 5433:db.internal:5432 web1 -N

# Remote forward: expose my laptop's :3000 as :8080 on the server (demo/webhook testing)
ssh -R 8080:localhost:3000 web1 -N

# Dynamic forward: SOCKS proxy for browsing via the server
ssh -D 1080 web1 -N
 laptop:5433 ═══ encrypted SSH tunnel ═══▶ web1 ───▶ db.internal:5432
 (psql connects here)                       (db port never public)

-N means no remote command; add -f to background. This beats opening the database port to the internet, always.

Hardening the server

After you confirmed key login works for a non-root user (in a second terminal!), edit /etc/ssh/sshd_config or better a drop-in at /etc/ssh/sshd_config.d/99-hardening.conf:

PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
AllowUsers deploy alice
MaxAuthTries 3
LoginGraceTime 20
X11Forwarding no
ClientAliveInterval 300
ClientAliveCountMax 2
sudo sshd -t                       # validate config: prints nothing if OK
sudo systemctl reload ssh          # service is "sshd" on RHEL-family
# Keep your current session open; test a NEW login before closing it.
MeasureBenefit
Disable password authEliminates brute-force of passwords
Disable root loginAttackers must also guess a username; sudo gives audit trail
Firewall / security group on port 22Allow only your office/VPN IPs where possible
fail2ban or sshguardBans IPs after repeated failures
Changing the portReduces log noise only; not real security
Bastion host or VPN (Tailscale/WireGuard)Private servers have no public SSH at all
Short-lived certificates (SSH CA), SSM, TeleportBetter than long-lived static keys at scale

sudo systemctl enable --now fail2ban
sudo fail2ban-client status sshd

SSH keys in CI/CD

  • Create a dedicated deploy key per project/environment, with no passphrase (CI cannot type one), stored in the CI secret store.
  • Limit its power on the server with a restricted sudo rule, or a forced command in authorized_keys: 
    command="/opt/myapp/bin/deploy.sh",no-port-forwarding,no-agent-forwarding,no-pty ssh-ed25519 AAAA... ci-deploy
  • Pin the host key instead of disabling checking: ssh-keyscan -H host >> known_hosts. Never use StrictHostKeyChecking=no in production pipelines.

Troubleshooting

SymptomCheck
Permission denied (publickey)ssh -v: is the key offered? Server's authorized_keys perms (700 ~/.ssh, 600 file, home not group-writable)? Right user? journalctl -u ssh on the server.
Connection timed outFirewall/security group, wrong IP, server down
Connection refusedsshd not running or other port: ss -tlnp | grep ssh
Too many authentication failuresAgent offers many keys; use IdentitiesOnly yes
Session freezesAdd ServerAliveInterval; use tmux
UNPROTECTED PRIVATE KEY FILEchmod 600 the key
Protect the private key

Anyone with it (and no passphrase) is you. Never commit it, paste it in chat or copy it to servers. If leaked, remove its public half from every authorized_keys immediately and generate a new pair.

Try it

  1. Create an alias in ~/.ssh/config for your VPS and log in with ssh myserver.
  2. Run a local web server on the VPS bound to 127.0.0.1:8000 and view it in your laptop browser with ssh -L 8080:localhost:8000 myserver -N.
  3. Harden sshd as above, validate with sshd -t, test a new session, then try logging in with -o PubkeyAuthentication=no and confirm it is refused.
  4. Use rsync -avzn (dry run) to preview syncing a folder, then run it for real.
