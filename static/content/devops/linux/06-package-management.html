Package Management and Runtimes

Installing software on a server should be repeatable, verifiable and updatable. Package managers give you that; downloading random tarballs and running "make install" gives you a snowflake.

Why package managers

A package manager knows what files belong to which package, what other packages are required (dependencies), which versions are available, and how to verify authenticity (cryptographic signatures). It lets you install, upgrade, list and cleanly remove software, and apply security patches with a single command. Without it you track versions in your head and leave orphaned files everywhere.

apt (Debian, Ubuntu)

sudo apt update                    # refresh the package INDEX (does not install anything)
sudo apt upgrade -y                # install available updates
sudo apt full-upgrade              # also allow removals/new deps (kernel upgrades)
sudo apt install -y nginx curl git # install
apt search redis                   # search
apt show nginx                     # details, version, dependencies
apt policy nginx                   # installed vs candidate versions and sources
sudo apt remove nginx              # remove program, keep config
sudo apt purge nginx               # remove program AND config
sudo apt autoremove                # remove no-longer-needed dependencies
dpkg -l | grep nginx               # installed packages
dpkg -L nginx                      # files a package installed
dpkg -S /usr/sbin/nginx            # which package owns this file?
sudo apt install ./package.deb     # local .deb with dependency resolution

dnf (RHEL, Rocky, Alma, Fedora)

sudo dnf check-update
sudo dnf upgrade -y
sudo dnf install -y nginx
dnf search redis; dnf info nginx
sudo dnf remove nginx
rpm -qa | grep nginx               # installed
rpm -ql nginx                      # files in package
rpm -qf /usr/sbin/nginx            # owner of a file
dnf provides '*/bin/dig'           # which package supplies this command?
sudo dnf install epel-release      # extra packages repo for RHEL family

In scripts and Dockerfiles

Use apt-get (stable CLI for scripting) and non-interactive mode: DEBIAN_FRONTEND=noninteractive apt-get install -y --no-install-recommends curl. In Docker, combine update, install and rm -rf /var/lib/apt/lists/* in one layer.

Repositories and trust

Packages come from repositories listed in /etc/apt/sources.list.d/ or /etc/yum.repos.d/. Distro repos are conservative: stable but often older versions (e.g. an old Node or Postgres). Vendors publish their own repos for newer versions. Adding one means trusting that vendor with root on your machine, so do it deliberately and use signed keyrings:

# Example: PostgreSQL's official apt repository (current, documented method)
sudo apt install -y postgresql-common
sudo /usr/share/postgresql-common/pgdg/apt.postgresql.org.sh

# Generic modern pattern (keyring per repo, not the deprecated apt-key):
curl -fsSL https://example.com/repo.gpg | sudo gpg --dearmor -o /etc/apt/keyrings/example.gpg
echo "deb [signed-by=/etc/apt/keyrings/example.gpg] https://example.com/apt stable main" \
  | sudo tee /etc/apt/sources.list.d/example.list
sudo apt update

Automatic security updates

Unpatched servers are the easiest targets. On Ubuntu/Debian:

sudo apt install -y unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades
cat /etc/apt/apt.conf.d/20auto-upgrades
# APT::Periodic::Update-Package-Lists "1";
# APT::Periodic::Unattended-Upgrade "1";
[ -f /var/run/reboot-required ] && echo "reboot needed (kernel update)"

On RHEL family use dnf-automatic. Kernel updates need a reboot (or live patching) to take effect. In a fleet, patch via rebuilding images rather than patching in place.

Language runtimes: the version problem

Your app needs Node 22, another needs Node 20; the distro ships Node 18. Installing a language runtime globally with the system package manager couples every app to one version. Use a version manager or isolate per app.

Node with nvm

curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.3/install.sh | bash   # check latest version first
source ~/.bashrc
nvm install --lts
nvm use --lts
node -v; npm -v
echo "22" > .nvmrc      # pin per project; then "nvm use"
nvm and systemd do not mix automatically

nvm modifies your interactive shell's PATH, which a systemd service never sees. In the unit file use the absolute path: ExecStart=/home/deploy/.nvm/versions/node/v22.11.0/bin/node server.js, or install Node system-wide (NodeSource repo, or unpack the official tarball in /opt/node). Better yet, build a container image with the runtime baked in.

Python

sudo apt install -y python3-venv python3-pip
cd /opt/myapp
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
# systemd: ExecStart=/opt/myapp/.venv/bin/gunicorn app:app -b 127.0.0.1:8000
# Do not "sudo pip install" system-wide: modern distros block it (PEP 668)

Installing binaries directly

Many tools ship as a single static binary on GitHub releases. Safe pattern: download, verify checksum, install into /usr/local/bin.

curl -fsSLO https://example.com/tool_1.2.3_linux_amd64.tar.gz
curl -fsSLO https://example.com/checksums.txt
sha256sum -c checksums.txt --ignore-missing
tar xzf tool_1.2.3_linux_amd64.tar.gz
sudo install -m 0755 tool /usr/local/bin/tool

Others: snap (Ubuntu's sandboxed packages, auto-updating), Flatpak (desktop), Homebrew on Linux, and of course containers, which bundle runtime and dependencies and avoid most problems here.

Best practices

  • Pin versions of important software; upgrade deliberately and test in staging first (apt-mark hold pkg to freeze).
  • Keep a list of what you installed (script or Ansible later). A server built from a script can be rebuilt in minutes.
  • Minimise installed software: every package is attack surface and something to patch.
  • Never pipe unknown scripts to a root shell. Read it, pin a version, verify checksums.
  • Commit lockfiles so every environment installs the same dependency tree.
