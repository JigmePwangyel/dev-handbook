Cron and Scheduled Automation

Backups, certificate renewals, log cleanup, report generation: servers constantly need things done on a schedule. Linux offers two tools, the classic cron and the modern systemd timers. Both fail quietly unless you design for it.

Why scheduling needs care

Scheduled jobs run unattended, with no terminal, a minimal environment and nobody watching. The typical failure: a nightly backup has silently failed for three months and you discover it when you need to restore. A good scheduled job is logged, idempotent, locked against overlap and monitored.

cron basics

The cron daemon reads tables ("crontabs") and runs commands when the time matches.

crontab -e        # edit YOUR crontab
crontab -l        # list
sudo crontab -u deploy -l   # another user's
# system-wide: /etc/crontab and /etc/cron.d/*  (these have an extra USER column)
# also drop scripts into /etc/cron.daily, .hourly, .weekly, .monthly

The five fields

 ┌───────────── minute        (0-59)
 │ ┌─────────── hour          (0-23)
 │ │ ┌───────── day of month  (1-31)
 │ │ │ ┌─────── month         (1-12)
 │ │ │ │ ┌───── day of week   (0-7, 0 and 7 = Sunday)
 │ │ │ │ │
 * * * * *  command to run
ExpressionMeaning
*/5 * * * *Every 5 minutes
0 * * * *Top of every hour
30 2 * * *Daily at 02:30
0 9 * * 1-509:00 Monday to Friday
0 0 1 * *Midnight on the 1st of each month
@rebootOnce at startup (also @daily, @hourly, @weekly)

Use a tool like crontab.guru to check expressions. Note: if both day-of-month and day-of-week are set, cron runs when either matches.

A sensible crontab

SHELL=/bin/bash
PATH=/usr/local/bin:/usr/bin:/bin
MAILTO=ops@example.com

# m h dom mon dow  command
30 2 * * *  /opt/myapp/bin/backup.sh >> /var/log/myapp/backup.log 2>&1
*/10 * * * * flock -n /tmp/sync.lock /opt/myapp/bin/sync.sh >> /var/log/myapp/sync.log 2>&1
0 4 * * 0   /usr/bin/certbot renew --quiet

Cron pitfalls (they all bite once)

  • Minimal environment. Cron has a tiny PATH and none of your shell profile (no nvm, no env vars). Use absolute paths, set PATH at the top, source env files inside the script.
  • Silent output. stdout/stderr go to mail (usually unconfigured) and vanish. Redirect to a log file as above, or pipe to logger -t backup to land in the journal.
  • Overlapping runs. If a job takes longer than its interval, copies pile up. Wrap in flock -n.
  • The % character means newline in crontab lines; escape as \% (e.g. in date +\%F).
  • Time zones. Cron uses the server's local time; DST can skip or repeat jobs. Run servers in UTC.
  • Missed jobs. If the machine is off at the scheduled time, plain cron skips it (anacron or systemd timers with Persistent=true catch up).
  • No failure alerting. Nothing tells you it stopped working. Add a dead-man's-switch ping (below).
  • Many servers, one schedule. If three replicas each run the nightly job, it runs three times. Use a leader, a lock in the DB, or a central scheduler.
# See what cron ran
journalctl -u cron --since today          # Debian/Ubuntu: service "cron"
journalctl -u crond --since today         # RHEL family
grep CRON /var/log/syslog | tail

Dead man's switch monitoring

Alerting on "job failed" misses the case where the job never ran. Invert it: the job pings a monitoring URL on success, and the service alerts if the ping does not arrive on schedule (Healthchecks.io, Cronitor, Uptime Kuma push monitors).

30 2 * * * /opt/myapp/bin/backup.sh && curl -fsS -m 10 --retry 3 https://hc-ping.com/YOUR-UUID >/dev/null

systemd timers

A timer is a unit that activates a matching service unit. Compared with cron you get journal logging, dependency ordering, resource limits, hardening, catch-up of missed runs, random delay, and a clear list of next/last run times.

1. The job: /etc/systemd/system/backup.service

[Unit]
Description=Nightly database backup
After=network-online.target postgresql.service

[Service]
Type=oneshot
User=backup
ExecStart=/opt/myapp/bin/backup.sh
# Failure notification hook (optional)
# OnFailure=notify-failure@%n.service
Nice=10
IOSchedulingClass=idle

2. The schedule: /etc/systemd/system/backup.timer

[Unit]
Description=Run backup nightly

[Timer]
OnCalendar=*-*-* 02:30:00
RandomizedDelaySec=300
Persistent=true

[Install]
WantedBy=timers.target

3. Enable and inspect

sudo systemctl daemon-reload
sudo systemctl enable --now backup.timer      # enable the TIMER, not the service
systemctl list-timers --all                   # NEXT / LEFT / LAST / PASSED
sudo systemctl start backup.service           # run it right now to test
journalctl -u backup.service -n 50            # output of runs
systemd-analyze calendar "Mon..Fri *-*-* 09:00"   # validate and preview schedules
Timer settingMeaning
OnCalendar=Wall-clock schedule: hourly, daily, Mon *-*-* 03:00, *:0/15
OnBootSec=, OnUnitActiveSec=Relative: 5 minutes after boot, every 1 hour after last run
Persistent=trueRun missed executions after downtime
RandomizedDelaySec=Spread load across many servers
AccuracySec=Allow coalescing wakeups (default 1 min)

Rule of thumb: quick personal chores, cron; anything operationally important on a modern Linux server, a timer.

Beyond one machine

  • Kubernetes CronJob: schedule container jobs in a cluster (Kubernetes section).
  • CI schedules: on: schedule: - cron: "0 3 * * *" in GitHub Actions for nightly builds and dependency checks.
  • Cloud schedulers: EventBridge Scheduler, Cloud Scheduler; use workflow engines (Airflow, Temporal) for complex dependent jobs.

Best practices

  • Make each job a script you can run by hand (set -euo pipefail), then schedule the script.
  • Idempotent, with locking and a timeout (timeout 30m cmd).
  • Log with timestamps; alert on failure and on silence.
  • Test restores, not just backups. A backup you never restored is unproven.
  • Stagger heavy jobs; avoid the top of the hour when everyone else runs theirs.

Try it

  1. Add a cron entry that runs every minute: * * * * * date >> /tmp/cron-test.log 2>&1. Confirm it works, then remove it.
  2. Write a script that fails, schedule it, and notice how you find out (logs, mail). Wrap it with flock and a log redirect.
  3. Convert the same job to a systemd service plus timer with OnCalendar=*:0/2, watch systemctl list-timers and journalctl -u.
