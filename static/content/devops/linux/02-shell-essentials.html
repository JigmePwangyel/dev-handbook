Shell Essentials

On a server there is usually no GUI. The shell is how you inspect, change and automate everything. A small set of commands and the idea of pipes cover 90% of daily work.

Why the command line

GUIs are great for one-off tasks but cannot be scripted, version-controlled, repeated on 50 servers, or used over a slow SSH link. Every command you type is also something you can paste into a script, a Dockerfile or a CI job. The shell is the common language of DevOps.

Shell, terminal, bash

  • Terminal: the window. Shell: the program interpreting your commands (bash on most servers, zsh on macOS, sh/dash for minimal scripts).
  • The prompt deploy@web1:~$ means user deploy on host web1 in the home directory (~); $ means normal user, # means root.
  • Command anatomy: command [options] [arguments], e.g. ls -l /var/log.

Navigating and looking around

pwd                    # where am I?
ls                     # list files
ls -lah                # long format, hidden files, human sizes
cd /var/log            # absolute path
cd ..                  # up one level
cd ~                   # home (or just: cd)
cd -                   # back to previous directory
tree -L 2 /etc/nginx   # directory tree (apt install tree)
file /bin/ls           # what kind of file is this?
stat app.log           # size, owner, permissions, timestamps

Working with files

mkdir -p app/releases/v1       # -p creates parents, no error if exists
touch notes.txt                # create empty file / update timestamp
cp config.yml config.yml.bak   # copy
cp -r src/ backup/             # copy directory recursively
mv old.txt new.txt             # rename OR move
rm file.txt                    # delete (no trash can!)
rm -r olddir/                  # delete directory recursively
ln -s /opt/app/releases/v2 /opt/app/current   # symbolic link
rm has no undo

Never run rm -rf with a variable you have not checked: rm -rf "$DIR/" with DIR empty becomes rm -rf /. Modern GNU rm refuses /, but not /* or a wrongly-set path. Use ls with the same argument first, and quote variables.

Reading and searching

cat file.txt                 # print whole file
less /var/log/syslog         # page through (q quit, / search, G end, F follow)
head -n 20 file              # first 20 lines
tail -n 50 file              # last 50 lines
tail -f /var/log/nginx/error.log   # follow new lines live (Ctrl+C to stop)
wc -l file                   # count lines

grep "error" app.log                 # lines containing "error"
grep -i -n "timeout" app.log         # case-insensitive, with line numbers
grep -r "DATABASE_URL" /etc/myapp    # recursive search
grep -v "healthz" access.log         # invert: lines NOT matching
find /var/log -name "*.log" -mtime -1      # modified in last day
find . -type f -size +100M                 # big files
rg "pattern"                         # ripgrep: faster grep (apt install ripgrep)

Pipes and redirection: the superpower

Every program has three streams: stdin (0), stdout (1), stderr (2). The shell lets you wire them together. Small tools doing one thing, composed with pipes, is the Unix philosophy.

command > out.txt        # stdout to file (overwrite)
command >> out.txt       # append
command 2> err.txt       # stderr to file
command > all.txt 2>&1  # both to the same file
command &> all.txt       # bash shorthand for the same
command > /dev/null 2>&1   # discard everything
command1 | command2      # stdout of 1 becomes stdin of 2
command < input.txt      # file as stdin

A realistic pipeline: top 5 client IPs hitting nginx.

awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -nr | head -5
#      1. take field 1 (IP)   2. group   3. count   4. numeric desc   5. top 5

echo "deploy ok" | sudo tee -a /var/log/deploys.log   # append with sudo (redirection ignores sudo!)

Variables, quoting and exit codes

NAME="web server"            # no spaces around =
echo "$NAME"                 # double quotes: variable expands
echo '$NAME'                 # single quotes: literal
export APP_ENV=production    # visible to child processes
echo "$HOME $USER $PATH"
today=$(date +%F)            # command substitution
echo "Backup-$today.tar.gz"

ls /nonexistent; echo $?     # $? = exit code of last command: 0 = success, nonzero = failure
mkdir build && cd build      # run second only if first succeeded
cmd || echo "failed"         # run second only if first failed
cmd1; cmd2                   # run both regardless

Exit codes are the glue of automation: CI jobs, cron and deploy scripts all decide success by them.

Running things in the background

long_task &           # run in background of this shell
jobs                  # list
fg %1                 # bring to foreground
nohup ./task.sh &     # survive logout (output to nohup.out)
tmux new -s work      # better: a persistent session; detach with Ctrl+B then D
tmux attach -t work   # come back after SSH dropped
Use tmux on servers

If your SSH connection drops mid-upgrade, a plain shell kills the job. Inside tmux it keeps running and you reattach later.

Pitfalls

  • Unquoted variables with spaces split into several arguments. Quote: "$file".
  • sudo cmd > /root/file: the redirect is done by your shell, not sudo. Use tee.
  • Copy-pasting commands from the web without reading them, especially curl ... | sudo bash. Download, inspect, then run.
  • Smart quotes from documents break commands. Plain " and ' only.

Try it

  1. In a scratch directory create 5 files with touch f{1..5}.log, then list, rename one, and delete the rest with a single rm.
  2. Generate some data: seq 1 1000 | shuf | head -20 | sort -n. Explain each stage.
  3. Find the five largest directories under /var: sudo du -h --max-depth=2 /var 2>/dev/null | sort -hr | head -5.
  4. Start tmux, run ping 1.1.1.1, detach, close the terminal, reconnect and reattach.
