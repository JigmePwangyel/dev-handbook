Logs and Troubleshooting

Something is broken at 2 a.m. The difference between a 5-minute fix and a 3-hour guessing game is knowing where logs live, which four resources can run out, and following a method rather than a hunch.

journalctl recipes

journalctl -u myapp -f                          # follow a service
journalctl -u myapp --since "30 min ago" -p warning
journalctl -b -p err                            # errors since boot
journalctl -k | grep -i "out of memory"         # OOM killer events
journalctl _PID=1234
journalctl -u ssh -u nginx --since today        # multiple units interleaved

Working with plain log files

sudo tail -f /var/log/nginx/error.log
sudo grep -E " 5[0-9]{2} " /var/log/nginx/access.log | tail    # recent 5xx
# status code breakdown
awk '{print $9}' /var/log/nginx/access.log | sort | uniq -c | sort -nr
# slowest requests, if $request_time is the last field in your log_format
awk '{print $NF, $7}' /var/log/nginx/access.log | sort -nr | head
zgrep "ERROR" /var/log/myapp/app.log.*.gz                       # rotated, compressed logs

Log rotation

Logs grow forever and fill disks. logrotate rotates, compresses and prunes them. Config in /etc/logrotate.d/:

/var/log/myapp/*.log {
    daily
    rotate 14
    compress
    delaycompress
    missingok
    notifempty
    copytruncate        # for apps that keep the file open and cannot reopen on signal
}

Test with sudo logrotate -d /etc/logrotate.d/myapp. The journal has its own limits (SystemMaxUse=500M in /etc/systemd/journald.conf).

Log levels and structure

Use levels (debug, info, warn, error), include timestamps, request IDs and enough context to reproduce. Prefer structured JSON logs; they can be queried by tools later (Observability section). Never log passwords, tokens or full card numbers.

The four resources

Most performance problems are one of CPU, memory, disk or network being exhausted. Check each quickly.

uptime                       # load averages (1, 5, 15 min). Compare against nproc.
top -o %CPU                  # or htop; press M to sort by memory
free -h                      # memory: look at "available", not "free"
vmstat 1 5                   # r=runnable, si/so = swap in/out (nonzero = memory pressure), wa = I/O wait
df -h                        # disk space
df -i                        # inodes (millions of tiny files can exhaust them)
du -xh / --max-depth=2 2>/dev/null | sort -hr | head -15   # what is eating disk
sudo lsof +L1                # deleted files still held open (space not freed!)
iostat -x 1 3                # disk utilisation/latency (apt install sysstat)
ss -s                        # socket summary
ResourceSymptomsTypical causes / fixes
CPULoad above core count, slow responsesRunaway process, inefficient code, too few cores. top, profile, scale.
MemorySwapping, processes killed, Killed messagesLeak or undersized box. Check OOM killer in journalctl -k; set limits; add RAM.
DiskNo space left on device, DB/app write errorsLogs, old releases, Docker images (docker system df), core dumps. Rotate and clean.
NetworkTimeouts, connection resetsFirewall, DNS, port exhaustion, remote down. See below.
"free" memory is a trap

Linux uses spare RAM as disk cache, so "free" looks tiny on a healthy box. The available column estimates what applications can actually get. Worry when available is low and swap is busy.

Network diagnostics

ip -br addr; ip route                 # my addresses and gateway
ss -tlnp                              # what is LISTENING (and which process)
ss -tn state established | wc -l      # connection count
curl -v http://localhost:3000/healthz # does the app answer locally?
curl -sI https://example.com          # headers only
dig +short example.com                # DNS
ping -c 3 1.1.1.1                     # reachability (ICMP may be blocked)
traceroute example.com                # path (or mtr: continuous)
nc -vz db.internal 5432               # can I open a TCP connection to this port?
sudo tcpdump -i any port 3000 -nn -c 20   # look at actual packets
sudo ufw status verbose               # host firewall

Key distinction in ss -tlnp: an app listening on 127.0.0.1:3000 is reachable only from the machine itself; 0.0.0.0:3000 or [::]:3000 means all interfaces. "Works locally, not remotely" is very often this, or a firewall.

A debugging checklist

 1. What exactly is the symptom?     Who is affected? Since when?
 2. What changed?                    Deploy, config, cert, dependency, traffic, time?
 3. Reproduce / observe              curl it, read the error verbatim
 4. Work along the request path      DNS ▶ firewall ▶ proxy ▶ app ▶ DB
 5. Check the four resources         CPU, memory, disk, network
 6. Read logs around the failure     time-bounded, errors first
 7. Form ONE hypothesis, test it     change one thing at a time
 8. Fix, verify, write it down       runbook + postmortem

Worked example: "the site returns 502"

  1. Symptom: curl -I https://example.com gives 502 Bad Gateway. 502 comes from the proxy: it could not get a valid reply from the app.
  2. On the server: systemctl status myapp shows failed (Result: exit-code).
  3. journalctl -u myapp -n 50 --no-pager shows Error: listen EADDRINUSE :::3000 or ECONNREFUSED db:5432 or Killed.
  4. Port in use: ss -tlnp | grep 3000 reveals a leftover process; stop it, restart the service.
  5. DB refused: systemctl status postgresql, then df -h (a full disk crashes databases).
  6. Killed: journalctl -k | grep -i oom confirms memory exhaustion; add swap or RAM, or fix the leak.
  7. After fixing, curl -I again, then add a monitoring alert so you hear about it before users do.

Principles

  • Change one thing at a time and note it; otherwise you will not know what fixed it.
  • Read the actual error completely. The answer is often in the line above the one you copied.
  • Restarting is not a fix, it destroys evidence. Capture logs and state first (journalctl, ps, ss output) then restart to restore service.
  • Binary search the path: test from the middle (e.g. curl localhost:3000) to learn which half is broken.
  • Use strace -p PID or lsof as last resorts to see what a stuck process is doing.

Try it

  1. Create a 1 GB file with fallocate -l 1G /tmp/big, find it with du, delete it, and watch df -h.
  2. Break your own service: set a wrong ExecStart path, reload, start it, and diagnose with only systemctl status and journalctl.
  3. Start two servers on port 8000 and read the EADDRINUSE error. Find the culprit with ss -tlnp.
  4. Write a one-page runbook for "disk full" using the commands above.
