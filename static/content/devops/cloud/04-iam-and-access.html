IAM and Access Control

Identity and Access Management answers one question for every API call: who is asking, and are they allowed to do this to that? Most cloud security incidents are IAM failures, so this is the most valuable cloud skill to get right.

Why IAM exists

Imagine one shared admin password and one access key that every engineer, server and CI job uses. When something is deleted you cannot tell who did it; when someone leaves you must rotate the key everywhere; and a leaked key hands over everything. IAM solves this with individual identities, fine-grained permissions, temporary credentials and audit trails.

Core concepts

ConceptMeaning
Root userThe account owner. Unlimited power. Lock it away with MFA; use it only for the few tasks that require it.
UserA long-lived identity for a person (or, legacy, a program). Modern practice: humans sign in through SSO (IAM Identity Center) instead of IAM users.
GroupA set of users that share policies (e.g. developers).
RoleAn identity with permissions but no password or permanent keys. Anyone/anything authorised can assume it and receive temporary credentials.
PolicyA JSON document listing allowed/denied actions on resources.
PrincipalThe entity making the request (user, role, service, account).

Anatomy of a policy

A policy is a list of statements. Each has an Effect (Allow/Deny), Actions, Resources, and optional Conditions.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadWriteAppBucketObjects",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::acme-app-uploads/*"
    },
    {
      "Sid": "ListTheBucket",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::acme-app-uploads"
    },
    {
      "Sid": "DenyUnencryptedTransport",
      "Effect": "Deny",
      "Action": "s3:*",
      "Resource": ["arn:aws:s3:::acme-app-uploads", "arn:aws:s3:::acme-app-uploads/*"],
      "Condition": { "Bool": { "aws:SecureTransport": "false" } }
    }
  ]
}

Note the two resource ARNs: object-level actions apply to bucket/*, bucket-level actions (ListBucket) to the bucket itself. This distinction trips up everyone once.

How a decision is made

  1. Everything is implicitly denied by default.
  2. An explicit Allow in an applicable policy grants access.
  3. An explicit Deny anywhere always wins over any Allow.
  4. Organisation-level SCPs and permission boundaries further cap what can be granted.

Least privilege

The principle

Grant only the permissions needed for the task, on only the resources needed, for only as long as needed. A compromised identity can then do limited damage.

BadBetter
"Action": "*", "Resource": "*"Specific actions on specific ARNs
s3:* on all bucketss3:GetObject on one bucket prefix
Shared admin userIndividual SSO users with role-based access
Permanent access keys in CIOIDC federation to a short-lived role

Practical workflow: start with an AWS-managed policy to get going, then use IAM Access Analyzer (policy generation from CloudTrail activity) and the "last accessed" data to trim down. Test with the policy simulator before deploying.

Roles for machines

Applications need to call AWS (read S3, fetch secrets). The wrong way is to paste an access key into an environment variable or config file: it lives forever, ends up in git, and is copied around. The right way is a role.

 EC2 instance / ECS task / Lambda
        │  "who am I?"
        ▼
 Instance metadata / task endpoint ──▶ STS issues TEMPORARY credentials
        │                                (access key + secret + token, ~1-6 h, auto-rotated)
        ▼
 AWS SDK uses them automatically ──▶ S3, Secrets Manager, ...

A role has two policies: a trust policy (who may assume it) and permissions policies (what it can do).

# Trust policy: lets ECS tasks assume this role
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "ecs-tasks.amazonaws.com" },
    "Action": "sts:AssumeRole"
  }]
}

With the role attached, your code needs no credentials at all:

import boto3
s3 = boto3.client("s3")          # SDK finds role credentials automatically
s3.put_object(Bucket="acme-app-uploads", Key="hello.txt", Body=b"hi")

Variants of the same idea: EC2 instance profiles, ECS task roles (distinct from the task execution role that pulls images), IRSA / EKS Pod Identity for Kubernetes pods, and GitHub Actions OIDC so CI assumes a role without stored secrets.

# GitHub Actions: no long-lived keys
permissions:
  id-token: write
  contents: read
steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123456789012:role/gha-deploy
      aws-region: eu-west-1

Humans: SSO, roles and MFA

  • Use IAM Identity Center (or your IdP such as Okta/Entra) so people log in once and get short-lived role sessions: aws sso login --profile dev.
  • Enforce MFA, ideally phishing-resistant (passkeys / FIDO2 hardware keys) rather than SMS. Root user always gets MFA.
  • Separate AWS accounts for prod, staging and dev (via AWS Organizations). Accounts are the hardest security boundary; a dev mistake cannot touch prod.
  • Use "break glass" admin roles for emergencies, with alerts when used.

Auditing

  • CloudTrail records every API call; send it to a locked-down bucket in a separate security account.
  • Alert on: root login, IAM policy changes, disabling of CloudTrail, console login without MFA.
  • Regularly review unused users, keys older than 90 days, and the credential report (aws iam generate-credential-report).

Common pitfalls

Leaked keys are found in minutes

Bots scan public GitHub for AKIA... keys continuously and spin up crypto miners within minutes of a push. If a key leaks: deactivate it first, then investigate via CloudTrail, then rotate. Deleting the commit is not enough. Use pre-commit scanners like gitleaks and enable GitHub secret scanning.

  • AdministratorAccess for everything "just to make it work". Then it never gets tightened.
  • Wildcards in iam:PassRole or iam:*: lets a user escalate to admin by creating/attaching powerful roles.
  • Public S3 buckets: enable account-wide "Block Public Access".
  • Confusing authentication with authorisation: being logged in does not mean being allowed.
  • Debugging AccessDenied: check identity policy, resource policy (bucket policy), SCPs, permission boundary, and KMS key policy. Read the error: it often names the missing action.

Equivalents

GCP: IAM roles bound to members at org/folder/project/resource level, and service accounts for workloads (use Workload Identity). Azure: Entra ID plus Azure RBAC role assignments with managed identities for workloads. The model is the same: identities, roles, scopes, short-lived tokens.

Try it

  1. Run aws sts get-caller-identity. Are you root, a user, or an assumed role?
  2. Write a policy allowing read-only access to s3://my-bucket/reports/* only. Test it with the policy simulator or by attaching it to a test role.
  3. Create a role for EC2 with S3 read access, attach it to an instance, and run aws s3 ls on it without configuring any keys. Then run curl http://169.254.169.254/latest/meta-data/iam/security-credentials/ (with IMDSv2 token) and observe the temporary credentials.
  4. Search your repos for committed secrets: gitleaks detect.
