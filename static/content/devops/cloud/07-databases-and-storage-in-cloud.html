Databases and Storage in the Cloud

Compute is disposable; data is not. State is where cloud projects get hurt: lost backups, corrupt failovers, surprise bills. This lesson covers the three kinds of storage, managed databases, backups, replicas and the S3 patterns you will use constantly.

Rule of thumb

If your app writes user files to local disk, move them to object storage. Local disks vanish with the container/instance and cannot be shared across replicas, which breaks horizontal scaling.

Managed databases

Why not run Postgres yourself on EC2?

You can, but you then own: installation, security patches, major version upgrades, backup scripts and restore drills, replication setup, failover logic, disk growth, monitoring, and 3 a.m. pages. A managed database (RDS, Aurora, Cloud SQL, Azure Database) automates all of that for roughly 20-40% premium. For almost every team the premium is worth it.

Start with Postgres. It handles JSON, full-text search, geospatial and queues well enough that you can defer specialised stores until measured need.

High availability vs read scaling: Multi-AZ vs replicas

These are frequently confused:

 MULTI-AZ (availability)                    READ REPLICA (scale reads)
 ┌────────┐ sync  ┌─────────┐               ┌─────────┐ async  ┌──────────┐
 │Primary │──────▶│ Standby │               │ Primary │───────▶│ Replica  │ ◀─ SELECTs
 │ AZ-a   │       │  AZ-b   │               │         │        │ (lag!)   │
 └────────┘       └─────────┘               └─────────┘        └──────────┘
 Standby serves NO traffic.                 Replicas serve reads, may lag by ms-seconds.
 Automatic failover ~60-120 s.              Can be promoted manually; can be cross-region.
  • Multi-AZ protects against an AZ failure or instance crash. Use for all production databases.
  • Read replicas offload read-heavy traffic and reports. Reads can be stale (replication lag): do not read-your-own-write from a replica without care.
  • Writes always go to the single primary; scaling writes means a bigger instance, sharding, or a different data model.

Backups: the part that saves your job

  • Automated snapshots + PITR: enable them, set retention (7-35 days). Point-in-time recovery lets you restore to any second.
  • Restores create a new instance; they do not rewind in place. Practise it and time it.
  • Cross-region / cross-account copies protect against region loss, ransomware and account compromise. Use AWS Backup with vault lock.
  • Logical dumps (pg_dump) as an extra, portable layer.
  • Deletion protection on, and a final snapshot on delete.
# Create a snapshot and restore it to a new instance
aws rds create-db-snapshot --db-instance-identifier prod-db \
  --db-snapshot-identifier prod-db-2026-10-05

aws rds restore-db-instance-to-point-in-time \
  --source-db-instance-identifier prod-db \
  --target-db-instance-identifier prod-db-restore-test \
  --restore-time 2026-10-05T09:15:00Z
A backup you have never restored is a hope, not a backup

Schedule a recurring restore drill into a scratch environment. Verify row counts and app startup against it. Record RTO (how long restore takes) and RPO (how much data you could lose).

Connection and security basics

  • Put databases in private subnets; allow only the app security group.
  • Encrypt at rest (KMS) and in transit (sslmode=require).
  • Keep credentials in Secrets Manager with rotation, or use IAM database authentication.
  • Use a connection pooler (RDS Proxy, PgBouncer): every Postgres connection costs memory, and serverless/autoscaled apps can open thousands.

S3 patterns

Presigned URLs for uploads

Do not proxy large uploads through your servers. Have the app hand the browser a short-lived signed URL; the browser uploads straight to S3.

import boto3
s3 = boto3.client("s3")
url = s3.generate_presigned_url(
    "put_object",
    Params={"Bucket": "acme-uploads", "Key": "users/42/avatar.png",
            "ContentType": "image/png"},
    ExpiresIn=300,
)
# browser: fetch(url, {method: "PUT", body: file, headers: {"Content-Type": "image/png"}})

Other essentials

  • Static website / SPA hosting: private bucket + CloudFront with Origin Access Control.
  • Block Public Access on at account level; grant access through IAM or presigned URLs.
  • Versioning: keeps old versions, protecting against accidental overwrite/delete. Add MFA delete or Object Lock for compliance.
  • Lifecycle rules: transition to cheaper classes and expire old data.
  • Event notifications: S3 → Lambda/SQS on object creation (thumbnails, virus scan, ETL).
  • Cross-region replication for DR or locality.

Pitfalls

  • Public buckets and leaked data: still the headline breach type.
  • Unbounded growth: logs and old snapshots accumulate; add lifecycle and retention policies.
  • Treating S3 as a filesystem: listing millions of keys is slow; design key prefixes and avoid rename-heavy workflows.
  • Reading stale replicas for just-written data.
  • Single-AZ databases in production and no tested restore.
  • Egress costs: serving big files straight from S3 to the internet is pricey; front with CloudFront.
  • Major version upgrades postponed until end-of-life forces a rushed migration.

Try it

  1. Create a small RDS Postgres (private subnet, Multi-AZ off for cost). Connect via an SSM tunnel or bastion, create a table, take a snapshot, then restore to a new instance and compare.
  2. Create an S3 bucket with versioning; overwrite an object and recover the previous version.
  3. Add a lifecycle rule transitioning logs/ to Standard-IA after 30 days and expiring after one year.
  4. Implement presigned-URL uploads from a tiny web page.
