AWS Core Services: The Essential Map

AWS has 200+ services, but a typical production web application uses about a dozen. Learn these well and you can read almost any architecture diagram. The same concepts exist on Google Cloud and Azure under different names.

Compute

EC2 (Elastic Compute Cloud)

Virtual machines. You choose an instance type (family + size, e.g. t3.micro, m7g.large, c7i.xlarge), an AMI (the OS image), a disk, a network location and a security group. Families: t burstable general purpose, m balanced, c compute-heavy, r memory-heavy, g/p GPU. A g suffix (e.g. m7g) means ARM Graviton chips, which are typically cheaper for the same performance.

aws ec2 run-instances \
  --image-id ami-0abcdef1234567890 \
  --instance-type t3.micro \
  --key-name my-key \
  --security-group-ids sg-0123456789abcdef0 \
  --subnet-id subnet-0123456789abcdef0 \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=demo}]'

Lambda

Run a function in response to an event (HTTP request, S3 upload, queue message, schedule). No servers to manage; billed per millisecond. Max 15 minutes per invocation.

ECS and EKS

ECS (Elastic Container Service) is AWS's own container orchestrator, simple and deeply integrated; run it on EC2 or on Fargate (serverless containers: no instances to manage). EKS (Elastic Kubernetes Service) is managed Kubernetes: AWS runs the control plane, you run (or Fargate-run) the nodes.

Storage

EBS (Elastic Block Store)

Network-attached disks for EC2. Behaves like a hard drive: one instance at a time (mostly), lives in one AZ, survives instance termination if configured. Types: gp3 (default SSD), io2 (high IOPS), st1 (throughput HDD). Snapshot them for backups.

S3 (Simple Storage Service)

Object storage: store files ("objects") in "buckets", addressed by key, over HTTP. Effectively unlimited, 11 nines of durability, cheap. Used for static sites, uploads, backups, logs, data lakes. Not a filesystem: no partial in-place edits, no directories (just key prefixes).

EFS

Managed NFS: a shared filesystem mountable by many instances at once. Useful for legacy apps needing shared files; pricier than S3 or EBS.

Networking

  • VPC: your private, isolated virtual network (next lesson).
  • ELB: load balancers. ALB (Layer 7, HTTP routing by path/host), NLB (Layer 4, TCP/UDP, extreme performance, static IPs).
  • Route 53: DNS plus health-checked routing (weighted, latency-based, failover).
  • CloudFront: CDN. Caches content at edge locations; terminates TLS near users; shields your origin.
  • API Gateway: managed front door for HTTP APIs, often in front of Lambda.

Databases

  • RDS: managed PostgreSQL, MySQL, MariaDB, SQL Server, Oracle. Automated backups, patching, Multi-AZ failover, read replicas.
  • Aurora: AWS's cloud-native MySQL/Postgres-compatible engine with shared storage across 3 AZs.
  • DynamoDB: serverless key-value/document NoSQL with single-digit-ms latency at any scale.
  • ElastiCache: managed Redis/Valkey/Memcached for caching and sessions.

Security and identity

  • IAM: users, roles, policies: every API call is authorised here.
  • KMS: encryption keys. Secrets Manager / SSM Parameter Store: store secrets and config.
  • ACM: free TLS certificates for ALB/CloudFront.

Observability

  • CloudWatch: metrics, logs, alarms, dashboards. EC2 CPU is free by default; memory and disk need an agent.
  • CloudTrail: audit log of every API call (who did what, when). Enable it in every account.

Learn concepts, not product names

Once you understand "a private network with subnets and route tables", every cloud is a dialect. Notable differences: GCP VPCs are global (subnets are regional), Azure organises resources into Resource Groups, and AWS accounts are the strongest isolation boundary.

Accounts, regions and the CLI

Most services are regional: an S3 bucket's data lives in one region, an EC2 instance in one AZ. IAM, Route 53 and CloudFront are global. "Where did my resources go?" almost always means the console is set to a different region.

# List S3 buckets (global listing, regional data)
aws s3 ls

# List EC2 instances in a region, compact output
aws ec2 describe-instances --region us-east-1 \
  --query 'Reservations[].Instances[].[InstanceId,InstanceType,State.Name]' \
  --output table

# Upload a file and share it temporarily (presigned URL, 1 hour)
aws s3 cp report.pdf s3://my-bucket/reports/report.pdf
aws s3 presign s3://my-bucket/reports/report.pdf --expires-in 3600

A first real architecture

A sensible small production setup: Route 53 points your domain to an ALB (with an ACM certificate). The ALB forwards to two ECS Fargate tasks in two AZs. They talk to an RDS Postgres instance (Multi-AZ) in private subnets. Static assets go to S3 behind CloudFront. Logs flow to CloudWatch. Secrets live in Secrets Manager. Everything is defined in Terraform. That is "the cloud" for 90% of products.

Pitfalls

  • Service sprawl. Newer is not better. Prefer boring, well-documented services you can operate.
  • Region confusion and resources "lost" in other regions (and still billing).
  • Lock-in via proprietary services such as DynamoDB or Step Functions. Often an acceptable trade for speed; decide consciously.
  • Default settings are not production settings: default VPCs, public subnets, and no backups on some services.

Try it

  1. Create an S3 bucket (block public access ON), upload a file, and generate a presigned URL. Open it in a private browser window.
  2. Launch a t3.micro (or free-tier equivalent) and note its AZ, its EBS volume, and the security group. Terminate it and check that the volume is gone.
  3. Draw the architecture of an app you know using only the services on this page, and write the GCP/Azure equivalent next to each box.
