Compute Options: VMs, Containers, Kubernetes, Serverless

"Where does my code run?" has five serious answers in the cloud. Each trades control for convenience. Choosing well is mostly about your team's size, your traffic shape, and how much operations work you are willing to own.

The spectrum

 More control, more ops work                              Less control, less ops work
 ◀────────────────────────────────────────────────────────────────────────────────▶
  VMs (EC2)     Kubernetes     ECS on EC2    Fargate / Cloud Run    Lambda / Functions
  you patch     you run apps   you run       you run containers,    you run functions,
  the OS        + cluster ops  containers    nothing below          nothing else

1. Virtual machines (EC2, Compute Engine, Azure VM)

You get a full OS. You install the runtime, deploy the app (often via systemd or Docker), patch the OS, configure autoscaling and load balancing.

  • Good for: legacy apps, special OS/kernel/GPU needs, licensed software, long-running stateful servers, maximum control, predictable steady load (cheapest per unit with reservations).
  • Costs: patching, hardening, AMI management, capacity planning, configuration drift.
  • Tip: bake images (Packer) or use user-data/Ansible so VMs are disposable; never hand-edit.

2. Containers on managed orchestrators (ECS / Fargate)

You package the app as a Docker image and tell the platform "run 3 copies, behind this load balancer". ECS schedules containers; with Fargate there are no servers to manage: you specify CPU and memory per task and pay for what runs.

# Minimal ECS task definition fragment (Fargate)
{
  "family": "web",
  "requiresCompatibilities": ["FARGATE"],
  "networkMode": "awsvpc",
  "cpu": "512",
  "memory": "1024",
  "executionRoleArn": "arn:aws:iam::123456789012:role/ecsTaskExecutionRole",
  "taskRoleArn":      "arn:aws:iam::123456789012:role/web-task-role",
  "containerDefinitions": [{
    "name": "web",
    "image": "123456789012.dkr.ecr.eu-west-1.amazonaws.com/web:1.4.2",
    "portMappings": [{ "containerPort": 8080 }],
    "healthCheck": { "command": ["CMD-SHELL", "curl -f http://localhost:8080/healthz || exit 1"] }
  }]
}
  • Good for: most web services and APIs, background workers; teams that want containers without Kubernetes complexity.
  • Trade-offs: AWS-specific; Fargate costs ~20-40% more per vCPU than equivalent EC2 but saves a lot of ops time; limited customisation (no privileged containers, no DaemonSets).

3. Kubernetes (EKS, GKE, AKS)

A portable, extensible orchestrator with a huge ecosystem (Helm, operators, service meshes, GitOps). The cloud runs the control plane; you still run nodes, upgrades (every ~4 months a new minor version), networking add-ons, ingress, observability and security policy.

  • Good for: many services and teams, platform engineering, multi-cloud/portability needs, complex scheduling (GPU, batch), rich ecosystem tooling.
  • Costs: a real learning curve and an ongoing operations burden. EKS control plane is ~$73/month before any nodes. You likely need a platform team.
  • Middle path: GKE Autopilot and EKS Auto Mode manage nodes for you.

4. Serverless containers (Cloud Run, Azure Container Apps, App Runner)

Deploy an image; the platform handles HTTPS, autoscaling (including to zero) and billing per request/CPU-second. Cloud Run in particular is a great default: any container, any language, scale to zero, up to hundreds of instances.

gcloud run deploy web \
  --image europe-docker.pkg.dev/my-proj/apps/web:1.4.2 \
  --region europe-west1 \
  --allow-unauthenticated \
  --min-instances 0 --max-instances 20 \
  --concurrency 80
  • Good for: HTTP services with variable traffic, internal tools, APIs, small teams.
  • Trade-offs: cold starts when scaled to zero; request time limits; harder for long-lived connections or heavy background processing (though workers/jobs variants exist).

5. Functions (Lambda, Cloud Functions, Azure Functions)

Write a handler; the platform runs it per event. Billing is per invocation and per ms of runtime. Scales from zero to thousands of concurrent executions automatically.

// Node.js Lambda behind an HTTP API
export const handler = async (event) => {
  const name = event.queryStringParameters?.name ?? "world";
  return {
    statusCode: 200,
    headers: { "content-type": "application/json" },
    body: JSON.stringify({ message: `Hello, ${name}` }),
  };
};
  • Good for: event-driven glue (S3 upload triggers, queue consumers, webhooks, scheduled jobs), spiky or low traffic APIs, prototypes.
  • Trade-offs:
    • Cold starts: 100 ms to a few seconds when a new environment spins up (mitigate with provisioned concurrency, small packages, SnapStart for Java).
    • Limits: 15 min max runtime, memory up to 10 GB, payload size caps.
    • Cost inversion: at high, steady traffic, containers are cheaper.
    • Harder local dev, debugging and observability; distributed by default; connection pooling issues with databases (use RDS Proxy).
    • Vendor lock-in to event formats and triggers.

A safe default path

Containerise your app first (it keeps every option open). Start on the simplest managed container platform. Move to Kubernetes only when you feel concrete pain: dozens of services, need for custom scheduling or a shared platform. Add Lambda where events make it natural.

Cross-cutting concerns

  • Statelessness: all options scale best if instances hold no local state. Keep sessions in Redis/DB, files in S3.
  • Configuration: env vars + Secrets Manager; never bake secrets into images.
  • Right-sizing: measure CPU/memory and shrink. Most instances are over-provisioned by 2-3x.
  • Architecture: ARM (Graviton, Axion, Ampere) is usually ~20% cheaper; build multi-arch images.

Pitfalls

  • Choosing Kubernetes for a 3-person team with one service ("résumé-driven architecture").
  • Using Lambda for a steady 500 requests/sec API and being surprised by the bill.
  • Ignoring cold starts in latency-sensitive paths.
  • Running one big pet VM with no autoscaling and no image-based rebuild path.

Try it

  1. Containerise a small HTTP app and deploy the same image to Cloud Run (or App Runner/Fargate). Measure the cold-start latency by requesting after 15 idle minutes.
  2. Write a Lambda that resizes an image when uploaded to S3. Check the invocation count and billed duration in CloudWatch.
  3. For a workload of 100 requests/second, 200 ms average, estimate monthly cost on Lambda versus two t3.small instances using the pricing calculator. Where is the crossover?
