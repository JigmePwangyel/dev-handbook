Scaling and High Availability

Two questions drive production architecture. Scaling: can the system handle more load? High availability (HA): does it keep working when parts fail? Hardware fails, deploys break, traffic spikes. The cloud gives you the tools; design is up to you.

Vertical vs horizontal scaling

Vertical (scale up)Horizontal (scale out)
HowBigger machine: more CPU/RAMMore machines behind a load balancer
SimplicityVery simple, no code changesRequires stateless design
LimitLargest instance available; downtime to resizePractically very high
FailureOne big single point of failureLose one node, others carry on
Cost curveGets superlinear at top endRoughly linear

Start vertical (it is easy and often enough, especially for databases). Go horizontal for the stateless application tier as you need resilience or exceed single-machine capacity.

Stateless design: the prerequisite

You can only add and remove copies of a server freely if any copy can serve any request. That means no state living on the instance:

  • Sessions: store in Redis/DB or use signed tokens (JWT), not in process memory.
  • Uploaded files: object storage, not local disk.
  • Caches: shared (Redis) or treat local caches as disposable.
  • Scheduled jobs: run in one place (a scheduler service, or a lock) so each replica does not run them.
  • Config: from env/parameter store, identical on every instance.

Stateful things (databases, queues) live in dedicated managed services that handle their own replication.

Autoscaling

An Auto Scaling Group (ASG) keeps a number of identical instances running between a minimum and maximum, replacing unhealthy ones and adding/removing capacity from a launch template.

resource "aws_autoscaling_group" "web" {
  name                = "web"
  min_size            = 2          # never fewer than 2: survive an AZ loss
  desired_capacity    = 2
  max_size            = 12
  vpc_zone_identifier = [aws_subnet.app_a.id, aws_subnet.app_b.id]  # 2 AZs
  target_group_arns   = [aws_lb_target_group.web.arn]
  health_check_type   = "ELB"      # replace instances failing LB health checks
  health_check_grace_period = 120

  launch_template {
    id      = aws_launch_template.web.id
    version = "$Latest"
  }
}

resource "aws_autoscaling_policy" "cpu" {
  name                   = "target-cpu-50"
  autoscaling_group_name = aws_autoscaling_group.web.name
  policy_type            = "TargetTrackingScaling"
  target_tracking_configuration {
    predefined_metric_specification {
      predefined_metric_type = "ASGAverageCPUUtilization"
    }
    target_value = 50
  }
}

Scaling policy types

  • Target tracking (recommended): "keep average CPU at 50%" or "keep 1000 requests per target". The service does the math.
  • Step scaling: add N instances at thresholds.
  • Scheduled: scale up before known peaks (9 a.m., Black Friday).
  • Predictive: learns daily/weekly patterns.
  • Queue-based: workers scale on queue depth (e.g. SQS messages per worker), often the best signal for async work.

Kubernetes equivalents: HorizontalPodAutoscaler (pods) plus Cluster Autoscaler or Karpenter (nodes). ECS has Service Auto Scaling; Cloud Run scales on concurrency.

Autoscaling is not instant

New VMs take 1-5 minutes to boot and warm up. Sudden spikes can overwhelm you before capacity arrives. Keep headroom, use fast-booting images or containers, scale on leading indicators, and use rate limiting or queues to absorb bursts. Also scale in conservatively to avoid flapping.

High availability architecture

                     Route 53 (health-checked DNS)
                              │
                       CloudFront (CDN)
                              │
        ┌────────────── Region eu-west-1 ──────────────┐
        │          Application Load Balancer           │
        │          (spans all AZs, health checks)      │
        │         ┌──────────────┼──────────────┐      │
        │   ┌─────▼─────┐  ┌─────▼─────┐  ┌─────▼─────┐│
        │   │   AZ-a    │  │   AZ-b    │  │   AZ-c    ││
        │   │ app x2    │  │ app x2    │  │ app x2    ││  ASG spreads
        │   └─────┬─────┘  └─────┬─────┘  └───────────┘│  across AZs
        │         │              │                     │
        │   ┌─────▼─────┐  ┌─────▼─────┐               │
        │   │ RDS       │◀─┤ RDS       │   Redis       │
        │   │ primary   │  │ standby   │   replicas    │
        │   └───────────┘  └───────────┘               │
        │         S3 (replicated across AZs by design) │
        └──────────────────────────────────────────────┘

The principles:

  1. No single point of failure: every layer has at least two of everything, in different failure domains.
  2. Spread across AZs: lose a data center, keep serving. Size so that N-1 AZs can carry full load (with 3 AZs, run at about 60-65% max utilisation each).
  3. Health checks + automatic replacement: the LB stops sending traffic to bad nodes; the ASG replaces them.
  4. Managed multi-AZ data stores for state.
  5. Graceful degradation: when a dependency fails, serve a reduced experience (cached data, disabled recommendations) rather than errors.

Availability math

AvailabilityDowntime / yearDowntime / month
99%3.65 days7.3 hours
99.9%8.76 hours43.8 minutes
99.95%4.38 hours21.9 minutes
99.99%52.6 minutes4.4 minutes

Components in series multiply: a 99.9% LB, 99.9% app and 99.9% DB give about 99.7% overall. Redundant components in parallel multiply failure probabilities: two independent 99% nodes give 99.99%. That is why redundancy beats trying to make one node perfect, and why every extra hard dependency in a request path costs you nines.

Multi-region

A region outage is rare but real, and some businesses (or regulations) cannot tolerate one. Multi-region patterns, in rising cost and complexity:

PatternDescriptionRTO / RPO
Backup & restoreCopy backups to another region; rebuild from IaC on disasterHours / minutes-hours
Pilot lightData replicated; minimal core running; scale up on failoverTens of minutes / seconds-minutes
Warm standbyScaled-down full copy runningMinutes / seconds
Active-activeBoth regions serve traffic (latency or geo routing)Near zero / near zero

The hard part is data: cross-region replication is asynchronous (risking loss), and active-active writes require conflict handling (DynamoDB global tables, Aurora Global Database, CockroachDB/Spanner). Route 53 failover or latency routing with health checks steers users. Also design for control-plane independence: during a regional event, your failover process must not depend on that region's APIs. Most applications are better served by a solid multi-AZ design and a practised pilot-light DR plan than by active-active.

Capacity planning

  • Load test (k6, Locust, Gatling) to find the throughput one instance sustains at acceptable latency. Capacity = peak load / per-instance throughput, plus headroom.
  • Know your bottleneck: usually the database (connections, IOPS, locks) long before the app tier. Autoscaling app servers just stampedes the DB.
  • Check quotas: service limits (vCPUs per region, ENIs, API rate limits) can block scale-out. Request increases ahead of launches.
  • Plan for events: marketing campaigns, launches, seasonal peaks. Pre-warm load balancers and scale proactively.
  • Re-measure after every major release.

Pitfalls

  • Autoscaling group with min=1 in a single AZ, the illusion of HA.
  • Sticky sessions hiding statefulness, then uneven load and lost sessions on scale-in.
  • Health checks too shallow (always 200) or too deep (failing when a non-critical dependency blips, causing cascading removal of all nodes).
  • Untested failover: you do not have HA until you have killed an instance, an AZ, and the primary DB on purpose.
  • Retry storms amplifying outages (see the resilience lesson in the Monitoring section).
  • Scaling the app but not downstream limits (DB connections, third-party API rate limits).

Try it

  1. Build an ASG across two AZs behind an ALB. Terminate an instance manually and watch the replacement. Then simulate load with hey -z 5m -c 100 http://your-alb/ and watch target tracking scale out.
  2. Failover a Multi-AZ RDS instance using "reboot with failover" and measure how long your app is unavailable and whether it reconnects by itself.
  3. Compute the combined availability of: CDN 99.99%, LB 99.99%, app 99.95% (two replicas independent), DB 99.95%.
