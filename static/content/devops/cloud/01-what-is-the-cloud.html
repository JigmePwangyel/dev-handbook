What Is "The Cloud"?

"The cloud" is just other people's computers, rented by the second, controlled by an API. That sounds trivial, but the API part changes everything: infrastructure becomes something you can create, change and destroy from code, in minutes, without buying hardware or filing a ticket.

The problem the cloud solves

Before public clouds, running software meant owning or leasing physical servers in a data center (on-premises, or "on-prem"). To launch a product you would:

  1. Forecast how much capacity you needed 1-3 years out (and almost always get it wrong).
  2. Order servers, wait weeks for delivery, rack them, cable them, install an OS.
  3. Pay the full cost up front (capital expenditure, "CapEx") whether or not anyone used the product.
  4. Staff people to replace failed disks, patch firmware, manage power and cooling, and handle physical security.

If you under-provisioned, a successful launch crashed your site and you could not add capacity for weeks. If you over-provisioned, you paid for idle machines. The cloud turns this into operational expenditure (OpEx): you pay for what you use, and capacity arrives in seconds.

Hybrid and multi-cloud

Hybrid means part on-prem, part cloud (often for legacy systems or regulated data). Multi-cloud means using more than one provider. Both add complexity; most teams are better off mastering one cloud first. Do not adopt multi-cloud "to avoid lock-in" without a concrete requirement; you will pay for portability in engineering time.

There are also managed services in between: a database like Amazon RDS is "IaaS with the boring parts removed". You do not patch Postgres or replace its disks, but you still choose instance size and schema.

Pick the highest abstraction that fits

Every layer you manage is a layer you must patch, monitor, secure and be paged for. A good default: use SaaS if a product exists, managed services for state (databases, queues), PaaS/containers/serverless for your code, and raw VMs only when you need the control.

The shared responsibility model

Security in the cloud is split. The provider secures the cloud; you secure what you put in it.

Provider is responsible forYou are responsible for
Physical data centers, power, coolingWho can access your account (IAM, MFA)
Hypervisor and host hardwareGuest OS patching (on IaaS)
Network backbone, managed service internalsNetwork rules (security groups, firewall)
Durability of services like S3 itselfWhether your S3 bucket is public
Encryption choices, backups, application code, data classification

The majority of real-world cloud breaches are customer misconfiguration: a public bucket, an access key committed to GitHub, an over-permissive role, an open database port. The provider's data center was never the weak link.

Regions and Availability Zones

Cloud providers are not one big computer. They are a hierarchy:

  • Region: a geographic area (e.g. us-east-1 N. Virginia, eu-west-1 Ireland, ap-southeast-1 Singapore). Regions are independent: separate pricing, separate service availability, separate failure domains.
  • Availability Zone (AZ): one or more discrete data centers within a region, with independent power and networking, connected to the others by low-latency links (e.g. us-east-1a, 1b, 1c).
  • Edge locations: hundreds of small points of presence used by CDNs and DNS to serve content close to users.
 AWS Cloud
 ├── Region us-east-1 (N. Virginia)
 │    ├── AZ us-east-1a   [data center(s)]
 │    ├── AZ us-east-1b   [data center(s)]
 │    └── AZ us-east-1c   [data center(s)]
 ├── Region eu-west-1 (Ireland)
 │    ├── AZ eu-west-1a ...
 └── Edge locations (CloudFront, Route 53) worldwide

How to choose a region

  • Latency: close to your users (or your other systems).
  • Data residency / law: GDPR or contracts may require data to stay in a country or bloc.
  • Service availability: new services launch in a few regions first.
  • Price: the same instance can cost 10-30% more in some regions.

Surviving a single data center failure means spreading across AZs. Surviving a whole region outage needs multi-region, which is much harder and costlier (see the scaling lesson).

Beyond compute, remember the hidden meters: data transfer out to the internet (and between AZs/regions), requests, storage operations, NAT gateway processing, and idle resources like unattached disks and Elastic IPs. See the cost-management lesson.

Getting started safely

  1. Create the account and immediately enable MFA on the root user. Then stop using root; create an admin identity (an IAM Identity Center user) for daily work.
  2. Set a budget alert (e.g. $10) before launching anything.
  3. Install the CLI and confirm who you are:
aws --version
aws configure sso          # or: aws configure
aws sts get-caller-identity
# {
#   "UserId": "AIDA...",
#   "Account": "123456789012",
#   "Arn": "arn:aws:iam::123456789012:user/alice"
# }

Pitfalls

  • Treating the cloud as a cheaper data center. "Lift and shift" of pet servers often costs more and gains little. Gains come from elasticity, managed services and automation.
  • Clicking in the console only. Console-built infrastructure cannot be reviewed, repeated or recovered. Move to Infrastructure as Code early.
  • Forgetting to turn things off. The meter runs until you delete the resource.
  • Assuming "managed" means "no responsibility". You still own backups testing, access control and capacity choices.

Try it

  1. Create a free cloud account, enable MFA on root, and create a $5 budget alert.
  2. Run aws ec2 describe-regions --output table and then aws ec2 describe-availability-zones --region eu-west-1. How many AZs does each region have?
  3. For three tools you use daily (e.g. GitHub, Postgres, Docker Hub), classify them as IaaS, PaaS, FaaS or SaaS.
  4. Pick a hypothetical app with EU customers. Which region would you choose and why?
