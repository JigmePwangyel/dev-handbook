PaaS and Modern Platforms

Platform-as-a-Service products let you git push and get a running, HTTPS-enabled, autoscaled application. They bundle what the earlier lessons made you assemble by hand: networking, load balancing, certificates, deploys, logs. For many products, this is the right answer for years.

The idea and why it exists

Building a production setup on raw AWS means wiring a VPC, load balancer, autoscaling, CI/CD, TLS, logging and secrets. That is weeks of work and ongoing maintenance, and none of it is your product. A PaaS says: "give me your code (or container) and some environment variables; I'll do the rest". Heroku popularised this in 2009 with git push heroku main; today's platforms extend it with preview environments, edge networks and managed databases.

 git push ──▶ Platform detects framework ──▶ builds (buildpack / Dockerfile)
                                              │
                    ┌─────────────────────────▼─────────────────────────┐
                    │ release: new instances start, health-checked,     │

                    └─────────────────────────┬─────────────────────────┘

             https://myapp.example.com  (managed TLS, CDN, logs, metrics, rollbacks)

Pricing changes constantly

Free tiers and plans on these platforms change often. Check current pricing before committing, and model your expected bandwidth, build minutes and function invocations.

A taste: deploying on three platforms

# Heroku-style (Procfile + buildpack)
echo "web: node server.js" > Procfile
heroku create myapp
git push heroku main
heroku config:set DATABASE_URL=postgres://...
heroku logs --tail

# Fly.io (containers, multi-region)
fly launch                 # generates fly.toml from your Dockerfile
fly secrets set API_KEY=abc123
fly deploy
fly scale count 3 --region fra,iad

# Vercel (frontend + serverless)
npm i -g vercel
vercel --prod              # or connect the Git repo; every PR gets a preview URL

Typical fly.toml:

app = "myapp"
primary_region = "fra"

[http_service]
  internal_port = 8080
  force_https = true
  auto_stop_machines = "stop"
  auto_start_machines = true
  min_machines_running = 1

  [[http_service.checks]]
    path = "/healthz"
    interval = "15s"
    timeout = "2s"

When PaaS beats DIY

  • Small team, no dedicated ops. Engineer time is your scarcest resource; a $200/month platform that saves a week of work per quarter is cheap.
  • Early product, uncertain traffic. You are still finding product-market fit; do not build a platform for a product that may pivot.
  • Preview environments per PR come free, speeding review and QA.
  • Standard architecture: web app, a worker, a database, a cache.
  • Compliance and security managed for you (patching, TLS renewal, DDoS basics).

When DIY (or a hyperscaler) beats PaaS

  • Scale economics. At large traffic, per-unit prices matter; companies with big bills move off PaaS (but often later than they think).
  • Special requirements: GPUs, custom networking, private connectivity to on-prem, strict data residency, exotic runtimes.
  • Deep integration with a cloud's IAM, VPC, data services.
  • Customisation limits: you cannot tune the kernel, load balancer or scheduler.
  • Compliance demanding specific audit controls the platform does not offer.

Trade-offs in detail

BenefitCost
Speed to production: hours, not weeksHigher price per unit of compute/bandwidth
No infrastructure to maintainLess control, platform's constraints become yours
Built-in best practices (TLS, zero-downtime deploys)Vendor-specific features create lock-in
Easy to scale up in clicksScaling limits and noisy bills at high volume

Lock-in is reduced when you follow the twelve-factor habits: config in env vars, stateless processes, logs to stdout, a Dockerfile in the repo. Then moving to Cloud Run, ECS or Kubernetes later is a weekend, not a rewrite.

Pitfalls

  • Surprise bills from bandwidth, function invocations, build minutes or team seats. Set spend limits and alerts.
  • Databases on free tiers that sleep or get deleted. Use a proper managed database with backups for real data.
  • Ephemeral filesystems: files written to disk disappear on deploy. Use object storage.
  • Cold starts and sleeping apps on cheap plans.
  • No observability beyond basics: ship logs/metrics to a real system (Grafana Cloud, Datadog, Axiom) as you grow.
  • Region mismatch: app in the US, database in Europe means slow every query.
The graduation path

Many successful products follow: PaaS (prototype) → PaaS + managed DB (launch) → containers on a hyperscaler (scale and cost) → Kubernetes (platform for many teams). Each step is justified by a concrete pain, not fashion.

Try it

  1. Take a small web app with a Dockerfile and deploy it to Render and Fly.io. Compare time-to-URL, logs UX, and the pricing page for 1 GB RAM always-on.
  2. Deploy a static site to Netlify or Vercel, then open a pull request that changes it and find the preview URL.
  3. Add a /healthz endpoint and configure the platform's health check.
  4. Write down what you would have to change to move this app to Cloud Run. If the answer is "nothing but the deploy command", your app is portable.
