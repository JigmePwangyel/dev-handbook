Logging

Logs are the oldest telemetry: a diary your program writes about what it is doing. Done well they let you reconstruct any request after the fact. Done badly they are an expensive pile of unsearchable text, or worse, a leak of customer secrets.

From printf to structured logs

Traditional logs are free-form text:

2026-10-05 09:14:22 ERROR Payment failed for user 42 order 881: card declined

A human can read this, but a machine must parse it with fragile regexes, and any change to the wording breaks queries. Structured logging emits one JSON object per line with consistent fields:

{"ts":"2026-10-05T09:14:22.318Z","level":"error","service":"checkout",
 "version":"1.8.3","msg":"payment failed","user_id":42,"order_id":881,
 "reason":"card_declined","provider":"stripe","duration_ms":412,
 "trace_id":"4bf92f3577b34da6a3ce929d0e0e4736","request_id":"req_8f2a1c"}

Now you can query "all level=error where reason=card_declined for version=1.8.3" and count, group and graph it. The message stays constant; variable data goes in fields (never interpolate IDs into the message string, or each event looks unique).

// Node (pino)
import pino from "pino";
const log = pino({ level: process.env.LOG_LEVEL ?? "info",
                   base: { service: "checkout", version: process.env.APP_VERSION } });
log.error({ order_id: 881, user_id: 42, reason: "card_declined" }, "payment failed");

# Python (structlog)
import structlog
log = structlog.get_logger()
log.error("payment failed", order_id=881, user_id=42, reason="card_declined")

// Go (slog, standard library)
slog.Error("payment failed", "order_id", 881, "user_id", 42, "reason", "card_declined")

Log levels

LevelMeaningProduction default?
DEBUGDetailed diagnostics for developersOff (enable temporarily per service)
INFONormal significant events: startup, request completed, job finishedOn
WARNUnexpected but handled: retry succeeded, deprecated call, nearing limitsOn
ERRORAn operation failed; someone may need to lookOn
FATAL/CRITICALProcess cannot continueOn

Discipline matters: if everything is ERROR, nothing is. A user typing a wrong password is INFO/WARN, not ERROR. Reserve ERROR for things that indicate a bug or an unavailable dependency. Make the level configurable at runtime by environment variable.

Where logs should go: stdout

The twelve-factor rule: applications write logs as an event stream to stdout/stderr and do not manage files, rotation or shipping themselves. The platform (Docker, Kubernetes, systemd, ECS) captures the stream and a collector forwards it. This keeps apps simple and portable.

docker logs -f --tail 100 web
kubectl logs -f deploy/checkout --since=15m
journalctl -u myapp -f -o json-pretty

Correlation IDs

One user action fans out across a load balancer, API, three microservices and a queue. Without a shared identifier you cannot stitch their logs together. Generate a request/correlation ID at the edge (or accept the incoming header), put it in every log line, and pass it on every outgoing call.

 Browser ─▶ Gateway ──────▶ Orders ──────▶ Payments ──────▶ Inventory
            X-Request-ID    X-Request-ID   X-Request-ID      X-Request-ID
            = req_8f2a1c    = req_8f2a1c   = req_8f2a1c      = req_8f2a1c
   every log line in every service carries  request_id=req_8f2a1c
   ⇒ one search in the log system shows the whole story

// Express middleware + AsyncLocalStorage
import { randomUUID } from "node:crypto";
import { AsyncLocalStorage } from "node:async_hooks";
const als = new AsyncLocalStorage();

app.use((req, res, next) => {
  const id = req.header("x-request-id") ?? randomUUID();
  res.setHeader("x-request-id", id);
  als.run({ request_id: id }, next);
});
const log = pino({ mixin: () => als.getStore() ?? {} });   // adds request_id to every line

With distributed tracing (next lessons) the trace_id plays the same role and also links logs to traces. Put it in your logs and you can jump from a slow trace straight to its log lines.

Centralised logging

When you have many instances and ephemeral containers, SSHing into hosts to grep does not work: containers vanish with their logs. Ship logs to a central searchable store.

 app (stdout) ─▶ agent/collector ─▶ (buffer: Kafka/Kinesis, optional) ─▶ storage+search ─▶ UI
 container logs   Fluent Bit /        absorbs bursts                      Loki / Elasticsearch    Grafana /

ELK / Elastic stack

Elasticsearch (indexed search engine), Logstash (or Beats / Fluent Bit for shipping and parsing), Kibana (UI). Full-text indexing of every field makes arbitrary search fast and powerful, at the price of CPU, RAM and disk. OpenSearch is the AWS-backed fork. Good when you need rich full-text search and analytics over logs.

Grafana Loki

"Like Prometheus, but for logs". Loki indexes only labels (app, namespace, env) and stores compressed log chunks in cheap object storage (S3). Much cheaper to run; queries filter by labels then grep within. Query with LogQL:

{app="checkout", env="prod"} |= "payment failed"
{app="checkout"} | json | level="error" | reason="card_declined"
sum by (reason) (rate({app="checkout"} | json | level="error" [5m]))
{app=~".+"} | json | request_id="req_8f2a1c"

Keep labels low-cardinality (service, env, level); put user/request IDs in the log body, not labels.

What NOT to log

Logs are a data-leak vector

Log systems are widely accessible, long-retained and replicated. Treat anything written to a log as published to every engineer, forever.

  • Secrets: passwords, API keys, tokens, session cookies, Authorization headers, private keys, connection strings.
  • Personal data: full card numbers (PCI), government IDs, health data, raw emails/phones where avoidable (GDPR). Hash or mask: user_id beats email.
  • Entire request/response bodies by default; log selected fields.
  • Noise: per-iteration loop messages, health-check requests every second, successful cache hits.
  • Exceptions swallowed and relogged at every layer (one error, ten log lines). Log once, where it is handled, with full stack trace and context.

Add redaction at the logger level (pino redact, structlog processors) and scan logs in CI/staging for patterns like card numbers and bearer tokens.

Retention, cost and sampling

  • Typical: 7-30 days hot and searchable, then archive to S3 (compliance may require a year or more).
  • Logs are usually the most expensive telemetry. Drop DEBUG in prod, sample high-volume INFO (e.g. keep 10% of successful request logs, 100% of errors), and filter health checks at the collector.
  • Prefer metrics for counting; do not grep | wc -l logs for dashboards.
  • Protect with access controls and audit who can read production logs.

Pitfalls

  • Unstructured, inconsistent field names (userId, user_id, uid): agree on a schema.
  • Missing timestamps in UTC, or no service/version/environment fields.
  • Logging to local files in containers: lost on restart, fill the disk.
  • Synchronous logging blocking request threads; use async/buffered appenders.
  • Multi-line stack traces split into separate log events; use JSON so the trace is one field.
  • No correlation ID: you can see errors but cannot connect them to a request.

Try it

  1. Convert one service from console.log/print to structured JSON with fields service, version, level, request_id.
  2. Add middleware that generates or propagates X-Request-ID and includes it in every log line and downstream HTTP call.
  3. Run Loki + Grafana with Docker Compose (grafana/loki, grafana/promtail), ship your container logs and write a LogQL query that charts errors per minute.
  4. Audit one service: grep a day of logs for password, token, @. What leaked?
