Chaos Engineering and Resilience Patterns

In distributed systems, partial failure is the normal state. Networks drop packets, dependencies slow down, instances disappear. Resilient software expects this and degrades gracefully. Chaos engineering goes further: it breaks things on purpose, in a controlled way, to prove the resilience is real.

Failure is normal

If your request touches ten services each at 99.9% availability, the combined availability is about 99.0%: roughly 7 hours of downtime a month from "healthy" parts. You cannot make dependencies perfect, so your code must handle their failures. The Eight Fallacies of Distributed Computing start with: "the network is reliable", and "latency is zero". Neither holds.

The most dangerous failure is not a clean crash (easy to detect and retry), but slowness: a dependency that responds in 30 seconds instead of 30 ms ties up your threads and connections until you fall over too. That is why timeouts come first.

Timeouts

Every network call must have a timeout. No exceptions. Default timeouts in many libraries are infinite or minutes long.

  • Set connect and read/total timeouts separately. Base them on the dependency's normal latency (e.g. p99 x 2-3), not on hope.
  • Use deadline propagation: if the user request has a 2-second budget and you already spent 1.2 s, the downstream call gets at most 0.8 s (gRPC deadlines, Go context deadlines).
  • Timeouts down the chain must be shorter than upstream ones, or the caller gives up while the callee keeps working for nobody.
// Go
ctx, cancel := context.WithTimeout(ctx, 800*time.Millisecond)
defer cancel()
resp, err := client.Do(req.WithContext(ctx))

# Python requests: (connect, read)
requests.get(url, timeout=(0.5, 2.0))

// Node fetch
const res = await fetch(url, { signal: AbortSignal.timeout(2000) });

Retries with exponential backoff and jitter

Many failures are transient (a dropped connection, a brief overload, a failover in progress). Retrying often succeeds. But naive retries are dangerous: if 1,000 clients all retry immediately and repeatedly, they hammer a struggling service and keep it down: a retry storm (a self-inflicted DDoS).

 Naive:        t=0 fail ─▶ t=0 retry ─▶ t=0 retry ... (instant hammering)
 Backoff:      wait 100ms, 200ms, 400ms, 800ms ... (exponential: reduces pressure)
 + Jitter:     wait random(0..delay) so clients do not retry in sync (thundering herd)

import random, time

def call_with_retries(fn, attempts=4, base=0.1, cap=2.0):
    for i in range(attempts):
        try:
            return fn()
        except TransientError:
            if i == attempts - 1:
                raise
            delay = min(cap, base * (2 ** i))
            time.sleep(random.uniform(0, delay))      # "full jitter"

Rules of retrying:

  • Retry only transient, safe errors: timeouts, 503, connection resets, 429 (respecting Retry-After). Never retry 400/401/404 or validation errors.
  • Only retry idempotent operations, or make them idempotent with an idempotency key (e.g. payments: send Idempotency-Key: <uuid> so a retry does not charge twice).
  • Cap attempts and total time, and use a retry budget (e.g. retries may add at most 10% extra load). Retries multiply across layers: three layers each retrying 3 times means 27 calls per failure. Retry at one layer only, usually the closest to the failure or the edge.

Circuit breakers

When a dependency is clearly failing, continuing to call it wastes resources and slows everyone. A circuit breaker watches failure rates and "trips", failing fast without calling the dependency, then probes occasionally to see if it recovered.

          failures exceed threshold
   ┌────────┐ ───────────────────────▶ ┌────────┐
   │ CLOSED │                          │  OPEN  │  all calls fail fast (no network)
   │ normal │ ◀─────────────────────── └───┬────┘
   └────────┘   probe calls succeed        │ after cool-down (e.g. 30 s)
        ▲                                  ▼
        │                           ┌─────────────┐
        └───────────────────────────│ HALF-OPEN   │ allow a few trial calls
              success                └─────────────┘ (failure sends it back to OPEN)

// Resilience4j (Java)
CircuitBreakerConfig cfg = CircuitBreakerConfig.custom()
    .failureRateThreshold(50)                     // open at 50% failures
    .slidingWindowSize(20)
    .waitDurationInOpenState(Duration.ofSeconds(30))
    .permittedNumberOfCallsInHalfOpenState(3)
    .build();

// Node: opossum;  Python: pybreaker;  Go: sony/gobreaker;  .NET: Polly
// Service meshes (Istio/Envoy) can do outlier detection without code changes

While open, return a fallback: cached data, a default, a degraded feature (hide recommendations), or a clear error. Failing fast keeps your own latency and thread pools healthy.

BulkheadsIsolate resources (thread/connection pools) per dependency so one slow dependency cannot exhaust everything, like watertight compartments in a ship.

Feature flags / kill switchesTurn off a misbehaving feature instantly without redeploying.
How they compose

A well-behaved call: timeout bounds each attempt; a few retries with backoff and jitter absorb transient errors; a circuit breaker stops calling a dead dependency; a bulkhead contains the blast radius; a fallback keeps the user experience acceptable; and metrics on all of them show when they are triggering.

Chaos engineering

Resilience features are code that rarely runs, so they are rarely tested, and untested failure handling usually fails when needed. Chaos engineering, pioneered by Netflix (Chaos Monkey), is the discipline of experimenting on a system to build confidence in its ability to withstand turbulent conditions in production.

The scientific method

  1. Define steady state: a measurable indicator of normal behaviour, ideally an SLI (orders per minute, p99 latency, error ratio).
  2. Hypothesise: "If one app instance dies, the steady state is unchanged." "If the cache is unavailable, checkout latency rises under 2x but stays successful."
  3. Inject a realistic fault, with the smallest blast radius that teaches you something.
  4. Observe versus the steady state. Did the system behave as hypothesised?
  5. Fix the weaknesses found, then rerun and automate.

Preconditions: you need decent observability and a working abort button. Do not run chaos on a system you cannot observe, or one already unreliable. Start in staging, then move to production in small, announced experiments (a small percentage of traffic, one instance, off-peak) with automatic halting when the SLI degrades.

Tools

  • Gremlin (commercial platform), Steadybit.
  • AWS Fault Injection Service (FIS), Azure Chaos Studio.
  • Toxiproxy (inject latency/failure on TCP connections in tests), tc netem, stress-ng.

apiVersion: chaos-mesh.org/v1alpha1

  action: delay
  mode: one
  selector:
    namespaces: [shop]

  delay: { latency: "200ms", jitter: "50ms" }
  duration: "5m"

# Simple: kill a random pod and watch recovery
kubectl delete pod -n shop $(kubectl get pods -n shop -l app=checkout -o name | shuf -n1)

Game days

A game day is a scheduled, collaborative exercise where the team deliberately simulates a failure and practises the response, testing systems, tooling, runbooks and people.

  1. Plan: choose a scenario ("primary DB fails over", "payment provider is down", "AZ lost"). Write the hypothesis and expected behaviour. Define abort criteria and a rollback.
  2. Brief: assign roles (facilitator, IC, observers/scribe). Tell stakeholders and support when it will run.
  3. Run: inject the fault; the responders work from alerts and runbooks, as in a real incident (or the facilitator reveals the scenario). Observers note what was confusing, missing or slow.
  4. Debrief: blameless review: did alerts fire? did dashboards help? were runbooks right? how long to detect and mitigate? What surprised us?
  5. Follow up: track action items like postmortem items; repeat with harder scenarios.

Variations: "Wheel of misfortune" tabletop (talk through an incident with no real fault), disaster recovery drills (restore from backup, fail over to another region), and security red-team exercises.

Pitfalls

  • No timeouts: the single most common cause of cascading failure.
  • Retries without backoff, jitter or limits, creating retry storms; retries at multiple layers.
  • Retrying non-idempotent operations (double charges, duplicate emails).
  • Circuit breakers never tuned or monitored: add metrics and alerts for state changes.
  • Fallbacks that were never exercised and themselves crash. Test them.
  • Chaos without a hypothesis or observability: random destruction teaches nothing.
  • Too large a blast radius too early, or experimenting during an existing incident or a peak event.
  • Finding issues and not fixing them: chaos creates a backlog; the value is in the follow-up.
  • Treating it as a one-off: systems change; run experiments continuously or on a schedule, ideally in CI/CD.

Try it

  1. Audit one service's outbound calls: list each with its timeout, retry policy and fallback. How many have none?
  2. Run two containers (your app and a dependency) behind Toxiproxy. Add 3 seconds of latency to the dependency and watch your app. Add a timeout and a fallback, and repeat.
  3. Implement retry with exponential backoff and full jitter for a flaky HTTP call, then write a test that proves it retries on 503 but not on 400.
  4. Plan a 1-hour game day: pick the scenario "kill one of three app instances during peak-like load", state the hypothesis and steady-state metric, and run it in staging with Chaos Mesh or kubectl delete pod.
