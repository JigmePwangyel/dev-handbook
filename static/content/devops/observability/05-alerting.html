Alerting

An alert is a machine tapping a human on the shoulder: "come look at this now". Every alert spends a scarce resource, human attention, and often sleep. Good alerting wakes people only for problems that matter and that they can act on. Bad alerting trains them to ignore the pager.

What alerts are for

Dashboards are for exploring. Alerts exist for the narrow case where a human must act soon. If nothing needs doing, it should not page. If it can wait until morning, it should be a ticket or an email, not a page.

SeverityMeaningChannel
Page (critical)User-visible impact now or imminent; needs immediate actionPhone call/push via PagerDuty or Opsgenie, 24/7
Ticket (warning)Will cause trouble within days; needs action in business hoursTicket queue / Slack channel
InfoContext, trendsDashboard, weekly review. Not an alert at all.

Alert on symptoms, not causes

The most important rule

Page on what users experience (errors, slowness, unavailability), not on internal causes (CPU, memory, one pod restarting). Causes are many and often harmless; symptoms are few and always matter. Use cause-based signals for dashboards and diagnosis.

Cause-based (noisy)Symptom-based (actionable)
CPU > 80% on web-3p99 checkout latency > 2 s for 10 min
A pod restarted5xx error ratio > 2% for 5 min
Disk 85% fullDisk predicted full in 4 hours (predict_linear) , because it needs action before it affects users
Queue length > 1000Oldest message age > 10 min (jobs are delayed)
DB replica lag > 1 sRead-after-write errors reported / SLO burn

Some cause-based alerts are still right: things that will become user-visible with no further warning (certificate expiring in 14 days, disk filling, backup job not run in 25 hours).

Best of all, alert on SLO burn rate: how fast you are consuming your error budget (see the SLO lesson). It ties paging directly to user impact and handles severity automatically.

Prometheus alert rules

# alerts.yml
groups:
- name: checkout
  rules:
  - alert: HighErrorRatio
    expr: |
      sum(rate(http_requests_total{service="checkout",status=~"5.."}[5m]))
        /
      sum(rate(http_requests_total{service="checkout"}[5m])) > 0.02
    for: 5m                         # must hold for 5 minutes: filters blips
    labels:
      severity: page
      team: payments
    annotations:
      summary: "Checkout 5xx ratio is {{ $value | humanizePercentage }}"
      description: "More than 2% of checkout requests fail (5 min window)."
      dashboard: "https://grafana.example.com/d/checkout"
      runbook_url: "https://wiki.example.com/runbooks/checkout-high-errors"

  - alert: DiskWillFillIn4Hours
    expr: predict_linear(node_filesystem_avail_bytes{mountpoint="/"}[6h], 4*3600) < 0
    for: 30m
    labels: { severity: ticket }
    annotations:
      summary: "{{ $labels.instance }} root disk predicted full within 4h"

  - alert: TargetDown
    expr: up == 0
    for: 3m
    labels: { severity: page }

The for: clause is your noise filter: the condition must be continuously true that long before firing. Always include a runbook_url and a dashboard link.

Alertmanager

Prometheus evaluates rules and sends firing alerts to Alertmanager, which does what a raw rule cannot: deduplicate, group related alerts into one notification, route by labels to the right team and channel, silence during maintenance, and inhibit downstream alerts when a root-cause alert is firing.

 Prometheus ──fires──▶ Alertmanager ─ group, dedupe, inhibit, silence ─▶ route by labels
                                                              ├─ severity=page  ─▶ PagerDuty (phone)
                                                              ├─ team=payments  ─▶ #payments-alerts (Slack)
                                                              └─ severity=ticket ─▶ Jira / email

# alertmanager.yml
route:
  receiver: slack-default
  group_by: [alertname, service]
  group_wait: 30s          # wait to batch the first alerts of a group
  group_interval: 5m       # then batch further changes
  repeat_interval: 4h      # re-notify if still firing
  routes:
    - matchers: [ severity="page" ]
      receiver: pagerduty-oncall
    - matchers: [ severity="ticket" ]
      receiver: jira

inhibit_rules:
  - source_matchers: [ alertname="ClusterDown" ]
    target_matchers: [ severity=~"page|ticket" ]
    equal: [ cluster ]      # if the cluster is down, mute everything inside it

receivers:
  - name: pagerduty-oncall
    pagerduty_configs: [{ routing_key: "<secret>", send_resolved: true }]
  - name: slack-default
    slack_configs:
      - channel: "#alerts"
        send_resolved: true
        title: "{{ .CommonAnnotations.summary }}"
  - name: jira
    webhook_configs: [{ url: "http://jira-bridge/alert" }]

Paging and on-call

  • A rotation (weekly, "follow the sun" for global teams) with a primary and a secondary. Tools: PagerDuty, Opsgenie, Grafana OnCall, incident.io.
  • Escalation policy: if the primary does not acknowledge in 5-10 minutes, page the secondary, then the manager.
  • Pages must be reachable: phone call/push that overrides Do Not Disturb, not just email.
  • Compensate and protect on-call: time off after rough nights, fair rotation, handover notes. Sustainable on-call is a reliability feature.
  • Test the whole path: send a test page monthly. Add a dead man's switch alert (an always-firing alert that pages when it stops arriving) to detect a broken monitoring pipeline.

Runbooks

An alert without a runbook forces the on-caller to reinvent investigation at 3 a.m. Each page should link to a short document:

# Runbook: HighErrorRatio (checkout)
## What this means
More than 2% of /checkout requests return 5xx for 5+ minutes.
## Impact
Customers cannot pay. Revenue loss ~ $X/min.
## First steps (5 min)
1. Open the dashboard (link). Is it one route, one region, one version?
2. Check recent deploys / feature flags: `kubectl rollout history deploy/checkout`
3. Check dependencies panel: payment provider, DB connections.
## Mitigation
- Bad deploy?  `kubectl rollout undo deploy/checkout`
- DB saturated? Scale read replicas / enable the `degraded_mode` flag.
- Provider outage? Switch to backup provider with flag `pay_fallback`.
## Escalate
If not mitigated in 15 min, page #payments-lead; open an incident (/incident).
## Related
Past incidents: INC-482, INC-517

Better still, automate the safe steps (self-healing, rollbacks) so a human is only needed when automation fails.

Avoiding alert fatigue

When people get paged constantly for non-issues, they mute, ignore, or burn out, and then miss the real one. Treat alert quality as engineering work.

  • Every page must be actionable and urgent. If the response is "ignore it" or "wait", delete or downgrade the alert.
  • Track metrics about alerts: pages per on-call shift (target: 0-2/day max, ideally far fewer), percent actionable, time-to-ack, repeated alerts. Review in a weekly on-call handoff.
  • Use for: durations and multi-window logic to ignore blips.
  • Group and inhibit so one outage is one page, not 40.
  • Fix the root cause of flappy alerts instead of tuning thresholds forever.
  • Prune: after each incident ask "which alerts were useless? what was missing?"
  • Prefer fewer, broader alerts on symptoms over many narrow ones.
  • Owner per alert: label with team; alerts route to the people who can fix them.

Pitfalls

  • Static thresholds on traffic-dependent metrics (error counts instead of ratios).
  • No alert for "no data": a dead service emits no errors. Alert on absent() or up == 0.
  • Alerting on averages; use percentiles.
  • Paging for things in non-prod.
  • Silences that never expire.
  • Alerts that fire but have no link to a dashboard or runbook.

Try it

  1. Take your noisiest alert list (or invent one) and classify each as page / ticket / delete using "must a human act now?".
  2. Write a Prometheus rule for error ratio above 2% for 5 minutes. Trigger it with a test app that returns 500s and watch Alertmanager route it to a Slack webhook.
  3. Write a runbook for it following the template above.
  4. Add an inhibit rule so a NodeDown alert suppresses all alerts from that node.
