Health Checks and Uptime Monitoring

Before anything else can work (load balancing, autoscaling, rolling deploys, alerting) the platform needs a cheap way to ask your service: "are you OK?" Health checks are that question. Synthetic monitoring and status pages extend it to "does it work from the user's side, and do users know?"

Why health checks exist

A process can be running yet useless: deadlocked, out of database connections, still loading its cache. If the load balancer keeps sending traffic to such an instance, users get errors. Health checks let infrastructure make three different decisions:

QuestionProbeIf it fails
Is the process alive or hopelessly stuck?LivenessRestart it
Is it ready to serve traffic right now?ReadinessRemove from load balancer rotation (do not restart)
Has it finished booting?StartupHold off liveness checks until it succeeds; kill if it never does

Mixing these up is the classic mistake. If liveness checks the database and the DB blips, every instance is "dead", all restart together, and a short DB blip becomes a full outage with a thundering herd on recovery.

Designing the endpoints

Liveness: /livez or /healthz

Answers only: "is the event loop/threads responsive?" Should be trivial, fast and depend on nothing external. Return 200 if the process can run code.

Readiness: /readyz

Answers: "can I usefully serve a request now?" Check critical, local-to-this-instance prerequisites: initial caches warmed, migrations done, a DB connection obtainable from the pool, not in shutdown. Return 503 while starting up or draining.

// Express example
let ready = false, shuttingDown = false;

app.get("/livez", (req, res) => res.status(200).send("ok"));

app.get("/readyz", async (req, res) => {
  if (!ready || shuttingDown) return res.status(503).json({ status: "not ready" });
  try {
    await db.query("SELECT 1");                      // fast, with a short timeout
    return res.status(200).json({ status: "ready" });
  } catch (e) {
    return res.status(503).json({ status: "db unavailable" });
  }
});

await warmCache(); await runMigrationsIfLeader(); ready = true;

process.on("SIGTERM", async () => {                 // graceful shutdown
  shuttingDown = true;                               // readiness flips to 503 first
  await sleep(10_000);                               // let the LB notice and drain
  server.close(() => process.exit(0));
});
Shallow vs deep checks

Deep checks (verifying every dependency) are tempting but dangerous in the readiness path: if a shared dependency fails, every instance goes unready at once and the load balancer has nowhere to send traffic, turning partial degradation into total outage. Check only what this instance needs to function, with timeouts; report optional dependencies in a separate diagnostic endpoint (/status) that feeds dashboards, not routing.

  • Keep checks fast (< 100 ms) and cheap; they run every few seconds on every instance.
  • Do not require authentication on them, but do not expose internals publicly; restrict to the internal network.
  • Return a proper HTTP status (200/503). A 200 with "status":"error" in the body fools the prober.

Where probes run

Kubernetes

containers:
- name: web
  image: acme/web:1.8.3
  ports: [{ containerPort: 8080 }]
  startupProbe:                  # allow up to 30 x 5 = 150 s to boot
    httpGet: { path: /livez, port: 8080 }
    periodSeconds: 5
    failureThreshold: 30
  livenessProbe:
    httpGet: { path: /livez, port: 8080 }
    periodSeconds: 10
    timeoutSeconds: 2
    failureThreshold: 3          # restart after 3 consecutive failures
  readinessProbe:
    httpGet: { path: /readyz, port: 8080 }
    periodSeconds: 5
    timeoutSeconds: 2
    failureThreshold: 2          # remove from Service endpoints
    successThreshold: 1
  lifecycle:
    preStop: { exec: { command: ["sleep", "10"] } }   # drain before SIGTERM

Docker, load balancers, platforms

# Dockerfile / Compose
HEALTHCHECK --interval=15s --timeout=3s --start-period=20s --retries=3 \
  CMD curl -fsS http://localhost:8080/livez || exit 1

# AWS ALB target group health check (Terraform)
health_check {
  path                = "/readyz"
  interval            = 15
  timeout             = 5
  healthy_threshold   = 2
  unhealthy_threshold = 3
  matcher             = "200"
}

Tune thresholds to avoid flapping: require several consecutive failures before removing a target and a couple of successes before adding it back. Set the ASG/ECS "health check grace period" long enough for boot.

Monitoring from outside: synthetic checks

Internal health checks cannot see DNS failures, expired certificates, CDN or firewall misconfigurations, a broken login flow, or regional network problems. Synthetic monitoring runs scripted requests against your public endpoints from outside, on a schedule, from several locations.

  • Uptime checks: HTTP GET every 30-60 s from multiple regions; assert status code, response time and a text snippet in the body.
  • TLS certificate expiry: alert 14+ days ahead.
  • DNS and domain expiry checks.
  • Multi-step browser flows (login, add to cart, checkout) with Playwright-based checks: Checkly, Datadog Synthetics, Grafana Synthetic Monitoring, AWS CloudWatch Synthetics.
  • Heartbeat / dead man's switch monitoring for cron jobs and batch tasks: the job pings a URL (Healthchecks.io, Cronitor) on success; no ping in the expected window triggers an alert. This catches jobs that silently never ran.
# Prometheus blackbox_exporter probing an endpoint
scrape_configs:
  - job_name: blackbox-http
    metrics_path: /probe
    params: { module: [http_2xx] }
    static_configs:
      - targets: [https://www.example.com/, https://api.example.com/healthz]
    relabel_configs:
      - source_labels: [__address__]
        target_label: __param_target
      - source_labels: [__param_target]
        target_label: instance
      - target_label: __address__
        replacement: blackbox:9115

# Alerts
- alert: SiteDown
  expr: probe_success{job="blackbox-http"} == 0
  for: 2m
- alert: CertExpiringSoon
  expr: probe_ssl_earliest_cert_expiry - time() < 14*24*3600
  for: 1h

# Cron heartbeat
0 3 * * *  /opt/backup.sh && curl -fsS --retry 3 https://hc-ping.com/your-uuid
Probe from at least three locations and require agreement

A single prober failing is often its own network. Alert when 2 of 3 locations fail for a couple of minutes to avoid false pages. Also run at least one probe from outside your cloud provider, so a provider-wide issue does not blind your monitor.

Status pages

When things break, customers want to know: is it me or you? A status page reduces support tickets and builds trust.

  • Host it on separate infrastructure and domain from your main app (otherwise it goes down with it). Options: Atlassian Statuspage, Instatus, Better Stack, Cachet (self-hosted), or a static page.
  • Show components (API, Web app, Payments, Webhooks) with current state: Operational, Degraded performance, Partial outage, Major outage.
  • Post incident updates with timestamps; keep a history and show uptime percentages (matching your SLOs).
  • Offer subscriptions (email, RSS, Slack, webhook). Automate updates from monitors for obvious outages, but have a human write the message for complex ones.
  • Be honest. Hiding problems damages trust more than the problem itself.

Pitfalls

  • Liveness probes that check dependencies, causing restart storms.
  • One endpoint for everything (/health returning 200 always, or deep-checking everything).
  • Slow start with an aggressive liveness probe: the app is killed before it finishes booting. Use startup probes.
  • Ignoring graceful shutdown: instance removed from rotation but killed mid-request; deploys drop connections. Handle SIGTERM and drain.
  • Health check endpoints hit by logs/metrics: they flood logs and skew latency statistics; filter them.
  • Green status while users suffer: health checks say 200 but the login flow is broken. Add synthetic journeys and SLI-based alerts.
  • Status page on the same infrastructure as the product.
  • Expired certificates and domains: boring, common, and preventable with a simple probe.

Try it

  1. Add /livez and /readyz to a service. Make readiness fail for the first 20 seconds after boot and observe a Kubernetes or Docker rollout wait for it.
  2. Kill the database and watch readiness fail while liveness stays green. Explain why that is the desired behaviour.
  3. Set up a free uptime monitor (UptimeRobot, Better Stack or Healthchecks.io) for a public URL, plus a heartbeat for a cron job. Let the job fail once on purpose and confirm the alert.
  4. Run openssl s_client -connect example.com:443 -servername example.com 2>/dev/null | openssl x509 -noout -dates and compute days until your cert expires.
