Distributed Tracing

In a microservice system one user click may touch ten services. Metrics tell you the checkout is slow; logs from ten services are a haystack. A trace shows the whole journey of one request as a timeline, revealing exactly which hop spent the time or failed.

The problem tracing solves

Imagine POST /checkout takes 3 seconds. It calls Auth, Cart, Inventory, Pricing and Payments, which call databases and caches. Which one is slow? Without tracing you guess, add timing logs, redeploy, and repeat. With tracing you open one request and see:

 trace_id = 4bf92f35...                                   total 1,240 ms
 ├─ gateway  POST /checkout ███████████████████████████████████████ 1240
 │  ├─ auth-svc  verify token  ██ 35
 │  ├─ cart-svc  GET /cart     ████ 80
 │  │   └─ redis GET cart:42   █ 3
 │  ├─ inventory-svc reserve   ████████████████████████ 780   ◀── slow
 │  │   ├─ postgres SELECT ... ███████████████████ 700           (missing index)
 │  │   └─ postgres UPDATE ...  ██ 60
 │  └─ payment-svc  charge     ███████ 290
 │      └─ HTTPS stripe.com    ██████ 250

Instantly: the inventory query takes 700 ms. That is the value of tracing: causality and latency breakdown across process boundaries.

Core concepts

TermMeaning
TraceThe complete path of one request through the system. Identified by a trace_id.
SpanOne timed unit of work (an HTTP handler, a DB query, an outgoing call). Has a span_id, a parent_span_id, start time, duration, status, name.
AttributesKey-value metadata on a span: http.route, db.statement, user.tier, order.id.
EventsTimestamped notes inside a span (exceptions, "cache miss").
Span kindserver, client, producer, consumer, internal.
Context propagationPassing trace identity across process boundaries so child spans join the same trace.
SamplingDeciding which traces to keep (full capture is expensive).

Context propagation: the magic ingredient

Spans in different services are linked only because the caller sends the trace identity to the callee, usually in an HTTP header. The W3C standard is traceparent:

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  └──────── trace_id (16 bytes) ─┘ └─ parent span id ─┘ └ flags (01 = sampled)
             version
 Service A                         Service B
 start span A (id=a1)
   │  outgoing HTTP call: adds header traceparent: ...trace=T...parent=a1
   ├────────────────────────────▶ extract header ⇒ start span B with
                                   trace=T, parent=a1
                                   ... work ...
   ◀──────────── response ───────  end span B
 end span A
 Both spans carry trace=T, so the backend assembles one tree.

Propagation must also cross async boundaries: put the context in message headers when publishing to Kafka/SQS/RabbitMQ and extract it in the consumer. Inside a process, instrumentation libraries carry context across threads/async tasks (Node's AsyncLocalStorage, Python contextvars, Go's context.Context). Any hop that drops the header breaks the trace into disconnected fragments.

OpenTelemetry (OTel)

OpenTelemetry is the CNCF standard for generating and shipping telemetry (traces, metrics, logs), with SDKs for every major language and a vendor-neutral wire protocol, OTLP. Instrument once; send to Jaeger, Tempo, Honeycomb, Datadog or anything else by changing config.

 app + OTel SDK ──OTLP──▶ OTel Collector ──▶ Tempo / Jaeger  (traces)
 (auto + manual           (receive, batch,  ├▶ Prometheus/Mimir (metrics)
  instrumentation)         sample, enrich,  └▶ Loki (logs)
                           route)

Auto-instrumentation

Often you get 80% of the value with zero code: agents/libraries wrap popular frameworks and clients (HTTP servers, Express/Django/Spring, database drivers, gRPC, Redis) and create spans automatically.

# Node.js
npm i @opentelemetry/api @opentelemetry/auto-instrumentations-node
export OTEL_SERVICE_NAME=checkout
export OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4318
export OTEL_TRACES_SAMPLER=parentbased_traceidratio
export OTEL_TRACES_SAMPLER_ARG=0.1
node --require @opentelemetry/auto-instrumentations-node/register server.js

# Python
pip install opentelemetry-distro opentelemetry-exporter-otlp
opentelemetry-bootstrap -a install
opentelemetry-instrument --service_name checkout python app.py

# Java: attach the agent, no code changes
java -javaagent:opentelemetry-javaagent.jar -Dotel.service.name=checkout -jar app.jar

Manual spans for business logic

import { trace, SpanStatusCode } from "@opentelemetry/api";
const tracer = trace.getTracer("checkout");

async function applyDiscounts(order) {
  return tracer.startActiveSpan("applyDiscounts", async (span) => {
    try {
      span.setAttribute("order.id", order.id);
      span.setAttribute("order.items", order.items.length);
      const result = await pricing.compute(order);
      span.addEvent("discounts computed", { count: result.length });
      return result;
    } catch (err) {
      span.recordException(err);
      span.setStatus({ code: SpanStatusCode.ERROR, message: err.message });
      throw err;
    } finally {
      span.end();
    }
  });
}

Follow the semantic conventions for attribute names (http.request.method, db.system, server.address) so backends and dashboards understand your data.

The Collector

# otel-collector.yaml
receivers:
  otlp: { protocols: { grpc: {}, http: {} } }
processors:
  batch: {}
  memory_limiter: { check_interval: 1s, limit_mib: 400 }
exporters:
  otlp/tempo: { endpoint: tempo:4317, tls: { insecure: true } }
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [otlp/tempo]

Running a Collector (as a sidecar, DaemonSet or gateway) decouples apps from backends and gives one place to batch, filter, redact and sample.

Sampling

Tracing every request at scale is costly in CPU, network and storage. Strategies:

  • Head sampling: decide at the start of the trace (e.g. keep 5%). Cheap and simple; but you may discard the rare slow or failing traces you most want. Use parent-based sampling so all services honour the root decision.
  • Tail sampling: the Collector buffers whole traces, then keeps 100% of errors and slow traces and a small percentage of the rest. Better data, more infrastructure.
  • Always sample low-volume critical flows (checkout).

Tying the pillars together

  • Inject trace_id and span_id into every log line, so from a trace you click to its logs (and the reverse).
  • Attach exemplars (sample trace IDs) to histogram metrics, so from a latency spike on a graph you jump to a representative slow trace.
  • Add the service version and deploy marker as attributes to spot regressions.

Pitfalls

  • Broken propagation: a gateway, message queue or custom HTTP client that strips headers fragments traces. Test end to end.
  • Too many spans (a span per loop iteration) bloats cost and hides the signal. Span meaningful operations.
  • Sensitive data in attributes: SQL with values, request bodies, tokens. Scrub in the SDK or Collector.
  • High overhead from 100% sampling on hot paths.
  • Clock skew between hosts producing odd-looking timelines: run NTP/chrony.
  • Treating tracing as optional until an outage: roll it out gradually but early, starting with the edge services and the databases they call.

  1. Run docker run -p 16686:16686 -p 4317:4317 -p 4318:4318 jaegertracing/jaeger:latest (or the grafana/otel-lgtm image).
  2. Auto-instrument two small services where A calls B over HTTP. Make B sleep 500 ms. Find the slow span in the UI.
  3. Confirm the traceparent header is sent by inspecting B's incoming request headers.
  4. Add trace_id to your structured logs and find a log line from a trace.
