Immutable Infrastructure and Golden Images

Instead of logging into servers to patch and tweak them, build a fresh, fully configured image, deploy it, and throw the old servers away. Immutable infrastructure eliminates drift by never modifying a running machine. Packer is the tool that builds the images.

Pets vs cattle

A famous analogy (Bill Baker, popularised by Randy Bias):

Pets (mutable)Cattle (immutable)
Namingzeus, db-prod-main: unique namesweb-7f3a9: numbered, interchangeable
When sickNursed back to health by handReplaced with a fresh one
ChangesSSH in, patch, tweak in placeBuild a new image, roll it out
RebuildingScary, undocumentedRoutine, automated
Over timeDrift, snowflakesAlways matches the image
The rule

Never fix a server; fix the image (or code) and replace the server. If you can not destroy a server without fear, it is a pet.

Mutable vs immutable deployment

 MUTABLE                                   IMMUTABLE
 server v1 ─ ssh, apt upgrade, edit ─▶ server v1'   image v1 ─▶ [server][server][server]
 server v1' ─ more tweaks ─▶ server v1''            build image v2 (new, tested, versioned)
 (state unknowable after a year)                    launch [v2][v2][v2], shift traffic, destroy v1
                                                    rollback = start the old image again

Benefits: identical servers everywhere, painless rollback (the previous image still exists), fast scale-out because the machine boots already configured (no 10-minute install script during autoscaling), security (no SSH needed; compromised hosts are replaced; patching is a rebuild) and testability (test the exact artifact you ship).

Containers are the most common immutable unit today: a Docker image is an immutable artifact and Kubernetes replaces Pods rather than modifying them. The same philosophy applies to VMs and to the nodes beneath your containers.

Golden images

A golden image is a pre-built machine image (AWS AMI, GCP image, Azure image, VMware template) containing the OS, patches, agents (monitoring, logging, security), your runtime and often the application itself. Typical layering:

  1. Base image: hardened OS plus common agents; rebuilt weekly/monthly for patches by a platform team.
  2. Application image: built on the base for each release; contains the app. Built by CI.

Runtime differences (database URL, secrets) are injected at boot through instance metadata, user-data, environment or a secret manager, not baked in. Per-environment images defeat the purpose: build once, promote the same image through staging to prod.

Packer

HashiCorp Packer automates image creation: launch a temporary VM from a source image, run provisioners to configure it, snapshot it as a new image, and clean up. It is itself declarative HCL and works across clouds (AWS, GCP, Azure, VMware, QEMU, Docker).

Example: an AMI with nginx and the app baked in

packer {
  required_plugins {
    amazon = {
      source  = "github.com/hashicorp/amazon"
      version = "~> 1.3"
    }
  }
}

variable "app_version" {
  type = string
}

locals {
  timestamp = formatdate("YYYYMMDD-hhmm", timestamp())
}

source "amazon-ebs" "web" {
  region        = "eu-west-1"
  instance_type = "t3.small"
  ssh_username  = "ubuntu"
  ami_name      = "shop-web-${var.app_version}-${local.timestamp}"

  source_ami_filter {
    filters = {
      name                = "ubuntu/images/hvm-ssd-gp3/ubuntu-noble-24.04-amd64-server-*"
      root-device-type    = "ebs"
      virtualization-type = "hvm"
    }
    owners      = ["099720109477"]
    most_recent = true
  }

  tags = {
    App     = "shop"
    Version = var.app_version
    Base    = "ubuntu-24.04"
  }
}

build {
  sources = ["source.amazon-ebs.web"]

  provisioner "shell" {
    inline = [
      "cloud-init status --wait",
      "sudo apt-get update -y",
      "sudo apt-get upgrade -y",
      "sudo apt-get install -y nginx"
    ]
  }

  provisioner "ansible" {                 # reuse the roles from the previous lesson
    playbook_file = "./ansible/site.yml"
    extra_arguments = ["--extra-vars", "app_version=${var.app_version}"]
  }

  provisioner "file" {
    source      = "dist/shop.tar.gz"
    destination = "/tmp/shop.tar.gz"
  }

  provisioner "shell" {
    inline = [
      "sudo tar -xzf /tmp/shop.tar.gz -C /opt",
      "sudo systemctl enable shop",
      "sudo rm -rf /tmp/* /home/ubuntu/.ssh/authorized_keys"   # leave no build residue
    ]
  }

  post-processor "manifest" {
    output = "manifest.json"             # records the resulting AMI ID for downstream steps
  }
}
packer init .
packer validate -var app_version=2.3.1 .
packer build -var app_version=2.3.1 .

Using the image

Terraform looks up the newest matching image and launches instances from it. Changing the image changes the launch template, which triggers a rolling replacement (an AWS Auto Scaling Group instance refresh).

data "aws_ami" "shop" {
  most_recent = true
  owners      = ["self"]
  filter {
    name   = "name"
    values = ["shop-web-2.3.1-*"]
  }
}

resource "aws_launch_template" "web" {
  name_prefix   = "shop-web-"
  image_id      = data.aws_ami.shop.id
  instance_type = "t3.small"
}

resource "aws_autoscaling_group" "web" {
  min_size            = 3
  max_size            = 10
  vpc_zone_identifier = var.private_subnet_ids
  launch_template {
    id      = aws_launch_template.web.id
    version = "$Latest"
  }
  instance_refresh {
    strategy = "Rolling"
    preferences { min_healthy_percentage = 66 }
  }
}
 git push ─▶ CI builds app ─▶ Packer bakes AMI ─▶ test the image (boot, smoke test)
        ─▶ Terraform updates launch template ─▶ ASG rolling instance refresh ─▶ old instances terminated

Practicalities

  • Rebuild regularly (at least weekly) even without app changes to pick up OS security patches. Old images rot.
  • Version and tag every image; keep the last few for rollback; garbage-collect the rest (storage costs).
  • Test images: boot one in CI and run smoke tests or InSpec/Goss checks.
  • Harden: CIS benchmarks, disable password SSH, minimal packages, run vulnerability scans (Trivy, Inspector).
  • Share images across accounts/regions with copy/share settings in the builder.
  • Logs and data must live off the instance (central logging, managed databases, attached volumes) because instances are disposable.

Trade-offs and pitfalls

  • Slower change cycle than editing a server: a full bake takes minutes. Mitigate with layered images and caching. For a typo fix, pets are faster; for fleet consistency, cattle win.
  • Stateful systems (databases) resist the model. Keep data on separate volumes or managed services; replace the compute, keep the disk.
  • Debugging with no SSH is harder: invest in logs, metrics, and a break-glass access path (SSM Session Manager) that is audited.
  • Secrets baked into images leak to everyone who can launch the image. Inject at runtime.
  • Image sprawl: without lifecycle policies you accumulate hundreds of AMIs.
  • Many modern teams skip VM images for apps entirely: containers on Kubernetes or ECS, with immutable node images (Bottlerocket, Talos, Flatcar, Amazon Linux managed AMIs) beneath. The principle is the same.

Config management vs immutable

Configure live servers (Ansible alone)Bake images (Packer, Docker)
Change speedFast, in placeSlower: rebuild + redeploy
Drift riskPresentEliminated by design
RollbackReverse the change (hard)Launch previous image
Scale-out start timeSlow (configure at boot)Fast (pre-baked)

They are complementary: use Ansible as a Packer provisioner to describe image contents.

Try it

  1. Use Packer's docker builder (no cloud account needed) to build an image with nginx installed, using a shell provisioner, then run it.
  2. Or build an AMI with the example above in a sandbox account; launch an instance from it and verify nginx runs without any user-data.
  3. Bump a version variable, rebuild, and practise "rolling back" by launching from the previous image.
  4. Identify one pet in your own environment and write down what it would take to make it cattle.
