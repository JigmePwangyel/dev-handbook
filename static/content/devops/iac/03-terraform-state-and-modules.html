Terraform State, Modules and Environments

State is Terraform's memory: the map between your code and real cloud resources. Understanding it, storing it safely, splitting code into reusable modules and organising environments are what separate a demo from a team-ready setup.

What state is and why it exists

When you declare aws_instance.web, Terraform must know which actual instance (i-0abc123) that refers to, otherwise it cannot tell "update" from "create a second one". That mapping, plus a cache of attributes, lives in the state file (terraform.tfstate, JSON). Each plan: read config, read state, query the real world (refresh), diff.

State is sensitive and precious

It contains resource attributes in plain text, including database passwords and generated keys. Treat it like a secret. If it is lost, Terraform believes nothing exists and will try to create duplicates. Never commit it to git, never edit by hand (use terraform state commands), and never run two applies at once.

Remote backends and locking

A local state file works for one person. For a team you need shared state with locking (so two applies cannot collide), encryption and versioning. Configure a remote backend:

terraform {
  backend "s3" {
    bucket       = "acme-tf-state"
    key          = "prod/network/terraform.tfstate"
    region       = "eu-west-1"
    encrypt      = true
    use_lockfile = true          # native S3 locking (Terraform 1.10+); older setups used a DynamoDB table
  }
}

Create the bucket beforehand (turn on versioning so you can recover prior states, block public access, restrict IAM). Other backends: GCS, Azure Blob, Terraform Cloud / HCP Terraform, GitLab-managed state, Postgres. Run terraform init -migrate-state to move existing state to a new backend.

Because state holds secrets, restrict who can read the bucket, and keep state per component (network, database, app) rather than one giant file, which limits blast radius and speeds up plans.

Inspecting and fixing state

terraform state list
terraform state show aws_instance.web
terraform state mv aws_instance.web aws_instance.app     # rename without recreating
terraform state rm aws_instance.legacy                   # stop managing, don't delete
terraform force-unlock LOCK_ID                           # only if a crashed run left a lock

# declarative rename in code (preferred, reviewable)
moved {
  from = aws_instance.web
  to   = aws_instance.app
}

Importing existing infrastructure

For resources created by hand, bring them under management without recreating them. Modern syntax is an import block, which participates in plan:

import {
  to = aws_s3_bucket.assets
  id = "acme-assets-prod"
}

resource "aws_s3_bucket" "assets" {
  bucket = "acme-assets-prod"
}
terraform plan -generate-config-out=generated.tf   # draft HCL for the imported resource
terraform plan    # should end with "No changes" once your config matches reality
terraform apply

Iterate until the plan shows no diff. Tools such as Terraformer or cloud-specific exporters help for large estates.

Drift

Drift is when real infrastructure differs from state or code because someone changed it outside Terraform.

terraform plan -refresh-only      # show drift without proposing code changes
terraform apply -refresh-only     # accept the real values into state
terraform plan                    # normal plan: will propose reverting drift to match code

Run a scheduled plan in CI (nightly) and alert if the exit code with -detailed-exitcode is 2. Decide per case: revert (code wins) or back-port the manual change into code.

Modules

A module is a folder of .tf files with inputs (variables) and outputs. Every Terraform configuration is already a "root module"; you call child modules to avoid copy-paste: a VPC pattern, a "service with load balancer and DNS" pattern.

 modules/
 └── web_server/
     ├── main.tf        resources
     ├── variables.tf   inputs
     └── outputs.tf     outputs
 envs/prod/main.tf  ──calls──▶ module "web" { source = "../../modules/web_server" ... }

# modules/web_server/variables.tf
variable "name"          { type = string }
variable "instance_type" {
  type    = string
  default = "t3.micro"
}
variable "vpc_id"        { type = string }

# modules/web_server/main.tf  (uses var.name etc; resources as in the previous lesson)
resource "aws_instance" "this" { /* ... */ }

# modules/web_server/outputs.tf
output "public_ip" { value = aws_instance.this.public_ip }

# caller
module "web" {
  source        = "../../modules/web_server"
  name          = "shop-prod"
  instance_type = "t3.large"
  vpc_id        = module.network.vpc_id
}

output "web_ip" { value = module.web.public_ip }

Sources: local paths, git URLs with a version ref (git::https://github.com/acme/tf-modules.git//web?ref=v1.4.0), or the public registry (source = "terraform-aws-modules/vpc/aws", version = "~> 5.0"). Always version-pin remote modules.

Good module design: small, focused, few required inputs with sensible defaults, outputs for everything callers might need, no provider configuration inside (pass providers in). Avoid wrapping a single resource in a module "just because"; the registry's community modules (VPC, EKS) are well tested and worth reusing.

Environments: workspaces vs directories

Workspaces

terraform workspace new staging
terraform workspace select prod
terraform workspace list
# in code: terraform.workspace gives the name

Workspaces keep multiple state files for the same code and backend. They are easy but hide which environment you are in (a classic way to destroy production), and encourage environments that must be identical. Many teams avoid them for dev/staging/prod.

Directory per environment (common recommendation)

 infra/
 ├── modules/                 reusable building blocks (versioned)
 │   ├── network/
 │   ├── database/
 │   └── service/
 └── live/
     ├── dev/
     │   ├── network/    main.tf, backend.tf, terraform.tfvars
     │   └── app/
     ├── staging/
     │   ├── network/
     │   └── app/
     └── prod/
         ├── network/
         └── app/

Each folder has its own backend key and state, so a mistake in dev/app cannot touch prod/network. Modules carry the logic; environment folders contain only configuration (sizes, counts, names). Tools like Terragrunt reduce boilerplate by generating backend config and wiring dependencies between folders. Use separate cloud accounts or projects per environment for real isolation.

Sharing data between states

Components need each other's outputs (the app needs the VPC ID). Options: terraform_remote_state data source (reads another state's outputs, couples you to that backend), or look values up with provider data sources (data "aws_vpc" with tags), or publish values to a parameter store (SSM, Consul) for loose coupling. Prefer data sources and tags.

Pitfalls

  • Committing terraform.tfstate to git, or storing it unencrypted.
  • One giant state: plans take minutes and an error can block everyone.
  • Manual terraform state rm followed by apply creates duplicates; understand what you are doing.
  • Deleting the state bucket with destroy if the backend resource is in the same configuration. Bootstrap backends separately.
  • Unpinned module versions, so an upstream change surprises you.

Try it

  1. Move your example from the previous lesson to an S3 (or any) remote backend with terraform init -migrate-state.
  2. Extract the VM and security group into modules/web_server and call it twice with different names; use moved blocks to avoid recreating existing resources.
  3. Create a resource manually in the console, import it with an import block, and reach a clean plan.
  4. Change a tag in the console and observe it in terraform plan -refresh-only.
