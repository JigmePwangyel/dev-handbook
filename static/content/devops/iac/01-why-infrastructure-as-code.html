Why Infrastructure as Code?

Servers, networks, databases and DNS records are infrastructure. If you create them by clicking through a cloud console, nobody can review, repeat or undo what you did. Infrastructure as Code (IaC) means describing infrastructure in text files and letting a tool make reality match.

The pain of ClickOps

"ClickOps" is building infrastructure by hand in a web console or via ad-hoc CLI commands. It feels fast the first time. Then:

  • No memory. Six months later nobody knows why that security group allows port 8443 from an odd IP, or who changed it.
  • Not repeatable. You need a staging environment "just like production". You click for two days and it is subtly different.
  • Not reviewable. A risky change (open a database to the internet) is made with no second pair of eyes.
  • Disaster recovery is a fantasy. If the region fails or an account is compromised, can you rebuild everything in an hour? From memory?
  • Knowledge lives in one head. The person who clicked it leaves.

Snowflakes and drift

A snowflake server is a machine that was hand-tuned over time and is unique: nobody dares touch it because nobody can recreate it. Configuration drift is the gradual divergence between machines (or between reality and documentation) as people make small manual changes: a hotfix applied to two of three servers, a package upgraded on one. Drift causes the worst class of bug: "works on node A but not node B".

 Day 0    prod-1 ≡ prod-2 ≡ prod-3          (identical, from the same recipe)
 Day 90   prod-1 + hotfix, prod-2 + manual tweak, prod-3 unchanged
 Day 180  nobody knows what differs. Rebuilding any of them is risky.

Declarative vs imperative

This is the central design choice in IaC tools.

  • Imperative (procedural): you write the steps. "Create a VM. Then attach this disk. Then open port 80." A shell script with the AWS CLI is imperative. Running it twice might create two VMs. You must handle "already exists" yourself.
  • Declarative: you write the desired end state. "There is one VM of this size with this disk and port 80 open." The tool compares to what exists, works out the difference and makes only the needed changes. Running it twice does nothing the second time.
# Imperative: order and existence checks are YOUR problem
aws ec2 run-instances --image-id ami-0abc --instance-type t3.micro
aws ec2 authorize-security-group-ingress --group-id sg-123 --protocol tcp --port 80 --cidr 0.0.0.0/0

# Declarative (Terraform): describe the end state; the tool computes the steps
resource "aws_instance" "web" {
  ami           = "ami-0abc"
  instance_type = "t3.micro"
}

Declarative tools (Terraform/OpenTofu, CloudFormation, Kubernetes manifests, Ansible modules to a degree) are idempotent: applying the same description repeatedly converges to the same result. Imperative code in general-purpose languages (Pulumi, AWS CDK) can still be declarative in effect: your program builds a desired-state graph that the engine reconciles.

Idempotency is the superpower

An operation is idempotent if doing it once or ten times yields the same state. It makes automation safe to re-run, safe to retry after a partial failure, and safe to run on a schedule to correct drift.

They compose: Terraform creates the VMs and network, Packer provides the image, Ansible (or cloud-init) configures anything that remains, and GitOps keeps the Kubernetes workloads in sync. The next lessons cover each.

Principles to adopt

  1. Everything in git. If it is not in code, it does not exist.
  2. Change only via the pipeline. Console access becomes read-only for production (break-glass excepted, then back-port the change to code).
  3. Small, frequent changes with a reviewed plan.
  4. Environments from one codebase, differing only in variables.
  5. No secrets in code. Reference a secret manager.
  6. Detect drift by scheduled plans that alert on differences.

Trade-offs and honest caveats

  • There is a learning curve and up-front investment; for one throwaway VM, a console click is fine.
  • Code can be wrong at scale: a bad destroy is faster than a bad click. Reviews, plans and guard rails matter more, not less.
  • State management (what the tool believes exists) is a new thing to protect, as you will see in the Terraform lessons.
  • Adopting IaC on existing hand-built infrastructure means importing it incrementally; start with new resources.
  • Cloud APIs change; providers and modules need maintenance.
Start small

You do not need to codify everything on day one. Begin with a new project or one environment, or capture the most error-prone piece (security groups, DNS, IAM) first. Use the console for exploration, but "promote" what you learn into code.

Try it

  1. List the infrastructure behind one app you run: servers, DNS records, buckets, databases, IAM roles. Mark each as "in code", "documented" or "only in someone's head".
  2. Pick the riskiest "only in someone's head" item and think about how long a full rebuild would take.
  3. Write the one-sentence declarative description of one thing (for example "a bucket named X, private, versioned") versus the three imperative commands needed.
