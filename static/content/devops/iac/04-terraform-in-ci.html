Terraform in CI/CD

Running terraform apply from a laptop works until two people do it at once, someone applies uncommitted code, or the person with production credentials is on holiday. Moving Terraform into a pipeline makes infrastructure changes reviewed, auditable and consistent, using the same pull-request workflow as application code.

The standard workflow

 feature branch ──▶ Pull Request ──▶ CI: fmt, validate, lint, security scan, terraform plan
                                         │  plan output posted as a PR comment
                                         ▼
                                  human review (code + plan) ──▶ approve
                                         │
                                  merge to main
                                         ▼
                             CI: terraform apply (saved plan)  ──▶ cloud
                                         │
                                  post-apply: outputs, notifications

The key rule: the plan a reviewer approved is the plan that gets applied. Infrastructure changes are not "done" until merged, and nobody needs production credentials on their laptop.

Example: GitHub Actions

name: terraform
on:
  pull_request:
    paths: ["infra/**"]
  push:
    branches: [main]
    paths: ["infra/**"]

permissions:
  id-token: write        # OIDC to the cloud, no long-lived keys
  contents: read
  pull-requests: write   # to comment the plan

env:
  TF_IN_AUTOMATION: "true"
  TF_VAR_environment: prod

jobs:
  plan:
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    defaults: { run: { working-directory: infra/live/prod/app } }
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gha-terraform-plan   # read-only role
          aws-region: eu-west-1
      - uses: hashicorp/setup-terraform@v3
        with: { terraform_version: 1.9.5 }
      - run: terraform fmt -check -recursive
      - run: terraform init -input=false
      - run: terraform validate
      - run: terraform plan -input=false -no-color -out=tfplan | tee plan.txt
      - uses: actions/github-script@v7        # comment the plan on the PR
        with:
          script: |
            const fs = require('fs');
            const plan = fs.readFileSync('infra/live/prod/app/plan.txt','utf8').slice(0, 60000);
            github.rest.issues.createComment({
              ...context.repo, issue_number: context.issue.number,
              body: "```\n" + plan + "\n```"
            });

  apply:
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    runs-on: ubuntu-latest
    environment: production        # protected environment: requires manual approval
    defaults: { run: { working-directory: infra/live/prod/app } }
    concurrency: tf-prod-app       # never two applies at once
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gha-terraform-apply   # write role
          aws-region: eu-west-1
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init -input=false
      - run: terraform apply -input=false -auto-approve

Notes: the simple form above re-plans on merge; for strict "apply what was reviewed" upload the tfplan artifact from the PR run and apply that, or use a purpose-built tool.

Credentials: use OIDC, not stored keys

CI platforms (GitHub, GitLab) can issue short-lived signed tokens that your cloud trusts to assume a role. No access keys sit in repo secrets to leak. Use a read-only role for PR plans and a separate write role that only the protected main branch can assume.

Policy as code

Reviewers miss things. Encode rules and enforce them automatically against the plan:

  • No S3 buckets or security groups open to the world; all disks encrypted; mandatory cost tags; only approved regions and instance sizes.
  • Static scanners on the code: Trivy (successor of tfsec), Checkov, KICS: easy to add as a CI step.
  • OPA / Conftest with Rego, evaluated on terraform show -json tfplan: 
    package terraform

deny[msg] {
  r := input.resource_changes[_]
  r.type == "aws_s3_bucket_public_access_block"
  r.change.after.block_public_acls == false
  msg := sprintf("%s must block public ACLs", [r.address])
}
  • Sentinel (HCP Terraform), and cost estimation with Infracost, which comments the monthly price delta on each PR.
  • Native testing: terraform test (HCL test files) and tools like Terratest for integration tests.
Fail fast, cheap checks first

Order the pipeline: fmt, validate, lint, security scan, then plan. Developers get feedback in seconds, and plans (which call the cloud API) only run on code that is already sane.

OpenTofu

In 2023 HashiCorp changed Terraform's license from MPL to the Business Source License. The community forked the last open-source version as OpenTofu, now a Linux Foundation project. It is a drop-in replacement for most users: same HCL, same providers (via its own registry), command tofu instead of terraform. It adds features such as client-side state encryption and early variable evaluation. The two diverge slowly; check compatibility for newer features. If your concern is licensing or vendor independence, OpenTofu is a sound choice; otherwise either works, and everything in these lessons applies to both.

Choosing: Terraform/OpenTofu has the largest ecosystem, hiring pool and community modules. Pick Pulumi when your team prefers general-purpose languages and testing tools. Pick CDK/CloudFormation for AWS-only shops that want AWS-managed state. The workflow described here (PR, plan, review, apply from CI) applies to all of them.

Pitfalls and best practices

  • Auto-applying on merge to production without a protected environment or approval for risky stacks. Keep a manual gate for destructive or sensitive layers.
  • Plans containing secrets posted into PR comments. Mask sensitive values and be careful about public repos.
  • Pipeline concurrency: use locking and CI concurrency groups; state locking is the last line of defence.
  • Giving CI admin credentials. Scope roles to the stack; separate plan and apply roles.
  • Failed applies halfway: do not panic; fix the cause and re-apply (idempotent). Do not delete state.
  • Plan drift between PR time and merge time: apply a fresh plan, or re-plan on merge and require approval if it differs.
  • Pin tool versions in CI to match local versions.
  • Back-pressure for emergencies: define a documented break-glass path, and back-port manual changes into code.

Try it

  1. Create a repo with a small Terraform config (even the local provider) and a workflow running fmt, validate and plan on PRs.
  2. Add trivy config . or Checkov as a step and make it fail on a deliberately insecure resource.
  3. Add a protected environment so the apply job waits for manual approval.
  4. Optional: run Atlantis locally with its docker image and see the PR-comment workflow.
