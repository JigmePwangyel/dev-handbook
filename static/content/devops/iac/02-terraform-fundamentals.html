Terraform Fundamentals

Terraform is the most widely used provisioning tool. You describe cloud resources in HCL, run terraform plan to preview exactly what will change, and terraform apply to make it so. This lesson builds a real example: a VM with a security group on AWS.

How it works

  *.tf files (desired)         state file (what Terraform believes exists)
        │                                   │
        └──────────▶  terraform plan  ◀─────┘
                           │  compares, and refreshes against the real cloud API
                           ▼
                  proposed diff: + create  ~ update  - destroy
                           │ (you review)
                           ▼
                    terraform apply ──▶ provider plugin ──▶ AWS / GCP / Azure / ... API

Terraform builds a dependency graph from references between resources, so it creates things in the right order and in parallel where possible. Providers are plugins that translate resources into API calls for a specific platform (AWS, Google, Azure, Cloudflare, Kubernetes, GitHub, Datadog and thousands more).

Install and workflow

brew install terraform        # or OpenTofu: brew install opentofu  (command: tofu)
terraform version

terraform init       # download providers/modules, set up backend (run first, and after adding providers)
terraform fmt        # canonical formatting
terraform validate   # syntax and internal consistency
terraform plan       # preview; changes nothing
terraform apply      # make the changes (asks for "yes")
terraform destroy    # delete everything this configuration manages

HCL building blocks

BlockPurpose
terraformRequired Terraform and provider versions, backend
providerConfigure a provider (region, credentials)
resourceA thing to create and manage
dataRead-only lookup of something that exists (an AMI, a VPC)
variableInput parameter
localsNamed expressions to avoid repetition
outputValues to print or share after apply
moduleReuse a group of resources (next lesson)

Resources reference each other with TYPE.NAME.ATTRIBUTE (for example aws_security_group.web.id), and that reference is what creates the dependency.

Complete example: a web server VM and security group

Layout: three files in a directory (the names are convention only; Terraform loads every .tf file in the folder).

versions.tf

terraform {
  required_version = ">= 1.7"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.60"      # allow 5.x, at least 5.60
    }
  }
}

provider "aws" {
  region = var.region
  default_tags {
    tags = { Project = "demo", ManagedBy = "terraform" }   # applied to everything
  }
}

variables.tf

variable "region" {
  type    = string
  default = "eu-west-1"
}

variable "instance_type" {
  type        = string
  description = "EC2 size"
  default     = "t3.micro"
}

variable "ssh_allowed_cidr" {
  type        = string
  description = "Your public IP in CIDR form, e.g. 203.0.113.7/32"
  validation {
    condition     = can(cidrnetmask(var.ssh_allowed_cidr))
    error_message = "Must be a valid CIDR block."
  }
}

variable "key_name" {
  type        = string
  description = "Name of an existing EC2 key pair"
}

main.tf

# Look up the latest Ubuntu 24.04 AMI instead of hard-coding an ID
data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"]   # Canonical
  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd-gp3/ubuntu-noble-24.04-amd64-server-*"]
  }
}

# Use the account's default VPC to keep the example short
data "aws_vpc" "default" {
  default = true
}

resource "aws_security_group" "web" {
  name_prefix = "web-"
  description = "Allow HTTP from anywhere, SSH from my IP"
  vpc_id      = data.aws_vpc.default.id

  ingress {
    description = "HTTP"
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  ingress {
    description = "SSH"
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = [var.ssh_allowed_cidr]
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  lifecycle {
    create_before_destroy = true
  }
}

resource "aws_instance" "web" {
  ami                    = data.aws_ami.ubuntu.id
  instance_type          = var.instance_type
  key_name               = var.key_name
  vpc_security_group_ids = [aws_security_group.web.id]   # implicit dependency

  user_data = <<-EOT
    #!/bin/bash
    apt-get update -y
    apt-get install -y nginx
    systemctl enable --now nginx
  EOT

  root_block_device {
    volume_size = 20
    encrypted   = true
  }

  metadata_options {
    http_tokens = "required"    # enforce IMDSv2
  }

  tags = { Name = "web-1" }
}

outputs.tf

output "public_ip" {
  value = aws_instance.web.public_ip
}

output "url" {
  value = "http://${aws_instance.web.public_dns}"
}

Run it

export AWS_PROFILE=dev        # credentials come from the environment, never from .tf files
terraform init
terraform plan  -var 'ssh_allowed_cidr=203.0.113.7/32' -var 'key_name=my-key'
terraform apply -var 'ssh_allowed_cidr=203.0.113.7/32' -var 'key_name=my-key'
# ...
# Outputs:
# public_ip = "54.12.34.56"
curl $(terraform output -raw public_ip)
terraform destroy ...         # stop paying for it

Reading the plan: + create, ~ update in place, -/+ destroy and recreate (some attribute changes force replacement, which for a database means data loss; always read for -/+ and must be replaced).

Variables, locals and loops

# terraform.tfvars (auto-loaded) or prod.tfvars (-var-file=prod.tfvars)
region           = "eu-west-1"
ssh_allowed_cidr = "203.0.113.7/32"
key_name         = "my-key"

locals {
  name = "web-${terraform.workspace}"
  common_tags = { Owner = "platform" }
}

# several similar resources with for_each (prefer over count: stable keys)
variable "buckets" { default = ["logs", "assets"] }
resource "aws_s3_bucket" "b" {
  for_each = toset(var.buckets)
  bucket   = "acme-${each.key}-prod"
}

Variable precedence (low to high): defaults, terraform.tfvars, *.auto.tfvars, -var-file, -var, and TF_VAR_name environment variables sit alongside these for CI. Mark secrets sensitive = true to hide them from output (they still end up in state).

Best practices

  • Always plan, read it, then apply; in CI save the plan file (-out=tfplan) and apply exactly that.
  • Pin provider and Terraform versions; commit .terraform.lock.hcl.
  • Do not commit .terraform/, *.tfstate or secret tfvars. Add them to .gitignore.
  • Prefer for_each over count for collections; removing the middle item with count shifts indexes and destroys things.
  • Tag everything; use lifecycle { prevent_destroy = true } on irreplaceable resources.
  • Never hard-code credentials; use environment, profiles, or OIDC-based roles in CI.
  • Run terraform fmt, validate, and a linter (tflint) and scanner (trivy, checkov) in CI.

Pitfalls

  • Editing resources in the console, then running Terraform: it will revert your change (drift).
  • Renaming a resource block in code means "destroy old, create new" unless you use a moved block.
  • Ignoring the state file's importance: the next lesson is about it.

Try it

  1. Apply the example in a sandbox account (a t3.micro costs pennies, or use the free tier), visit the nginx page, then run terraform destroy.
  2. Change instance_type and read the plan: is it an in-place update or a replace?
  3. Add an output for the security group ID and re-apply; note that only outputs change.
  4. No cloud account? Use the hashicorp/local or hashicorp/docker provider to practice the same workflow.
