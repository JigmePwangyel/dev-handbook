GitOps

GitOps takes infrastructure as code one step further: git is the single source of truth for what should run, and an automated agent inside the environment continuously makes reality match it. Deployments become pull requests; rollbacks become reverts.

The problem with push-based deployment

In a classic CI/CD pipeline, the CI server builds the image and then pushes the change: kubectl apply or helm upgrade from a CI job. This works but has weaknesses:

  • CI needs powerful credentials to your production cluster, which is a juicy target (a compromised pipeline owns production).
  • The cluster may be behind a firewall that CI cannot reach.
  • Someone runs kubectl edit in production and nobody notices: drift between git and reality.
  • "What is running in prod right now?" requires checking the cluster, not the repo.
  • A failed or partial pipeline run leaves an unknown state.

The four principles

  1. Declarative: the whole system is described as desired state (Kubernetes YAML, Helm, Kustomize).
  2. Versioned and immutable: the desired state is stored in git, with full history, review and audit.
  3. Pulled automatically: an agent in the cluster pulls approved changes; humans do not push.
  4. Continuously reconciled: the agent constantly compares live state to git and corrects drift.

This is the same reconciliation loop Kubernetes itself uses (see the architecture lesson), applied one level up: Kubernetes reconciles Pods to the spec; the GitOps controller reconciles the spec to git.

Argo CD example

# Install
kubectl create namespace argocd
kubectl apply -n argocd --server-side -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml

# An Application: "keep this path of this repo synced to this namespace"
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: shop
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/acme/platform-config.git
    targetRevision: main
    path: apps/shop/overlays/production      # Kustomize overlay, or a Helm chart
  destination:
    server: https://kubernetes.default.svc
    namespace: shop
  syncPolicy:
    automated:
      prune: true        # delete resources removed from git
      selfHeal: true     # revert manual changes in the cluster
    syncOptions:
      - CreateNamespace=true

Flux example

flux bootstrap github --owner=acme --repository=platform-config --path=clusters/prod --personal

apiVersion: source.toolkit.fluxcd.io/v1
kind: GitRepository
metadata: { name: platform-config, namespace: flux-system }
spec:
  interval: 1m
  url: https://github.com/acme/platform-config
  ref: { branch: main }
---
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata: { name: shop, namespace: flux-system }
spec:
  interval: 5m
  path: ./apps/shop/overlays/production
  prune: true
  sourceRef: { kind: GitRepository, name: platform-config }
  healthChecks:
    - { apiVersion: apps/v1, kind: Deployment, name: shop, namespace: shop }

Repository layout

Separate application source code from deployment configuration. Reasons: different change frequency, different access control (not every developer can edit prod), and config commits (image bumps) do not trigger source builds in a loop.

 app repo (shop)                         config repo (platform-config)
 ├── src/                                ├── apps/
 ├── Dockerfile                          │   └── shop/
 └── .github/workflows/ci.yml            │       ├── base/            deployment, service, ...
                                         │       └── overlays/
                                         │           ├── dev/         image tag, 1 replica
                                         │           ├── staging/
                                         │           └── production/  image tag, 6 replicas
                                         ├── infrastructure/          ingress, cert-manager, monitoring
                                         └── clusters/
                                             ├── dev/                 which apps/overlays this cluster runs
                                             └── prod/

Environments are directories (or Helm values files), not long-lived branches. Branch-per-environment causes painful merges and drift between branches. Promotion from staging to production is a pull request changing the image tag (or a config copy) in the production overlay.

The complete flow

 1. Developer merges code to app repo
 2. CI: test ─▶ build image ─▶ scan ─▶ push shop:2.4.0 to registry
 3. CI (or Flux image automation / Argo CD Image Updater) opens a commit/PR in the CONFIG repo:
        overlays/staging: newTag 2.3.1 ─▶ 2.4.0
 4. Review/auto-merge ─▶ GitOps agent in the staging cluster sees the new commit
 5. Agent renders manifests, diffs against live state, applies the change
 6. Kubernetes performs a rolling update; agent reports Healthy / Degraded
 7. After verification, a PR bumps overlays/production to 2.4.0 ─▶ same sync in prod
 8. Rollback: git revert that commit ─▶ the agent restores the previous state
 9. Someone runs kubectl edit in prod? selfHeal reverts it (and the event is visible)

Secrets in GitOps

Git must not hold plaintext secrets. Use Sealed Secrets, SOPS-encrypted files (native Flux support) or External Secrets Operator referencing a vault (see the Kubernetes configuration lesson). Git then contains only encrypted values or references.

GitOps for infrastructure, not just Kubernetes

The pattern extends beyond clusters: Terraform changes flow through PR, plan and merge (previous lesson), which is GitOps-like in workflow. Operators such as Crossplane or the Flux Terraform controller reconcile cloud resources from the cluster continuously. A common stack: Terraform creates the cluster and a bootstrap of Argo CD or Flux; from then on Kubernetes workloads and add-ons are managed from git.

Trade-offs and pitfalls

  • Extra moving parts: another controller to operate, upgrade and secure. Its repository access is the new crown jewel: protect main with required reviews and signed commits.
  • Feedback is slower and less direct than a push pipeline: "did my deploy work?" means watching the agent's status; wire up notifications (Slack, GitHub status).
  • Image tag updates need a deliberate mechanism (CI commit, image automation); latency and commit noise are real.
  • Auto-prune is dangerous: deleting a manifest from git deletes the resource (even a PVC). Use finalizers, Prune=false annotations on stateful things, and review diffs carefully.
  • Ordering and dependencies: CRDs before custom resources, namespaces before workloads. Use sync waves (Argo) or dependsOn (Flux).
  • Helm hook and non-declarative edge cases, such as data migrations, need Jobs and care.
  • Fields mutated by controllers (HPA changing replicas) appear as drift; configure ignore differences.
  • Do not use selfHeal blindly during an incident when you need to hotfix live; pause sync, then back-port to git.
Why it matters

With GitOps the answer to "what changed, who approved it, and how do we undo it?" is always "look at git". Combined with Terraform and immutable images, your entire stack becomes reviewable, reproducible and recoverable from a repository.

Try it

  1. On a kind cluster install Argo CD, then port-forward the UI (kubectl port-forward svc/argocd-server -n argocd 8080:443).
  2. Create a config repo with a Kustomize base and a dev overlay of a simple nginx Deployment; register it as an Application with automated sync.
  3. Change replicas in git and watch the cluster follow. Then kubectl scale manually and watch selfHeal revert it.
  4. Break the repo (invalid YAML) to see how failures are reported, then git revert to recover.
