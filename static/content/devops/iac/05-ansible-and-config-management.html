Ansible and Configuration Management

Terraform creates the server; something must then install packages, write config files and start services. Configuration management tools do this declaratively and repeatably across many machines. Ansible is the most popular because it needs nothing installed on the targets except SSH and Python.

The problem it solves

You have ten web servers. Installing nginx by SSHing into each and typing commands creates drift, and adding an eleventh means remembering all the steps. A shell script helps, but running it twice may append duplicate lines, reinstall things, or fail on "already exists". Configuration management describes the desired state of a machine and brings each machine to it safely, any number of times.

Why Ansible

  • Agentless: connects over SSH (WinRM for Windows). Nothing to install, no daemon, no central server required. Chef and Puppet traditionally need an agent on every node.
  • Push model: you run it from a laptop or CI; it connects out to the hosts.
  • YAML playbooks: readable by non-programmers.
  • Huge module library: packages, users, files, services, cloud, network devices, Kubernetes.
  • Trade-off: SSH round-trips make it slower than agent pull models at very large scale; and while modules are declarative, playbooks are ordered procedures, so state tracking is weaker than Terraform's.

Install and first command

pipx install ansible-core     # or: brew install ansible
ansible --version
ansible all -i inventory.ini -m ping          # ad-hoc: "can I reach everyone?"
ansible webservers -i inventory.ini -m apt -a "name=htop state=present" --become

Inventory

A list of hosts, grouped, with variables.

# inventory.ini
[webservers]
web1 ansible_host=203.0.113.10
web2 ansible_host=203.0.113.11

[dbservers]
db1  ansible_host=203.0.113.20

[all:vars]
ansible_user=ubuntu
ansible_ssh_private_key_file=~/.ssh/id_ed25519

[webservers:vars]
http_port=80

YAML inventories work too. For clouds use dynamic inventory plugins (amazon.aws.aws_ec2) that discover hosts by tag, so Terraform-created machines appear automatically. Per-host and per-group variables live in host_vars/ and group_vars/ directories.

Playbooks

A playbook is a list of plays; each play maps a host group to a list of tasks; each task calls a module with arguments.

Complete example: configure an nginx web server

# site.yml
- name: Configure web servers
  hosts: webservers
  become: true                      # sudo
  vars:
    site_domain: example.com
    web_root: /var/www/example

  tasks:
    - name: Install nginx
      ansible.builtin.apt:
        name: nginx
        state: present
        update_cache: true
        cache_valid_time: 3600

    - name: Create web root
      ansible.builtin.file:
        path: "{{ web_root }}"
        state: directory
        owner: www-data
        group: www-data
        mode: "0755"

    - name: Deploy index page from template
      ansible.builtin.template:
        src: index.html.j2
        dest: "{{ web_root }}/index.html"
        owner: www-data
        mode: "0644"

    - name: Deploy nginx site config
      ansible.builtin.template:
        src: site.conf.j2
        dest: /etc/nginx/sites-available/{{ site_domain }}
        mode: "0644"
      notify: Reload nginx            # only fires if the file CHANGED

    - name: Enable the site
      ansible.builtin.file:
        src: /etc/nginx/sites-available/{{ site_domain }}
        dest: /etc/nginx/sites-enabled/{{ site_domain }}
        state: link
      notify: Reload nginx

    - name: Remove default site
      ansible.builtin.file:
        path: /etc/nginx/sites-enabled/default
        state: absent
      notify: Reload nginx

    - name: Ensure nginx is enabled and running
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true

    - name: Allow HTTP through firewall
      community.general.ufw:
        rule: allow
        port: "80"
        proto: tcp

  handlers:
    - name: Reload nginx
      ansible.builtin.service:
        name: nginx
        state: reloaded
# templates/site.conf.j2
server {
    listen {{ http_port | default(80) }};
    server_name {{ site_domain }};
    root {{ web_root }};
    index index.html;
    location / { try_files $uri $uri/ =404; }
}

# templates/index.html.j2
<h1>Hello from {{ inventory_hostname }}</h1>
ansible-playbook -i inventory.ini site.yml --check --diff   # dry run: show what WOULD change
ansible-playbook -i inventory.ini site.yml                  # apply
ansible-playbook -i inventory.ini site.yml --limit web1     # one host
ansible-playbook -i inventory.ini site.yml --tags nginx -v

Output shows per-task ok (already correct), changed (it made a change) or failed. Run it twice: the second run should report changed=0.

Idempotency

Well-written modules describe state: state: present, state: started, state: absent. The module checks first and only acts if needed. Contrast:

# NOT idempotent: appends a line every run, always reports "changed"
- ansible.builtin.shell: echo "export FOO=1" >> /etc/profile

# idempotent
- ansible.builtin.lineinfile:
    path: /etc/profile
    line: export FOO=1
Avoid shell and command when a module exists

The shell/command modules are an escape hatch with no idea of state. If you must use them, add creates:, removes: or changed_when: to make them behave. Run ansible-lint to catch these.

Handlers, variables, conditionals, loops

- name: Install tools
  ansible.builtin.apt:
    name: "{{ item }}"
    state: present
  loop: [git, curl, htop]
  when: ansible_facts['os_family'] == "Debian"

- name: Create app users
  ansible.builtin.user:
    name: "{{ item.name }}"
    groups: "{{ item.groups }}"
  loop:
    - { name: alice, groups: sudo }
    - { name: bob,   groups: docker }

Facts are auto-gathered host details (ansible_facts): OS, IPs, memory. Handlers run once at the end of a play, only if notified by a changed task: perfect for "reload service after config change". Variable precedence is deep (about 22 levels); keep it simple: defaults in roles, overrides in group_vars.

Roles

A role packages tasks, templates, handlers and defaults into a reusable directory structure.

 roles/nginx/
 ├── tasks/main.yml         the tasks
 ├── handlers/main.yml      reload nginx, etc.
 ├── templates/             *.j2 files
 ├── files/                 static files
 ├── defaults/main.yml      overridable default variables (lowest precedence)
 ├── vars/main.yml          internal constants
 ├── meta/main.yml          dependencies
 └── README.md

# site.yml, now tiny
- hosts: webservers
  become: true
  roles:
    - role: common          # users, ssh hardening, unattended-upgrades
    - role: nginx
      vars: { site_domain: example.com }

- hosts: dbservers
  become: true
  roles: [common, postgresql]

Create a skeleton with ansible-galaxy init roles/nginx. Reuse community roles and collections from Ansible Galaxy (ansible-galaxy collection install community.general), pin versions in requirements.yml.

Secrets: Ansible Vault

ansible-vault create group_vars/prod/vault.yml      # encrypted file with db_password etc.
ansible-playbook site.yml --ask-vault-pass          # or --vault-password-file
ansible-vault encrypt_string 's3cr3t' --name 'db_password'

Alternatively pull secrets from a manager at runtime (community.hashi_vault, AWS lookup plugins).

Where Ansible fits (and where it does not)

  • Good: bootstrapping and configuring long-lived VMs, bare metal and network gear; one-off orchestration (rolling restarts, patching: use serial: 1); glue tasks.
  • Weaker: creating cloud resources (Terraform tracks state and does that better); keeping hundreds of machines continuously converged (agent-based or immutable approaches fit better).
  • Combined: Terraform provisions; Ansible (or cloud-init) configures; or Ansible runs inside Packer to bake an image (next lesson), which avoids configuring live servers at all.

Best practices

  • Keep playbooks in git; run via CI against staging first.
  • Always test with --check --diff; use Molecule to test roles in containers.
  • Use fully qualified module names (ansible.builtin.apt).
  • Name every task clearly; the names are your run log.
  • Use serial and max_fail_percentage for safe rolling changes.
  • Pin Ansible and collection versions.
  • Do not edit servers by hand afterwards; that is how drift returns.

Try it

  1. Launch two cheap VMs (or two Docker containers with SSH, or a local Multipass/Vagrant VM) and write an inventory.
  2. Run the nginx playbook; confirm curl on each host. Run it again and check for changed=0.
  3. SSH to one server, edit the nginx config manually, re-run the playbook, and watch it repair the drift and fire the handler.
  4. Refactor the tasks into a roles/nginx role.
