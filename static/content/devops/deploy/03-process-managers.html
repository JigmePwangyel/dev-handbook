Process Managers: systemd, PM2, supervisor

Running node server.js in an SSH session works until you close the terminal, the process crashes, or the server reboots. A process manager keeps your app alive, restarts it when it fails, captures its logs and starts it at boot.

The problem

Run node server.js & and log out: depending on the shell, the process gets SIGHUP and dies. Use nohup or screen and it survives logout, but when it crashes at 3 a.m. nobody restarts it, logs go to a random file, and after a reboot it is gone. A process manager (also called a supervisor or init system) is a small, trusted program whose job is to run your programs and keep them running:

  • Start on boot, in the right order (after network, after database).
  • Restart on crash, with back-off so a crash loop does not melt the CPU.
  • Run as a specific unprivileged user with resource limits.
  • Collect stdout/stderr and manage logs.
  • Offer start/stop/restart/status commands and send signals correctly for graceful shutdown.

Option 1: systemd (the default on modern Linux)

systemd is PID 1 on Ubuntu, Debian, RHEL, Fedora. It is already installed, supervises everything on the machine, and needs no extra runtime. For a single server, it is usually the right answer. A unit file:

# /etc/systemd/system/myapp.service
[Unit]
Description=My Node API
After=network-online.target postgresql.service
Wants=network-online.target

[Service]
Type=simple
User=myapp
Group=myapp
WorkingDirectory=/srv/myapp/current
EnvironmentFile=/etc/myapp/myapp.env
ExecStart=/usr/bin/node server.js
Restart=on-failure          # restart if exit code != 0, killed by signal, or timeout
RestartSec=3
StartLimitIntervalSec=60    # give up (mark failed) if it restarts too often...
StartLimitBurst=5           # ...more than 5 times in 60 s
TimeoutStopSec=30           # how long to wait after SIGTERM before SIGKILL
LimitNOFILE=65536
MemoryMax=1G                # cgroup limit: OOM-kill this service, not the whole box
NoNewPrivileges=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload            # after editing any unit file
sudo systemctl enable --now myapp       # start now AND at boot
sudo systemctl restart myapp
sudo systemctl status myapp
sudo systemctl reload myapp             # if you defined ExecReload (e.g. send SIGHUP)
journalctl -u myapp -f                  # follow logs
journalctl -u myapp --since "1 hour ago" -p err
systemctl list-units --failed
systemd-analyze security myapp          # hardening score card

Logs: stdout and stderr go to the journal automatically. Just console.log; no log files to rotate. Make sure the journal is persistent (/var/log/journal exists) and size-limited (SystemMaxUse= in /etc/systemd/journald.conf).

Running several instances: template units

# /etc/systemd/system/myapp@.service   (the "@" makes it a template; %i is the instance name)
[Service]
Environment=PORT=%i
ExecStart=/usr/bin/node server.js
# ...rest as above

sudo systemctl enable --now myapp@3000 myapp@3001 myapp@3002
# then load-balance across 3000-3002 with nginx upstream

Other useful systemd features: .timer units (a better cron), socket activation, ExecStartPre (run migrations or checks), DynamicUser=yes, WatchdogSec with sd_notify for liveness.

Option 2: PM2 (Node-specific)

PM2 is a Node process manager with batteries: clustering, zero-downtime reload, built-in log management and a monitor UI. It is popular because it is easy for Node developers and does not require systemd knowledge.

sudo npm install -g pm2

pm2 start server.js --name myapp -i max      # cluster mode: one worker per CPU core
pm2 list
pm2 logs myapp
pm2 monit
pm2 reload myapp                             # graceful zero-downtime reload (cluster mode)
pm2 restart myapp
pm2 stop myapp

# Survive reboots: PM2 registers itself with systemd
pm2 startup systemd -u myapp --hp /srv/myapp   # prints a command to run with sudo
pm2 save                                       # remember the current process list

Better to declare it in a file:

// ecosystem.config.js
module.exports = {
  apps: [{
    name: 'myapp',
    script: 'server.js',
    instances: 'max',            // or a number
    exec_mode: 'cluster',
    max_memory_restart: '500M',  // restart a leaking worker
    kill_timeout: 10000,         // ms before SIGKILL after SIGINT/SIGTERM
    wait_ready: true,            // wait for process.send('ready') before routing traffic
    listen_timeout: 10000,
    env_production: { NODE_ENV: 'production', PORT: 3000 }
  }]
};
// pm2 start ecosystem.config.js --env production

Pros: cluster mode with rolling reload; simple for Node; cross-platform (works on a laptop and macOS). Cons: another daemon (which itself needs supervising, hence pm2 startup using systemd); logs live in ~/.pm2/logs unless configured (add pm2-logrotate); a Node-centric tool, so mixed-language servers need a second manager; the free tier pushes toward the paid PM2 Plus.

Option 3: supervisor

Supervisor (supervisord) is a Python-based, language-agnostic process control system, historically popular for Python/PHP/Ruby apps before systemd was universal, and still common inside containers that must run several processes.

# /etc/supervisor/conf.d/myapp.conf
[program:myapp]
command=/usr/bin/node /srv/myapp/current/server.js
directory=/srv/myapp/current
user=myapp
autostart=true
autorestart=true
startretries=5
stopsignal=TERM
stopwaitsecs=30
numprocs=1
environment=NODE_ENV="production",PORT="3000"
stdout_logfile=/var/log/myapp/out.log
stderr_logfile=/var/log/myapp/err.log
stdout_logfile_maxbytes=50MB
stdout_logfile_backups=5
sudo apt install -y supervisor
sudo supervisorctl reread && sudo supervisorctl update
sudo supervisorctl status
sudo supervisorctl restart myapp

On a modern server it duplicates what systemd already does; choose it when you are inside a container or on a system without systemd.

Clustering: using every core

A Node process runs JavaScript on one thread, so a 4-core VPS wastes 3 cores with a single process. Options:

  1. PM2 cluster mode or Node's cluster module: the master process listens on the port and distributes connections to workers. Easiest.
  2. Multiple processes behind nginx: systemd template units on ports 3000, 3001, ... listed in an nginx upstream. More explicit, plays well with drain-and-restart one at a time.
  3. Containers: one container per core or many replicas behind a load balancer (the Kubernetes way).

Constraints: workers share nothing. In-memory sessions, caches, rate-limit counters and WebSocket rooms are per process. Move shared state to Redis/Postgres. This is the same stateless-app requirement as for load balancers. For other stacks the equivalents are gunicorn/uvicorn workers (-w 4), Puma workers, PHP-FPM pools. JVM apps typically use threads in one process instead.

Signals and graceful stop

All managers stop a process the same way: send SIGTERM, wait a timeout, then SIGKILL. Your app should handle SIGTERM by finishing in-flight work (details in the zero-downtime lesson). Two traps: running via npm start or a shell wrapper puts an intermediate process between the manager and Node that may not forward signals. Execute node directly in ExecStart. And in Docker, the same applies to PID 1.

Which should you choose?

  • A Linux server, any language: systemd. Fewer moving parts, best isolation, native logging.
  • Node, want clustering and graceful reloads with minimal fuss: PM2 (ideally started by systemd), or systemd with several instances behind nginx.
  • Inside a container: usually none. One process per container; the orchestrator (Docker restart policy, Kubernetes) is the manager.
  • Multiple processes in one container or no systemd: supervisor (or s6-overlay).
Don't forget what supervises the supervisor

Whatever you choose, check it survives a reboot and that its own crash is handled. A process manager that is not enabled at boot is just a more elaborate way to forget to start your app.

Pitfalls

  • Crash loops hiding a real bug: a restart policy with no limit and no alert. Alert on restart count.
  • Memory leaks "fixed" by max_memory_restart forever. It is a safety net, not a cure.
  • Relative paths and missing environment: services run with a minimal environment, not your shell's. Specify WorkingDirectory, absolute paths and EnvironmentFile.
  • Forgetting daemon-reload after editing a unit; changes silently do not apply.
  • Running as root. Always set User=.
  • PM2 started as your login user, so it does not run after reboot unless pm2 startup and pm2 save were done.

Try it

  1. Write a tiny Node HTTP server, create a systemd unit for it with Restart=on-failure, start it and curl it.
  2. Kill it with kill -9 and confirm it comes back (journalctl -u). Add process.exit(1) on a route to make it crash on demand; check StartLimitBurst behaviour by triggering it repeatedly.
  3. Set MemoryMax=100M and write a route that leaks memory. Watch systemd kill and restart the service.
  4. Install PM2, run the same app with -i 2, and hit the endpoint repeatedly while it returns process.pid to see requests spread across workers. Run pm2 reload under load with curl in a loop and count failures.
  5. Reboot the machine and verify which of the two setups came back on its own.
