Manual Deploy to a VPS: Node.js, Postgres, nginx, HTTPS

This is the capstone of the first half of the handbook: take an Express app with a Postgres database from your laptop to a real domain over HTTPS on an Ubuntu server, by hand. Everything later (CI/CD, Docker, Terraform) automates exactly these steps, so doing them manually once is how you understand what the automation is doing.

What we will build

 Browser ──HTTPS 443──▶ nginx ──▶ Express (127.0.0.1:3000, systemd service, user "deploy")
                          │                    │
                    certbot cert           Postgres (127.0.0.1:5432)
 DNS: app.example.com ──▶ VPS public IP        ufw: only 22, 80, 443 open

Assumptions: a fresh Ubuntu 24.04 LTS VPS (DigitalOcean, Hetzner, Linode, EC2...) with a public IP and root or sudo SSH access; a domain you control; an Express app in a Git repo with package.json, a start script, and a /health route. Replace 203.0.113.10, app.example.com, you and the repo URL with yours.

Step 0: The sample app

Your app should read its configuration from the environment (see the config lesson), listen on 127.0.0.1 behind the proxy, and expose a health check:

// server.js
const express = require('express');
const { Pool } = require('pg');

const app = express();
app.set('trust proxy', 1);                       // we sit behind nginx
const pool = new Pool({ connectionString: process.env.DATABASE_URL });

app.get('/health', async (req, res) => {
  try { await pool.query('SELECT 1'); res.json({ status: 'ok' }); }
  catch (e) { res.status(503).json({ status: 'db_unreachable' }); }
});
app.get('/', (req, res) => res.send('Hello from ' + (process.env.NODE_ENV || 'dev')));

const port = process.env.PORT || 3000;
const host = process.env.HOST || '127.0.0.1';
const server = app.listen(port, host, () => console.log(`listening on ${host}:${port}`));

process.on('SIGTERM', () => {                   // graceful shutdown (systemd sends SIGTERM)
  server.close(() => pool.end().then(() => process.exit(0)));
});
// package.json (relevant part)
{ "scripts": { "start": "node server.js" }, "engines": { "node": ">=22" } }

Step 1: Point DNS at the server

Do this first, because DNS takes time to be visible and certificates need it.

  1. At your DNS provider, create A app 203.0.113.10 with TTL 300 (and an AAAA record if the VPS has IPv6).
  2. Verify from your laptop: dig +short app.example.com should print the IP.

Step 2: First login and a non-root user

Running everything as root means any bug is a total compromise. Create two accounts: an admin (sudo) for you, and a service account that runs the app with minimal privileges.

ssh root@203.0.113.10

apt update && apt -y upgrade
timedatectl set-timezone UTC

# Admin user with sudo
adduser --gecos "" you
usermod -aG sudo you

# Copy your SSH public key to the new user
rsync --archive --chown=you:you ~/.ssh /home/you

In a new terminal, confirm ssh you@203.0.113.10 works and sudo whoami prints root. Only then harden SSH:

sudo nano /etc/ssh/sshd_config.d/99-hardening.conf
#   PermitRootLogin no
#   PasswordAuthentication no
#   KbdInteractiveAuthentication no

sudo sshd -t && sudo systemctl reload ssh      # (service is "ssh" on Ubuntu)

Keep your existing session open while testing a new login, so a typo cannot lock you out.

Now the service user: no password, no login shell, home directory for the app:

sudo adduser --system --group --home /srv/myapp --shell /usr/sbin/nologin myapp
sudo mkdir -p /srv/myapp
sudo chown myapp:myapp /srv/myapp

Step 3: Firewall

sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status verbose

Postgres and Node are deliberately not opened. Only nginx is public. Optionally install fail2ban to ban IPs that brute-force SSH, and enable unattended security upgrades: sudo apt install -y unattended-upgrades fail2ban.

Step 4: Install Node.js

Ubuntu's packaged Node is often old. Use NodeSource (system-wide, good for servers) or a version manager. Install the current LTS (check nodejs.org for the active LTS line; 22.x or newer in 2026):

curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs build-essential git
node -v && npm -v

Piping a script from the internet into a root shell is trust-on-first-use. Read it first (curl -fsSL URL | less) or use the signed apt repository instructions from NodeSource's docs.

Step 5: Install and configure Postgres

sudo apt install -y postgresql postgresql-contrib
sudo systemctl status postgresql           # active (exited/running)
sudo ss -tlnp | grep 5432                  # should show 127.0.0.1:5432 only

Create an application role with a strong generated password, and its database:

DBPASS=$(openssl rand -base64 24 | tr -d '/+=')
echo "Save this password in your password manager: $DBPASS"

sudo -u postgres psql <<SQL
CREATE ROLE myapp LOGIN PASSWORD '$DBPASS';
CREATE DATABASE myapp OWNER myapp;
SQL

# Test the TCP login the app will use
PGPASSWORD="$DBPASS" psql -h 127.0.0.1 -U myapp -d myapp -c 'SELECT version();'

Default Ubuntu Postgres listens on localhost only: good, leave it. Do not change listen_addresses unless you have a specific reason. Backups come later in the production section, but at minimum plan pg_dump to somewhere off this machine.

Step 6: Get the code onto the server

Use a read-only deploy key so the server can clone a private repo without your personal credentials.

# On the server, as the service user (use sudo -u, since it has no login shell)
sudo -u myapp ssh-keygen -t ed25519 -f /srv/myapp/.ssh_deploy_key -N "" -C "myapp-deploy"
sudo cat /srv/myapp/.ssh_deploy_key.pub     # paste into GitHub: Repo ▸ Settings ▸ Deploy keys (read-only)

# Clone
sudo -u myapp GIT_SSH_COMMAND='ssh -i /srv/myapp/.ssh_deploy_key -o IdentitiesOnly=yes' \
     git clone git@github.com:you/myapp.git /srv/myapp/app

cd /srv/myapp/app
sudo -u myapp npm ci --omit=dev             # reproducible install from package-lock.json
# If your app needs a build step (TypeScript, bundler): install dev deps, build, then prune
#   sudo -u myapp npm ci && sudo -u myapp npm run build && sudo -u myapp npm prune --omit=dev

npm ci installs exactly what the lockfile says and fails if it disagrees with package.json; npm install can drift. Use ci in deployments.

Step 7: Environment variables and secrets

Create an env file outside the repo, readable only by the service user. systemd will load it.

sudo mkdir -p /etc/myapp
sudo tee /etc/myapp/myapp.env >/dev/null <<EOF
NODE_ENV=production
HOST=127.0.0.1
PORT=3000
DATABASE_URL=postgres://myapp:${DBPASS}@127.0.0.1:5432/myapp
SESSION_SECRET=$(openssl rand -hex 32)
EOF

sudo chown root:myapp /etc/myapp/myapp.env
sudo chmod 640 /etc/myapp/myapp.env
ls -l /etc/myapp/myapp.env       # -rw-r----- root myapp

Special characters in the password would need URL-encoding in a connection string; our tr removed the troublesome ones.

If you have migrations, run them now (see the migrations lesson), for example sudo -u myapp env $(cat /etc/myapp/myapp.env | xargs) npm run migrate. A quick manual run to sanity check the app before involving systemd:

sudo -u myapp bash -c 'set -a; . /etc/myapp/myapp.env; set +a; cd /srv/myapp/app; timeout 5 node server.js'
# expect: listening on 127.0.0.1:3000

Step 8: systemd service

systemd starts the app at boot, restarts it on crash and collects logs.

sudo tee /etc/systemd/system/myapp.service >/dev/null <<'EOF'
[Unit]
Description=My Express App
After=network-online.target postgresql.service
Wants=network-online.target

[Service]
Type=simple
User=myapp
Group=myapp
WorkingDirectory=/srv/myapp/app
EnvironmentFile=/etc/myapp/myapp.env
ExecStart=/usr/bin/node server.js
Restart=on-failure
RestartSec=3
KillSignal=SIGTERM
TimeoutStopSec=30

# Sandboxing: cheap, effective hardening
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/srv/myapp
LimitNOFILE=65536

[Install]
WantedBy=multi-user.target
EOF

sudo systemctl daemon-reload
sudo systemctl enable --now myapp
systemctl status myapp --no-pager
journalctl -u myapp -f                      # live logs (Ctrl-C to stop)
curl -i http://127.0.0.1:3000/health        # {"status":"ok"}

If it fails: journalctl -u myapp -n 50 --no-pager shows the error. Common causes: wrong ExecStart path (which node), file permissions, bad DATABASE_URL.

Step 9: nginx reverse proxy

sudo apt install -y nginx
sudo tee /etc/nginx/sites-available/myapp >/dev/null <<'EOF'
server {
    listen 80;
    listen [::]:80;
    server_name app.example.com;

    client_max_body_size 10m;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade           $http_upgrade;
        proxy_set_header Connection        "upgrade";
        proxy_read_timeout 60s;
    }
}
EOF
sudo ln -s /etc/nginx/sites-available/myapp /etc/nginx/sites-enabled/myapp
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx

curl -i http://app.example.com/health        # from your laptop

If DNS has not propagated, test with curl -i -H 'Host: app.example.com' http://203.0.113.10/health.

Step 10: HTTPS with certbot

sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d app.example.com --redirect --agree-tos -m you@example.com --no-eff-email
sudo certbot renew --dry-run                 # confirm automatic renewal works
systemctl list-timers | grep certbot

Certbot edits the nginx file to add the listen 443 ssl server block and certificate paths, plus the HTTP to HTTPS redirect. View the result with sudo nginx -T | less and add HSTS if you like:

add_header Strict-Transport-Security "max-age=31536000" always;

Verify from outside: curl -I https://app.example.com/, and run an SSL test in your browser. Check http:// redirects to https://.

Step 11: Verify end to end

curl -sS https://app.example.com/health          # {"status":"ok"}
sudo systemctl restart myapp && sleep 2 && curl -s https://app.example.com/health
sudo reboot                                      # after boot, the site must come back by itself
# then:  curl -s https://app.example.com/health

The reboot test is the one that separates "it works" from "it will keep working". Everything should start on its own: Postgres, the app, nginx.

Step 12: How you deploy updates

This is the manual routine every later lesson improves on:

cd /srv/myapp/app
sudo -u myapp GIT_SSH_COMMAND='ssh -i /srv/myapp/.ssh_deploy_key -o IdentitiesOnly=yes' git pull --ff-only
sudo -u myapp npm ci --omit=dev
# sudo -u myapp ...run migrations...
sudo systemctl restart myapp
sleep 2 && curl -fsS https://app.example.com/health || echo "DEPLOY FAILED, ROLL BACK"

Rolling back: git log --oneline, git checkout <previous-sha> (or git reset --hard), npm ci, restart. Notice the weaknesses: restart drops in-flight requests; the code changes in place while running; a failed npm ci leaves a half-updated app; no history. The zero-downtime lesson fixes these with release directories and symlinks.

What is still missing (and where it is covered)

  • Backups of Postgres, tested restores (production readiness).
  • Logs shipped off the box and monitoring/alerts (observability).
  • Reproducibility: if this server dies, can you rebuild it in minutes? Today it took an hour of typing. Infrastructure as Code and containers fix that.
  • Zero-downtime releases and fast rollbacks (this section, later lessons).
  • CI: tests running before anything reaches the server.

Try it

  1. Rent the cheapest Ubuntu VPS you can find (a few dollars a month; destroy it afterwards) and a domain or a free subdomain, and perform every step above with your own small Express + Postgres app.
  2. Kill the process with sudo kill -9 $(systemctl show -p MainPID --value myapp) and watch systemd restart it (journalctl -u myapp).
  3. Stop Postgres (sudo systemctl stop postgresql) and look at what /health returns and what nginx and the app log. Start it again.
  4. Run nmap -Pn SERVER_IP from your laptop. Confirm only 22, 80 and 443 are visible.
  5. Write the whole procedure as a single Bash script. Where does it get hard to make safe to re-run? (This is the motivation for idempotent tools such as Ansible.)
