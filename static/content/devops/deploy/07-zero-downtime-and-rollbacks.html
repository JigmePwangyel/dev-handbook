Zero-Downtime Deploys and Rollbacks

Users should never notice you deployed, and when a release is bad, you should be able to undo it in seconds, not hours. Both goals come from the same few techniques: graceful shutdown, health checks, atomic switching of releases, and a rehearsed rollback plan.

Where downtime comes from

With git pull && npm ci && systemctl restart myapp on a live server:

  • The restart gap: the old process dies, the new one needs seconds to boot. Requests in that window get 502 from nginx.
  • Dropped in-flight requests: a request halfway through is cut off when the process is killed.
  • Half-updated code: while git pull and npm ci run, files on disk change under a running app; a lazy require() may load a new file against old ones.
  • Broken release, no way back: npm ci fails midway and node_modules is gone; the previous version no longer exists on disk.
  • Not ready, but receiving traffic: the new process is listening but still warming up its DB pool and caches.

The fixes, in the order we will cover them: (1) shut down gracefully, (2) report readiness honestly, (3) build the new release next to the old one and switch atomically, (4) verify and roll back automatically.

1. Graceful shutdown

When a process manager or orchestrator stops your app it sends SIGTERM, waits a grace period, then SIGKILL. A well-behaved app on SIGTERM: stops accepting new connections, finishes in-flight requests, closes DB pools and queues, then exits 0.

const server = app.listen(port, '127.0.0.1');
let shuttingDown = false;

function shutdown(signal) {
  if (shuttingDown) return;
  shuttingDown = true;
  console.log(`${signal} received: draining`);

  // Fail readiness immediately so the LB stops sending new requests
  // (health endpoint checks the `shuttingDown` flag)

  server.close(async (err) => {          // stops accepting; waits for open connections to end
    try {
      await pool.end();                    // DB pool
      await redis.quit();
    } finally {
      process.exit(err ? 1 : 0);
    }
  });
  server.closeIdleConnections?.();         // Node 18.2+: drop idle keep-alive sockets now

  // Hard deadline: never hang forever. Must be shorter than the manager's kill timeout.
  setTimeout(() => { console.error('forced exit'); process.exit(1); }, 25_000).unref();
}
process.on('SIGTERM', () => shutdown('SIGTERM'));
process.on('SIGINT',  () => shutdown('SIGINT'));

app.get('/health/ready', (req, res) => res.status(shuttingDown ? 503 : 200).end());

Checklist: the manager's stop timeout (TimeoutStopSec, Kubernetes terminationGracePeriodSeconds, Docker --stop-timeout) must exceed your drain deadline, which must exceed your longest legitimate request. Run node directly, not via npm start or a shell wrapper that swallows signals. Long-lived WebSockets need an explicit "reconnect to another server" message, and background workers should finish or re-queue the current job.

Kubernetes extra

Pods are removed from Service endpoints asynchronously, so for a few seconds after SIGTERM they may still receive new requests. A preStop hook of sleep 5 before the app starts draining prevents a burst of errors during rolling updates.

2. Health checks: liveness and readiness

CheckQuestionFailure actionWhat to test
LivenessIs the process stuck beyond repair?Restart itCheap: the event loop answers. Do not check dependencies, or a DB blip restarts every instance.
ReadinessCan it serve traffic right now?Remove from load balancer (do not restart)DB reachable, migrations applied, caches warm, not shutting down
StartupHas it finished booting?Wait; restart if too slowSlow-starting apps (JVM)

A deploy tool that waits for readiness before shifting traffic, and aborts if readiness is never reached, converts "deployed a broken build" from an outage into a failed deployment that users never saw.

3. Atomic releases with symlinks (the Capistrano pattern)

Instead of updating one directory in place, each deploy creates a new timestamped release directory, prepares it completely (install, build, migrate), and only then atomically repoints a current symlink to it. Switching a symlink is one atomic filesystem operation; there is never a half-updated state. Capistrano (Ruby) popularised this layout; Deployer (PHP), Mina, and many hand-rolled scripts use it.

 /srv/myapp/
 ├── releases/
 │   ├── 20260610-101500-a1b2c3d/     ← old release (still on disk: instant rollback)
 │   ├── 20260611-143000-e4f5a6b/     ← previous
 │   └── 20260612-091200-c7d8e9f/     ← new, fully prepared BEFORE the switch
 ├── shared/                           ← persists across releases
 │   ├── .env  (or /etc/myapp/myapp.env)
 │   ├── uploads/
 │   └── logs/
 └── current  ─────────▶ releases/20260612-091200-c7d8e9f      (symlink: the "switch")

Rules: code is immutable once released; anything that must persist (uploads, local files) lives in shared/ and is symlinked in (better: object storage); keep the last N releases (3 to 5) and delete older ones.

A deploy script

#!/usr/bin/env bash
# /srv/myapp/deploy.sh  -  usage: ./deploy.sh [git-ref]      (run as the service user)
set -euo pipefail

APP=/srv/myapp
REPO=git@github.com:you/myapp.git
REF=${1:-main}
KEEP=5
HEALTH_URL=http://127.0.0.1:3000/health
SERVICE=myapp

TS=$(date +%Y%m%d-%H%M%S)
RELEASE="$APP/releases/$TS"
PREV=$(readlink -f "$APP/current" || true)

log() { echo "[deploy $(date +%T)] $*"; }

rollback_to_prev() {
  if [ -n "$PREV" ] && [ -d "$PREV" ]; then
    log "ROLLING BACK to $PREV"
    ln -sfn "$PREV" "$APP/current.tmp" && mv -Tf "$APP/current.tmp" "$APP/current"
    sudo systemctl restart "$SERVICE"
  fi
}

mkdir -p "$APP/releases" "$APP/shared"

log "cloning $REF into $RELEASE"
git clone --depth 1 --branch "$REF" "$REPO" "$RELEASE"
SHA=$(git -C "$RELEASE" rev-parse --short HEAD)
rm -rf "$RELEASE/.git"
echo "$SHA" > "$RELEASE/REVISION"

log "installing dependencies"
( cd "$RELEASE" && npm ci --omit=dev )
# ( cd "$RELEASE" && npm ci && npm run build && npm prune --omit=dev )   # if you build

log "linking shared files"
ln -sfn "$APP/shared/uploads" "$RELEASE/uploads"

log "running migrations (must be backward compatible!)"
( cd "$RELEASE" && set -a && . /etc/myapp/myapp.env && set +a && npm run migrate )

log "switching current -> $RELEASE"
ln -sfn "$RELEASE" "$APP/current.tmp"
mv -Tf "$APP/current.tmp" "$APP/current"          # atomic rename: no moment without a valid current

log "restarting service"
sudo systemctl restart "$SERVICE"                 # or: pm2 reload / HUP / start new then drain

log "health check"
ok=0
for i in $(seq 1 30); do
  if curl -fsS --max-time 2 "$HEALTH_URL" >/dev/null; then ok=1; break; fi
  sleep 1
done
if [ "$ok" -ne 1 ]; then
  log "health check FAILED"
  rollback_to_prev
  exit 1
fi

log "cleaning old releases (keep $KEEP)"
ls -1dt "$APP"/releases/* | tail -n +$((KEEP+1)) | xargs -r rm -rf

log "deployed $SHA"

The unit file uses WorkingDirectory=/srv/myapp/current. The sudoers file allows only systemctl restart myapp without a password for the deploy user (%deploy ALL=(root) NOPASSWD: /bin/systemctl restart myapp). Two details: ln -sfn alone is not atomic (it unlinks then creates), so create the symlink under a temp name and mv -T (rename) over current, as above. And a plain systemctl restart still has a short gap; the next section removes it.

4. Rollback plans

A rollback is not a failure; it is a feature you must have designed before you need it at 2 a.m. under stress.

Rollback script

#!/usr/bin/env bash
# /srv/myapp/rollback.sh  - switch to the previous release
set -euo pipefail
APP=/srv/myapp
CUR=$(readlink -f "$APP/current")
PREV=$(ls -1dt "$APP"/releases/* | grep -vxF "$CUR" | head -n1)
[ -n "$PREV" ] || { echo "no previous release"; exit 1; }

echo "rolling back: $(basename "$CUR") -> $(basename "$PREV")"
ln -sfn "$PREV" "$APP/current.tmp"
mv -Tf "$APP/current.tmp" "$APP/current"
sudo systemctl restart myapp
for i in $(seq 1 30); do curl -fsS http://127.0.0.1:3000/health >/dev/null && { echo "healthy"; exit 0; }; sleep 1; done
echo "rollback unhealthy!"; exit 1

It takes seconds because the previous release is still on disk with its dependencies installed. Compare with "git revert, rebuild, reinstall, restart" taking 5 to 15 minutes while customers are failing.

What can and cannot be rolled back

ThingRollback
Application codeEasy: switch symlink / previous image tag / previous Kubernetes ReplicaSet (kubectl rollout undo deployment/myapp)
Configuration and flagsEasy if versioned; hard if edited by hand on servers with no record
Database schemaOnly if backward compatible (expand/contract). Rolling the code back must work against the new schema.
Data written by the new versionCannot be un-written. Plan data fixes; take a backup/snapshot before risky releases.
External side effects (emails sent, payments made)Impossible. Feature-flag risky behaviour so it can be switched off.

Because of the last rows, "roll forward" (ship a quick fix) is sometimes the right answer when the change is a data migration or the bad release has been live for hours with new data. Decide the policy beforehand: default to rollback when the problem started with the deploy; roll forward only when rollback is unsafe or the fix is trivial and certain.

A rollback runbook

  1. Detect: error rate, latency, failing smoke test, alerts, user reports. Compare timing with the deploy time.
  2. Decide fast: if in doubt, roll back first, investigate afterwards. Set a rule such as "error rate above X for 5 minutes after deploy triggers rollback".
  3. Execute: ./rollback.sh or the platform's equivalent. Announce in the incident channel.
  4. Verify: health, error rate, key user journey. Confirm the version running (/health returns the git SHA).
  5. Freeze further deploys until the cause is understood. Then write up a short post-mortem.

Automate steps 1 to 3 where you can: pipelines that run smoke tests after the switch and roll back on failure, Kubernetes progressDeadlineSeconds plus automated undo, Argo Rollouts or Flagger analysis, AWS CodeDeploy alarms.

Putting it together

 build immutable artifact ──▶ run migrations (backward compatible) ──▶ start new release beside old
        │                                                                   │
        │                                                           readiness check passes?
        │                                                             │ yes            │ no
        │                                                             ▼                ▼
        │                                                  shift traffic / flip symlink   abort, old keeps serving
        │                                                             │
        │                                                  old instances SIGTERM → drain → exit
        │                                                             │
        └──────────────────────  smoke tests + metrics watch ◀────────┘
                                         │ regression? ──▶ rollback (previous release still ready)

Pitfalls

  • Health endpoint returns 200 before the app is actually ready (no DB connection yet), so the deploy "passes" and users get errors.
  • Shutdown deadline longer than the manager's kill timeout: SIGKILL arrives mid-drain.
  • Keeping uploads or SQLite files inside the release directory; they vanish on the next deploy. Put them in shared/ or object storage.
  • Deleting old releases too eagerly (rollback target gone) or not at all (disk full).
  • Rollback never rehearsed: the script rots, or depends on a tool missing on the server. Practise in staging.
  • Releases that cannot run against the previous schema, making rollback impossible.
  • Build on the server taking minutes and consuming CPU; prefer building once in CI and shipping the artifact, so what you tested is what runs.

Try it

  1. Add the SIGTERM handler to a small Express app with a route that sleeps 10 seconds. Start a request with curl, then kill -TERM the process: the request should still complete. Remove the handler and see it fail.
  2. Measure downtime of the naive approach: while true; do curl -s -o /dev/null -w '%{http_code}\n' localhost:3000/health; sleep 0.1; done | sort | uniq -c in one terminal while running systemctl restart in another. Count the non-200s.
  3. Set up the releases/ + current layout and the deploy and rollback scripts (clone from a local bare repo if you have no remote). Deploy three versions, then roll back.
  4. Deliberately ship a version whose /health returns 500 and confirm the script rolls back by itself.
  5. Repeat the downtime measurement using the two-port blue-green nginx switch and compare.
  6. Write the rollback runbook for your own app: who decides, what command, how you verify, and what cannot be undone.
