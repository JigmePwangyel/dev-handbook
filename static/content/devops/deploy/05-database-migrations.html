Database Migrations in Deployments

Code is easy to roll back; data is not. The database schema is the one part of a deployment that carries state, and most "bad deploy" horror stories (locked tables, dropped columns, hours of downtime) are migration mistakes. Learn to change schemas safely while the app keeps running.

What a migration is, and why you need them

Your code expects a certain schema: tables, columns, indexes. When a feature needs a new column, the schema must change in lockstep with the code. If you apply changes by hand (psql on production, "I'll run this SQL after the deploy"), you get environments that disagree, forgotten steps, and no history.

A migration is a small, ordered, versioned script that moves the schema from version N to N+1. The tool records which migrations have run (in a table such as schema_migrations) so each runs exactly once, in the same order, in every environment: your laptop, CI, staging, production. Schema becomes code, reviewed in pull requests and reproducible from scratch.

Anatomy of a migration

-- migrations/20260314_001_add_users_phone.up.sql
ALTER TABLE users ADD COLUMN phone text;

-- migrations/20260314_001_add_users_phone.down.sql
ALTER TABLE users DROP COLUMN phone;
// Knex style
exports.up   = (knex) => knex.schema.alterTable('users', t => t.string('phone'));
exports.down = (knex) => knex.schema.alterTable('users', t => t.dropColumn('phone'));

# Typical commands
npx knex migrate:latest          # apply all pending
npx prisma migrate deploy        # apply committed migrations (use in production; not "migrate dev")
alembic upgrade head
flyway migrate

Rules: never edit a migration that has already been applied anywhere shared (add a new one instead); commit migrations with the code that needs them; keep each small and focused; test them against a copy of production-sized data.

Where migrations fit in the deploy

 Old code (v1) running ──────────────────────────────────────────────┐
                                                                      ▼
 1. Run migration  ──▶  schema S1 → S2     v1 code must STILL work on S2   ◀── the key constraint
 2. Deploy v2 code (rolling / blue-green)   v1 and v2 BOTH run during the rollout
 3. v2 verified; v1 gone

The critical insight: during a deploy, old and new code run simultaneously (rolling update, canary, or just the seconds between processes), and a rollback means old code runs against the new schema. So every migration must be compatible with both the previous and the next version of the application.

The golden rule

Schema changes must be backwards-compatible with the code that is currently running. If a change breaks the old code, you cannot deploy without downtime, and you cannot roll back. Split the change into several safe steps across several deployments.

Safe versus dangerous changes

ChangeSafe?Why / how to do it safely
Add a nullable columnSafeOld code ignores it. (PostgreSQL 11+ also makes ADD COLUMN ... DEFAULT const instant.)
Add a tableSafeNothing uses it yet.
Add an indexCarefulPlain CREATE INDEX blocks writes. Use CREATE INDEX CONCURRENTLY in Postgres (outside a transaction).
Add NOT NULLDangerousOld code inserting without it fails. Add nullable, backfill, then add constraint (NOT VALID then VALIDATE).
Add a foreign key / check constraintCarefulFull-table scan under lock. In Postgres: ADD CONSTRAINT ... NOT VALID then VALIDATE CONSTRAINT (lighter lock).
Rename a column or tableDangerousOld code references the old name. Use expand/contract (below).
Drop a column or tableDangerousOld code (or a rollback) will break. Only after no running code references it.
Change a column typeDangerousMay rewrite the whole table under an exclusive lock. Add a new column and migrate.
Backfill millions of rows in one UPDATEDangerousLong transaction, bloat, replication lag, lock contention. Batch it.

The expand / contract pattern

Also called "parallel change". To make a breaking change, do it in phases where each phase is individually safe and deployable:

  1. Expand: add the new structure alongside the old (migration only; app unchanged).
  2. Migrate code (dual write): deploy code that writes to both old and new, still reading from old.
  3. Backfill: copy existing data into the new structure, in batches.
  4. Switch reads: deploy code that reads from new (still writes both, so rollback is safe).
  5. Stop writing old: deploy code that only uses new.
  6. Contract: later, drop the old column in a separate migration, after you are sure you will not roll back past step 5.

Worked example: rename users.fullname to users.display_name

-- Release 1 (expand): add new column
ALTER TABLE users ADD COLUMN display_name text;

-- Optional: keep both in sync even for old code, using a trigger
CREATE OR REPLACE FUNCTION sync_display_name() RETURNS trigger AS $$
BEGIN
  IF NEW.display_name IS NULL THEN NEW.display_name := NEW.fullname; END IF;
  IF NEW.fullname     IS NULL THEN NEW.fullname     := NEW.display_name; END IF;
  RETURN NEW;
END $$ LANGUAGE plpgsql;
CREATE TRIGGER users_sync BEFORE INSERT OR UPDATE ON users
  FOR EACH ROW EXECUTE FUNCTION sync_display_name();

-- Backfill in batches (repeat until 0 rows updated; sleep between batches)
UPDATE users SET display_name = fullname
 WHERE id IN (SELECT id FROM users WHERE display_name IS NULL ORDER BY id LIMIT 5000);
// Release 2: code reads display_name, writes both
await db.query('UPDATE users SET display_name=$1, fullname=$1 WHERE id=$2', [name, id]);
const { display_name } = row;

// Release 3: code only uses display_name  (fullname untouched)

-- Release 4 (contract), days or weeks later:
DROP TRIGGER users_sync ON users;
ALTER TABLE users DROP COLUMN fullname;

It takes four deploys instead of one. That is the price of doing it without downtime or rollback risk. For small apps with a maintenance window and a few users, a single "rename" migration at 2 a.m. may be perfectly acceptable. Choose deliberately.

Locks: how migrations cause outages

In PostgreSQL, ALTER TABLE commonly takes an ACCESS EXCLUSIVE lock, blocking even reads. Worse: if a long-running query holds a conflicting lock, your ALTER waits in the queue, and every query that arrives after it queues behind your ALTER. The whole table freezes. Defend with timeouts so the migration fails quickly instead of stalling the app:

SET lock_timeout = '3s';          -- give up if we cannot get the lock quickly
SET statement_timeout = '60s';    -- cap runtime of the statement
ALTER TABLE orders ADD COLUMN note text;
-- If it fails with "canceling statement due to lock timeout", retry later; nothing broke.

-- Index without blocking writes (cannot run inside a transaction block)
CREATE INDEX CONCURRENTLY idx_orders_user_id ON orders (user_id);

-- Constraint with minimal locking
ALTER TABLE orders ADD CONSTRAINT orders_user_fk FOREIGN KEY (user_id) REFERENCES users(id) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT orders_user_fk;

-- NOT NULL safely (Postgres 12+ uses a validated CHECK to avoid a full scan under lock)
ALTER TABLE orders ADD CONSTRAINT orders_note_nn CHECK (note IS NOT NULL) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT orders_note_nn;
ALTER TABLE orders ALTER COLUMN note SET NOT NULL;      -- fast, uses the validated check
ALTER TABLE orders DROP CONSTRAINT orders_note_nn;

MySQL has its own online DDL rules (ALGORITHM=INPLACE, LOCK=NONE, tools like gh-ost and pt-online-schema-change for huge tables). Linters such as squawk (Postgres), strong_migrations (Rails) and Atlas lint can flag unsafe migrations in CI.

# Example pipeline order
1. CI: run tests including a migration test on a fresh DB AND on a copy of the previous schema
2. Backup / snapshot (or confirm point-in-time recovery is on)
3. Run migrations (with lock_timeout) using a dedicated migration DB role
4. Deploy new code (rolling)
5. Smoke test; keep the old version ready for rollback

Use a separate database role for migrations (can ALTER) and for the app (only SELECT/INSERT/UPDATE/DELETE) when feasible, limiting what an SQL injection can do.

Rollbacks and down migrations

"Down" migrations look reassuring but are often a trap: a down that drops a column destroys the data written since. In practice, many mature teams do not rely on down migrations in production: they roll back the code (which still works against the expanded schema) and roll forward with a fix migration. Hence: make every release compatible with the previous schema, keep destructive contract steps separate, and treat dropped data as unrecoverable except from a backup. Test your restore.

Other practices

  • Seed/reference data as migrations (idempotent), separate from test fixtures.
  • Test migrations on production-like data volume: a migration instant on 100 rows can lock for minutes on 100 million.
  • Idempotency and transactions: Postgres supports transactional DDL (a failed migration rolls back cleanly), MySQL does not (DDL auto-commits, leaving half-applied migrations). Use IF NOT EXISTS where helpful.
  • Branching: two branches adding migrations produce ordering conflicts; use timestamp prefixes and resolve in review.
  • Schema drift: nobody should hand-edit production. Tools like Atlas and Prisma migrate diff can detect drift.
  • Document the plan in the pull request for anything risky: expected duration, lock levels, rollback.

Pitfalls

  • Deploying code that needs the new column before the migration has run, or running a destructive migration before all old instances are gone.
  • ORM auto-sync (synchronize: true in TypeORM, db push, Django --run-syncdb) in production, which can drop data silently.
  • Long migrations inside the request path or app startup, blowing health-check timeouts and causing crash loops.
  • Backfilling in one giant transaction.
  • No backup before a risky migration.

Try it

  1. Start Postgres locally (docker run -e POSTGRES_PASSWORD=pw -p 5432:5432 postgres:17). Create users(id, fullname) and insert 1 million rows with generate_series.
  2. In one psql session, open a transaction that reads from users and does not commit. In another run ALTER TABLE users ADD COLUMN x int; and watch it hang; in a third session try a plain SELECT and see it queue behind the ALTER. Then retry with SET lock_timeout='2s'.
  3. Time CREATE INDEX versus CREATE INDEX CONCURRENTLY while a loop inserts rows from another session.
  4. Walk through the rename example using a migration tool of your choice: write the four releases as separate migrations and a tiny app version for each. Confirm that app v1 still works after release 1 and release 2's schema.
  5. Add a migration linter (squawk or Atlas lint) to a CI job and see what it flags on a DROP COLUMN.
