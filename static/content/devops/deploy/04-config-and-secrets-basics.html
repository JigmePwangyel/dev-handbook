Config and Secrets Basics

The same code must run on your laptop, in CI, in staging and in production, talking to different databases with different credentials. The way to achieve this is to keep configuration out of the code. Secrets deserve extra care, because a leaked key is an incident, not a bug.

Why separate config from code

Hard-coded values cause two kinds of pain:

  • Inflexibility: changing a URL or feature switch requires a rebuild and redeploy; the same build cannot be promoted from staging to production because the database address is baked in.
  • Leaks: a password committed to Git lives in history forever, in every clone and fork. Bots scan public GitHub in real time for cloud keys and use them within minutes (crypto mining on your account; five-figure bills are common stories).

The principle (from the Twelve-Factor App, factor III): strict separation of config from code; store config in the environment. Build once, deploy the same artifact everywhere, and inject differences at runtime.

What is "config"?

Anything that varies between deploys of the same code:

KindExamplesSensitive?
Environment settingsNODE_ENV, LOG_LEVEL, PORT, feature flags, timeoutsNo
EndpointsAPI_BASE_URL, REDIS_HOST, S3 bucket namesUsually no
SecretsDB passwords, API keys, JWT signing keys, OAuth client secrets, TLS private keys, webhook secretsYes

Not config: internal application constants that do not change per environment (route definitions, business rules). Those belong in code. A good test: could you open-source the repo right now without leaking anything? If not, something sensitive is in it.

Environment variables

Environment variables are key/value strings the OS passes to every process. They are language-agnostic, supported everywhere (shells, systemd, Docker, Kubernetes, every cloud), and cannot be accidentally committed.

# Shell
export DATABASE_URL="postgres://app:s3cret@db.internal:5432/app"
node server.js

# One-shot for a single command
LOG_LEVEL=debug node server.js

// Node
const dbUrl = process.env.DATABASE_URL;
if (!dbUrl) throw new Error('DATABASE_URL is required');   // fail fast!

# Python
import os; db_url = os.environ["DATABASE_URL"]      # KeyError if missing: good

Best practices: read config once at startup into a typed object; validate and fail fast if a required variable is missing (use zod, envalid, pydantic-settings, Spring @ConfigurationProperties); remember all values are strings ("false" is truthy in JavaScript, parse explicitly); provide safe defaults only for non-sensitive values.

// config.js
const { z } = require('zod');
const schema = z.object({
  NODE_ENV: z.enum(['development', 'test', 'production']).default('development'),
  PORT: z.coerce.number().int().default(3000),
  DATABASE_URL: z.string().url(),
  SESSION_SECRET: z.string().min(32),
  ENABLE_BETA: z.enum(['true', 'false']).default('false').transform(v => v === 'true'),
});
module.exports = schema.parse(process.env);   // throws a clear error at boot if invalid

.env files

Typing exports every time is tedious, so a .env file holds KEY=value lines that a library (dotenv, node --env-file=.env in modern Node, python-dotenv, Docker Compose env_file) loads into the environment for local development.

# .env  (local only: NEVER committed)
NODE_ENV=development
DATABASE_URL=postgres://postgres:postgres@localhost:5432/app_dev
SESSION_SECRET=dev-only-not-a-real-secret
STRIPE_API_KEY=sk_test_xxx

# .env.example  (committed: documents which variables exist, with fake values)
NODE_ENV=development
DATABASE_URL=postgres://user:password@localhost:5432/dbname
SESSION_SECRET=change-me-32-chars-minimum
STRIPE_API_KEY=sk_test_replace_me

# .gitignore
.env
.env.*
!.env.example
node --env-file=.env server.js        # Node 20.6+, no dotenv package needed

Conventions: commit .env.example so newcomers know what to set; keep the real .env out of version control; do not rely on .env files in production. There, the platform injects variables (systemd EnvironmentFile, Docker/Kubernetes, PaaS dashboards, a secrets manager).

Per-environment configuration

Typical environments: development (laptop), test/CI, staging (production-like), production. Two approaches:

  1. Same code, different variables (preferred): every environment sets DATABASE_URL, API_BASE_URL. No if (env === 'production') branches scattered through the code.
  2. Config files per environment (config/production.yml, Spring profiles, Rails credentials): fine for non-secret structured settings. Resist the explosion of environment-named files; the "staging" and "production" variants drift apart. Keep the set of differing keys small.

Avoid the antipattern of a single NODE_ENV switching dozens of behaviours. Use explicit variables (LOG_LEVEL, CACHE_TTL) so staging can be genuinely similar to production. The more production differs from staging, the less staging proves.

Secrets: handling them properly

Never commit secrets

Not in code, .env, Dockerfiles, CI YAML, Terraform state or Slack. Deleting the file in a later commit does not remove it from history. Treat any committed secret as compromised: rotate it first (generate a new one, revoke the old), then clean up history (git filter-repo, BFG) as a secondary step.

Where secrets can live (weakest to strongest)

MethodNotes
In the repoNever.
Env file on the server (/etc/myapp/myapp.env, mode 640, owned root:app)Fine for a single VPS. Manual rotation. Back up securely.
CI/CD secret store (GitHub Actions secrets, GitLab CI variables)Masked in logs; injected at deploy time
PaaS config vars (Heroku, Render, Fly secrets)Managed in the dashboard or CLI
Encrypted-in-repo (SOPS with age/KMS, git-crypt, sealed-secrets)Secrets versioned but unreadable without keys; great for GitOps
Secret manager (AWS Secrets Manager / SSM Parameter Store, GCP Secret Manager, HashiCorp Vault, Doppler, 1Password)Central, audited, access-controlled, rotation support, dynamic short-lived credentials
Workload identity (IAM roles, no static secret at all)Best: the instance/pod itself is the credential. Prefer it over long-lived keys wherever possible.

Leak surfaces to watch

  • Logs: printing the whole config or request headers. Redact Authorization, cookies, passwords.
  • Process listings and crash dumps: command-line arguments are visible to all users in ps; environment is readable via /proc/PID/environ by the same user and root. Do not pass secrets as CLI arguments.
  • Docker images: ENV and COPY .env bake secrets into layers anyone with the image can read. Inject at run time; use BuildKit --mount=type=secret for build-time secrets.
  • Front-end bundles: anything in client-side code is public. VITE_* / NEXT_PUBLIC_* variables are embedded in the JavaScript sent to browsers.
  • Error trackers and analytics capturing request bodies.
  • Shell history: export SECRET=... lands in ~/.bash_history. Use read -s or prefix the command with a space (with HISTCONTROL=ignorespace).
  • Chat, tickets and screenshots.

Practices

  1. Least privilege: a DB user limited to the app's database and needed operations, not the superuser; scoped API tokens, read-only deploy keys.
  2. Separate secrets per environment: a leaked staging key must not open production. Developers rarely need production secrets.
  3. Rotate: on a schedule and immediately on suspicion or when someone leaves. Design for rotation (accept two valid keys during a changeover; load secrets without a rebuild).
  4. Generate strong secrets: openssl rand -base64 32 or openssl rand -hex 32. Never reuse a password across environments.
  5. Scan: pre-commit hooks and CI with gitleaks, trufflehog, GitHub secret scanning and push protection.
  6. Audit access: managed secret stores log who read what.
  7. Back up and document where each secret lives, so a rebuilt server is not blocked by a missing value.
# Install a pre-commit secret scan (gitleaks)
brew install gitleaks            # or download from GitHub releases
gitleaks detect --source . -v    # scan the repo history
gitleaks protect --staged -v     # scan staged changes (use in a pre-commit hook)

# Example: fetch a secret at deploy time from AWS SSM instead of storing it on disk long-term
aws ssm get-parameter --name /myapp/prod/DATABASE_URL --with-decryption \
    --query Parameter.Value --output text

Injecting config on a server (systemd)

# /etc/myapp/myapp.env  → chmod 640, chown root:myapp
DATABASE_URL=postgres://myapp:REDACTED@127.0.0.1:5432/myapp

# unit file
[Service]
EnvironmentFile=/etc/myapp/myapp.env
# For systemd 250+, secrets can also be passed as files with LoadCredential=
# (not exposed in the process environment).

Remember: environment variables need a restart to change. For values that must change live, read from a file or secret store with caching and a refresh.

Trade-offs

ChoiceProCon
Env varsUniversal, simpleFlat strings; visible to child processes; no audit; need restart
Config filesStructured, versioned (non-secret)Drift per environment; risk of secrets creeping in
Secret managerAudit, rotation, access controlAnother dependency, cost, startup latency, bootstrapping (how does the app authenticate to it? IAM role)
Encrypted in Git (SOPS)Reviewable changes, GitOps-friendlyKey management; easy to mis-encrypt

Pitfalls

  • Committing .env "just once". Add it to .gitignore before the first commit.
  • Different variable names across environments, discovered at deploy time. Validate config at startup everywhere, including CI.
  • Production fallback defaults (DATABASE_URL || 'localhost') hiding misconfiguration. Fail instead.
  • Using production data and secrets in development.
  • Printing process.env in a debug route or startup log.

Try it

  1. Take a project with hard-coded values. Move each to an environment variable, create .env.example, and add the validation snippet so the app refuses to start when a variable is missing.
  2. Run gitleaks detect on one of your own repos. Anything found? Decide how you would rotate it.
  3. Create /tmp/test.env with a fake secret, then run a program with it via env $(cat /tmp/test.env | xargs) node -e "console.log(process.env.FOO)" and compare with node --env-file.
  4. On a Linux box, start a process with a secret in its environment and read it back via sudo cat /proc/PID/environ | tr '\0' '\n' to see who can read it. Then check file mode and ownership on a systemd EnvironmentFile.
  5. Write the secret-rotation procedure for your database password step by step. How would you do it without downtime?
