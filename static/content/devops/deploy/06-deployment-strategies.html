Deployment Strategies

"Stop the old version, start the new one" works until the first time it fails with real users watching. Deployment strategies are different answers to one question: how do you move users from version A to version B while limiting the damage if B is broken?

What you are trading

Every strategy balances four things:

  • Downtime: is there a gap where nobody can be served?
  • Blast radius: if the new version is bad, how many users see it before you notice?
  • Rollback speed: how fast can you get back to the good version?
  • Cost and complexity: extra capacity, extra tooling, harder database changes.

Underneath all of them, remember the rule from the migrations lesson: two versions of the app will coexist, so the database and any shared state must support both.

1. Recreate (big bang)

 Time ──▶
 v1  ████████████████│
                     │  (downtime)
 v2                  │░░░░░████████████████
                  stop v1   start v2

Stop everything, deploy, start again. It is what git pull && systemctl restart does.

  • Pros: simplest; no version coexistence (migrations can be breaking); cheapest.
  • Cons: downtime on every release; the whole user base meets any bug; slow recovery.
  • Use for: internal tools, dev/staging, apps with maintenance windows, major migrations that cannot coexist.

2. Rolling update

 Servers:   [v1] [v1] [v1] [v1]
 step 1:    [v2] [v1] [v1] [v1]     take one out of the LB, update, health check, put back
 step 2:    [v2] [v2] [v1] [v1]
 step 3:    [v2] [v2] [v2] [v1]
 step 4:    [v2] [v2] [v2] [v2]

Replace instances gradually, a few at a time (batch size, "max surge", "max unavailable"). Traffic flows throughout. This is the default in Kubernetes Deployments, ECS and Auto Scaling group instance refresh.

  • Pros: no downtime; no duplicate full environment; native in most platforms.
  • Cons: v1 and v2 serve simultaneously (need compatibility); rollback is another rolling update (minutes); a bug is already on part of the fleet when detected; capacity dips if you remove instances before adding new ones.
  • Use for: the default for stateless services with backward-compatible changes.
# Kubernetes rolling update parameters
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 25%         # extra pods allowed above desired during the rollout
    maxUnavailable: 0     # never drop below desired capacity
# Needs a readinessProbe, otherwise "ready" is declared before the app can serve

3. Blue-green

              ┌─────────────┐
 Users ─────▶ │ Router / LB │───────────────┐ (switch)
              └─────────────┘               │
                     │ today                ▼ after verification
                     ▼                 ┌────────────┐
              ┌────────────┐           │ GREEN (v2) │  full copy, already running and tested
              │ BLUE  (v1) │           └────────────┘
              └────────────┘            keep BLUE idle for instant rollback

Run two complete, identical environments. Blue serves production. Deploy v2 to green, test it with real infrastructure (smoke tests, internal traffic), then flip the router/DNS/LB target group so all traffic goes to green at once. To roll back, flip back.

  • Pros: near-zero downtime; instant, simple rollback; the new version is tested in a production-like environment before users see it.
  • Cons: double the infrastructure during the release; the switch is all-or-nothing (100 percent of users hit v2 immediately); database must serve both (shared DB means expand/contract; separate DBs means data sync pain); in-flight requests and sessions at switch time; warm-up (cold caches).
  • Use for: when fast rollback matters and extra capacity is affordable (cheap with cloud or containers).

On a single VPS you can emulate it with two app instances on different ports and an nginx proxy_pass pointing at one; switching means editing the upstream and nginx -s reload. On AWS, swap target groups on an ALB listener, or use CodeDeploy blue/green; on Kubernetes, switch a Service selector.

4. Canary

 100% ─ v1 ████████████████████████████████████████

  stage 1:  v1 95% ███████████████████░  v2 5%  █       watch error rate, latency, business KPIs
  stage 2:  v1 75% ███████████████░░░░░  v2 25% █████
  stage 3:  v1 50% ██████████░░░░░░░░░░  v2 50% ██████████
  done:                                  v2 100%
  any stage fails ──▶ route 100% back to v1 (smallest possible blast radius)

Named after the canary in the coal mine. Send a small share of real traffic (1 to 5 percent, or only employees or one region) to v2, compare its metrics against v1, and increase gradually only while healthy.

  • Pros: minimal blast radius; real production validation; data-driven promotion; automatic rollback possible (Argo Rollouts, Flagger, Spinnaker/Kayenta, AWS CodeDeploy, Istio/Envoy weighted routing).
  • Cons: needs good observability (without metrics a canary is blind); needs fine-grained traffic splitting; more complex; slow; both versions must be compatible; low traffic means too few samples to detect problems; sticky users (decide whether a user stays on one version).
  • Use for: high-traffic services where a bad release is costly.
# nginx: crude canary with weighted upstream (about 10% to canary)
upstream app {
    server 10.0.1.11:3000 weight=9;
    server 10.0.1.12:3000 weight=1;      # canary running v2
}
# Better: pin specific users via a cookie or header
map $http_x_canary $backend { default stable; "1" canary; }

5. Shadow (mirroring / dark launch)

 Users ──▶ LB ──▶ v1 (production)  ──▶ response to the user
            │
            └────▶ copy of each request ──▶ v2 (shadow)  ──▶ response DISCARDED, compared/logged

Duplicate live traffic to the new version, but ignore its responses. Users are never affected; you compare behaviour, performance and diffs against production load.

  • Pros: zero user impact; tests with real traffic shape and volume; great for rewrites and migrations (new database, new language, new algorithm).
  • Cons: the shadow must not cause side effects (duplicate emails, payments, writes to the shared database): requires stubbing or a separate datastore; doubles load; nondeterministic comparison; engineering effort.
  • Tools: nginx mirror directive, Envoy/Istio traffic mirroring, GitHub Scientist-style libraries.

6. A/B testing

Not a safety mechanism, but an experiment: route different user segments (by cookie, user id hash, geography, plan) to different versions of a feature to measure which performs better on a business metric (conversion, retention). It needs a stable assignment per user and statistical analysis. Canary asks "is v2 healthy?" A/B asks "is v2 better for the business?" They can use the same routing machinery but have different goals and durations (A/B runs for days or weeks).

7. Feature flags (decouple deploy from release)

// The code ships dark; the flag decides who sees it
if (flags.isEnabled('new-checkout', { userId: user.id, plan: user.plan })) {
  return newCheckout(req);
}
return oldCheckout(req);

A feature flag is a runtime conditional controlled outside the code (config service, LaunchDarkly, Unleash, Flagsmith, OpenFeature standard, or a database table). You deploy the code with the feature off, then turn it on for staff, then 1 percent, then everyone, and can turn it off in seconds without a deploy or a rollback.

  • Pros: separates deployment (technical act) from release (business decision); instant kill switch; enables trunk-based development, canary by user, A/B tests, gradual rollouts, per-customer features.
  • Cons: code complexity (two paths); tests multiply; flags rot into permanent clutter ("flag debt"); a flag service becomes a dependency (needs safe defaults and caching); flags interacting in unforeseen ways; schema must support both paths.
  • Discipline: give each flag an owner and an expiry date; delete it once fully rolled out; default to the safe state if the flag service is unreachable.

Combining strategies

Real systems combine them. A typical modern setup: rolling or blue-green for the deploy mechanism, canary analysis to gate promotion, feature flags to release functionality independently, and expand/contract migrations to keep it all compatible. Shadowing is reserved for big rewrites.

Choosing

  1. Internal tool, few users, downtime fine: recreate.
  2. Normal web service, backward-compatible changes: rolling, with health checks.
  3. Need one-click rollback, can afford duplicate capacity: blue-green.
  4. High traffic, strong monitoring, risky changes: canary, automated.
  5. Rewriting a critical component: shadow first, then canary.
  6. Product experiments or gradual feature rollout: feature flags (and A/B).
No strategy rescues a missing health check or metric

All of the above depend on knowing whether the new version is healthy. Without readiness probes, error-rate dashboards and alerting, a rolling update will happily roll out a broken version to 100 percent, just slowly. Build observability first or alongside.

Pitfalls

  • Forgetting that v1 and v2 share the database, caches, queues and message formats. A new message schema consumed by old workers breaks them.
  • Blue-green with sessions stored in app memory: users are logged out at the switch.
  • Canary on too little traffic: 1 percent of 100 requests per hour tells you nothing.
  • Choosing the strategy before the problem. A single-server hobby app does not need canaries.
  • Permanently-on "temporary" flags.
  • Rolling back code but not config or flags that were changed at the same time.

Try it

  1. Build two tiny apps that return "v1" and "v2" on ports 3001 and 3002. With nginx, simulate a blue-green flip: proxy_pass to 3001, curl in a loop, change to 3002, nginx -s reload, and observe no failed requests.
  2. Do a canary: upstream with weights 9 and 1. Run 100 requests and count versions. Make v2 fail 50 percent of the time and compute the overall error rate; at what weight would your alert fire?
  3. Try nginx mirroring: mirror /shadow; location = /shadow { internal; proxy_pass http://127.0.0.1:3002$request_uri; } and watch v2's logs receive copies.
  4. Implement a feature flag as an environment variable or JSON file read per request, flip it live and observe the behaviour without a restart.
  5. For a service you know, fill in the comparison table: which strategy fits, what would break if v1 and v2 ran concurrently?
