The Deploy Checklist

Experienced engineers are not people who never break production; they are people who run the same boring checks every time. A checklist moves deployment from heroics to routine. Use this one as a starting point and edit it after every incident.

Why checklists work

Pilots and surgeons use checklists not because they are novices, but because under time pressure and routine, humans skip steps. Most failed deployments come from a short list of repeated mistakes: a missing environment variable, a migration that was not run, a port not opened, a certificate that expired, no one watching after release. Writing them down converts tribal knowledge into something a new teammate (or you at 5 p.m. on Friday) can follow. Better still: automate every checkbox you can (CI gates, pipeline steps) and keep humans for judgement.

Before you deploy

Code and build

  • [ ] Changes are merged via a reviewed pull request; the main branch is green in CI (lint, unit tests, integration tests).
  • [ ] You know exactly what is being deployed: version/tag/commit SHA, and you have read the diff or changelog since the last release.
  • [ ] The artifact (image, tarball) was built once in CI and is the same one that passed on staging. No "build on the server".
  • [ ] Dependencies are locked (package-lock.json, poetry.lock); security scan passed or accepted.

Configuration and secrets

  • [ ] Any new environment variables or secrets are already set in the target environment (diff your .env.example against production).
  • [ ] Config is validated at startup (app refuses to boot on missing values), so a mistake fails the deploy rather than a user.
  • [ ] Feature flags for risky features are defined and set to the safe state.

Database

  • [ ] Migrations are backward-compatible with the version currently running (expand before contract), and tested on production-like data volume.
  • [ ] A recent backup or snapshot exists, and you know how to restore it. Point-in-time recovery is on if available.
  • [ ] Long-running or locking migrations have lock_timeout, batching, and a scheduled quiet period.

Infrastructure and timing

  • [ ] Disk space, memory and CPU headroom are fine (df -h, free -m): a full disk kills deploys.
  • [ ] Dependencies are healthy (DB, cache, third-party APIs, certificate expiry more than 14 days away).
  • [ ] It is a sensible time: avoid Friday afternoon, peak traffic, and when the one person who knows the system is unreachable. Ideal: small, frequent deploys on weekdays with people around.
  • [ ] Stakeholders/support know if user-visible changes or brief degradation are expected. Incident channel open.

Rollback readiness

  • [ ] The previous version is still available (previous release dir, previous image tag) and you know the exact rollback command.
  • [ ] You have decided in advance the signal that triggers a rollback (for example "error rate above 2 percent for 5 minutes").

During the deploy

  • [ ] Announce the start (team chat) with version and expected duration. Change freeze for others touching the same system.
  • [ ] Run migrations first (if any) and confirm success before shipping code.
  • [ ] Roll out using the agreed strategy (rolling/blue-green/canary). Watch logs live: journalctl -u myapp -f or kubectl logs -f.
  • [ ] Do not make unrelated changes in the same window. One change at a time makes failures attributable.

After the deploy: smoke tests

A smoke test is a tiny, fast, automatic check that the most critical paths work, named after turning on new electronics to see if smoke comes out. It does not prove correctness; it proves "not obviously broken".

#!/usr/bin/env bash
# smoke.sh  -  usage: ./smoke.sh https://app.example.com EXPECTED_SHA
set -euo pipefail
BASE=${1:?base url}; WANT=${2:-}
fail() { echo "SMOKE FAIL: $*" >&2; exit 1; }

# 1. Process healthy, dependencies reachable
curl -fsS --max-time 5 "$BASE/health" >/dev/null || fail "/health"

# 2. Correct version is live
if [ -n "$WANT" ]; then
  GOT=$(curl -fsS "$BASE/health" | jq -r .version)
  [ "$GOT" = "$WANT" ] || fail "version $GOT != $WANT"
fi

# 3. Home page renders
code=$(curl -s -o /dev/null -w '%{http_code}' --max-time 10 "$BASE/")
[ "$code" = 200 ] || fail "home returned $code"

# 4. HTTPS and redirect behave
curl -sI "http://${BASE#https://}/" | grep -qi '^location: https://' || fail "no http->https redirect"

# 5. A critical read path works with test credentials
curl -fsS -H "Authorization: Bearer $SMOKE_TOKEN" "$BASE/api/me" >/dev/null || fail "/api/me"

# 6. Static assets and TLS expiry
curl -fsSI "$BASE/assets/app.js" >/dev/null 2>&1 || echo "warn: assets not found at the guessed path"
exp=$(echo | openssl s_client -connect "${BASE#https://}:443" -servername "${BASE#https://}" 2>/dev/null \
      | openssl x509 -noout -enddate | cut -d= -f2)
echo "TLS expires: $exp"

echo "SMOKE OK"

Run it from outside the server (CI runner or your laptop) so it exercises DNS, TLS, the proxy and the firewall, not just localhost. Run it in the pipeline automatically, and fail the deploy (and trigger rollback) if it fails. Test credentials should belong to a dedicated test account with minimal rights.

Post-deploy observation (the "bake" period)

  • [ ] Error rate (5xx, exceptions) is at or below baseline. Compare with the same time yesterday.
  • [ ] Latency (p50, p95, p99) has not regressed.
  • [ ] Saturation: CPU, memory (leaks show up as a slow climb), DB connections, queue depth, disk.
  • [ ] Business metrics: signups, checkouts, jobs processed. A deploy can be technically healthy and functionally broken.
  • [ ] Logs: no new error patterns, no flood of warnings. Check the error tracker for new issue types.
  • [ ] Background workers and cron jobs are running the new version and consuming from queues.
  • [ ] Watch for at least 15 to 30 minutes (longer for risky changes, covering at least one peak or cron cycle).
  • [ ] Announce completion. Tag the release in Git; update the changelog. Remove temporary flags you are done with.

When it goes wrong

  1. Stay calm and communicate: post in the incident channel what you see and what you are doing.
  2. Roll back first, debug later when the deploy is the likely cause. Restoring service beats diagnosing in production.
  3. Preserve evidence: logs, metrics screenshots, the failing request, before restarting things.
  4. Verify recovery with the same smoke tests.
  5. Blameless post-mortem: what happened, why the system allowed it, what automatic check would have caught it. Add that check to this list (or better, to the pipeline).

Maturing the checklist into automation

Manual checklist itemBecomes
Tests passRequired CI status check on the main branch
Env vars presentConfig schema validation; pipeline step diffing required keys
Migration safeMigration linter in CI
Deploy and wait for healthOrchestrator readiness gates; deploy tool health check with auto-rollback
Smoke testsPost-deploy pipeline job; synthetic monitoring running continuously
Watch dashboardsSLO-based alerts; automated canary analysis
AnnouncePipeline posts the deploy and version to chat; deploy markers on graphs

The goal is not a longer checklist but a shorter one, because the system itself refuses to do the unsafe things.

Pitfalls

  • Checklist fatigue: ticking boxes without looking. Keep it short, specific, and tied to real past incidents.
  • Treating smoke tests as full regression tests: they should run in seconds and cover only critical paths.
  • Smoke tests that call localhost and miss DNS, TLS and proxy problems.
  • Deploying and immediately leaving. The first 30 minutes are when most issues surface.
  • A checklist that exists only in one person's head or an out-of-date wiki page. Version it in the repo next to the deploy scripts.

Try it

  1. Copy this checklist into your repo as DEPLOY.md. Delete the items that do not apply and add two that come from your own past incidents.
  2. Adapt smoke.sh to your app, run it against staging, then deliberately break something (stop the service, break the nginx config in a staging copy) and confirm the script fails with a clear message.
  3. Hook the smoke test into your deploy script so a failure triggers rollback (see the previous lesson).
  4. Take the failure-mode table and, for three rows, write the exact command you would run to detect that failure on your server.
  5. Run a "game day": have a teammate (or a future-you) break one thing in staging after a deploy, and practise detecting and rolling back within five minutes. Time it.
