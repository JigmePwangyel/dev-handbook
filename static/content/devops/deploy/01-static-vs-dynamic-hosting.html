Static vs Dynamic Hosting: What Goes Where

Before choosing tools, decide what kind of thing you are deploying. A pile of HTML and JavaScript files and a long-running server process have very different needs, costs and failure modes. Picking the simplest hosting that fits is the cheapest optimisation in DevOps.

Why this decision comes first

Many teams run a full server (OS patches, process manager, nginx, monitoring) to serve files that could be uploaded to a CDN for pennies with no servers to maintain. Others try to run a stateful, long-lived backend on a platform built only for static files and hit a wall. Match the hosting model to the workload.

Static content

Static means the bytes served are the same for every user and exist before the request arrives: HTML, CSS, JS, images, PDFs. A server (if any) only reads files and returns them.

Examples: a marketing site, documentation (like this one), a blog built with a static site generator (Hugo, Astro, Jekyll, Eleventy), and a single-page app (React, Vue, Angular) compiled to a dist/ folder. An SPA is static hosting plus a separate API: the browser downloads files, then JavaScript calls the backend.

 npm run build  ──▶  dist/  (index.html, assets/app.3f9c.js, ...)
                       │ upload
                       ▼
                Object storage + CDN  (S3+CloudFront, Cloudflare Pages, Netlify, Vercel, GitHub Pages)
                       ▲
 Users ───────────────┘   served from the nearest edge. No server of yours is involved.

Why it is great: no servers to patch, nothing to crash, virtually infinite scale, global speed, very low cost (often free), and a tiny attack surface (no code executing on the server means nothing to exploit there).

Dynamic content

Dynamic means code runs per request: reads a database, checks a session, calls other services, builds a response. REST/GraphQL APIs, server-rendered pages (Rails, Django, Laravel, Express with templates), WebSockets, background workers, cron jobs.

Why it needs more: it needs a runtime, a process that stays up, secrets, a database, scaling for CPU/memory, deployments that do not drop requests, logging and monitoring. It is where most DevOps work lives.

A useful trick: make as much static as possible. A product page that changes hourly can be a cached or pre-rendered file, not a database query per visitor.

Neither is "better". A common path: start on a PaaS, move to containers when you outgrow it. Learning on a VPS first makes every later abstraction understandable, which is why the next lesson is a full manual deployment.

Serverless

Pros: no idle cost, automatic scaling to zero and to thousands, no servers. Cons: cold-start latency, execution time limits, awkward with persistent database connections (use a pooler/proxy), harder local debugging, vendor-specific APIs, costs that can spike unpredictably under sustained high load.

Don't forget the supporting pieces

Whatever hosts the app, you also need decisions for:

  • Database: managed (RDS, Cloud SQL, Neon, Supabase, PlanetScale) versus self-run on the VPS. Managed gives backups and failover for a fee. Self-run is cheap but you own backups and recovery.
  • File uploads: object storage (S3), never the app server's local disk if you may ever run two servers.
  • Background jobs and cron: where does the worker run?
  • DNS, TLS, email sending, monitoring: each a separate service or setup.
Rule of thumb

Use the highest-level thing that meets your needs. Static host before PaaS, PaaS before VPS, VPS before Kubernetes, unless you have a concrete reason (cost, control, compliance, learning). Complexity is a cost you pay every day, not once.

Worked example: one product, three hosting choices

A SaaS has a marketing site, a React dashboard, a REST API with Postgres, and nightly report generation.

PartHostingWhy
Marketing site (Astro)Cloudflare PagesStatic; free; global
Dashboard (React SPA)S3 + CloudFront or NetlifyStatic files; calls the API
API (Node/Express)VPS or Cloud Run/Fly.ioDynamic; needs process, secrets, DB access
PostgresManaged PostgresBackups and failover handled

Three kinds of hosting in one product is normal. The DNS records tie them together: www to the CDN, app to the SPA host, api to the server.

Pitfalls

  • Running an SSR framework in "static export" mode and wondering why dynamic routes 404, or the reverse.
  • SPA deep links returning 404 on refresh: static hosts need a rewrite of unknown paths to index.html (nginx try_files, Netlify _redirects, CloudFront custom error response).
  • CORS: API and SPA on different origins need explicit CORS headers on the API.
  • Putting secrets in front-end bundles. Anything shipped to the browser is public. API keys that must stay secret belong on a server or function.
  • Running state (uploads, sessions, SQLite files) on ephemeral PaaS or serverless filesystems; it vanishes on restart.
  • Choosing Kubernetes for a single app with ten users.

Try it

  1. Take an existing project (or npm create vite@latest) and run the build. Look at the output folder: could any web server serve it as-is? That is a static deploy.
  2. Deploy that folder for free to GitHub Pages, Cloudflare Pages or Netlify. Note the URL, the TLS certificate and the response headers (curl -I).
  3. Test the SPA refresh problem: open a deep link, refresh, and add the rewrite rule your host needs.
  4. List the components of an app you work on. For each, classify static / dynamic / job / data and name the simplest hosting that could work.
  5. Compare the monthly cost of a $6 VPS, a PaaS tier running one small container, and a serverless function at 1 million requests. Which is cheapest at your real traffic?
