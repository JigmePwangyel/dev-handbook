Error Handling

Go has no exceptions. Errors are ordinary values returned from functions. It is verbose by design: every failure path is visible in the code, which makes programs easier to reason about.

The basic pattern

f, err := os.Open("config.json")
if err != nil {
    return fmt.Errorf("open config: %w", err)
}
defer f.Close()

The built-in error interface has a single method: Error() string. A nil error means success.

Creating errors

errors.New("something broke")
fmt.Errorf("user %d not found", id)

// sentinel error: a package-level value callers can compare against
var ErrNotFound = errors.New("not found")

Wrapping with %w

Add context as the error travels up the stack, while preserving the original:

func loadUser(id int) (*User, error) {
    u, err := db.Find(id)
    if err != nil {
        return nil, fmt.Errorf("loadUser(%d): %w", id, err)
    }
    return u, nil
}
// message: "loadUser(7): sql: no rows in result set"

Inspecting errors: errors.Is and errors.As

if errors.Is(err, ErrNotFound) {      // matches anywhere in the wrap chain
    http.Error(w, "not found", 404)
}

var pe *fs.PathError
if errors.As(err, &pe) {              // extract a specific error type
    fmt.Println("failed path:", pe.Path)
}

Custom error types

type ValidationError struct {
    Field, Reason string
}
func (e *ValidationError) Error() string {
    return fmt.Sprintf("invalid %s: %s", e.Field, e.Reason)
}

func validate(u User) error {
    if u.Email == "" {
        return &ValidationError{"email", "required"}
    }
    return nil
}

Joining errors

err := errors.Join(err1, err2)   // Go 1.20+: reports all failures

Guidelines

  • Handle an error once. Either log it or return it, not both.
  • Add context where you have it ("what was I doing?"), with lowercase messages and no trailing punctuation.
  • Don't ignore errors. If you truly must, write _ = f.Close() to make it explicit.
  • Use sentinel errors or custom types for conditions the caller needs to branch on. Otherwise plain wrapped errors are fine.
Early return, avoid else

Handle the error and return, keeping the happy path un-indented. This "line of sight" style is idiomatic.
