Goroutines

A goroutine is a lightweight thread managed by the Go runtime. You start one with the go keyword. They cost a few KB of stack each, so programs routinely run hundreds of thousands of them.

Concurrency is not parallelism

  • Concurrency: structuring a program as independently executing tasks.
  • Parallelism: running tasks at the same instant on multiple cores.

Go's scheduler multiplexes many goroutines onto a few OS threads (by default one per CPU core, controlled by GOMAXPROCS), giving you both.

Starting a goroutine

func say(msg string) {
    for i := 0; i < 3; i++ {
        fmt.Println(msg, i)
        time.Sleep(100 * time.Millisecond)
    }
}

func main() {
    go say("goroutine")   // runs concurrently
    say("main")
}
main exiting kills everything

When main returns, the program ends, even if goroutines are still running. You need a way to wait.

Waiting with sync.WaitGroup

var wg sync.WaitGroup
for i := 1; i <= 5; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        fmt.Println("worker", i)
    }()
}
wg.Wait()   // blocks until the counter hits zero

Call wg.Add before starting the goroutine. Since Go 1.25 you can also write wg.Go(func() { ... }).

Data races

counter := 0
var wg sync.WaitGroup
for i := 0; i < 1000; i++ {
    wg.Add(1)
    go func() { defer wg.Done(); counter++ }()   // RACE
}
wg.Wait()
fmt.Println(counter)   // not reliably 1000

counter++ is read-modify-write, not atomic. Detect such bugs with go run -race . or go test -race. Fix with a mutex, an atomic, or by communicating over channels (next lessons).

Goroutine leaks

A goroutine blocked forever on a channel nobody will use is never freed. Always make sure every goroutine has a way to finish: closing a channel, cancelling a context, or reaching the end of its work.

Go proverb

"Don't communicate by sharing memory; share memory by communicating."
