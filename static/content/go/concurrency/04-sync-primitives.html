The sync Package

Channels are great for passing ownership of data, but sometimes you simply need to protect shared state. The sync and sync/atomic packages give you the classic tools.

Mutex

type SafeCounter struct {
    mu sync.Mutex
    n  map[string]int
}

func (c *SafeCounter) Inc(key string) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.n[key]++
}

func (c *SafeCounter) Get(key string) int {
    c.mu.Lock()
    defer c.mu.Unlock()
    return c.n[key]
}
  • Keep critical sections short, and always defer Unlock().
  • Never copy a struct containing a mutex (use pointer receivers). go vet warns about it.

RWMutex

Allows many concurrent readers or one writer:

var mu sync.RWMutex
mu.RLock();  v := cache[k];  mu.RUnlock()   // readers
mu.Lock();   cache[k] = v;   mu.Unlock()    // writer

Once

var (
    once sync.Once
    cfg  *Config
)
func GetConfig() *Config {
    once.Do(func() { cfg = loadConfig() })   // runs exactly once, even if concurrent
    return cfg
}

Newer alternatives: sync.OnceValue and sync.OnceFunc.

atomic

var hits atomic.Int64
hits.Add(1)
fmt.Println(hits.Load())

Lock-free operations on single values. Great for counters and flags.

sync.Pool and sync.Map

  • sync.Pool: reuse temporary objects (e.g. buffers) to reduce GC pressure.
  • sync.Map: a concurrent map optimized for keys written once and read many times, or disjoint key sets. For most cases a plain map plus a mutex is simpler and faster.

errgroup

From golang.org/x/sync/errgroup. It runs goroutines, waits, and returns the first error:

g, ctx := errgroup.WithContext(ctx)
for _, url := range urls {
    g.Go(func() error { return fetch(ctx, url) })
}
if err := g.Wait(); err != nil { return err }

Mutex or channel?

Use a channel to…Use a mutex to…
Transfer ownership of dataProtect a shared cache or counter
Distribute work, pipelinesGuard internal struct state
Signal events and completionKeep a critical section tiny and obvious
