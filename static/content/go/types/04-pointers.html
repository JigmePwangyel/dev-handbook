Pointers

A pointer holds the memory address of a value. Go has pointers but no pointer arithmetic, so you get the performance benefits without most of C's danger.

Basics

x := 42
p := &x          // p is *int, the address of x
fmt.Println(*p)  // 42: dereference
*p = 100         // modify x through the pointer
fmt.Println(x)   // 100

var np *int      // nil pointer
// fmt.Println(*np)  // panic: nil pointer dereference

Why pointers matter: pass by value

func incrementBad(n int)   { n++ }    // changes a copy
func increment(n *int)     { *n++ }   // changes the original

v := 1
incrementBad(v); fmt.Println(v) // 1
increment(&v);   fmt.Println(v) // 2

new and composite literals

p := new(int)            // *int pointing to 0
u := &User{Name: "Ada"} // pointer to a new struct (most common)

Pointers to structs

Field access through a pointer needs no *: u.Name works the same for a value or pointer. Returning a pointer to a local variable is fine. Go's escape analysis moves it to the heap automatically:

func newCounter() *int {
    n := 0
    return &n      // safe!
}

When to use pointers

  • You need a function or method to mutate its argument.
  • The value is large and copying would be wasteful.
  • You need to signal absence (nil) of an optional value.
  • The type contains a lock or must not be copied.
Don't over-use them

For small values (ints, strings, small structs) copying is cheap and often faster than pointer chasing. Slices, maps and channels are already reference-like, so you rarely need a pointer to them.

The classic loop-variable trap

var ptrs []*int
for i := 0; i < 3; i++ {
    ptrs = append(ptrs, &i)
}
// Go 1.22+: each iteration has its own i → prints 0 1 2
// Go ≤1.21: all point to the same i → prints 3 3 3

Go 1.22 changed loop variables to be per-iteration, fixing this long-standing bug. Make sure your go.mod says go 1.22 or later.
